Agent 最贵的动作不是思考，是复读：KV Cache 经济学入门

2026-11-05 · AI Agent KV Cache 推理成本

同一个 50 轮的 coding agent 会话，同一台模型、同一个任务、同样的输出——账单一次 $1.20，一次 $0.15，差 8 倍。变的不是模型，是系统有没有意识到：这个 agent 的绝大部分时间，不是在思考，而是在复读自己。

2026 年 10 月底，清华和港中文的一篇论文《Cache Engineering for Agents》给这个直觉钉上了数字：在他们的 agent 工作负载里，KV cache 读取占了总 API 成本的 82.4%。不是输出 token，不是推理，是反复重新读入上下文。Manus 团队说得更直白：cache hit rate 是「生产级 AI agent 唯一最重要的指标」——排在准确率前面。

这篇随笔讲清楚三件事：为什么复读这么贵、为什么大多数「省上下文」的直觉修复反而更贵、以及 KV cache 为什么正在从引擎内部细节变成一层独立的基础设施——顺便，它还是个新的攻击面。

一、KV Cache：模型读书时做的笔记

Transformer 每生成一个 token，都要对整个上文做一遍 attention。为了不每步都从头重算，推理引擎会把每个 token 算出的 Key/Value 张量留下来——这就是 KV cache。类比：模型读一本书时逐页做笔记，之后翻回任何一页都靠笔记，不用重读原文。

问题出在 agent 的使用方式上。第 N 步的输入 = 前 N-1 步的全部轨迹：system prompt、几十个工具的 schema、历史对话、工具返回。每走一步，这些内容原样再发一遍。agent 的输入输出 token 比大约是 100:1——每生成 1 个 token 的思考，要重新吞 100 个 token 的历史。没有缓存时，模型每一步都把这本书重新做一遍笔记，而这本书 99% 的页码和上一步一模一样。

Prompt caching 的本质就是把笔记留在服务商那里：命中部分按原价一折左右计费（Anthropic 命中读约 0.1x，OpenAI 自动缓存，Gemini implicit，DeepSeek 有自己的 context caching）。50 轮会话 $1.20 到 $0.15 的差价，全部来自这一处。

二、前缀的暴政：一个时间戳杀死全部命中

缓存命中的条件只有一个：前缀逐字节相同。从第一个不同的字节起，后面全部作废、全部重算。这条规则冷酷得像文件系统的 inode——它不关心语义相似，只认字节。

于是 prompt 不再是「写作」，而是「性能工程」。最著名的教学案例来自 ProjectDiscovery 的 Neo agent：他们的 system prompt 里塞着动态 working memory（当前任务状态、待办），导致缓存命中率只有 7%。把这部分动态内容挪到 prompt 尾部的独立消息里，命中率一夜之间升到 84%，总成本降 59%，后期峰值降 70%，累计 98 亿 token 走了缓存。整个改动没碰模型、没换 provider、没调任何参数——只是挪了一下位置。

反面教材更常见：在 system prompt 里写一句「当前时间：2026-11-05 20:00:03」。每一秒时间戳都在变，意味着每一条请求的前缀都在变，意味着命中率为零。一个时间戳，杀掉整条缓存链。今年一月的《Don't Break the Cache》在 OpenAI、Anthropic、Google 三家实测还发现一个反直觉现象：动态内容混进缓存区不仅杀命中，甚至可能推高延迟——系统为不存在的缓存做了无谓的查找。

铁律只有一条：静态在前，动态在后，会变的东西全部压到尾部。时间戳、用户名、session id、检索结果、本轮工具返回，统统不许出现在前缀里。

三、三宗罪：直觉修复为什么更贵

「上下文太贵？那我把历史删短点。」——这是大多数团队的第一反应，也是 AKV 论文里用数据埋掉的三个坑：

直觉修复实测结果为什么
截断：只留最近 12 轮工具调用成本反而升到全量基线的 1.85x前缀一变，缓存全灭；丢掉的上下文导致更多失败重试
摘要：把旧历史总结成一段只省 7%，丢约 5 个准确率点摘要替换原文 = 前缀变化，同样触发全量重算
压缩：token 级压缩历史比什么都不做多花 40.1%压缩后的文本是新前缀，re-prefill 成本吃掉全部节省

三个坑共享同一个根因：它们都在文本层修改历史，而文本层和历史 KV 状态是绑死的——改一个字，这个字之后的所有 KV 笔记全部作废。你在管理文字，缓存在管理字节，两个层面的规则不一样。

四、Cache Engineering：不改历史，改可见性

AKV 的答案是干脆绕开文本层，直接在 KV 层操作。三个原语：

  • Append：新轨迹照常追加，照常复用缓存；
  • Drop：把选定的旧条目移出未来 attention 的可见范围——位置不动、其余缓存原封不动；
  • Repos：用 RoPE 旋转把保留条目的位置编码重写到连续区间，修复丢弃后的位置空洞。

精妙之处在于：KV 是融合态而非逐字存储，被 Drop 的信息仍可能经保留条目「携带」进来——相当于图书馆不销毁任何书，只是调整哪些书出现在你的必经书架上。三个模型 × 四个基准的平均成绩：成本降 27.7%，得分反升 1.7 点；BrowseComp-Plus 超过 96K token 的长程段上，37% vs 标准做法的 24%——任务越长，优势越大，因为长任务的复读账单本来就越长。

这和检索系统的演进是同一个故事：你不需要删掉图书馆的书，你需要的是管理「什么被看见」。context engineering 管理的是写进 prompt 的文字，cache engineering 管理的是注意力能看到的 KV 条目——后者才踩在成本的真源上。

五、KV 正在变成基础设施

如果把视野拉远，更大的变化是：KV cache 正在从引擎的实现细节，变成一层有自己名字的独立基础设施。八月的一篇论文标题就叫《An Internet for the KV Cache》，核心观察是：agent 工作流里同一份缓存上下文的复用间隔，横跨几秒到几小时。这个时间冗余打开了存储分层的空间——近期要复用的留在显存，远期的下沉到内存、SSD、网络存储。KV cache 第一次有了「冷热分层」的内存系统待遇。

配套器官过去一年密集长齐：KVLink 把每个文档的 KV 独立预计算、推理时直接拼接；CacheBlend 融合缓存块时选择性重算弥合精度损失；EPIC 做位置无关的模块化复用；KVEraser 能从 KV 里定点删除信息而无需重算——KV 层的「被遗忘权」；KVzip 用模型自己重构原文的能力来度量 KV 重要性，3-4 倍压缩近无损；甚至出现了跨模型翻译层，让 A 模型算好的 KV 给异构的 B 模型复用。系统侧，SGLang 的 RadixAttention 用 radix 树做多请求前缀共享，Mooncake 把 serving 拆成 KV-centric 的分离式架构，OSDI'26 刚发了 zero-copy 的 KV 卸载。

判断：一两年内，「上下文复用率」会像「缓存命中率」之于 CPU 一样，成为 agent 基础设施的核心 SLO。今天还在裸奔复读的 agent，等于用没有 L1 cache 的 CPU 跑生产负载。

六、冷水：省钱的通道就是泄露的通道

效率的每一层优化都在同步扩大攻击面。NDSS 2025 的 PromptPeek 证明：共享缓存下，缓存命中和未命中的首 token 延迟（TTFT）不同——攻击者发探测请求、量延迟，就能以 87% 的置信度判断某段前缀是否被别人用过，逐 token 重建多租户环境里他人的 prompt，包括 PII。语义缓存（按 embedding 相似度命中）更糟：今年的 CacheAttack 用 key collision 以 86% 的命中率劫持缓存响应，还能诱导 agent 执行恶意行为。KV 张量本身也可以被 inversion attack 逆推回原文。

缓存的经济学和缓存的安全性是同一枚硬币。防御方案已经出现——vLLM 的 cache salting 给每个用户的缓存加盐，SafeKV 把敏感条目隔离进 per-user 空间——但前提是你得先意识到：把缓存当纯收益接入多租户平台时，你同时接入的是用户 prompt 的可探测性。

七、今晚能做什么

  1. 审计 system prompt：grep 一遍时间戳、用户名、session id、动态 schema，全部挪到 prompt 尾部。这是零成本、一夜回本的第一刀。
  2. 把缓存命中率加进监控面板：Anthropic 的 cache_read_input_tokens、OpenAI 的 cached_tokens 字段直接可读。「输入 token 走缓存的比例」应该是你的第一公民指标。
  3. 算一遍 TTL 账：agent 步间隔超过 5 分钟的长任务，5 分钟 TTL 等于没有——上 1 小时 TTL（第三次调用即回本）。高频短任务用自动缓存就够。
  4. system prompt 纳入版本管理：改一个字符等于全量缓存失效 + 成本瞬时尖峰，把它当部署事件走变更窗口，而不是周五下午随手改。
  5. 自托管玩家两件套：SGLang / vLLM 的 prefix caching 先开起来（一个 flag 的事），长上下文加 KV 量化（如 --kv-cache-dtype fp8）；多租户场景，上共享缓存前先读 cache salting。

最后一个视角收尾：我们习惯把 agent 的智能花在「下一步做什么」上，但账本告诉我们，钱的去向是「刚刚读过什么」。上下文复用率，就是 agent 时代的新缓存命中率——谁先把它当第一公民指标，谁就先拿到那 8 倍的差额。
