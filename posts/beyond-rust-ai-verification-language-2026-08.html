Beyond Rust · AI 时代的验证语言会是什么样

Rust 解决了
内存安全， 那"功能正确"呢？AI 能否从零设计一门更进一步的验证语言？

Rust 的 borrow checker 是编译期白送的形式化验证——它免费送了一大堆分离逻辑性质。 但它管不了逻辑 bug（off-by-one、错误的状态机、错误的算法）。 这页要回答一个问题：下一门语言会是什么样，AI 在其中扮演什么角色？

THE GAP · Rust 的边界

Rust 解决了什么，没解决什么

要回答"比 Rust 更进一步"，得先看清楚 Rust 的边界在哪。 Rust 用 borrow checker 把一整类分离逻辑性质塞进了类型系统——这是它革命性的贡献。 但有一整类问题，它无能为力。

Rust 已经免费送你的

  • 无双重释放（double free）
  • 无 use-after-free
  • 无数据竞争（data race）
  • 无空指针解引用
  • 无迭代器失效
  • 无悬垂引用
  • 线程安全由 Send / Sync 类型保证
  • unsafe 边界被显式标注

Rust 完全管不了的

  • off-by-one 错误
  • 状态机迁移错误
  • 算法本身错（错误的排序、错误的搜索）
  • 资源泄漏（锁没释放、文件没关）
  • 协议实现错（TLS、共识算法）
  • 加密代码的常数时间性质
  • 业务逻辑（"金额不能为负"）
  • unsafe 块内部的正确性

// 一句话：Rust 保证"不崩"，不保证"对"。而形式化验证，就是补上"对"。

ALREADY EXISTS · 已经存在

"比 Rust 更进一步"不是空想

下面 5 个语言/工具，已经在不同方向上把 Rust 的边界推得更远。 它们是任何"AI 设计新语言"设想必须先看懂的已有素材库。

F*

PROOF-ORIENTED
证明优先的通用编程语言。类型系统就是规范，写代码即写证明。 Project Everest 用它验证了整个 HTTPS 栈（mirage / everCrypt）。
出身
MSR / Inria
逻辑
依赖类型 + SMT 自动化
招牌
everCrypt TLS 实现
哲学
不"加"验证，本身就是验证

Lean 4

THEOREM PROVER
编程语言 = 定理证明器。de Moura 设计，AWS 自 2023 起用它做实际软件验证。 AlphaProof 在 IMO 拿银靠的就是它。
出身
Lean Community / MSR
逻辑
依赖类型论 (DTT)
招牌
Mathlib · AlphaProof
哲学
Curry-Howard 的工业级实现

Verus

EMBEDDED IN RUST
不离开 Rust，加规范注解。你写 ensures，Z3 在背后自动证。 内存安全由 borrow checker 白送，你只证功能。
出身
MSR / CMU / VMware
逻辑
一阶逻辑 → SMT
招牌
Rust 工程代码验证
哲学
工业友好，零迁移成本

RefinedRust

COQ-BACKED
Rust → 翻译到 Coq。用 refinement type 给 Rust 加规范， 整个类型系统在 Coq 里被证明 sound——foundational 保证。
出身
MPI-SWS
逻辑

招牌
真实 Rust surface 代码
哲学
基础可信，每层都验证

Flux

RUST PLUGIN
Rust 的 refinement type 检查器。liquid types 思路， 在现有 Rust 类型上加 {n: i32 | n >= 0} 这样的谓词约束。 上手最轻，最有希望进入 Rust 主线。
出身

THE VISION · 核心设想

AI 时代的"验证优先"语言会长什么样

我的判断是：AI 不会一次生成一门新语言（语言设计是超高维耦合系统，LLM 一次搞不定）。 但 AI 可以做层级翻译器——让程序员在最高层用自然语言写意图， 让 AI 把它逐层翻译成机器可检查的证明。这就是下面这个四层架构。

LAYER 3 · TOP

自然语言层

NATURAL LANGUAGE INTENT

程序员用自然语言描述意图，不写代码、不写规范。 这是当前最缺的一层—— 也是 AI 最有可能填补的空白。

// 程序员说人话： "这个函数接收非空列表，返回它的最小值，且结果必须属于原列表"
// ↓ LLM 自动翻译到 L2 ↓
AI 翻译 NL → Spec 2026 前沿
LAYER 2

规范层

REFINEMENT TYPES + GHOST CODE

形式化的函数契约：前置条件、后置条件、循环不变式。 这一层已经存在—— Flux / RefinedRust / Verus 都在做。关键是让 LLM 能自动产出它。

fn min(xs: List<Nat<{xs.len > 0}>>) -> (r: Nat) ensures r ∈ xs && ∀ e ∈ xs, r ≤ e
Flux / RefinedRust 已实现 AI 辅助生成 spec
LAYER 1

Rust 内核

BORROW CHECKER = FREE SEPARATION LOGIC

真正执行运算的代码。内存安全由 Rust 编译器免费送—— 这就是 Rust 在这场游戏里的战略价值：它让 L0 不用重新证明一遍分离逻辑。

fn min(xs: &[i64]) -> i64 { let mut m = xs[0]; for &x in xs { if x < m { m = x; } } m }
Rust 已成熟 无 AI 需求
LAYER 0 · FOUNDATION

机器检查层

LEAN 4 / COQ / SMT — GROUND TRUTH

最终的真理裁判。AI 生成证明候选项， 引擎逐行检查——这正是不允许 AI 越权的一层。 2026 年最活跃的方向：AlphaProof 思路迁移到程序证明。

/* AI 提议证明 */ by induction xs; simp [*] /* 引擎裁定 */ ✓ accepted (Lean 4 kernel)
AlphaProof 思路 lean-dojo / Copaea 2026 研究热点

↑ 自下而上：越靠下越成熟　|　越靠上越需要 AI　|　L3 是接下来 3-5 年的突破口

REALISTIC PATHS · 现实路径

想做这件事，三条切入点

不是"等 AI 设计新语言"，而是站在已有工具肩膀上。 按可行性排序（最现实 → 最前沿）：

1

先玩 Flux —— 体感最接近"AI 帮你写验证"

cargo 装 flux-rs，在现有 Rust 项目里加 refinement type。 这一层 2026 年最成熟，立刻能用于真实工程，零迁移成本。

可行性 90%
2

研究 F* 的 Everest 案例 —— 验证优先语言的范本

F* 不是"给 Rust 加验证"，它是从零设计成证明优先。 读它的类型系统设计，能看清"下一门语言"应该长什么样。

可行性 60%
3

追 Lean 4 + AWS 验证项目 —— 最有工业落地希望

de Moura 亲自推的方向，AWS 已经在用。AlphaProof 的思路（生成 + 检查分离） 会迁移到程序验证——这是 L0 的主战场。

可行性 40%

⚠️ 一个清醒的认知： "AI 从零设计一门新语言"在 2026 年仍不可行。 语言设计是超高维耦合系统（类型、语义、证明规则、生态），LLM 一次生成解决不了。 真正可行的路是让 AI 当层级翻译器—— 把"自然语言 → 规范 → 证明"这段最难的桥补上。L3 是未来 3-5 年的突破口。
