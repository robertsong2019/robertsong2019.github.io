单日 5.4 万星背后的「证据契约」：rea 如何把认识论编码进 Agent 工具

2026-10-15 · 罗嵩 · Agent 工具设计 逆向工程 MCP 证据契约
一个让 agent 逆向工程任何东西的 MCP，半年 23.8 万星、单日 +5.4 万——但它真正值得学的不是「把 Ghidra 接上 MCP」，而是一份 6,521 词的运行时契约：每个结论必须携带机器可读的证据记录，每个「空结果」必须声明自己是观察到的空还是没观察到，每个未知项都有稳定 ID 进台账，每段来自分析目标的文本都打上不可信标记。这套设计把认识论（我们如何知道我们所知道的）编码进了协议层，从根上堵住 LLM 最经典的失败模式：把数据的缺席当成事实的否定。

一、现象：一次教科书级的爆发

先看数字（GitHub API，2026-10-15 05:05 CST 核验）：morluto/rea（Reverse Engineer Anything）238,637 星 / 59,403 forks，创建于 2026-04-14，TypeScript，MIT 协议，18 种语言 README。Trendshift 徽章、skills.sh 集成、npm 一键安装（npx rea-agents setup）。爆发到什么程度？README 顶部挂了反仿冒声明："A similar repository name or copied README does not establish that a download is official"——火到需要防李鬼，本身就是一种认证。

它做一件事：让你的 agent 逆向工程任何东西——从 app 行为到 native 二进制。口号是 "See a feature you like. Understand how it works, down to the binary level." 看到别家 app 有个功能想要？让 agent 用 REA 去调查：无源码检查目标、解释功能如何实现、出示证据、然后给你的项目写一个版本。底层桥接 Hopper / Ghidra / IDA / JADX；同一天 ghidra 本体也在 trending 榜上——rea 在给整个逆向工程生态导流。

但「RE 能力即服务」只是包装。真正的设计密度在 docs/mcp-contracts.md 里。

二、核心：四个契约支柱

支柱一：证据是一等公民，缺字段即拒绝

每个产出证据的工具返回完整规范化的 Evidence 记录：normalized_result（规范化结论）+ evidence_id（身份）+ raw_result（上游工具原始报告，与规范化结论分开存放）+ analysis_profile（分析环境指纹）。契约原文写得极硬："Records omitting this field are rejected."——缺 coverage 字段的记录直接拒收，不是降级警告。证据记录还能跨工具传递：analyze_function 的 Evidence 可以直接喂给 compare_functions，比较工具天然信任输入的证据身份。

这解决了一个微妙问题：同一个数字在不同工具里有不同的「原产地」。规范化结论和原始报告并存，agent 引用时可以同时说「结论是什么」和「这结论是从哪份原始数据归一化来的」。

支柱二：空结果的三值逻辑

这是整份契约最精彩的一句：

"An empty call list with partial or unknown coverage is not proof that the function has no calls."（覆盖不完整或未知时，空调用列表不能证明函数没有调用。）

REA 给每个清单类结果声明 coverage：scope（root 还是 container-entries）和 status（complete 还是 unknown）独立于诊断措辞存在。函数档案进一步有 facet_availability 映射：pseudocode / assembly / callers / callees / references / cfg 每个侧面要么 {available: true}，要么 {available: false, reason: "..."}。契约特意强调："Availability describes whether that facet was observed, not whether its collection contains any entries."——有没有观察到和观察到的东西是不是空的是两个正交维度。

更狠的是相等判定：比较函数要求双方 scope 匹配、图成员完整、遍历覆盖完整，三者齐备才允许下「相等」结论；任何一侧缺 facet，该维度保持 unknown 和 null 计数。甚至诚实到自曝边界："Static artifact equality does not establish unchanged runtime behavior."（静态工件相等不能确立运行时行为未变。）

支柱三：未知项有台账

record_unknown / update_unknown / list_unknowns——未知不是一个耻辱的空白，而是有稳定 ID、可分页、可过滤、可后续更新的记录。agent 调查到一半发现解不了的问题，登记进台账，换个角度继续；下次工具升级了，把旧 unknown 翻出来重试。翻页时契约还提醒 "keep the unknown ledger unchanged while traversing it"（遍历台账时别改它）——工程细节认真到可爱。

支柱四：目标内容一律标记为不可信

逆向工程的对象是对抗性的：二进制里的字符串可以伪装成给 agent 的指令。REA 的防御是把不信任编码进协议：所有可能返回目标内容（字符串、符号、反编译伪码、日志、文件列表）的工具，结果 _meta 里带稳定标记：

{ "provenance": { "untrusted_content": true, "source": "analysis_target" } }

标记按工具契约声明（returnsTargetContent），且默认开启——"A new tool is marked until it is audited into that exception list"（新工具一律标记，审计通过才能进豁免名单）。这是安全设计的白名单反转：不可信是默认态，可信才需要证明。连错误结果也带标记，因为失败信息可能包含目标派生文本。宿主和 hook 可以据此收紧策略——比如读取目标内容后，要求人工批准任何进程启动类工具。

三、60 行看懂三值逻辑

把契约精髓压成可运行的对照实验（本机验证通过，输出为真实结果）：

def validate_evidence(rec: dict) -> dict:
    # rea 契约原文：Records omitting this field are rejected.
    if "coverage" not in rec or "status" not in rec.get("coverage", {}):
        raise ValueError("REJECTED: missing coverage.status — "
                         "'unknown' must be declared explicitly, never implied")
    return rec

def conclude_about_calls(rec: dict) -> str:
    # 契约原文：An empty call list with partial or unknown coverage
    # is not proof that the function has no calls.
    calls = rec["normalized_result"]["calls"]
    status = rec["coverage"]["status"]
    if not calls and status == "unknown":
        return "❌ 不能下结论：calls=[] 但 coverage=unknown，空可能是截断"
    if not calls and status == "complete":
        return "✅ 可以下结论：完整观察下的空 = 真的没有调用"
    return f"观察到 {len(calls)} 个调用（coverage={status}）"

bare_empty   = {"normalized_result": {"calls": []}}        # 普通工具的返回
cov_unknown  = {"normalized_result": {"calls": []},
                "coverage": {"status": "unknown"},
                "limitations": ["call graph traversal truncated at depth 3"]}
cov_complete = {"normalized_result": {"calls": []},
                "coverage": {"status": "complete"}}

运行结果：

实验一：同一个 [] 的三种人生
  裸返回   -> ❌ 无 coverage 字段，agent 只能猜（猜 = 幻觉入口）
  unknown  -> ❌ 不能下结论：calls=[] 但 coverage=unknown，空可能是截断
  complete -> ✅ 可以下结论：calls=[] 且 coverage=complete —— 真的没有调用

实验二：记录级拒绝
  裸空结果     -> REJECTED: evidence record missing coverage.status
  带coverage -> ACCEPTED
同一个 []，三种人生。裸返回把解释权丢给了模型——而模型的默认解释往往是最顺滑的那个（「没有调用方」），这恰恰是幻觉的经典入口。

四、为什么这值得每个工具作者抄

LLM 幻觉有个认识论根源：absence of evidence 被当成 evidence of absence。上下文里没有的信息，模型会用手头最 plausible 的叙事填补——它分不清「我查过了，没有」和「我没查到」。

我在自己的工程实践里反复撞见同一族事故：评测脚本用平行常量 Q 当分母而不是 len(实际集合)，Q 与真实集合漂移后数字看起来依然合理；同分排序的第二键即排序本身，制造出「好得可疑」的榜单；采样单点推周期规律，得出不存在的漂移曲线。每次事故后立的规矩，本质都是 REA 契约的朴素版：汇报数字必须与它的事实来源逐字段同源，空/缺失必须显式标注语义。

rea 的贡献是把这些散落的纪律编译成了协议层强制——不是 README 里的「请小心」，而是缺字段即拒收的 schema。模型想不诚实都难：不完整的记录根本进不了对话。

对比主流 MCP 工具的返回形态（一段人类可读的文本，顶多带个 JSON），这是代差。工具输出的结构决定 agent 推理的下限：文本输出时下限是模型的语文水平；证据契约输出时，下限是契约本身。

五、清醒剂

  1. 复杂度成本真实存在。6,521 词的契约文档，消费方（agent 框架）要理解三值逻辑、证据传递、分页 continuation、10 MiB 传输预算——这套设计对作者和维护者都是重税。简单工具不值得，只有「结论会被下游做高风险决策」的工具才配。
  2. coverage 声明本身可能是错的。producer 说 complete 就是 complete 吗？上游 provider 的 bug 会让「完整」名不副实。REA 的缓解是 analysis_profile 版本化声明、快照不复用——但最终仍是「生产者负责制」，消费方信任的粒度从「结论」移到了「元数据」，不是消除信任而是搬迁信任。
  3. 静态分析的边界它自己承认。反编译丢失信息、Hopper 缺 reference-kind 元数据、完整调用覆盖 "does not claim every runtime target"（不声称覆盖每个运行时目标）。契约没有把 RE 做成水晶球，只是把水晶球的雾区画在了地图上。

六、行动清单

  • 给自己的 MCP 工具加最小 coverage：返回集合类结果时附 {observed, scope, truncated} 三件套，空结果必须能区分「观察到的空」和「截断」；缺字段拒收放 consumer 侧。
  • 空结果配 provenance：[] 永远伴随一个机器可读的「为什么是空的」。这条对内部工具同样成立。
  • 目标派生内容默认标记：任何会返回外部文本的工具，从第一天就把 untrusted 标记做进 schema，新工具默认开、审计后豁免——别等第一次注入事故。
  • 评估 rea 装机：npx rea-agents setup 一条命令，逆向/协议分析场景直接受益；即便不用，docs/mcp-contracts.md 也值得通读一遍当工具设计教材。

结语

rea 单日五万星当然有话题成分，但这份契约文档配得上热度。它示范了一个正在成形的共识：agent 时代的工具设计，核心竞争力不是让模型更聪明，而是让不聪明变得不可能——用协议堵住猜测的缝隙，用结构替代叙事，用拒收替代警告。工具作者的下一个差异化战场，不在功能列表，在认识论。
