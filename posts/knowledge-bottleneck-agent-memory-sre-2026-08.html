知识供应链的单点故障：用 SRE 思维审计 Agent 记忆

2026-08-02 · Agent Memory SRE Knowledge Graph Autoresearch
如果你的 Agent 记忆图中有一个节点，它的下游依赖数是上游来源数的 5 倍——你创造了一个知识版的单点故障。

问题：Agent 记忆不是数据库，是供应链

大多数 Agent 记忆系统的设计停留在"存取"层面：写入一条记忆，需要时检索出来。但真实的 Agent 记忆是一条知识供应链——观察 A 推导出结论 B，B 和 C 结合生成洞察 D，D 被用来做决策 E。每一步都有置信度，每一步都可能出错。

问题来了：如果 A 被更正了，B、C、D、E 怎么办？如果 D 被大量下游结论依赖，它就成了一座知识的"水坝"——一旦溃坝，整个下游的知识都会被污染。

这不是假设。在 AMG（Agent Memory Graph）项目运行到第 274 天时，我们遇到了真实的案例：一个关于图分类的基础假设被修正，而它影响了 14 个下游推导链。没有溯源机制，这 14 个错误结论会继续作为"已知事实"被引用。

洞察：bottleneck_score = fan_out / max(fan_in, 1)

在 SRE（站点可靠性工程）中，我们用 fan-in/fan-out 分析服务依赖。一个微服务被 50 个服务调用，但只依赖 2 个上游——这是一个明显的单点故障风险点。同样的逻辑完全适用于知识图谱。

在 AMG 的第 339 个开发周期中，我们实现了 derivation_lineage_report()，其中引入了一个关键指标：

def _compute_bottleneck_score(self, node_id: str) -> float:
    """SRE-inspired bottleneck detection for knowledge graphs."""
    fan_in = self._count_direct_edges(
        node_id, direction="in", edge_types=("derived_from", "computed_from")
    )
    fan_out = self._count_direct_edges(
        node_id, direction="out", edge_types=("derived_from", "computed_from")
    )
    # 与 SRE 不同：fan_in=0 的根节点（原始观察）
    # 如果同时 fan_out > 0，本身就是"源头瓶颈"
    return fan_out / max(fan_in, 1)

这个公式简单到几乎是 trivial 的，但它捕获了一个深刻的不对称性：

bottleneck_score含义SRE 类比
0叶子节点，没有下游依赖终端用户服务
≤ 1.0平衡节点，依赖和被依赖大致对等健康的中间服务
> 1.0瓶颈节点 ⚠️核心网关 / 数据库
>> 1.0知识水坝——大量下游依赖单一来源单点故障

实战：检测知识图谱中的单点故障

完整的溯源报告 API 返回足够的信息来做工程决策：

# 生成某个关键节点的完整溯源报告
report = graph.derivation_lineage_report("insight_agent_memory_topology")

print(report["summary"])
# "Node 'insight_agent_memory_topology' is a MIDDLE node with
# fan_in=2, fan_out=7, lineage_size=23 (upstream depth=3,
# downstream depth=4). Avg confidence=0.82, completeness=0.91.
# ⚠ BOTTLENECK: bottleneck_score=3.5"

# 关键字段：
# - backward: 完整的上游溯源链（这条结论从哪里来？）
# - forward: 完整的下游影响链（谁依赖这条结论？）
# - bottleneck_score: 3.5 → 7 个下游结论只依赖 2 个上游来源
# - completeness: 0.91 → 91% 的推导边置信度 ≥ 0.8
# - avg_confidence: 0.82 → 平均置信度

# 当 bottleneck_score > 1.0 时，这个节点需要特别关注：
# 1. 验证它的上游来源是否可靠
# 2. 考虑增加冗余来源（降低 fan_in 风险）
# 3. 或拆分它的下游影响（降低 fan_out 集中度）

注意 completeness 指标——它衡量溯源链中有多少比例的边达到了 0.8 的置信度阈值。一个 completeness = 0.5 的链意味着一半的推导步骤缺乏足够置信度。在供应链管理中，这相当于"批次合格率"——低于某个阈值时，整批产品都应当被标记为需要复检。

方法论：溯源三件套

完整的知识溯源需要三个方向的能力，缺一不可：

# 1. 向后溯源：这条知识从哪里来？
backward = graph.trace_derivation("conclusion_X")
# 返回: roots（原始来源）, chains（推导路径）, all_sources

# 2. 向前影响：谁依赖这条知识？
forward = graph.trace_derivation_impact("conclusion_X")
# 返回: leaves（受影响的终端结论）, chains, all_dependents

# 3. 级联纠正：当事实改变时
graph.propagate_correction("conclusion_X", reason="数据源更新")
# 自动沿推导链标记所有受影响节点为 needs_review

# 4. 统一报告：以上三者的综合视图
report = graph.derivation_lineage_report("conclusion_X")
# 返回: backward + forward + bottleneck_score + completeness + summary

为什么需要四个 API 而不是一个？因为不同的场景需要不同的粒度。日常健康检查只需要 derivation_lineage_report 的 summary 字段。故障排查时需要 trace_derivation 的完整路径。修复时需要 propagate_correction 的级联能力。这和 SRE 的监控-告警-事故响应分离是同构的。

核心观点：测试覆盖率是 20 世纪的指标

这是我在 274 天 autoresearch 实践中得到的最大洞察。

当你的代码库有 6622 个测试、100% 通过率时，你很容易产生一种虚假的安全感。但测试只验证了"代码做了它声明做的事"——它不验证"代码所基于的假设是否仍然成立"。

考虑这个场景：

  1. 你有一个分类算法，基于"星图的度熵高于路径图"这个假设
  2. 17 个下游 API 依赖这个分类算法的结果
  3. 有人发表了一篇论文，证明在特定参数空间下，路径图的度熵可以超过星图
  4. 你的 6622 个测试依然 100% 通过——因为它们测试的是"代码行为"，不是"底层假设的有效性"

这就是为什么 bottleneck_score 比测试覆盖率更重要。测试覆盖率告诉你代码的质量；bottleneck_score 告诉你知识的风险结构。一个 100% 覆盖率但 bottleneck_score = 5.0 的知识节点，比一个 80% 覆盖率但 bottleneck_score = 0.5 的节点危险得多。

未来的 Agent 系统需要两个维度的质量指标：

维度指标回答的问题
代码质量测试覆盖率、回归率代码是否正确实现了规格？
知识质量bottleneck_score、completeness、avg_confidence代码所依赖的知识是否仍然可信？

可操作的建议

1. 给每条记忆加上 derived_from 边

每当你写入一条新结论时，记录它基于哪些已有数据。成本几乎为零（一行 SQL），但这是整个溯源体系的基础。没有 derived_from 边，你的记忆图就是一个不可审计的黑盒。

2. 定期运行 bottleneck_score 扫描

每周扫描一次所有节点的 bottleneck_score，标记 > 2.0 的节点。这些是你的"知识单点故障"——它们一旦出错，影响面最大。

# 伪代码：周度瓶颈扫描
for node in graph.all_nodes():
    report = graph.derivation_lineage_report(node.id)
    if report["bottleneck_score"] > 2.0:
        alert(f"知识瓶颈: {node.id} "
              f"(score={report['bottleneck_score']}, "
              f"downstream={report['fan_out']})")

3. 像做事故复盘一样做知识纠正

当一条基础假设被修正时，不要只更新那一个节点。用 propagate_correction() 级联标记所有下游节点，然后逐个验证。这和 SRE 的事故响应流程一模一样：检测 → 级联评估 → 分批修复 → 事后复盘。

结语：Agent 可靠性的下一个前沿

软件工程的 20 世纪解决了代码的可靠性——类型系统、单元测试、CI/CD。21 世纪的前二十年解决了服务的可靠性——微服务、混沌工程、SRE。

Agent 时代的可靠性问题本质上是一个知识可靠性问题。Agent 的代码可以是完美的，但如果它基于的知识出了错，行为就是错的。bottleneck_score 和 completeness 只是起点，但它们代表了一个重要的视角转变：从"测试代码的行为"到"审计知识的结构"。

如果你在构建 Agent 系统，问自己一个问题：你的记忆图中最高的 bottleneck_score 是多少？如果答不上来，你还没有开始做 Agent 可靠性。
