Agent 的记忆不该是硬盘——时间知识图谱与海马体索引

Agent 记忆 知识图谱 Personalized PageRank LongMemEval 2026-09-15 · 基于 Zep/HippoRAG/A-Mem/MemOS 等 12+ 系统的系统调研

你问 AI 助手："我上次说我的过敏药换成什么了？"它翻出三百页聊天记录，全文塞进上下文，答了一个错的。而另一套系统只往上下文里放了 1.6k token 的精选记忆，答对了，还快了十倍。问题不在模型——在于"把一切都存下来"根本不是记忆。

一、全上下文是假安全

2025 年的 Zep 论文做了一个让人不舒服的实验：在 LongMemEval 长对话记忆基准上，把整个对话历史（平均 115k token）全部塞进 GPT-4o 的上下文窗口，准确率 60.2%；而 Zep 用时间知识图谱检索出约 1.6k token 的记忆注入，准确率 71.2%，平均延迟从 28.9 秒降到 2.58 秒。

多给了七十倍的上下文，反而更笨了。这不是 bug，是注意力机制的物理性质：上下文里的无关细节每多一分，模型对关键事实的聚焦就弱一分。这和人的记忆一样——让你把过去一年的每句话都背下来再回答问题，你也会被噪音淹没。

记忆的价值在于删除，不在于保存。从全部经历中筛出"此刻相关的那几条"，这个筛选动作本身就是智能的一部分。我跑 amg 评测项目几个月，反复看到同一件事：检索器选对了句子，模型就答对；检索器塞一堆"长得像"的干扰句，模型就被带偏。上下文工程不是把窗口塞满的工程，是把窗口留白的工程。

二、向量检索找"长得像的"，图找"连得上的"

那为什么不用向量数据库就够了？因为 embedding 相似度有个结构性盲区。

你问："我上次提到的那位换了工作的同事，他妻子叫什么？"答案分散在两段语义毫不相似的对话里——一段聊工作变动，一段聊家庭聚会。向量检索找的是长得像查询的，而这个问题需要的是连得上的——从"同事"跳到"工作变动"，再跳到"他的家庭"。多跳关联在向量空间里没有对应操作，在图上就是沿着边走两步。

这就是 HippoRAG（NeurIPS 2024）的洞见，而且它偷师的对象很高明：人脑。神经科学的海马体索引理论认为，大脑的新皮层存记忆内容，海马体只存一张索引——记录哪些皮层区域互相关联。你闻到一股味道，海马体顺着索引把当年那个夏天的画面、声音、情绪一起点亮。这个过程叫扩散激活（spreading activation）。

HippoRAG 把它变成了可计算的东西：LLM 当新皮层（读文档、抽实体和关系），知识图谱当海马体（存关联索引），检索时从查询实体出发跑一次 Personalized PageRank——概率从种子节点出发沿着图扩散，最后停在哪儿，哪些文档就被"点亮"。一次图算法调用，完成传统 RAG 要多轮检索才能拼出来的多跳推理，多跳问答上比标准检索高出最多 20%。

PageRank 本来是 Google 给网页排序的算法。三十年后它回来给 AI 当海马体用——图算法这门老手艺，在记忆系统里找到了第二春。

三、每个事实都有生日和忌日

光有图还不够。记忆还有个维度经常被忽略：时间。

"用户住在上海"这句话，2026 年 3 月是真的，9 月他搬去深圳之后就假了。如果记忆系统只存"用户住在上海"和"用户住在深圳"两条事实，问"他现在住哪"没问题，问"他三月住哪"就抓瞎——更糟的是向量检索可能因为"上海"出现次数多而答错。

Zep 背后的 Graphiti 引擎用了数据库领域的双时间轴（bi-temporal）设计：每条事实带两个时间戳——valid time（这件事在现实中什么时候为真，有出生日 t_valid 和忌日 t_invalid）和 transaction time（系统是什么时候知道这件事的）。新事实与旧事实矛盾时，不覆盖，而是给旧边打失效标记。三个月后你问"我当时为什么推荐了那家上海的公司"，图里还留着完整的演化史。

这是数据库工程三十年的老智慧第一次大规模进入 AI 记忆设计。时间不是挂在数据外面的元数据过滤条件，而是织进数据结构本身。

四、旧记忆要不要改写——记忆系统的根本分歧

到这里出现了一个有意思的哲学分歧。NeurIPS 2025 的 A-Mem 论文走向另一个方向：借鉴 Zettelkasten 卡片盒笔记法，新记忆进来时不仅存储，还会反向改写旧记忆——更新旧笔记的描述、关键词、链接关系，让整个记忆网络随着新知识的到来不断重塑。这更像人脑：你的记忆每次被回忆都会被重新加工一遍。

一边是改写主义（A-Mem：旧记忆被新理解重塑，灵活但有篡改历史的风险），一边是审计主义（Graphiti：旧事实只失效不删除，可信但图越来越重）。没有标准答案，但选择标准很清晰：你的业务需不需要解释"当时为什么这么做"？金融、医疗、法律场景必须偏审计端；陪伴型、创作型助手偏改写端更自然。

顺带一提，Anthropic 给 Claude 的 Memory Tool + Context Editing 走的是第三条朴素路线：快到上下文上限时提前警告模型"旧内容即将被清除"，让模型自己决定什么值得抢救进持久记忆文件。把遗忘的决定权交给模型本身——工程上粗糙，哲学上却很诚实：我们其实还不知道该忘什么，那就先让当事人自己选。

五、生态速览与基准的坑

系统一句话定位

最后泼一盆冷水：这个领域的基准数字已经高度政治化。每家都在自己最擅长的基准上"达到 SOTA"——Mem0 赢 LoCoMo，Zep 赢 LongMemEval，开源阵营赢成本。而 LoCoMo 被社区审计出 6.4% 的标准答案是错的，至今还在被各家刷分；最新的 BEAM 基准刻意设计到百万级上下文、没有任何现有系统能饱和（最好成绩 64.1%）。

读这类论文的纪律只有一条：配对读数。准确率必须和 token 成本、延迟一起看——"71.2% @ 1.6k token @ 2.6s"和"71.2% @ 115k token @ 29s"是两个完全不同的东西。单独报一个准确率的，默认当营销处理。

可以立刻做什么

  1. 给记忆加三个时间戳。不管你用什么存储，每个事实加 valid_from / valid_to / ingested_at。写路径做矛盾检测：新事实与旧事实冲突时打失效标记而不是覆盖。一个下午就能加完，"他三月住哪"这类时间敏感问题立刻可答。
  2. 在检索里加一层图扩散。已经存了实体关系的，把 Personalized PageRank 加进检索管线（networkx 十几行代码），向量召回当种子节点，PPR 沿边扩散一圈再做重排。多跳问题的召回率通常立刻上一个台阶。
  3. 审计你的"全上下文"幻觉。如果你的 agent 在把整个历史往窗口里塞，做一个对照实验：人工筛 2k token 的精选记忆 vs 全量历史，各测 20 个问题。被自己的实验结果吓到的人，远比想象中多。
  4. 建一个配对读数习惯。评估记忆系统时固定报告三元组：准确率 × token 成本 × 延迟。三个数不齐的对比一律存疑——包括你自己的内部评测。

记忆不是存储问题，是索引问题。硬盘早就够大了，缺的是海马体。
