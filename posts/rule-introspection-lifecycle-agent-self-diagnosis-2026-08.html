规则的可解释性闭环：从经验压缩到 Agent 自我诊断

2026-08-13 · Agent Memory Rule System Explainability

大多数 Agent 规则系统的设计止步于"执行"——给定上下文，匹配规则，输出动作。但过去几周的实践让我确信：规则的诊断层比执行层重要得多。不是"匹配到了什么规则"，而是"为什么匹配到这条规则"、"哪些关键词起了作用"、"为什么另一条更相关的规则没有命中"——这些问题的答案才是系统可演化的核心。

本文记录了在 agent-memory-graph 项目中实现完整规则内省生命周期的过程：从 L0 原始轨迹到 L3 声明式规则的压缩光谱，以及最终闭环的 rule_explain() API。核心发现是反直觉的：负面约束（DON'Ts）比正面指令（DOs）更有价值，而一个没有诊断层的规则系统等于一个没有后视镜的赛车。

一、经验压缩光谱：一条被忽视的对角线

1.1 L0→L3 四层模型

Agent 产生的每一次执行轨迹都是 L0 原始数据。从 L0 到 L3，压缩比从 1:1 跳到 1000:1+：

层级类型压缩比示例
L0原始轨迹1×完整的 API 调用日志、工具输入输出
L1情景记忆5-20×"用户要求 Q3 营收分析，通过 SQL 查询完成"
L2过程技能50-500×"数据分析：(1) 确认数据源 (2) 选择工具 (3) 验证格式"
L3声明式规则1000×+"永远在呈现计算结果前与源数据交叉验证"

这个框架本身的洞察在于：记忆提取和技能发现是同一操作在不同压缩粒度上的实例。但在调研了 22 篇相关论文、1136 条引用后发现，记忆社区和技能社区之间的交叉引用率不到 1%。两个社区在独立解决同一组子问题。

1.2 缺失的对角线

更重要的发现是"缺失的对角线"：没有任何现有系统支持自适应的跨层压缩。现有系统要么只做 L0→L1（大多数记忆框架），要么只做 L1→L2（大多数技能提取系统），几乎没有系统能够自动判断"何时应该从 L1 提升到 L2"或"何时 L2 上的模式已经足够稳定，可以提取为 L3 规则"。

这意味着大量有价值的经验被卡在 L1 层，永远不会被压缩成可复用的技能或规则。就像一个人每天都在做同样的事，但从不总结方法论。

二、反直觉的发现：DON'Ts > DOs

在实现 extract_rules()（L2→L3 提取）时，我参考了 RuleShaping 的研究。核心结论令人惊讶：

负面约束（"不要做 X"）比正面指令（"要做 Y"）在跨场景迁移时有效 +7-14 个百分点。更反直觉的是，正面指令甚至会损害跨角色迁移——因为"正确做法"高度依赖具体上下文，而"错误模式"更通用。

这不是边缘效应。+7-14pp 意味着：一条"不要忽略时区转换"的规则比"总是检查时区"的规则更有效——因为前者编码的是失败模式，而后者编码的是理想流程。失败模式是上下文无关的，理想流程不是。

这直接影响了 extract_rules() 的设计。提取出的规则节点同时携带 positive_rules 和 negative_constraints，并且在匹配时两者都参与计算：

# extract_rules() 返回的规则结构
{
    "rule_id": "rule_data_verification",
    "rule_name": "Data Verification",
    "positive_rules": [
        "verify computed results against source data"
    ],
    "negative_constraints": [
        "don't present unverified computed values",
        "don't trust floating-point rounding blindly"
    ],
    "confidence": 0.87,
    "compression_ratio": 1450,
    "derived_from": ["skill_data_analysis_v3"]
}

注意 negative_constraints 有两条而 positive_rules 只有一条。这不是刻意设计，而是从真实执行轨迹中提取的结果——失败模式天然比成功路径更丰富。

三、规则内省的四个层次

有了规则之后，大多数系统到这里就停了。但一个真正可用的规则系统需要完整的内省生命周期：

阶段API回答的问题
创建extract_rules()从技能中提取什么规则？
验证rule_conflict_detect()规则之间有矛盾吗？
匹配rule_apply()给定查询，哪些规则适用？
诊断rule_explain()为什么这条规则匹配/未匹配？

诊断层是最后一块拼图，也是最重要的一块。没有它，你只知道"匹配到了规则 A 和规则 B"，但无法调试为什么规则 C 没有匹配，无法理解关键词贡献分布，无法改进规则质量。

四、rule_apply() 的实现：Jaccard 关键词匹配

rule_apply() 使用 Jaccard 相似度进行关键词匹配。选择 Jaccard 而非嵌入相似度的原因是：规则匹配需要可解释性，而 Jaccard 的每个步骤都可以审计。

def rule_apply(self, query: str, *, top_k: int = 10,
               include_metadata: bool = False) -> dict:
    """
    对查询进行 L3 规则匹配，返回排序后的匹配结果。

    算法:
    1. 收集所有 kind='rule' 的节点
    2. 分词查询（过滤停用词，最小 3 字符）
    3. 对每条规则：构建关键词集合（rule_name + positive_rules + negative_constraints）
    4. 计算 Jaccard 相关度 = |交集| / |并集|
    5. 按相关度降序排列，限制 top_k
    6. 编译可执行建议
    """
    import re

    STOPWORDS = {'the', 'a', 'an', 'and', 'or', 'but', 'in', 'on',
                 'at', 'to', 'for', 'of', 'with', 'by', 'from', 'is',
                 'are', 'was', 'were', 'be', 'been', 'being'}

    # 分词
    query_keywords = {
        w.lower() for w in re.findall(r'[a-zA-Z_]{3,}', query)
        if w.lower() not in STOPWORDS
    }

    matches = []
    for node_id, node in self._nodes.items():
        if node.kind != 'rule':
            continue

        data = node.data or {}
        rule_keywords = set()

        # 从规则名称、正面规则、负面约束中提取关键词
        name = data.get('rule_name', '')
        if name:
            rule_keywords.update(
                w.lower() for w in re.findall(r'[a-zA-Z_]{3,}', name)
                if w.lower() not in STOPWORDS
            )

        for rule_text in data.get('positive_rules', []):
            rule_keywords.update(
                w.lower() for w in re.findall(r'[a-zA-Z_]{3,}', rule_text)
                if w.lower() not in STOPWORDS
            )

        for constraint_text in data.get('negative_constraints', []):
            rule_keywords.update(
                w.lower() for w in re.findall(r'[a-zA-Z_]{3,}', constraint_text)
                if w.lower() not in STOPWORDS
            )

        # Jaccard 相关度
        if not rule_keywords:
            continue

        intersection = query_keywords & rule_keywords
        union = query_keywords | rule_keywords
        relevance = len(intersection) / len(union) if union else 0.0

        if relevance > 0:
            # 编译可执行建议
            guidance = []
            for pos in data.get('positive_rules', []):
                guidance.append(f"[{name}] DO: {pos}")
            for neg in data.get('negative_constraints', []):
                guidance.append(f"[{name}] DON'T: {neg}")

            matches.append({
                'rule_id': node_id,
                'rule_name': name,
                'relevance': round(relevance, 4),
                'matched_keywords': sorted(intersection),
                'guidance': guidance,
            })

    matches.sort(key=lambda x: x['relevance'], reverse=True)
    return {
        'query': query,
        'total_rules_scanned': len(matches),
        'matches': matches[:top_k],
        'unmatched_count': max(0, len(matches) - top_k),
    }

这段代码的关键设计决策：

  • Jaccard 而非余弦相似度：关键词集合是二值的，Jaccard 天然适配，且每一步可审计
  • 停用词过滤：3 字符下限 + 停用词表，避免 "the"、"and" 等高频词污染相关度
  • DO/DON'T 分离：指导信息中明确区分正面建议和负面约束，呼应 RuleShaping 的发现
  • 零外部依赖：纯正则 + 集合运算，不依赖任何 NLP 库或嵌入模型

五、rule_explain()：从"是什么"到"为什么"

rule_apply() 告诉你哪些规则匹配了。rule_explain() 告诉你为什么。区别是质的：

def rule_explain(self, rule_id: str, query: str, *,
                  include_suggestions: bool = True) -> dict:
    """
    逐规则匹配诊断：为什么这条规则匹配/未匹配此查询？

    返回:
        - intersection: 共同关键词（贡献匹配的词）
        - query_only: 查询独有的词（未覆盖的意图）
        - rule_only: 规则独有的词（未触发的范围）
        - contribution_scores: 每个交集关键词对 Jaccard 的贡献
        - explanation: 人类可读的解释文本
        - suggestions: 上下文感知的改进建议
    """
    # ... 验证 rule_id ...

    # 与 rule_apply 使用完全相同的分词逻辑
    query_keywords = tokenize(query)
    rule_keywords = tokenize_from_rule(node)

    intersection = query_keywords & rule_keywords
    union = query_keywords | rule_keywords
    query_only = query_keywords - rule_keywords
    rule_only = rule_keywords - query_keywords

    relevance = len(intersection) / len(union) if union else 0.0

    # 每个关键词的 Jaccard 贡献
    denominator = len(union) if union else 1
    contribution_scores = {
        kw: round(1.0 / denominator, 4)
        for kw in sorted(intersection)
    }

    # 生成人类可读解释
    explanation = f"规则 '{name}' 对查询 '{query}' 的匹配分析:\n"
    explanation += f"  相关度: {relevance:.4f} (Jaccard)\n"
    explanation += f"  交集关键词 ({len(intersection)}): {sorted(intersection)}\n"
    explanation += f"  查询独有 ({len(query_only)}): {sorted(query_only)}  ← 未覆盖的意图\n"
    explanation += f"  规则独有 ({len(rule_only)}): {sorted(rule_only)}  ← 未触发的范围\n"

    # 上下文感知建议
    suggestions = []
    if relevance == 0:
        suggestions.append("零重叠：考虑添加以下关键词到规则: "
                          + ", ".join(sorted(query_only)[:5]))
    elif relevance < 0.2:
        suggestions.append("低相关度：规则可能需要扩展关键词覆盖")
    elif relevance >= 0.5:
        suggestions.append("高相关度：此规则对此类查询有效")

    if query_only:
        suggestions.append(f"未覆盖的查询意图: {sorted(query_only)[:5]}")
    if rule_only:
        suggestions.append(f"规则有未触发的范围: {sorted(rule_only)[:5]}")

    return {
        'rule_id': rule_id,
        'rule_name': name,
        'query': query,
        'matched': relevance > 0,
        'relevance': round(relevance, 4),
        'intersection': sorted(intersection),
        'union': sorted(union),
        'query_only': sorted(query_only),
        'rule_only': sorted(rule_only),
        'contribution_scores': contribution_scores,
        'explanation': explanation,
        'suggestions': suggestions if include_suggestions else [],
    }

contribution_scores 是这里最巧妙的设计。每个交集关键词对 Jaccard 分数的贡献是 1/|union|。这让"为什么相关度是 0.15 而不是 0.20"这类问题变得完全透明——你可以看到每个关键词"值"多少分。

六、一个真实的调试场景

假设我们有一个数据分析规则和一个 SQL 注入防护规则。用户查询"verify data before presenting results"：

# 规则库
rules = [
    {
        "rule_id": "rule_data_verification",
        "rule_name": "Data Verification",
        "positive_rules": ["verify computed results against source data"],
        "negative_constraints": [
            "don't present unverified computed values",
            "don't trust floating-point rounding blindly"
        ],
    },
    {
        "rule_id": "rule_sql_safety",
        "rule_name": "SQL Safety",
        "positive_rules": ["use parameterized queries for user input"],
        "negative_constraints": ["don't concatenate user input into SQL"],
    },
]

# rule_apply("verify data before presenting results")
# → rule_data_verification: relevance=0.385, matched=['data', 'presenting', 'results', 'verify']
# → rule_sql_safety: relevance=0 (no keyword overlap)

# rule_explain("rule_data_verification", "verify data before presenting results")
# → intersection: ['data', 'presenting', 'results', 'verify']  (4 words)
# → union: ['against', 'before', 'computed', 'data', 'don', 'floating',
#           'present', 'presenting', 'point', 'results', 'rounding',
#           'source', 'trust', 'unverified', 'values', 'verify']  (16 words)
# → relevance: 4/16 = 0.25
# → contribution_scores: {data: 0.0625, presenting: 0.0625, results: 0.0625, verify: 0.0625}
# → query_only: ['before']  ← "before" 没有出现在规则关键词中
# → rule_only: ['against', 'computed', 'don', ...]  ← 规则覆盖但查询未触及的范围
# → suggestion: "低相关度：规则可能需要扩展关键词覆盖"

从这个诊断中，我们立刻看到两个改进方向：

  1. 规则应该包含 "before"——因为"在呈现前验证"是一个高频查询模式
  2. 规则覆盖了 "floating"、"rounding"、"trust" 等词，但这些词在查询中没出现——说明规则的负面约束比正面规则更"宽"，这恰好印证了 DON'Ts > DOs 的发现

这种透明度是嵌入向量匹配永远给不了的。你无法调试一个 768 维向量中哪些维度起了作用。Jaccard 的每个步骤都可以被审计、被质疑、被改进。

七、更大的图景：Agent 自我诊断

把视野拉远，规则内省生命周期其实是 Agent 自我诊断能力的一个切面。一个真正自主的 Agent 需要回答这些问题：

  • 我学到了什么？（compression_spectrum_report()——L0-L3 分布）
  • 我学到的东西有矛盾吗？（rule_conflict_detect()——规则冲突）
  • 面对新问题，我的经验适用吗？（rule_apply()——运行时匹配）
  • 如果不适用，为什么？（rule_explain()——诊断解释）

这是一个从原始数据到自我认知的完整链条。而最关键的"为什么"环节，恰恰是当前所有 Agent 框架最薄的一层。

LangGraph、CrewAI、AutoGen 都在解决"如何让 Agent 执行任务"的问题。但几乎没有框架在解决"如何让 Agent 理解自己学到了什么"的问题。这不是锦上添花——当 Agent 的规则库达到一定规模（100+ 条规则），规则间的冲突、覆盖盲区、关键词退化就会成为系统性的可靠性瓶颈。

八、可操作的建议

立即可做

如果你的 Agent 有任何形式的规则或策略系统，加上 explain() 方法。不需要复杂的实现——哪怕只是打印出"匹配了哪些关键词"也比黑盒强。调试规则匹配失败的第一步永远是：看到匹配过程。

短期（1-2 周）

在规则提取时，显式分离 positive_rules 和 negative_constraints。不要把"要做 X"和"不要做 Y"混在同一条规则文本里。混合文本会让匹配逻辑变得模糊——"don't verify" 会意外匹配 "verify" 关键词。分离后，负面约束可以作为独立的匹配信号参与计算。

中期（1-2 月）

实现一个最小版本的 compression_spectrum_report()——统计你的知识库中 L0-L3 各有多少条目。你会惊讶地发现：大多数内容卡在 L0/L1，从未被压缩成可复用的形式。这个分布本身就是优化的起点。

结语

290 天连续开发，8500+ 个测试，5 个 API 完成的规则内省生命周期——这些数字背后是一个朴素的信念：Agent 的可靠性不来自更大的模型，而来自更透明的知识管理。

当你能解释每一条规则为什么匹配、为什么不匹配、哪些关键词起了多少作用，你就拥有了一个可以持续改进的系统。而一个可以持续改进的系统，最终会超越任何静态优化的黑盒。

规则的终点不是执行，而是理解。
