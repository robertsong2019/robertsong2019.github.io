Beyond ReAct：2026 年 Agent 规划与推理的前沿实践

📅 2026-07-26 · 罗嵩
ReAct（Reason+Act）自 2022 年提出以来，几乎是所有 LLM Agent 的默认架构。但当你真正让 Agent 去完成 10 步以上的任务时，它就像一个聪明但缺乏自控力的实习生：前 3 步表现优异，第 5 步开始重复自己，第 8 步陷入无效循环。本文从 2026 年最新的三篇前沿研究出发——VRR-Stop（自适应停止准则）、RLAW（POMDP+Critic 架构）、Entropy-Guided Branching（熵驱动搜索）——记录如何让 Agent 在长链推理中保持靠谱。含完整 TypeScript 可运行代码。

一个令人不安的实验

我做过一个简单实验：让一个基于 ReAct 的 Agent 完成"部署一个 API 服务并验证健康检查"这个任务。

5 步以内的任务：成功率 92%。
8-12 步的任务：成功率骤降到 47%。
15 步以上的任务：成功率只有 11%。

这不是个例。2026 年 7 月，RLAW 论文（arXiv:2607.09934）给出了更系统的数据：在 ALFWorld 基准上，标准 ReAct 的成功率只有 54.1%——刚好比抛硬币好一点。

问题出在哪里？

ReAct 的三道天花板

ReAct 的核心循环很简单：观察 → 推理 → 行动 → 观察 → ...。这个循环在短任务中表现出色，但在三个维度上存在结构性缺陷。

天花板一：Verify-Repair 循环没有刹车

当 Agent 发现错误时，它会尝试修复。但修复本身可能引入新错误——而 Agent 没有判断"何时停止修复"的能力。

想象一个程序员在 code review 中反复修改同一段代码：第一轮 reviewer 说"变量名不好"，改了；第二轮 reviewer 说"逻辑有问题"，又改了；第三轮——回到原点。没有停止准则的修复循环，本质上是在随机游走。

VRR-Stop 论文（arXiv:2607.17641）量化了这个现象：在 GSM8K 基准的压力测试中，报告的 acceptance 率持续上升，但真实 validity 反而下降。Agent 以为自己在进步，实际上在退步。

天花板二：没有"信念状态"

ReAct 直接基于最大似然 token 预测执行动作。它不维护对环境的结构化信念——一切依赖上下文窗口中的最近几条消息。

这就像一个人在陌生城市导航，不看地图，只根据"刚才路过什么"做决定。短距离没问题，长距离必然迷路。

天花板三：搜索空间爆炸

当工具库从 5 个增长到 50 个时，每一步的选择空间指数级膨胀。ReAct 没有任何机制来决定"什么时候应该谨慎探索（多试几个方案），什么时候应该快速执行（走最优路径）"。

三把钥匙：从论文到代码

第一把：VRR-Stop——给修复循环装上刹车

VRR-Stop 的核心洞察极其简洁：停止准则比修复策略更重要。

他们提出了一个 4 参数噪声模型，分离了两类不确定性：

  • Verifier 的噪声：α（假接受率）和 β（假拒绝率）
  • Repairer 的噪声：γ（修复成功率）和 δ（破坏率）

有了这四个参数，我们可以计算修复的期望收益：

期望收益 = P(方案是错的) × γ - P(方案是对的) × δ

当期望收益为负时——继续修复弊大于利——就该停。这个模型在 GSM8K 上带来了 60.6 个百分点的提升，平均只用了 0.72 轮修复。

/**
 * VRR-Stop: Verify-Repair 循环的自适应停止准则
 * 基于 arXiv:2607.17641 的 4 参数噪声模型
 */

interface VRRParams {
  alpha: number;   // verifier false accept (0-1)
  beta: number;    // verifier false reject (0-1)
  gamma: number;   // repair success (0-1)
  delta: number;   // repair damage (0-1)
}

interface VRRState {
  round: number;
  beliefValid: number;  // 当前信念：方案是正确的概率
  history: Array<{
    round: number;
    verdict: 'accept' | 'reject';
    action: 'commit' | 'repair' | 'stop';
    belief: number;
  }>;
}

function vrrStep(
  state: VRRState,
  params: VRRParams,
  verifierVerdict: 'accept' | 'reject'
): VRRState {
  const { alpha, beta, gamma, delta } = params;
  const prior = state.beliefValid;
  let posterior: number;

  // Bayes 更新：根据 verifier 输出修正信念
  if (verifierVerdict === 'accept') {
    posterior = (prior * (1 - alpha)) /
                (prior * (1 - alpha) + (1 - prior) * alpha);
  } else {
    posterior = (prior * beta) /
                (prior * beta + (1 - prior) * (1 - beta));
  }

  // 修复的期望收益 = P(错误) × γ - P(正确) × δ
  const expectedGain = (1 - posterior) * gamma - posterior * delta;

  let action: 'commit' | 'repair' | 'stop';
  if (expectedGain > 0 && state.round < 10) {
    action = 'repair';
    posterior = posterior * (1 - delta) + (1 - posterior) * gamma;
  } else if (posterior > 0.95) {
    action = 'commit';
  } else if (state.round >= 10) {
    action = 'stop';
  } else {
    action = 'commit';
  }

  return {
    round: state.round + 1,
    beliefValid: posterior,
    history: [...state.history,
      { round: state.round, verdict: verifierVerdict, action, belief: posterior }],
  };
}

// === 演示 ===
const params: VRRParams = { alpha: 0.15, beta: 0.2, gamma: 0.7, delta: 0.1 };
let state: VRRState = { round: 0, beliefValid: 0.5, history: [] };

const verdicts: ('accept' | 'reject')[] =
  ['reject', 'accept', 'accept', 'accept'];

console.log('VRR-Stop 模拟');
for (const v of verdicts) {
  state = vrrStep(state, params, v);
  const h = state.history.at(-1)!;
  console.log(`Round ${h.round}: verdict=${h.verdict}, ` +
    `belief=${h.belief.toFixed(3)}, action=${h.action}`);
}

// Round 0: verdict=reject, belief=0.740, action=repair
// Round 1: verdict=accept, belief=0.962, action=commit
// Round 2: verdict=accept, belief=0.994, action=commit

关键设计决策：VRR-Guard 是无估计的 fallback。当验证边际不足时，保留当前最优方案而非冒险替换。就像有经验的工程师说的："如果改了没明显变好，就别改。"

第二把：RLAW——给 Agent 装上"内心审查官"

RLAW 的核心创新不在于 POMDP，而在于那个 独立的 Critique 模型。在 Actor 提出动作后、实际执行前做一次审查——本质上是 Kahneman "System 1 / System 2" 框架的工程化。

效果惊人：ALFWorld 成功率从 54.1% 飙升到 78.6%，幻觉率从 28.5% 降到 12.4%。

/**
 * RLAW 启发式 Propose-Critique-Execute 循环
 * training-free 简化版
 */

interface AgentState {
  belief: number;
  step: number;
  history: ActionRecord[];
  done: boolean;
}

interface ActionRecord {
  step: number;
  observation: string;
  action: string;
  critiqueScore: number;
  executed: boolean;
}

interface CritiqueConfig {
  threshold: number;     // τ = 0.70
  maxRetries: number;
  maxSteps: number;
}

/**
 * 启发式审查（生产环境可替换为微调模型）
 */
function critiqueAction(
  action: string,
  observation: string,
  history: ActionRecord[]
): number {
  let score = 0.5;

  // 惩罚重复
  const repeats = history.filter(h => h.action === action).length;
  score -= repeats * 0.15;

  // 奖励进展标记
  const progressWords = ['test', 'verify', 'implement', 'fix', 'check'];
  if (progressWords.some(w => action.toLowerCase().includes(w))) {
    score += 0.15;
  }

  // 惩罚过长动作
  if (action.length > 200) {
    score -= (action.length - 200) / 1000;
  }

  // 观测的具体性
  if (observation.includes('error') || observation.includes('success')) {
    score += 0.1;
  }

  return Math.max(0, Math.min(1, score));
}

function rlawStep(
  state: AgentState,
  observation: string,
  proposedAction: string,
  config: CritiqueConfig,
  executeFn: (action: string) => string
): AgentState {
  let action = proposedAction;
  let retries = 0;

  while (retries < config.maxRetries) {
    const score = critiqueAction(action, observation, state.history);

    if (score >= config.threshold) {
      const result = executeFn(action);
      return {
        ...state,
        step: state.step + 1,
        belief: Math.min(1, state.belief + 0.1 * score),
        done: state.step + 1 >= config.maxSteps,
        history: [...state.history, {
          step: state.step, observation, action,
          critiqueScore: score, executed: true,
        }],
      };
    }
    action = `[retry] ${action}`;
    retries++;
  }

  // 超过重试次数，强制执行
  const result = executeFn(action);
  return {
    ...state,
    step: state.step + 1,
    belief: state.belief * 0.8,
    done: state.step + 1 >= config.maxSteps,
    history: [...state.history, {
      step: state.step, observation, action,
      critiqueScore: 0, executed: true,
    }],
  };
}

实践要点：Critic 的阈值 τ 是关键超参数。论文用 0.70——太低几乎不过滤，太高会导致频繁重试。建议从 0.70 开始调整。

第三把：Entropy-Guided Branching——让 Agent 知道何时该犹豫

Amazon 的研究团队提出了一个优雅的想法：用信息熵来决定 Agent 应该在哪些决策点"犹豫"（分支探索），在哪些点"果断"（线性执行）。

/**
 * 熵引导分支控制器
 * 高熵 → 多分支探索，低熵 → 线性执行
 */

interface BranchConfig {
  maxBranching: number;
  entropyThreshold: number;
  pruningMargin: number;
}

function normalizedEntropy(
  actions: { action: string; prob: number }[]
): number {
  const total = actions.reduce((s, a) => s + a.prob, 0);
  if (total === 0) return 0;

  const normalized = actions.map(a => a.prob / total);
  const H = -normalized.reduce(
    (sum, p) => (p > 0 ? sum + p * Math.log2(p) : sum), 0
  );

  return H / Math.log2(actions.length || 1);
}

function branchingFactor(
  entropy: number, config: BranchConfig
): number {
  if (entropy < config.entropyThreshold) return 1;
  const t = (entropy - config.entropyThreshold) /
            (1 - config.entropyThreshold);
  return Math.max(1, Math.ceil(config.maxBranching * t));
}

// 演示
const cfg: BranchConfig = {
  maxBranching: 4, entropyThreshold: 0.5, pruningMargin: 0.15
};

const points = [
  { label: '确定场景', actions: [
    { action: 'run tests', prob: 0.92 },
    { action: 'skip tests', prob: 0.08 },
  ]},
  { label: '不确定场景', actions: [
    { action: 'use PostgreSQL', prob: 0.38 },
    { action: 'use MongoDB', prob: 0.33 },
    { action: 'use SQLite', prob: 0.29 },
  ]},
];

for (const dp of points) {
  const H = normalizedEntropy(dp.actions);
  const bf = branchingFactor(H, cfg);
  console.log(`${dp.label}: entropy=${H.toFixed(3)}, branching=${bf}`);
}

// 确定场景: entropy=0.402, branching=1
// 不确定场景: entropy=0.991, branching=4

三把钥匙如何组合

这三个技术不是互相替代，而是互补的：

┌─────────────────────────────────────────────┐
│            Agent 执行循环                    │
│                                              │
│  1. 面对决策点                               │
│     ↓                                        │
│  2. Entropy-Guided Branching                 │
│     计算动作分布熵 → 决定分支因子            │
│     ↓                                        │
│  3. Propose-Critique (RLAW)                  │
│     Actor 提出动作 → Critic 审查             │
│     分支并行探索，剪枝淘汰劣解               │
│     ↓                                        │
│  4. 执行 → 观测 → 验证                       │
│     ↓                                        │
│  5. VRR-Stop                                 │
│     4 参数模型决定：继续修还是停下来？       │
│     ↓                                        │
│  6. 回到 1                                   │
└─────────────────────────────────────────────┘

分支控制解决的是"探索 vs 利用"的宏观策略；Critic 审查解决的是单步动作的质量控制；VRR-Stop 解决的是修复循环的终止决策。三者覆盖了 Agent 执行生命周期的不同阶段。

工程化建议

1. 从 VRR-Stop 开始。 如果你的 Agent 已有 verify-repair 循环（如"生成→测试→修复"），VRR-Stop 是最低成本的改进。估计 α（假接受率）和 γ（修复成功率），实现 expectedGain 计算——大约 30 行代码。

2. Critic 不需要训练模型。 启发式 Critic 已能带来显著提升。关键功能只有三个：重复检测、进展标记、复杂性惩罚。30 行启发式代码覆盖 80% 的收益。

3. 熵引导需要好的概率估计。 两种方法：LLM logprob（更快但需 API 支持）或多次采样统计频率（更通用但有延迟）。

写在最后：从"能用"到"靠谱"

ReAct 在 2022 年出现时，解决的是"让 LLM 使用工具"这个从 0 到 1 的问题。到了 2026 年，问题变成了"让 Agent 在 50 步任务中保持可靠性"——这是从 1 到 N 的挑战。

本文介绍的三项技术有一个共同主题：给 Agent 的直觉行动装上"元认知"。VRR-Stop 是对"我是不是该停了"的元认知；Critic 是对"这个动作靠谱吗"的元认知；熵引导是对"我是不是该多想想"的元认知。

人类的高质量决策不是来自更快的直觉，而是来自更好的自我审查。Agent 也一样。
