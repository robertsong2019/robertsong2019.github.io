相似≠相关：向量检索之外，让模型自己翻目录

📅 2026-09-30 · RAG · 检索架构 · PageIndex

一、同一个靶子，两条路

昨天写了 hindsight（40.8k stars 的会学习记忆），同一天 GitHub Trending 上另一个老将回榜：VectifyAI/PageIndex，37.2k stars、单日 +822。它的 README 第一句就把人钉住了：

Vector-based RAG retrieves by semantic similarity. But similarity ≠ relevance — what retrieval actually needs is relevance, and relevance requires reasoning.

基于向量的 RAG 按语义相似度检索，但相似不等于相关——检索真正需要的是相关性，而相关性需要推理。

hindsight 和 PageIndex 从两个相反的方向否定同一件事：chunk + embed + cosine 万能论。昨天那条路是「让记忆学会」（vector + learning），今天这条是「让检索理解」（tree + reasoning）。一个治「检索到了但不更新」，一个治「根本就检索不到」。

二、向量检索到底错在哪：vibe retrieval

给一个具体例子。查询：「三季度现金流恶化，管理层的归因是什么？」

答案藏在年报的这句话里：「营运资金周转天数由 45 天升至 92 天，主要由于应收账款回款周期延长及存货积压。」

注意：「现金流」三个字在答案段落里一次都没出现。嵌入空间里，问句和这段话的余弦相似度未必排得进前十——这是「相关但不相似」，漏检。反过来，查询里只要有「风险」二字，相似度会把整本风险章节、连同其他文件的风险提示全捞回来——「相似但不相关」，误检。

根因是结构性的：向量检索的全部信号只有一个 query embedding。它不知道你在问什么，只知道你的问句「长得像」什么。PageIndex 给这起了个刻薄的名字：vibe retrieval（氛围检索）。对比表里最扎心的一行是上下文：vector RAG 填的是「query embedding only」，PageIndex 填的是「对话历史、领域知识、随便什么」——因为它的检索器是个 LLM，能带着完整上下文读问题。

三、建树，翻树：两个动作

方案说穿了只有两步：

  1. Index：为每篇文档生成 LLM 构建的层级树索引——像人类专家给长报告做目录
  2. Retrieve：agent 沿树推理式导航——像人翻年报：先看目录猜答案在哪章，翻到那章再看小节，直到定位

README 说灵感来自 AlphaGo：树搜索 + 推理。有个容易被忽略的工程细节：树结构本身从文档版式提取，不经 LLM；模型只做摘要精炼。所以建树用基础模型就够（官方实测基础模型不损质量），聪明模型留给检索阶段——沿树推理才是精度瓶颈。成本结构因此清晰：便宜的一次性索引 + 按问题付费的聪明检索。

8 月刚发的 SDK local mode 让这条路可以本机全跑：

import os
from pageindex import PageIndexClient

os.environ["OPENAI_API_KEY"] = "your-openai-key"

client = PageIndexClient(
    index="gpt-5.6-luna",   # 建树：基础模型就够——树结构来自文档版式，模型只做摘要
    chat="gpt-5.6-sol",     # 检索：用买得起的最强模型——沿树推理才是精度瓶颈
)
doc_id = client.submit_document("report.pdf")["doc_id"]

print(client.chat("What was the 2023 operating margin?", doc_id=doc_id))

官方数字（口径见仓库 benchmark）：

  • 建索引约 $0.001/页：1000 页教科书一美元多、几分钟，之后所有问题复用；9~1,098 页的实测文档 13 秒到 4.5 分钟建完
  • 检索成本 vs 每次把整个 PDF 原生塞进 context：52 页时便宜 2.1 倍，420 页时 16.6 倍，805 页时原生路线直接超出 context window
  • FinanceBench（金融文档 QA 基准）：98.7% vs 向量 RAG 的约 50%

第三组数字最值得看的其实是评测设计：OSS Benchmark 用 62 道查找题、34 个 PDF、1,945 页（取自 MMLongBench-Doc-V2），每道题的答案都是正文里明写的事实——答错只能是检索或阅读失败，赖不到推理头上。把「检索」从「推理」里剥出来单独测，这本身就是值得偷的评测方法论。

四、四十行说清机制

不装 SDK 也能理解机制。推理式检索的本质是：每层让 LLM 做一次选择题。

def tree_retrieve(node: dict, question: str, ask) -> tuple[str, list[str]]:
    """node 形如 {"title": ..., "children": [...]} 或叶子 {"title": ..., "passage": ...}"""
    path = [node["title"]]
    while node.get("children"):
        options = "\n".join(
            f"{i}. {c['title']}" for i, c in enumerate(node["children"]))
        choice = ask(f"问题：{question}\n当前节的子目录如下，答案最可能在哪一节？只回序号。\n{options}")
        node = node["children"][int(choice.strip().rstrip('.'))]
        path.append(node["title"])
    return node["passage"], path   # path 即显式引用链：第7章 → 7.2 → 7.2.3

# 向量检索：question → embedding → 最近邻 top-k   （一次几何运算，黑箱）
# 树检索：  question → 树深次阅读理解              （多次 LLM 调用，白箱可追溯）

注意 path 的返回：引用天然锚定到显式节点。向量检索给你 top-k 相似 chunk 是黑箱；这里「答案来自第 7 章 7.2.3 节」是结构事实——审计场景（金融、法务）的刚需，也是 PageIndex 把 traceable 当第一卖点的原因。通用 LLM 幻觉率再高，「翻到哪一节」是可复核的。

五、冷水：什么时候别用

  • 每次检索是一串 LLM 调用：树深 × 每层一次推理，延迟秒级起步；向量检索毫秒级。高频短查询用树是自找的。
  • 文档一改，树要重建：高频更新的语料，树索引维护成本会吃人。索引是一次性成本，但不是零成本。
  • 短文档、闲聊记忆：杀鸡用牛刀。向量 RAG 生态的部署成熟度在大量场景仍是正确答案。

选型一句话：长专业文档（财报/法务/手册/教材）+ 要可追溯引用 → 树；海量短 chunk + 毫秒响应 → 向量；同一系统可按查询类型路由，两者共存。

另外注意 hindsight 与 PageIndex 在这里正交：一个治「学到的东西会过时」，一个治「读不懂长文档」。别指望一个工具治两种病——hindsight 的 mental model 解决「答了千百遍的问题别再检索」，PageIndex 解决「第一次读千页文档时去哪找」。一个管复用，一个管初见。

六、落地：给 amg 加第二路检索

amg 的 memory 检索目前是 embedding 单路。LongMemEval 的失分题里有相当比例的「时序倒置」类——需要理解事件先后顺序的问题，恰好是「相似但不相关」的重灾区：旧会话和新会话谈论同一话题，相似度分不开谁先谁后。

可做的实验：给 session 记忆加一路树索引（按时间 × 主题组织的层级结构，建树成本可控），exact_judge 下对照两路的误检率与时序题得分。PageIndex 官方没测过对话记忆场景——这是个空白，做出来就是增量。

昨天说「记忆系统别看存了多少，看第二次遇到同一件事省了多少」；今天补一句：检索系统别看捞回了多少相似的，看它是否真的在回答你的问题。相似度是几何，相关性是理解——前者可以离线算好，后者只能临场想清楚。
