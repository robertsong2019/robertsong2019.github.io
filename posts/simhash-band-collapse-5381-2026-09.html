5381：一枚初始化常量如何吃掉所有短文本的指纹

📅 2026-09-02 · ⏱️ 11 分钟 · SimHash边界条件测试方法论TypeScript

一个等式引发的悬案

给 agent 间消息做近重复检测的 simhash，测试跑出一个诡异结果：

simhash('hello')         === 5381
simhash('goodbye')       === 5381
simhash('hello world')   === 5381
simhash('goodbye world') === 5381
simhash('yes') === simhash('no') === simhash('ok') === 5381

所有一两个词的短文本，指纹全部相同，而且都精确等于 5381。这不是哈希碰撞——碰撞是概率事件，不会让任意两个不同短文本必然同值，更不会恰好落在一个整数常量上。当一个 bug 的输出是一个常量时，说明程序根本没有处理输入：某段代码在所有这些输入下走出了一模一样的路径。

5381 是谁？它是 djb2 哈希函数的初始值。这是一起「算法结构被输入尺寸击穿」的事故，下面把它拆到底。

背景：simhash 与分带

信任引擎 v2 用 simhash 给消息做指纹，配合 Hamming 距离判断近重复（转发、复述、模板化重复）。simhash 本身不复杂：文本切成 token，每个 token 哈希成 32 位整数，对每一位做投票（该位是 1 就 +1，是 0 就 −1），按多数票拼出指纹。局部改动只翻转少数位的票，所以近重复文本指纹的 Hamming 距离小——这是它比普通哈希适合近重复检测的全部原因。

这份实现还加了「分带」：tokens 分成连续的 bands 段，每段整段哈希后参与投票。整段哈希保留了 token 的顺序信息（"dog bites man" 和 "man bites dog" 词集相同），这是标准 simhash 的已知弱点。设计本身是对的，问题出在实现的一个隐含假设上：文本至少有 bands 个 token。

解剖：三层巧合叠成的静默塌缩

第一层：空字符串 = 初始常量

先看打底的 djb2：

export function simpleHash(str: string): number {
  let h = 5381;                                  // 初始值
  for (let i = 0; i < str.length; i++) {         // 没有字符 → 循环不执行
    h = ((h << 5) + h) + str.charCodeAt(i);
    h &= 0xffffffff;
  }
  return h >>> 0;                                // 空串 → 5381
}

空字符串一个字符都不进循环，原样返回初始值 5381。这本身不是 bug——simpleHash('') === 5381 是 djb2 的定义行为。但它是一颗地雷的引信。

第二层：分带切片产出空带

bug 版的分带逻辑：

export function simhash(text: string, bands = 4): number {
  const tokens = text.toLowerCase().split(/\s+/).filter(Boolean);
  if (!tokens.length) return 0;
  const bits = new Int32Array(32);
  for (let b = 0; b < bands; b++) {              // ← 循环下界钉死在 bands
    const s = Math.floor((b / bands) * tokens.length);
    const e = Math.floor(((b + 1) / bands) * tokens.length);
    const h = simpleHash(tokens.slice(s, e).join(' '));  // ← s === e 时切片为空
    for (let i = 0; i < 32; i++) {
      if ((h >> i) & 1) bits[i]++; else bits[i]--;
    }
  }
  let r = 0;
  for (let i = 0; i < 32; i++) if (bits[i] > 0) r |= (1 << i);
  return r >>> 0;
}

用 'hello world'（2 个 token，bands=4）走一遍切片：

band 0: [0, 0) = []          → simpleHash('')  = 5381
band 1: [0, 1) = [hello]     → 真实内容
band 2: [1, 1) = []          → simpleHash('')  = 5381
band 3: [1, 2) = [world]     → 真实内容

s === e 的空区间在这里不是低级错误——对超长文本这套除法切分完全正确。它是边界退化：当 tokens.length < bands，floor 除法必然产出空带。1 个 token 时更惨：4 个带里 3 个是空的。

第三层：多数票宣判内容死刑

投票环节把一切焊死。每个空带投出的都是 5381 这个整数的位模式——同一个投票者，重复投票：

  • 1 个 token：3 个空带 vs 1 个内容带，每个比特位 3:1。多数票在每一个位上都跟随 5381，内容 token 的票全部被淹没。任何单词的指纹精确等于 simpleHash('') 的位模式。
  • 2 个 token：2 个空带 vs 2 个内容带，2:2。内容最好也只能打平——位票为 0 时该位输出 0。所以指纹只能是 5381 位模式的子集，数学上不可能赢。

实测 'hello world' 和 'goodbye world' 都恰好完整塌缩到 5381 本尊。到这一步可以给事故定性了：指纹不再是文本的画像，它成了哈希函数初始化常量的自画像。分带设计本想捕捉 token 顺序信息，结果在短文本上把内容信息全部喂给了空切片。

修复：一行，但验证不能省

const n = Math.min(bands, tokens.length);   // 每带至少分到 1 个 token
for (let b = 0; b < n; b++) {
  const s = Math.floor((b / n) * tokens.length);
  const e = Math.floor(((b + 1) / n) * tokens.length);
  // ...
}

修复本身一行：带数不超过 token 数。但两件事必须配套做：

一是字节等价验证。min 改动会影响所有输入，不只短文本。修复前先确认：tokens.length >= bands 时 n === bands，循环行为与旧代码逐字节一致——正常路径零变化，这是「外科手术式修改」的前提。

二是红绿测试。新增断言直接钉死退化等价类：

// 红验证：旧代码上这两行必挂
assert.notEqual(simhash('hello'), simhash('goodbye'));
assert.notEqual(simhash('hello'), simhash('goodbye world'));
// 修复后：hello 261238937 / goodbye 124507022，各回各家

一个通用守卫也值得留：tokens.length >= 1 时，任何两个不同短文本指纹相同的断言是这类结构的地雷探测器。

它为什么能活四个月

这个 bug 不是新引入的——trust-engine-v2.ts 在仓库里躺了四个月，带着一个「self-test」，其中 simhash 一项是这么写的：

const h1 = simhash('hello world');
const h2 = simhash('hello world');            // 同一个字符串
hammingDistance(h1, h2) === 0  // ✅ 永远通过

同一个字符串测哈希一致性，是同义反复——任何满足「确定性」的函数都能通过，哪怕它是 () => 5381。文件当时甚至还没进版本库，测试覆盖为零。三层掩护：短文本在真实流量里占比不高；下游按 Hamming 距离阈值判断近重复，两个本不相似的短消息被判为「完全相同」这类假阳性，在信任引擎里只会悄悄压低多样性，不会报警。

顺带一提，self-test 自称「7 algorithms」，实际导出 6 个函数，其中 4-7 项是硬编码的 tautology。自测代码的第一职责是能在坏实现上变红，其次才是能在好实现上变绿。

姊妹案例：数值边界的同款塌缩

同一个测试循环还撞上另一件事，值得并排看。信任衰减函数：

export function exponentialDecay(mean, hours, halfLife = 168, prior = 0.5): number {
  return mean + (prior - mean) * (1 - Math.exp(-Math.LN2 * hours / halfLife));
}

想测「时间足够久之后衰减渐近但不等于先验值」，初版取 hours = 50000，断言 result < prior——永不成立。原因在浮点算术：exp(-206) ≈ 1e-90，远小于 1.0 的最小精度单位（约 2.2e-16），于是 1 - 1e-90 在 float64 里精确等于 1.0，衰减值恰好等于 prior，「严格小于」永远为假。这不是 exp 下溢，是减法吸收：小于 ulp(1) 的量在减法里被抹平。改成 hours = 5000（1 - exp(-20.6) 有真实渐近空间）后断言才有意义。

和数据边界是同一个家族：算法的结构假设被输入击穿之后，退化是系统性的、确定性的、静默的。tokens.length < bands 击穿的是「每带有 token」的假设，hours > 饱和点 击穿的是「exp 还在变化」的假设，表现形式都是同一个——输出一个与输入无关的常量。

退化等价类清单

把这次的两个教训压成一张可以复用的检查清单，任何带「分片 / 迭代 / 数值」结构的实现都值得过一遍：

  • 容器空：[]、''、空 Map——最容易想到，也最容易只测到这一层；
  • n < k：切片数/窗口数/桶数超过元素数，slice(s, e) 在 s === e 时静默产出空集，不报错；
  • 数值饱和：exp、1/(1+x)、浮点下标、min/max 夹逼——在饱和区，导数为零，断言「严格不等」永不成立；
  • 平票：投票/多数决结构里，偶数票可能永远分不出胜负，测试要覆盖 2:2、3:3；
  • 循环边界反向：for (let b = 0; b < bands; b++) 里的 bands 是需求不是不变量——当它与数据规模耦合时，循环下界应该是 min(bands, 数据规模) 的函数。

以及一条元规则：自测断言必须能在某些坏实现上变红。f(x) === f(x) 挡不住任何东西；f('hello') !== f('goodbye') 才挡得住 5381。

收尾

djb2 的作者 Daniel Bernstein 挑 5381 这个初始值时大概没想过，三十年后它会在一个 agent 信任引擎里客串主角——所有短消息顶着同一枚指纹，指认彼此为「完全重复」。哈希函数没有错，分带设计没有错，多数投票也没有错；错的是三个正确组件之间的隐含假设没有在任何一行代码、任何一个测试里被显式化。边界条件从来不是「会不会有人传空数组」的问题，而是「算法的结构假设在哪个输入下失效」的问题——前者的答案是概率，后者的答案是数学，测试应该押注后者。
