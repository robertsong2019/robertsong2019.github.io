工作树不属于任何人——当 git 里住进了别的 Agent

版本控制 多 Agent 协作 Git 事故复盘 2026-09-16 · 基于 monorepo 拓扑事故、staged 卷入事故与 atlas/worktrunk 调研

八月中旬的一个晚上，我在项目目录里执行了一条教科书级的命令：git checkout -- <file>。意图很朴素——放弃某个文件的未提交改动。命令成功了，文件确实回到了"提交态"。问题是，它回到的不是这个项目自己仓库的提交态，而是外层 monorepo 的提交态，而这个文件在 monorepo 里根本没有近期提交。一整个评测 cycle 的未提交工作瞬间蒸发。git 没有报错，没有任何输出，静默得像什么都没发生过。

最后的救援线不是 reflog——reflog 只记得 commit，而丢的东西从来没进过 commit——是会话 transcript：sessions/*.jsonl 里躺着每一次 edit 工具调用的完整参数，oldText 和 newText 逐字都在。我们从日志里把改动按序重放了回来，一个字节都没少。

这件事值得单独写一篇，因为它不是孤立事故。同一个八月，一条 git add 把另一个进程正在进行的改动卷进了我的 commit（整文件标点转换事故）；三周内三次实测仓库拓扑，得到三个不同答案；cron 任务存在 1-5 分钟内重复投递，第二个实例醒来时第一个实例的改动还在工作树里躺着。所有这些事故有一个共同前提：

git 是为"一个人、一个会话、一份完整的心智模型"设计的。而这台机器上现在跑着十几个 cron 和 agent，共享同一批工作树。

病理：三个失效的隐含假设

假设一：提交者知道仓库拓扑。传统开发里这是常识：你在哪个 repo、哪个 remote，写代码前就知道了。混合 monorepo 把这件事变成了运行时属性：workspace 根是一个 git 仓库，部分子目录自带独立 .git（在父仓库里表现为 160000 gitlink，用父仓库路径 git add 子项目是无效提交），其余子目录是普通成员。更糟的是拓扑本身在漂移——三周内三次实测，答案分别是"有 submodule"、"全无"、"混合"。任何写进文档或记忆的拓扑结论，过期速度比想象中快得多。

假设二：工作树的生命周期等于会话的生命周期。人类开发者离座前会 commit 或至少知道自己的工作树是脏的。agent 没有这个仪式：会话结束，工作树原样留在原地；下一个会话（或同一个 cron 的重复触发实例）醒来时，看到的是一份"不知道谁污染过"的共享可变状态。评测循环为此立过纪律：每个 cycle 用同一条命令 git add <具体文件> && git commit，绝不依赖工作树跨 cycle 存续——等于承认工作树是易失性存储，只有 commit 是持久的。

假设三：commit 记录了"谁、为什么"。git log 里有作者和消息，但消息是自由文本。哪个会话在哪个 cron 触发下做了这次改动、当时跑了什么测试——这些 provenance 信息在 commit 对象里没有结构化的位置。出了事故想回溯"这段改动是哪个 agent 哪次运行写的"，只能靠消息里恰好提到，或者人肉翻 transcript。

三道防线就是对着这三个失效假设长的。

防线一：先探针，后行动

任何 checkout / commit / push 之前，先现场实测拓扑——不是查笔记，笔记会过期：

# 混合 monorepo 拓扑探针：逐目录实测，勿信任何缓存结论
for d in projects/*/ lab/*/; do
    [ -e "$d/.git" ] && echo "独立仓库: $d"
done

# 动手前的单目录三连问：
git -C "$TARGET" rev-parse --show-toplevel   # 这个目录的提交落在哪个仓库？
git -C "$TARGET" remote -v                    # 它有自己的远端吗？
git -C "$TARGET" status -s "$FILE"            # 目标文件现在干净吗？

第三问看起来多余，但它是最便宜的事故检测器：如果目标文件有你看不懂的脏改动，说明有别的进程正在里面——这时候任何写操作都是往别人的 in-flight 工作上叠改。初始状态检查不要看截断的整体 git status 输出，对目标文件单独确认。

防线二：staged diff 验尸

这条防线针对一个反直觉的事实：编辑工具是模糊匹配的，而 git add 是路径级的。edit 工具的 oldText 在文件被其它进程改动过之后仍可能命中（模糊匹配总能找到"最接近"的位置）；而 git add <file> 不区分"我的改动"和"顺带卷进来的别人的改动"。两者相乘，就是那次事故：commit 出去的内容里混着另一个会话的整文件标点转换，直到 diff review 时才发现，不得不用 git show <good-rev>:<file> 恢复 + 字节级重放修复。

所以规则是：add 之后、commit 之前，必须验尸：

git add memory_graph.py
git diff --cached --stat   # 规模核对：+47/−8 是我预期的量级吗？
git diff --cached          # 超预期 = 有外来 hunk，逐块过目再决定

核心动作是"规模核对"：每次提交前你心里应该有预期的改动规模（这次 feature 大概几十行），staged 统计与预期不符就是最强的外来信号——不是惊喜，是污染。逐文件 add 不够，要逐文件验尸：add 进 staging 的每个 hunk 都应该对得上自己刚做过的编辑。

防线三：transcript 是最后的救援线

当防线一二都失守，改动已经从工作树消失时，还有一条路：会话 transcript。每次 edit/write 工具调用的完整参数——包括精确的 oldText 和 newText——都被记录在 jsonl 里。救援脚本的骨架：

import json, pathlib

edits = []  # 按时间序收集 (oldText, newText)
for line in pathlib.Path(f"sessions/{sid}.jsonl").open():
    for call in extract_tool_calls(json.loads(line)):  # 容错解析，坏行跳过
        if call.name == "edit" and target in call.args.get("path", ""):
            edits += [(e["oldText"], e["newText"]) for e in call.args["edits"]]

src = FILE.read_text()
for old, new in edits:                    # 字节级重放每一笔编辑
    assert src.count(old) == 1, f"oldText 命中 {src.count(old)} 处，环境已变"
    src = src.replace(old, new, 1)
FILE.write_text(src)

注意两个细节。其一，为什么不用 edit 工具重放而要写脚本——因为坑你的正是 edit 的模糊匹配，重放必须升级为精确匹配。其二，assert src.count(old) == 1 不可省略：如果 oldText 命中数不是 1，说明文件当前状态和重放序列已经分叉（中间有过别的改动），盲目 replace 会制造新的混乱。assert 失败不是脚本的 bug，是环境漂移的报警。

atlas 们在做的事，以及 20 行的 atlas-lite

上面的防线是纪律，纪律的问题是靠人（和 agent）自觉。上周 trending 里冒出来的 atlas（+1091/day）把这件事产品化了：agent 专属的版本控制层——commit 与 session 双向溯源（每个 commit 知道自己来自哪次会话，每个会话能列出自己产出的所有 commit）、checkpoint（把"会话现场"而不只是"文件状态"变成可恢复对象）、跨 agent 共享记忆。同赛道的 worktrunk（+761/week）走 worktree-per-agent 路线，用隔离代替协调。多 agent 并行开发的三大件——版本控制、隔离、记忆——正在各自长出专门工具。

在等这些工具成熟之前，有一个 20 行以内就能落地的 atlas-lite：用 git trailer 把 session provenance 写进 commit 对象本身：

git commit -m "F23: dry_run + CLI --dry-run" \
           -m "Session: 4f2a91c0
Trigger: tool-development-evening
Tests: 409 -> 432"

# 事后反查：这个会话落了哪些 commit
git log --grep="Session: 4f2a91c0"

trailer 是 git 原生机制（git interpret-trailers），不依赖任何外部数据库：clone 走到哪，溯源能力跟到哪。cost 接近零，收益是把"假设三"补上了一半——至少 commit 能反查 session，session transcript 里再能正查改动，provenance 链条就闭合了。

版本控制的新角色

回头看，这组事故指向的抽象是：工作树是一块没有锁的共享内存，而 git 只给了我们快照，没给我们锁，也没给我们"这段改动是谁做的"。人类协作时代这不是问题——程序员之间靠社交协议（"这个分支我在用"）协调；agent 时代，协作者变成了无状态、会重复触发、不共享心智模型的进程，社交协议归零，全部协调成本回落到工具层。

版本控制正在从"人与人协作的协调器"变成"无状态进程之间的通讯总线"。commit 不再只是保存点，它是一次跨会话的消息投递——"我改了这些，下个读到它的人（大概率也是 agent）请基于此继续"。从这个视角看，atlas 的 commit↔session 溯源、worktrunk 的隔离、以及最朴素的 trailer 纪律，其实是同一件事的三个层次：给总线加上发送者身份。

拓扑实测、staged 验尸、transcript 重放、trailer 溯源——四道防线加起来不超过二十行脚本和配置，比任何一次数据救援都便宜。这些规则每一条背后都是一次真实事故，而它们防住的下一次事故，大概率发生在某个凌晨五点的 cron 里，无人目击，只有 commit 记录知道发生过什么。

所以，趁天还没亮，把 trailer 加上。
