Building Effective Agents：Anthropic 的 Agent 设计全景拆解

📅 2026-07-27 · 🏷️ Agent Design · Workflow Patterns · Anthropic · ACI
原文：Building Effective Agents — Anthropic

Anthropic 这篇《Building Effective Agents》是 Agent 工程领域被引用最多的文献之一。它不谈花哨的框架，而是老老实实地把"什么时候该用 Agent、什么时候不该用"以及"真要用的时候怎么搭"讲清楚了。本文基于原文逐段拆解，保留原始定义的精确性，同时补上中文语境下的工程理解。

一、核心定义：Workflow ≠ Agent

Anthropic 把所有 agentic 系统分成两类，定义非常干脆：

Workflows are systems where LLMs and tools are orchestrated through predefined code paths.

Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

翻译过来：

类型谁决定流程适用条件
Workflow代码（开发者预先写死的路径）步骤可预测、可拆分
AgentLLM 自己（动态决定下一步做什么）开放式问题、步骤数未知
⚠️ 最容易被忽略的一条原则

原文反复强调：

"We recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all."

也就是说——别上来就做 Agent。能用一次 LLM 调用 + RAG + few-shot 解决的，就别整多步 Agent。Anthropic 自己说"很多应用，单次 LLM 调用就够了"。

二、5 种 Workflow 模式（核心干货）

这是文章的真正骨架。从简单到复杂：

1. Prompt Chaining（提示链）

LLM → [检查门] → LLM → [检查门] → LLM → 输出
  • 本质：任务切成固定顺序的子任务，前一个的输出喂给后一个
  • 关键：中间可以插程序化的"检查门"（gate），不达标就停下来
  • 场景：任务能干净地分解成固定子任务
  • 例子：先写营销文案 → 再翻译成另一种语言；先写大纲 → 检查大纲 → 再写正文
  • 代价：用延迟换准确率（每多一环就多一点延迟）

2. Routing（路由 / 分流）

输入 → [分类器 LLM 或规则] ─┬─→ 处理器 A（专用 prompt） ├─→ 处理器 B（专用 prompt） └─→ 处理器 C（专用 prompt）
  • 本质：先把输入分类，再分发到专门优化过的下游流程
  • 关键：分离关注点（separation of concerns），每个分类用自己的 prompt
  • 场景：有明显类别，且分类可准确判定
  • 例子：客服系统里"普通咨询 / 退款 / 技术支持"分流；简单问题丢给 Haiku，复杂问题丢给 Sonnet
  • 反例：如果不分流，为一个输入优化往往会伤害其他输入

3. Parallelization（并行化）

两种变体：

  • Sectioning（分块）：把任务拆成独立子任务并行跑，结果聚合
  • Voting（投票）：同一个任务跑多次，得到多样化输出

典型场景：

  • Sectioning：一个 LLM 处理用户请求，另一个同时做内容审核——比一个 LLM 同时干两件事效果好
  • Voting：审代码漏洞，多个不同 prompt 各自审一遍，谁发现问题就标记；内容审核里设不同投票阈值来平衡误报和漏报

4. Orchestrator-Workers（编排者 + 工人）

┌─→ Worker LLM ─┐ Orchestrator ──┼─→ Worker LLM ──┼──→ 汇总 └─→ Worker LLM ─┘
  • 本质：中央 LLM 动态拆任务、分派给 Worker、汇总结果
  • 关键差别（vs. Parallelization）：子任务不是预先定义的，而是 Orchestrator 根据输入动态决定的
  • 场景：你无法预测需要哪些子任务
  • 例子：代码产品对多文件的复杂修改——要改几个文件、每个文件怎么改，取决于具体任务

5. Evaluator-Optimizer（评估者-优化者，闭环反思）

LLM 生成 → 评估 LLM 打分+反馈 → 再生成 → 再评估 → ...（直到满意）
  • 本质：一个 LLM 生成，另一个 LLM 评估并给反馈，循环改进
  • 场景：有明确评估标准，且迭代能带来可衡量提升
  • 判断信号：① 人类给出反馈时 LLM 能改进；② LLM 自己也能给出这种反馈
  • 例子：文学翻译的细微差别；需要多轮搜索的复杂研究任务

三、Agent 模式（自主性）

原文定义：

"Agents begin their work with either a command from, or interactive discussion with, the human user. Once the task is clear, agents plan and operate independently... it's crucial for the agents to gain 'ground truth' from the environment at each step to assess its progress."
"They are typically just LLMs using tools based on environmental feedback in a loop."

一句话：LLM 在一个循环里，根据环境反馈自己决定调哪个工具，直到任务完成或撞墙。

适用场景：

  • 开放式问题，步骤数无法预测
  • 无法硬编码固定路径
  • 必须对 LLM 决策有一定信任
  • 在可信环境里可规模化

代价：

  • 更贵（每一步都是 LLM 调用）
  • 错误会复合（compounding errors）
  • 必须在沙箱里充分测试 + 加 guardrails

四、5 种模式速查表

模式核心机制适用场景复杂度
Prompt Chaining固定顺序 + 检查门任务可线性拆分⭐⭐
Routing分类 → 专用 prompt输入有明显类别⭐⭐
Parallelization并行 + 聚合/投票子任务独立 / 需要多次确认⭐⭐⭐
Orchestrator-Workers动态拆分 + 汇总子任务不可预测⭐⭐⭐⭐
Evaluator-Optimizer生成-评估-再生成循环有明确评估标准⭐⭐⭐
AgentLLM 自主循环 + 工具开放式、不可预测⭐⭐⭐⭐⭐

五、文章给的 3 条核心原则

结尾点睛，Anthropic 给了三条工程建议：

1. Maintain simplicity in your agent's design.

2. Prioritize transparency by explicitly showing the agent's planning steps.

3. Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing.

第 3 条特别有意思——他们做 SWE-bench agent 时发现：花在优化工具上的时间，比花在 prompt 上的还多。比如强制工具用绝对路径，模型就再没出过错。

六、关键洞察：ACI > HCI

原文 Appendix 2 的精华：

"Think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good agent-computer interfaces (ACI)."

具体建议：

  • 格式对齐：工具格式要接近模型在互联网上自然见过的格式（别让它写 diff chunk header，因为要算行数）
  • 别让模型做格式杂活：JSON 里转义换行、计算几千行代码的行号——这些交给代码
  • 给足思考空间：给模型足够的 token 思考，别让它把自己写进死胡同
  • 防呆设计（Poka-yoke）：把参数设计得让模型不容易犯错——比如同样意思的参数别起两个名字
💡 实践经验补充

在我们的 Agent 项目中，ACI 优化的投入产出比确实远高于 prompt 调优。具体案例：

  • 把"请返回 JSON"改成 JSON Schema 强约束 + 自动校验，格式错误率从 ~12% 降到 0
  • 把相对路径换成绝对路径（和 Anthropic 的经验一致），路径相关错误直接消失
  • 工具描述里加一个具体调用示例，比写三行规则描述有效得多

总结

Anthropic 这篇文章的价值不在于教你怎么搭 Agent——恰恰相反，它教你什么时候不要搭 Agent。核心信息：

  1. 先问"能不能不用 Agent"——单次调用能解决的别复杂化
  2. Workflow 是主力工具——5 种模式覆盖了 90% 的工程场景
  3. Agent 是最后手段——留给真正不可预测的开放式问题
  4. ACI 的投入产出比 > Prompt 调优——把时间花在工具设计上
  5. 简单 > 复杂——每次加复杂度都要有明确的 ROI 论证
