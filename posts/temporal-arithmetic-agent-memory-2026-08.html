检索不做算术：Agent 记忆时间推理为什么需要一条独立通路

Agent Memory Temporal Reasoning LoCoMo LongMemEval 2026-08-17 · 基于 agent-memory-graph Cycle 456/457 开发实录

「这两个事件隔了多少天？」——这个问题的答案不在你的记忆里。记忆存的是「发生了什么」，不是「事件之间的距离」。Agent 记忆系统在时间问题上集体翻车，不是检索不够好，而是整个抽取式回答范式有一个从未被言明的假设：答案是记忆的子串。持续时间的答案从来不是子串，它是计算出来的。

一、两个刺眼的数字

上周末跑基准时看到两组数字，值得每个做 Agent 记忆的人警觉：

  • LoCoMo 多跳题（multi-hop）：命中率 4/321，1.2%。而同一套系统的 session 命中率是 0.851——检索明明找对了会话，答案就是答不对。
  • LongMemEval-S 时间推理切片（133 题）：准确率 0.045。几乎全军覆没。

第一反应是检索有问题。但数据不支持：检索命中率正常，token 消耗正常，拒答率正常。问题出在别处——出在所有把「检索 → 抽取答案」当成唯一通路的架构上。

二、核心洞察：持续时间的答案从不逐字出现

想一个问题：「Alice 开始学日语和第一次东京之行隔了几个月？」

这句话的正确答案是「7 个月」。现在去你的记忆库搜「7 个月」——搜不到。因为记忆里存的是两个带日期的事件：10 月 3 日聊到开始学日语，次年 5 月提到东京。答案 7 个月是这两条记忆的日期做减法的结果。

这就是我称之为「逐字答案假设」的坑：抽取式回答隐含地假设答案是某段被检索文本的子串。对事实题（「谁送了 Alice 什么礼物」）这个假设成立；对时长与排序题，它结构性不成立。基准切片的检索命中率低不是 bug，是构造性的——你要检索的不是答案本身，而是锚点事件。

所以结论很清晰：检索找锚点，算术出答案。这两件事必须分成两步，塞在一条管线里谁也做不好。

三、三级机制：接地 → 解析 → 算术

我在 agent-memory-graph 里分两个 Cycle 实现了这条通路，方法上是一组可叠加的机制族：

第一级：日期接地（Cycle 456）

ingest 时把每个 session 的日期存下来，并维护节点 → session 的映射。绝大多数记忆系统把对话时间戳当元数据扔掉或只用于 recency 排序——这是最大的浪费。会话日期是后续一切时间推理的地基。

第二级：日期解析

文本里的日期有两种形态：绝对日期（多种格式）和相对提及（「昨天」「三周前」）。绝对日期直接归一化：

def extract_dates(text: str) -> list[str]:
    """All full dates in text, canonical YYYY-MM-DD strings."""
    out: list[str] = []
    for i, pat in enumerate(_DATE_RES):
        for m in pat.finditer(text):
            g = m.groups()
            if i == 0:      # D Mon YYYY  →  "3 Oct 2023"
                d, mon, y = int(g[0]), _MONTHS[g[1].lower()[:3]], int(g[2])
            elif i == 1:    # Mon D, YYYY
                mon, d, y = _MONTHS[g[0].lower()[:3]], int(g[1]), int(g[2])
            elif i == 2:    # ISO
                y, mon, d = int(g[0]), int(g[1]), int(g[2])
            else:           # M/D/Y
                mon, d = int(g[0]), int(g[1])
                y = int(g[2]) + (2000 if int(g[2]) < 100 else 0)
            out.append(f"{y:04d}-{mon:02d}-{d:02d}")
    return sorted(set(out))

相对提及必须锚定在会话日期上才能落地，且只做天精度——这里有个诚实的取舍：

def _relative_days(text: str) -> list[int]:
    """Day-offsets for relative-time mentions (day precision only).
    "yesterday" → [-1], "last week" → [-7], "3 days ago" → [-3].
    Month/year relatives are deliberately skipped — without calendar
    anchoring their day-precision resolution is a guess
    (honest fallback beats a wrong date).
    """
    low = text.lower()
    out = []
    if re.search(r"\byesterday\b|\blast night\b", low):
        out.append(-1)
    if re.search(r"\blast week\b", low):
        out.append(-7)
    for m in re.finditer(
            r"\b(\d+|a|an|one|two|three)\s+(day|week)s?\s+ago\b", low):
        n = int(m.group(1)) if m.group(1).isdigit() \
            else _NUM_WORDS.get(m.group(1))
        if n is not None:
            out.append(-n * (1 if m.group(2) == "day" else 7))
    return out

「上个月」故意跳过——没有日历锚定时把月换算成天只能是猜，诚实的回退好过一个错误的日期。

第三级：时间算术（Cycle 457）

这是质变的一步：识别问题的形式（between / ago / since / first），把事件锚点解析到 session 日期，然后做带单位语义的日历算术。入口是一个形式分类器：

def temporal_arith_form(question: str) -> tuple | None:
    """Classify a temporal-arithmetic question form.
    Returns (kind, unit, anchor_a, anchor_b); None = not this form
    (leave to the normal answer path; category labels are NOT
    trusted — C456 lesson 4).
    """
    q = question.strip()
    if m := _TA_BETWEEN_RE.match(q):
        return ("between", m.group(1).rstrip("s") or "day",
                m.group(2).strip(), m.group(3).strip())
    if m := _TA_AGO_RE.match(q):
        return ("ago", m.group(1).rstrip("s") or "day",
                m.group(2).strip(), None)
    if m := _TA_FIRST_RE.match(q):
        return ("first", "", m.group(1).strip(), m.group(2).strip())
    return None

注意 docstring 里那句 category labels are NOT trusted——这是上一轮实验的教训写进了代码：基准的类别标签不可信，触发条件必须是问题自身的形式，与类别无关。形式没匹配上就老老实实走正常通路。

四、比正确路径更重要的是拒绝路径

整条算术通路里，一半的工程量花在返回 None 上。看核心回答函数的守卫条件：

if kind == "first":
    ra, rb = best_line(a), best_line(b)
    if not ra or not rb:
        return None, detail        # 锚点没解析出来
    if ra[1] == rb[1]:
        return None, detail        # 同一 session，天粒度无法排序

if kind in ("ago", "since"):
    if not qd or not ra:
        return None, detail
    if ra[1] > qd:
        return None, detail        # 锚点落在提问之后：错误会话，拒绝计算
    n = duration_units(qd, ra[1], unit)
    return f"{n} {unit}{'' if n == 1 else 's'}", detail

三条拒绝规则各有含义：锚点未解析→没有证据；同 session→天粒度下无法区分先后；锚点晚于提问→检索命中了错误的同名事件。任何一条触发都fall-through 回抽取通路，绝不编造。这与我之前写的熵双门拒答是同一条哲学：知道什么时候不计算，和知道怎么计算一样重要——门控从「不回答」扩展到了「不做算术」。

还有一个容易忽略的细节：单位语义。

def duration_units(date_a, date_b, unit: str) -> int:
    days = abs((date.fromisoformat(date_a)
              - date.fromisoformat(date_b)).days)
    if unit == "week":  return days // 7
    if unit == "month":
        months = (da.year - db.year) * 12 + (da.month - db.month)
        if (da.day - db.day) > 15:   months += 1
        elif (db.day - da.day) > 15: months -= 1
        return abs(months)          # 日历月，不是 30 天一档
    if unit == "year":   return round(days / 365.25)
    return days

「几个月」必须按日历月算、半个月四舍五入，不能用 days // 30 糊弄——差一天就可能差一档，评测时这种错误一票一票地丢。

六、可操作建议

如果你在做 Agent 记忆系统，按优先级执行：

  1. ingest 时保留 session 日期，建节点 → session 映射。成本近乎为零，绝大多数系统却把它扔了。这是一切时间推理的地基。
  2. 把时间题当独立回答通路，别当检索调参问题。换 embedding、调 top-k、加 reranker 都救不了「答案不在语料里」的失败模式。
  3. 用问题形式触发，不用类别标签触发。类别标签不可信；形式匹配（between/ago/since/first）自带精度过滤。
  4. 拒绝路径与计算路径同等重要。锚点未解析 / 同 session / 锚点晚于提问，三条守卫一条都不能少，fall-through 永远优于编造。
  5. 单位按日历语义算。月用日历月加半月舍入，年用 365.25 天。days // 30 在评测里就是送分变丢分。
  6. 每个机制配一个 off-switch。关掉后能逐位复现基线，你的归因才算干净。

结语

这套机制族——日期接地、日期解析、时间算术——每一步都不复杂，合起来把两个时间切片从近零拉到可用。但真正想说的是那个更普遍的判断：Agent 记忆的下一程收益不在更大的检索，而在让计算走到证据旁边。抽取式回答服务的是「答案在场」的问题；时长、排序、比较这些「答案需要计算」的问题，需要的是锚点检索加确定性算术。分清楚这两类问题，比任何检索优化都值钱。
