Graph RAG 的真实图景：$33,000 到 $33 的 18 个月，谁赢了谁死了

2026-08-08 · 罗嵩 · Graph RAG Knowledge Graph Agent Memory RAG
2024 年 4 月，Microsoft 发布了 GraphRAG，用知识图谱取代向量数据库做检索增强。整个 AI 社区兴奋了——"向量搜索已死，图才是未来"。两年后回头看，这个故事比任何人预想的都复杂：成本暴跌了 1000 倍，好几个曾经的明星方案已经死了，而最有效的替代品可能根本不需要图。

一、先说结论：Graph RAG 没有赢，也没有输——它分化了

如果你在 2026 年还在讨论"Graph RAG 好不好"，你问的是个错误的问题。真正的答案是：取决于你做什么。

过去 18 个月，Graph RAG 从一个单一的架构方案（Microsoft 原版），分裂成了至少 5 个独立的技术流派，各自解决不同问题、服务于不同场景。有些流派赢了，有些悄悄死了，有些以没人预料到的方式重生。

这篇文章是我花了两天时间梳理 40+ 篇论文、benchmark 和生产案例后的总结。不堆论文摘要，只说判断。

二、$33,000 的问题：为什么原始 GraphRAG 不可用

先理解 Microsoft 原版 GraphRAG 到底做了什么。它的管线是：

文档 → LLM 抽取实体 → LLM 抽取关系 → 构建知识图谱 → Leiden 算法做社区检测 → LLM 生成社区摘要 → 查询时用社区摘要做全局检索

问题出在哪？每一步都调 LLM。实体抽取是 LLM 调用，关系抽取是 LLM 调用，社区摘要是 LLM 调用。一篇 5GB 的法律文档，索引成本高达 $33,000。同期向量 RAG 索引同样数据只需要几美元。

10,000 倍的成本差距。这在任何预算评审中都是直接否决的数字。

但成本还不是唯一问题。2025 年的研究揭示了更深层的缺陷：

  • 噪声传播：LLM 抽取实体时出错（幻觉），错误沿着图的边传播，越查越歪
  • 冗余检索：PathRAG 的论文证明，GraphRAG 的核心问题不是"检索不够"，而是"检索了太多噪声"
  • 在很多任务上不如 vanilla RAG：不是打平，是输——Microsoft 自己的研究也承认了
判断：Microsoft GraphRAG 原版架构在 2026 年已不推荐用于新项目。它的历史贡献是证明了"图可以增强 LLM 推理"，但它的工程实现代价太高。所有有价值的能力都已经被后续系统以更低成本继承。

三、18 个月，1000 倍成本下降：LazyGraphRAG 的关键洞察

2024 年底，Microsoft 自己提出了 LazyGraphRAG，做了一件非常聪明的事：

把 LLM 推理从索引阶段推迟到查询阶段。

原版 GraphRAG 在建索引时就做完整的实体摘要和社区报告。LazyGraphRAG 说：索引阶段只做名词短语抽取（不调 LLM），社区检测也只做结构层面的聚类。等用户真正问问题了，再去相关社区做 LLM 推理。

结果：

指标原版 GraphRAGLazyGraphRAG
索引成本（100K tokens）$2-5~$0.02-0.05
索引成本（5GB 语料）~$33,000~$33
查询质量（全局问题）72-83% comprehensiveness相当或更好
成本降低—1000x

这是一个改变游戏规则的时刻。$33,000 → $33，意味着 Graph RAG 从"只有大企业用得起"变成了"和小团队用向量 RAG 一样的成本"。

关键洞察：LazyGraphRAG 的哲学是"按需推理"——不是所有信息都值得在索引阶段用 LLM 处理。大部分查询只需要图的结构信息，不需要完整的 LLM 摘要。把昂贵的 LLM 调用留到真正需要的时候，这是一个简单但被忽视了两年多的道理。

四、六个赢家：每个解决了不同问题

1. HippoRAG2：模仿大脑海马体的检索

ICML 2025 上，HippoRAG2 带来了一个优雅的思路：模仿人类海马体的记忆索引机制。

人类大脑不是把所有记忆都存成向量然后做相似度搜索。海马体做的是关联索引——通过 Personalized PageRank 算法在海马体构建的图上传播激活信号，让相关记忆自动浮现。

数字说话：比迭代检索方法便宜 10-30 倍、快 6-13 倍。索引成本只有 GraphRAG 的 1/10（3.2M tokens vs 37.1M tokens）。

最佳场景：多跳问答。"A 的妻子的雇主总部在哪个城市？"这种需要跨文档串联事实的查询，是 HippoRAG2 的杀手锏。

2. PathRAG：解决图噪声的关键论文

PathRAG（2025.02）提出了一个非常精准的诊断：Graph RAG 的问题不是"检索不够"，而是"检索了太多无关路径"。

它的解法是流式路径剪枝——在图上做检索时，不是返回整个子图，而是只保留从查询实体到答案实体的最相关路径，用基于信息流的算法剪掉噪声分支。

结果：在 6 个数据集上全面超越 GraphRAG 和 LightRAG。

3. LazyGraphRAG：成本之王

上文已详述。补充一点：LazyGraphRAG 是批量分析场景的最佳选择。如果你的用户期望"问一个问题等几秒没关系，但答案要全面"，LazyGraphRAG 的查询预算参数让你精确控制成本-质量权衡。

4. Graphiti / Zep：Agent 记忆的时序杀手锏

这是 2026 年最让我兴奋的系统。

想象你的 AI Agent 去年记住了一个用户"单身"。今年用户结婚了，Agent 更新了状态。但如果你问 Agent "去年 6 月这个用户的婚姻状态是什么"，传统系统会崩溃——它只知道"现在"，不知道"曾经"。

Graphiti（Zep 的开源引擎）用双时序模型解决这个问题：每条事实都有两个时间戳——valid time（事实在现实世界中何时为真）和 transaction time（系统何时记录了这个事实）。

这不仅仅是理论上的优雅。Zep 在 LoCoMo benchmark 上达到 94.7% 准确率，在 LongMemEval 上 90.2%——远超 Mem0（68.44%）和 MemGPT/Letta（74.0%）。

为什么时序是 Agent 记忆的关键维度？因为 Agent 不是在查文档，而是在查"一段不断变化的历史"。文档库里的知识是静态的，但 Agent 的记忆是活的——人会换工作、会搬家、会改变偏好。没有时序感知的 Agent 记忆系统，就像一个只会覆盖旧日记的人，永远只记得今天。

5. Agentic Search：Claude Code 的"反 RAG"哲学

2026 年 1 月，Claude Code 的创建者 Boris Cherny 公开说了一段在整个 RAG 社区引起地震的话：

"Claude Code 早期版本用了 vector RAG。但我们发现 agentic search 的效果明显更好。所以我们移除了向量数据库。"

Claude Code 现在用的是 grep 和 glob——就是 Unix 最基础的搜索工具。让 LLM Agent 自主决定搜索什么、怎么搜索、什么时候搜索够了。

这听起来很"原始"，但它揭示了一个深刻的道理：如果你有一个足够聪明的 Agent，给它搜索工具可能比预建索引更好。因为 Agent 可以根据推理状态动态调整搜索策略，而预建的索引是静态的。

6. DCI（Direct Corpus Interaction）：零索引范式

Contextual AI 把 Agentic Search 推到了极致：不构建任何索引——不用向量数据库、不用知识图谱——Agent 直接通过终端工具（rg、find、sed）与原始语料交互。

在 BRIGHT benchmark 上，DCI 比 ColBERT-v2 和 BGE-M3 高出 12%，且零离线索引成本。

这意味着什么？对于很多用例，你可能根本不需要 RAG。你需要的只是一个能搜索文件的 Agent。

五、三个输家：什么死了

1. "LangChain + Neo4j = Graph RAG"的教程式管线

2025 年每个 AI 博主（包括一些大 V）都在教你怎么用 LangChain + Neo4j 搭 Graph RAG。2026 年回头看，这些教程的价值主要在教学演示。生产环境中，这套管线的实体抽取质量高度依赖你用的 LLM——而 LLM 出错时，错误会沿着图传播。Atlan 的分析报告指出，LlamaIndex 的 PropertyGraphIndex 甚至存在"静默吞掉异常"的问题（issue #22194），直到有人提交了 raise_on_error 修复。

2. Mem0 的图变体

这是一个重要的反面案例。Mem0 在 v3 开源重写中移除了图存储层，改用 spaCy 做实体链接 + 向量检索。为什么？因为他们自己的论文数据显示：

指标Mem0（纯向量）Mem0g（图变体）
LOCOMO 总分66.8868.44
搜索速度1x~3x 慢
Token 消耗1x~2x

图的收益只有 1.5 分，但代价是 3 倍慢、2 倍贵。这说明图不是万能药——在很多场景，复杂度的代价远超收益。

3. "纯向量 RAG 够用了"的幻觉

虽然 Agentic Search 和 DCI 在某些场景证明了不需要传统 RAG，但这不意味着纯向量 RAG 就够了。在多跳推理（"连接多个文档中的事实"）和全局主题分析（"这个语料库的主要主题是什么"）上，向量 RAG 系统性地落后于图增强方案。HippoRAG2 在多跳 QA 上的表现证明了这一点。

六、FactConsolidation：所有系统都过不了的新基准

2026 年 6 月，一篇 arxiv 论文悄悄发表，但它的结果值得所有人注意。作者提出了 FactConsolidation benchmark——测试系统在事实冲突时的表现。

场景很简单：先告诉系统"A 公司的 CEO 是张三"，再告诉它"A 公司的 CEO 是李四"。然后问"A 公司的 CEO 是谁？"

结果令人震惊：

系统单跳准确率
HippoRAG2（最强）54.0%
MemGPT/Letta28.0%
Cognee28.0%
GraphRAG~21%
Graphiti/Zep7.0%
Mem018.0%

多跳版本更惨：所有系统都是 0-7%。

论文的核心发现是：架构复杂度并不能解决事实冲突。知识图谱系统反而更差——因为 LLM 驱动的实体/关系抽取在写入时就引入了噪声，冲突发生时噪声被放大而不是被解决。

这对所有 Agent 记忆系统都是一记警钟。你的 Agent 记忆系统可能在 benchmark 上表现很好，但在真实世界的信息变更面前完全失灵。如果你在构建 Agent，请把 FactConsolidation 加入你的评估维度。

七、2026 年的正确决策树

别再问"Graph RAG 好不好"了。问自己：

你的查询类型是什么？ │ ├─ 单点事实查询（"公司的地址是什么？"） │ └─→ 向量 RAG + BM25 混合搜索 │ 成本最低，效果足够 │ ├─ 多跳推理（"A 的合伙人的母校在哪里？"） │ └─→ HippoRAG2 或 PathRAG │ 图的收益真实存在 │ ├─ 全局主题分析（"这个语料库的核心争论是什么？"） │ └─→ LazyGraphRAG │ 索引成本 = 向量 RAG，质量远超 │ ├─ Agent 长期记忆（"用户上次提到这个是什么时候？"） │ └─→ Graphiti / Zep │ 时序维度是刚需，不是可选 │ ├─ 代码/文档搜索（"这个函数在哪里被调用？"） │ └─→ Agentic Search（grep + glob + LLM 多轮） │ 不需要预建索引 │ └─ 小语料（<100K tokens） └─→ 跳过 RAG，直接全塞上下文窗口 你可能根本不需要检索

八、你可以立刻做的 5 件事

  1. 审计你现有的 RAG 系统。如果你在用原版 Microsoft GraphRAG，评估迁移到 LazyGraphRAG 的成本。索引成本会降低 1000 倍，质量不降反升。
  2. 给 Agent 记忆加时序维度。不管你用什么向量数据库，如果 Agent 需要跟踪变化的状态（用户信息、项目进度、业务规则），时序感知不是 nice-to-have，是 must-have。先试 Graphiti。
  3. 做个 Agentic Search 的对比实验。在你最复杂的查询场景上，让 LLM Agent 直接搜索原始文档（用 grep/find + LLM 判断），对比你当前 RAG 系统的结果。你可能会惊讶。
  4. 用 FactConsolidation 测试你的系统。写入两条冲突信息，看系统怎么处理。如果准确率低于 50%，你需要重新设计记忆更新策略。
  5. 别再追求"通用 RAG 架构"。2026 年的教训是：不同查询类型需要不同架构。与其花三个月搭一个大而全的系统，不如花一周搭一个精准匹配你核心查询类型的简单系统。

尾声：图的价值没有消失，但它不再是卖点

2024 年，"我们用了 Graph RAG"是一个技术亮点。2026 年，它只是说明你做了技术选型。图的真正价值——多跳推理、关系建模、全局视图——依然不可替代，但实现方式已经从"砸钱建索引"变成了"按需推理、智能查询、时序感知"。

用 Andrej Karpathy 的话说：添加功能的时机是你需要它的时候，而不是你觉得可能需要的时候。Graph RAG 在 2026 年终于听到了这句话。
