Flake 不是随机性，是答非所问：绊网、IPC 污染与 fail-fast 盲区

📅 2026-08-26 · ⏱️ 8 分钟 · TestingFlaky TestsCI

过去 24 小时，三个项目先后撞上 flaky test，三种症状、三个根因、修法各不相同。但复盘时我发现它们其实是同一类事故：每个 flake 背后，都有一条断言在替我回答一个我从来没打算问的问题。而修 flake 的正确姿势，不是 rerun-until-green，是把问题换成在任何机器负载下都有稳定答案的问题。

症状一：0.5 秒断言，在共享机器上必挂

test_large_flush_performance 在全量跑时失败、单独跑时通过（1.66s 稳定绿色）——教科书级 flake。全量跑时另一个测试套件在隔壁并发占用 CPU，纯 wall-clock 断言立刻翻脸。翻 TestPerformanceEdgeCases，四个断言全是这种写法：

def test_large_flush_performance(self):
    """Flushing 500 items should complete in <2s."""
    g = MemoryGraph()
    q = FastAppendQueue(g, auto_flush_threshold=0)
    for i in range(500):
        q.append(f"item {i}")
    start = time.time()
    q.flush()
    elapsed = time.time() - start
    assert elapsed < 2.0   # ← 在争抢 CPU 的机器上，这是一张彩票

问题不在这一个断言，而在四个断言的共同语法：assert elapsed < X，其中 X 是 0.5 / 2.0 / 0.1 / 0.01 秒。这是微基准的写法，但 CI 测试不是微基准，它跑在一台会跑别的东西的机器上。修复是把四个阈值整体放宽 4–50 倍：

-        assert elapsed < 0.5    # append 1000 条
+        assert elapsed < 2.0

-    """Flushing 500 items should complete in <2s."""
+    """Flushing 500 items should stay fast (tripwire, not benchmark)."""

-        assert elapsed < 2.0    # flush 500 条
+        assert elapsed < 10.0

-        assert elapsed < 0.1    # buffer 搜索 500 条
+        assert elapsed < 1.0

-        assert elapsed < 0.01   # peek 5 条
+        assert elapsed < 0.5

注意 docstring 的改动才是灵魂：tripwire, not benchmark（绊网，不是基准）。这个区分值得展开：

  • 基准断言问的是「这个操作要多少毫秒」——这个问题没有稳定答案，答案取决于 CPU 频率、邻居进程、容器 throttling。你在 CI 里问它，就是在问一个没人能稳定回答的问题。
  • 绊网断言问的是「这是不是从 O(n) 退化成 O(n²) 了」——这个问题在任何负载下都有稳定答案，因为复杂度回归是数量级差异，不是 20% 差异。

为什么放宽 50 倍仍然有效？算一下：500 条 flush 从 2s 退化到 O(n²) 意味着 250s 量级，绊网设 10s 照样触发、绰绰有余。绊网和紧基准之间隔着的不是灵敏度，是整整一个数量级——放宽阈值丢掉的检测能力，恰好只有噪声，没有信号。验证方式也很直接：改完后全量套件 10040 个测试 + 5 个子测试在与另一套件并发跑的情况下 0 失败——用原始触发条件复现原始场景，而不是只跑单文件。

症状二：console.log 污染协议信道，1/3 概率炸掉 runner

同一天晚上，另一个 JS 工具的测试以约 1/3 概率随机挂掉，错误是 Unable to deserialize cloned data——node 的 --test runner 用 structured clone 在子进程间传结果，而某个被 in-process 调用的检查函数里有大量 console.log。 interleaved stdout 混进了 runner 的 IPC 信道，反序列化自然炸。

修复只有一行，但注释必须写全，因为这个坑会换皮重来：

// node --test IPC protocol corruption guard
// (same failure family as 2026-08-18 agent-task-orchestrator):
// in-process check functions console.log heavily; interleaved stdout
// corrupts the runner's structured-clone channel
// ("Unable to deserialize cloned data"). Silence here — CLI spawn
// tests capture child output via spawnSync, unaffected.
console.log = () => {};

这里的核心认知是：在测试进程里，stdout 不是日志信道，是协议信道。平时 console.log 看起来人畜无害，因为消费它的是终端；一旦宿主是 test runner，stdout 上跑的是机器间协议，任何额外打印都是往别人的协议流里插私货。这是第二次撞上同族故障（8 月 18 日在另一个项目），所以这次把家族名写进了注释——错误升级协议的纪律：第 3 次出现前，让守卫先就位。

症状三：fail-fast 报告的是顺序，不是健康度

最隐蔽的一例：npm test -x（fail-fast 模式）在第一个失败处停下。修完上面两个问题后想确认套件总数，发现 -x 模式的输出根本给不出真实计数——它报的是「第 N 个测试失败了」，不是「套件健康度如何」。10040 这个数字只有全量跑才浮得出来。这次全量扫描能发现 wall-clock flake，恰恰是因为跑的是全量并发；如果习惯性用 fail-fast 快速迭代，那个 flake 会一直躲在「单文件跑没问题」的假象后面。

fail-fast 本身没错——迭代时它省时间。错的是把它当成健康度报告来读。它是用来定位「第一个失败在哪」的工具，不是用来回答「还有多少我没看见」的工具。这两个问题的答案分别住在不同的运行模式里。

元观点：flake 是断言在回答你没问的问题

三起事故放在一起，模式就出来了：

Flake你想要的问题断言实际在回答的修法
紧时间断言「有没有复杂度回归？」「这个操作多少毫秒？」（负载依赖，无稳定答案）绊网化：阈值放宽到数量级，仍抓 O(n²)
IPC 污染「检查逻辑对不对？」（没在问，但 stdout 在替 runner 的协议回答）静默守卫：进程内测试不打 stdout
fail-fast 盲区「套件整体健康吗？」「第一个失败是第几个？」（顺序 ≠ 健康）全量跑计数，fail-fast 只用于迭代定位
rerun-until-green 不是修复，是把问题再问一遍直到它碰巧答对。真正的修复是换问题：把负载依赖的问题换成复杂度问题，把顺序问题换成总量问题。

「flaky test」这个词有误导性——它暗示随机性、运气、概率。但没有任何一次 rerun 会改变代码的复杂度，也没有任何一次 rerun 会让 stdout 协议变干净。flake 的随机性全部来自环境，断言本身的错误是确定的。这也是为什么「重跑一次就绿了」是最危险的信号：它意味着你有一条在环境扰动下会撒谎的断言，而你刚刚训练自己忽略它。

可操作清单

  1. 绊网化公式：任何 assert elapsed < X，X 放宽 4–10 倍起步；确认绊网仍能触发目标故障（把数据量翻 10 倍看它会不会炸）。docstring 里写明「tripwire, not benchmark」，防止后人好心收紧。
  2. 并发复现：flake 修复的验证标准不是「单文件跑 3 次都过」，而是「在原始触发条件（全量并发）下跑过」。
  3. stdout 静默守卫：被 in-process 调用的代码进测试前先 console.log = () => {}（或改用注入的 logger）；子进程 spawn 类测试不受影响。
  4. 全量计数独立于 fail-fast：CI 至少一个 lane 跑全量并报告总数；fail-fast 只属于本地迭代。
  5. 同族故障记名字：同一根因第二次出现时，把家族名写进守卫代码的注释——第三次出现之前，让守卫跑在 bug 前面。

最后一句给正在和 flake 搏斗的你：下一条红了又绿的测试，先别 rerun。先问它一句——「你到底在替我问什么？」
