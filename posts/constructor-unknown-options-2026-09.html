构造函数不认识你的选项，但它不说

2026-09-04 · 罗嵩 · JavaScript 静默回落 配置契约 防呆设计
一个 OOM 了两个月没人当回事的测试，背后是 10 个测试文件长年污染真实存储的静默事故。根因只有一行：options.dbPath || './data/memory'——传错键名不报错，默认值静默接管，测试以为自己写在临时目录，实际写在 9743 条真实记忆上。宽容的接收面不会消灭错误，只会把「立即崩溃」降解成「正确性悄悄变质」。

一个崩了两个月没人当回事的测试

agent-memory-service 的测试套件长期停在 721/722：七百多个用例全绿，只有一个红的，谁也没急过。红的是 safeMerge 套件——跑起来 V8 堆顶到 930MB，203 秒后 OOM 崩掉。它看起来像一个「写得不够环保」的测试：加个 heap 限制、或者跳过、回头再优化，都是合理选项。

凌晨的例行测试循环终于把它当成了真问题。顺着内存曲线查下去发现，崩掉的那 203 秒里，测试在做一件它绝不该做的事：加载整个真实存储——9743 条真实记忆，全部反序列化、建索引、放进内存。一个本该在临时目录里造三四条假数据的单元测试。

然后是那个只有一行的真相。

漏洞只有一行

测试是这样写的：

beforeEach(async () => {
  dir = await mkdtemp(join(tmpdir(), 'mem-sm-'));   // 一次性临时目录
  svc = new MemoryService({ dataDir: dir });        // ← 键名错了
});

构造函数是这样写的：

constructor(options = {}) {
  this.#dirPath = options.dbPath || './data/memory';   // ← 真名是 dbPath
  this.#store = new MemoryStore(this.#dirPath);
  // ...
}

dataDir 不是 dbPath。于是 options.dbPath 是 undefined，|| 右边的默认值顺理成章地接管。没有报错，没有警告，没有任何一行日志提到「你传了一个我不认识的键」。测试坚信自己写进了临时目录，实际上每一次写、每一次合并、每一次冲突，都落在 ./data/memory——真实存储上。

这不是孤例。审计发现10 个测试文件在犯同一个错：8 个用 dataDir，1 个用 { dir }，还有 1 个直接把路径字符串当第一个参数传进去（在字符串上访问 .dbPath，同样得到 undefined）。这些测试一路全绿，有的已经跑了很久。

为什么全绿？因为污染通道本身就是成功通道。写 ./data/memory 不但不报错，而且每次都成功——断言该过的全过。测试隔离的目标是「不碰真实数据」，而它碰得比谁都勤快。唯一的症状是性能：每个测试都加载全量存储，套件整体慢到 91 秒，safeMerge 因为数据量最大第一个被堆预算掐死。OOM 是哨兵，但它把自己伪装成了性能问题。

为什么每一层防御都没拦住

运行时层。 JavaScript 对象对多余的键完全宽容——往任何对象上多塞一个键都不犯法。options.dbPath 取不到就返回 undefined，|| default 再补一刀。语言层面没有任何机制提示「你传了我不认识的东西」。

类型层。 源码里其实一直有 JSDoc：@param {{dbPath?: string, embedFn?: EmbedFn}} options。类型写得清清楚楚——但 JSDoc 是给人看的注释，运行时不执法。就算换成 TypeScript 也别高兴太早：excess property check 只在对象字面量直接传参时生效，一旦先赋给变量再传入（测试代码最常见的中转写法），多余键检查静默失效。

测试层。 这是最讽刺的一层：测试全绿不是覆盖好的证据。写默认目录是「成功路径」，断言全部通过。如果默认路径不存在、构造函数当场抛错，这个 bug 反而活不过第一次 CI——是那个贴心的默认值给了它长达数月的生命。

修复：让入口执法

修复本身只有八行，但思路值得写下来——不是「修正错误的键名」，而是让构造函数拒绝它不认识的一切：

constructor(options = {}) {
  const KNOWN = new Set(['dbPath', 'embedFn', 'maxCacheSize']);
  if (typeof options !== 'object' || options === null || Array.isArray(options)) {
    throw new TypeError('MemoryService: expected an options object, e.g. new MemoryService({ dbPath })');
  }
  const unknown = Object.keys(options).filter(k => !KNOWN.has(k));
  if (unknown.length > 0) {
    throw new TypeError(`MemoryService: unknown option(s) '${unknown.join("', '")}' — valid: dbPath, embedFn, maxCacheSize`);
  }
  this.#dirPath = options.dbPath || './data/memory';
  // ...
}

注意守卫顺序：先拦「根本不是对象」的参数（null、数组、字符串），再拦「对象但键不认识」。字符串那一拦不是多余——把 new MemoryService('/tmp/x') 写进代码的人，值得一个立刻的 TypeError，而不是一次静默写入默认目录。

修完立竿见影：十个文件改成正确的 dbPath，safeMerge 从 OOM+203 秒变成秒级 4/4，全套件 724/724。被污染的 data/memory 从 git 恢复。两个月的幽灵，一晚上清零。

这是一个家族

「接收面吞掉它不认识的输入」，跨语言都有亲戚：

  • Python **kwargs：kwargs.get('dbPath', default) 与 JS 的 || 是同一个陷阱的两种方言；
  • argparse 默认开 allow_abbrev，前缀匹配能把拼写误差变成另一个合法参数的静默命中；
  • Pydantic v2 默认 extra='ignore'——要 model_config = ConfigDict(extra="forbid") 才会拒绝未知字段；
  • Zod 默认 strip 掉未知键，要显式 .strict()；
  • CSS 是这个家族的祖师爷：未知属性静默丢弃是浏览器的容错传统，代价是全人类几十年的「为什么这条样式不生效」。

家族共性是同一个裂缝：调用方相信的事（我传的选项在起作用）和实际发生的事（键被扔掉，默认值接管）之间出了偏差。宽容的接收面不会消灭错误，只会把错误从「立即崩溃」降解成「行为正确性悄悄变质」。前者五分钟修好，后者两个月才见血。

原则可以一句话说完：契约的严格程度，应该和它守护的东西的价值成正比。 应用内部随手传个 options，宽容无妨；但库的构造函数、一次性解析的配置、任何默认值指向真实数据的入口——这三类接收面必须严格。未知键不是噪音，是调用方错误信念的直接证据，最便宜的失败时机就是它出现的瞬间。

和上一篇是同一战线的两个哨位

上一篇《让降级路径在报告里自首》讲的是出口：降级发生了，报告必须承认，知识要放在数据里而不是注释里。这篇讲的是入口：别让静默回落轻易发生，把错误信念挡在构造函数门口。

入口拒绝是第一防线，出口自白是最后防线。两条都做，静默回落才没有生存空间。

落地清单

  1. 给 options 类构造函数加白名单：未知键 → TypeError。一段八行守卫，一次成本，永久收益；
  2. 拦「非对象」三连：null、数组、字符串参数各自给出人话报错——传字符串的人不是傻子，是记错了签名的人；
  3. 测试脚手架自证写入目标：mkdtemp 后立刻断言 service 解析出的路径在 tmp 下（或写入一条后断言 tmp 文件存在），让「写错地方」从静默变成秒红；
  4. 警惕带默认值的路径选项：默认值是污染放大器——必填比默认安全；要给默认，就让它指向一个空目录，而不是真实存储；
  5. TypeScript 用户别迷信 excess check：字面量直传才检查，变量中转即失效，库的入口仍需运行时守卫；
  6. 做一次全局审计：grep 所有 options.xxx || default 和 kwargs.get(xxx, default)，每个命中处问一句——传错键的人会得到什么？
