Agent 记忆的快与慢：双系统写入模型的工程实践

2026-08-14 · Agent Memory Dual-Process Theory Knowledge Graph System Design
每个 Agent 都面临一个两难：写入记忆时，是立刻处理（太慢），还是先存起来稍后处理（可能遗忘）？本文将 Kahneman 的双系统认知模型引入 Agent 记忆架构，介绍一种已在生产环境运行 290+ 天的双管道写入方案，附完整 Python 实现。

一、两难困境

先看一个常见场景。你的 Agent 刚完成了一次工具调用，产生了以下信息：

# 一次工具调用的完整轨迹
event = {
    "type": "tool_call",
    "tool": "web_search",
    "query": "Rust async runtime comparison tokio vs async-std",
    "result": "tokio 胜出：社区更大、生态更完整、性能...",
    "timestamp": "2026-08-14T10:32:00Z",
    "session_id": "sess_abc123",
    "user_id": "user_42",
    "confidence": 0.87,
    "tags": ["rust", "async", "benchmark"],
    "duration_ms": 1200,
}

这条信息需要被写入记忆系统。问题来了——

方案 A：立刻全量处理。 实体识别、去重、与现有知识图谱建边、嵌入向量计算、冲突检测……一套流程跑下来，耗时 200-800ms。在对话场景中，用户已经等了 LLM 生成的时间，再等记忆系统处理，体验不可接受。

方案 B：先存队列，稍后处理。 把原始事件丢进队列，后台慢慢处理。延迟解决了，但新的问题出现了：在处理之前，这条记忆不可查询。如果用户紧接着问"刚才搜到什么了？"，系统会回答"我不知道"——明明 5 秒前还知道。

这不是假想的问题。2026 年 ICML 发表的 MemoryArena 基准测试揭示：在 LoCoMo 上得分 90%+ 的系统，在多会话决策任务上得分只有 40-60%。一个重要原因就是写入管道设计不当——要么太慢影响响应，要么太延迟导致信息真空。

行业大部分精力花在了检索（Read）侧的优化上：更好的嵌入模型、更聪明的重排序、混合搜索策略。但写入侧的架构决策，往往才是决定 Agent 记忆质量的分水岭。

二、Kahneman 的启示

Daniel Kahneman 在《思考，快与慢》中提出了人类认知的双系统模型：

  • System 1（快思考）：快速、自动、直觉式。看到 2+2 不需要思考就知道答案。它几乎不消耗工作记忆资源，但容易出错。
  • System 2（慢思考）：缓慢、费力、深思熟虑。计算 17×24 需要调动注意力。它精确但昂贵。

这个模型的精妙之处不在于两个系统的速度差异，而在于它们的协作机制：System 1 持续运行，快速产生印象和直觉；System 2 在需要时介入，对 System 1 的输出进行深度加工。大多数时候，我们靠 System 1 就能应对——只有在遇到复杂问题时才"调动"System 2。

把这个模型映射到 Agent 记忆系统，会得到一个自然的设计：

人类认知Agent 记忆
System 1直觉反应，快速但有偏见即时写入缓冲区，粗索引，O(1) 追加
System 2深度推理，精确但耗能后台整合：去重、建边、冲突检测、图结构更新
协作System 1 快速响应，System 2 事后整理缓冲区秒级可查，后台 flush 后全图谱整合

这不是牵强附会。人类的记忆系统本身就是这样工作的——工作记忆（working memory）快速捕获信息但容量有限，长期记忆（long-term memory）通过海马体的巩固过程（consolidation）缓慢但持久。睡眠期间的"记忆巩固"就是大脑的 System 2 flush。

三、System-1：快速缓冲管道

System-1 的设计目标是零延迟写入 + 秒级可查。它不做任何重计算，只做三件事：追加、索引、返回。

from collections import defaultdict, deque
import time, re

class FastAppendQueue:
    """
    System-1 写入管道：O(1) 追加，关键词即时可查。
    
    设计约束：
    - 写入延迟 < 1ms（不含 IO）
    - 不触发任何图操作、嵌入计算或 LLM 调用
    - 缓冲区数据在 flush 前为"原始记忆"，
      但已可通过关键词检索
    """

    def __init__(self, max_size=500, auto_flush_threshold=50):
        self._buffer = deque(maxlen=max_size)
        self._keyword_index = defaultdict(list)
        self._kind_index = defaultdict(list)
        self._auto_flush_threshold = auto_flush_threshold
        self._seq = 0  # 单调递增序列号

    def append(self, event):
        """O(1) 追加。不做去重、不做建边、不做嵌入。"""
        seq = self._seq
        self._seq += 1
        
        entry = {
            "seq": seq,
            "timestamp": time.time(),
            **event,  # 展开原始事件
        }
        self._buffer.append(entry)
        
        # 构建关键词倒排索引（纯字符串切分，无 NLP）
        text = self._flatten_text(event)
        for token in self._tokenize(text):
            self._keyword_index[token].append(seq)
        
        # 按类型索引
        kind = event.get("kind", event.get("type", "unknown"))
        self._kind_index[kind].append(seq)
        
        return seq

    def search(self, query, limit=10):
        """关键词检索缓冲区。不查图、不走向量。"""
        tokens = self._tokenize(query)
        if not tokens:
            return list(self._buffer)[-limit:]
        
        # 简单投票：匹配 token 越多，分数越高
        scores = defaultdict(int)
        for token in tokens:
            for seq in self._keyword_index.get(token, []):
                scores[seq] += 1
        
        ranked = sorted(scores.items(), key=lambda x: -x[1])[:limit]
        seq_set = {s for s, _ in ranked}
        return [e for e in self._buffer if e["seq"] in seq_set]

    def _tokenize(self, text):
        """极简分词：小写化 + 非字母数字切分 + 2 字符过滤。"""
        return {t for t in re.split(r'[\s\W]+', text.lower()) if len(t) >= 2}

    def _flatten_text(self, event):
        """把事件的关键字段拍平成纯文本用于索引。"""
        fields = ("content", "query", "result", "summary", "tags", "kind")
        return " ".join(str(event.get(f, "")) for f in fields)

    def should_flush(self):
        return len(self._buffer) >= self._auto_flush_threshold

    def drain(self):
        """取出并清空缓冲区。调用方负责 System-2 整合。"""
        items = list(self._buffer)
        self._buffer.clear()
        self._keyword_index.clear()
        self._kind_index.clear()
        return items

关键设计决策：

  1. append() 是 O(1)：除了字符串切分建索引外，没有任何重计算。500 个事件的缓冲区，追加延迟稳定在 0.1ms 以下。
  2. 关键词索引而非向量索引：在缓冲阶段，精确的关键词匹配比模糊的语义检索更有用。用户刚说过的话，原词重现概率极高。
  3. search() 直接查缓冲区：这意味着即使在 System-2 还没 flush 之前，Agent 也能检索到最近的记忆——只是精度较低。

四、System-2：深度整合管道

当缓冲区达到阈值（默认 50 条）或空闲超时触发时，System-2 介入。它的任务是把原始事件整合进持久化知识图谱。

from dataclasses import dataclass
from typing import Optional

@dataclass
class GraphNode:
    """知识图谱节点。"""
    node_id: str
    kind: str           # fact / preference / skill / decision ...
    content: str
    tags: list
    timestamp: float
    source_events: list  # 溯源到 System-1 的 seq

class System2Integrator:
    """
    System-2 深度整合：去重、建边、冲突检测、图结构更新。
    
    这是"慢思考"——可以花 100-500ms 处理一条事件，
    因为它不在用户请求的关键路径上。
    """

    def __init__(self, graph=None, edges=None):
        self.graph = graph or {}    # node_id -> GraphNode
        self.edges = edges or []    # [(src, dst, relation)]

    def flush(self, buffer):
        """处理整个缓冲区，返回整合报告。"""
        report = {"processed": 0, "deduped": 0,
                  "linked": 0, "conflicts": 0}
        
        # 按类型分组处理
        by_kind = defaultdict(list)
        for event in buffer:
            kind = event.get("kind", event.get("type", "unknown"))
            by_kind[kind].append(event)
        
        for kind, events in by_kind.items():
            for event in events:
                # Step 1: 去重 — 内容相似度检测
                existing = self._find_duplicate(event)
                if existing:
                    existing.source_events.append(event.get("seq", -1))
                    report["deduped"] += 1
                    continue
                
                # Step 2: 创建新节点
                node = self._create_node(event)
                self.graph[node.node_id] = node
                report["processed"] += 1
                
                # Step 3: 按类型建边
                links = self._link_by_kind(node, event)
                report["linked"] += len(links)
                
                # Step 4: 冲突检测
                conflicts = self._detect_conflicts(node)
                report["conflicts"] += len(conflicts)
                for conflict in conflicts:
                    self._resolve_conflict(node, conflict)
        
        return report

    def _find_duplicate(self, event):
        """简单去重：同 kind + 内容前 50 字符匹配。"""
        kind = event.get("kind", event.get("type", "unknown"))
        prefix = str(event.get("content", ""))[:50]
        for node in self.graph.values():
            if node.kind == kind and node.content[:50] == prefix:
                return node
        return None

    def _link_by_kind(self, node, event):
        """按事件类型建立不同类型的边。"""
        links = []
        kind = node.kind
        if kind == "preference":
            for tag in node.tags:
                for nid, other in self.graph.items():
                    if (other.kind == "preference" 
                            and tag in other.tags
                            and nid != node.node_id):
                        self.edges.append(
                            (node.node_id, nid, "related_preference"))
                        links.append("related_preference")
        elif kind == "decision":
            for tag in node.tags:
                for nid, other in self.graph.items():
                    if other.kind == "preference" and tag in other.tags:
                        self.edges.append(
                            (node.node_id, nid, "constrained_by"))
                        links.append("constrained_by")
        return links

    def _detect_conflicts(self, node):
        """检测与已有知识的冲突。"""
        conflicts = []
        for other in self.graph.values():
            if other.node_id == node.node_id or other.kind != node.kind:
                continue
            if set(node.tags) & set(other.tags) and node.content != other.content:
                if node.timestamp > other.timestamp:
                    conflicts.append(other)
        return conflicts

    def _resolve_conflict(self, new_node, old_node):
        """冲突解决：新信息覆盖旧信息，保留旧节点为历史。"""
        self.edges.append((new_node.node_id, old_node.node_id, "supersedes"))
        old_node.tags.append("superseded")

    def _create_node(self, event):
        import hashlib
        content = str(event.get("content", event.get("result", "")))
        kind = event.get("kind", event.get("type", "fact"))
        tags = event.get("tags", [])
        node_id = hashlib.md5(
            f"{kind}:{content[:100]}".encode()
        ).hexdigest()[:12]
        return GraphNode(
            node_id=node_id, kind=kind, content=content, tags=tags,
            timestamp=event.get("timestamp", time.time()),
            source_events=[event.get("seq", -1)])

System-2 做了四件 System-1 做不了的事：

  1. 去重：相同事实的多次记录合并为一个节点，保留溯源链
  2. 语义建边：偏好与决策之间的 constrained_by 关系，偏好之间的 related_preference 关系——这些边是后续推理的基础
  3. 冲突检测与解决：新信息与旧信息矛盾时，用时间戳决定优先级，但保留旧节点为历史记录
  4. 类型感知：不同类型的事件用不同的建边策略，这是纯关键词索引做不到的

五、协作协议：两个系统如何配合

双系统不是两个独立模块，而是有明确的协作协议：

class DualSystemMemory:
    """
    Agent 记忆的双系统写入网关。
    
    对外暴露一个 write() 接口，内部自动路由到 System-1 或两者。
    """

    def __init__(self, consistency="eventual"):
        """
        consistency 模式：
        - "strong":    每次写入立即 flush（最慢，最一致）
        - "eventual":  达到阈值时 flush（推荐，平衡）
        - "lazy":      仅在查询时 flush（最快，最不一致）
        """
        self.queue = FastAppendQueue(
            max_size=500, auto_flush_threshold=50)
        self.integrator = System2Integrator(
            graph={}, edges=[])
        self.consistency = consistency

    def write(self, event):
        """统一写入入口。"""
        # Step 1: 永远先写 System-1（保证可查）
        seq = self.queue.append(event)
        result = {"system1_seq": seq, "flushed": False}
        
        # Step 2: 根据一致性模式决定是否触发 System-2
        if self.consistency == "strong":
            self._flush_internal()
            result["flushed"] = True
        elif (self.consistency == "eventual" 
                and self.queue.should_flush()):
            self._flush_internal()
            result["flushed"] = True
        return result

    def read(self, query, limit=10):
        """统一读取入口：先查缓冲区，再查图谱，合并结果。"""
        if self.consistency == "lazy":
            self._flush_internal()
        
        # System-1 结果（新鲜但粗粒度）
        buffer_hits = self.queue.search(query, limit=limit)
        
        # System-2 结果（整合后但可能有延迟）
        graph_hits = []
        tokens = set(query.lower().split())
        for node in self.integrator.graph.values():
            node_tokens = set(node.content.lower().split())
            overlap = len(tokens & node_tokens)
            if overlap > 0:
                graph_hits.append((overlap, node))
        graph_hits.sort(key=lambda x: -x[0])
        graph_hits = [
            {"node_id": n.node_id, "content": n.content, 
             "kind": n.kind, "source": "graph"}
            for _, n in graph_hits[:limit]
        ]
        
        # 合并：图谱结果优先（已整合），缓冲区补充（最新）
        seen_content = {h["content"][:50] for h in graph_hits}
        merged = list(graph_hits)
        for hit in buffer_hits:
            prefix = str(hit.get("content", ""))[:50]
            if prefix not in seen_content:
                merged.append({
                    "content": hit.get("content", ""),
                    "source": "buffer", "seq": hit.get("seq")})
        return merged[:limit]

    def _flush_internal(self):
        """执行 System-2 整合。"""
        buffer = self.queue.drain()
        if buffer:
            report = self.integrator.flush(buffer)
            # logger.info(f"System-2 flush: {report}")

三种一致性模式的权衡：

模式写入延迟数据一致性适用场景
strong100-500ms最高（写后立即可查全图谱）金融、医疗等高要求场景
eventual<1ms最终一致（flush 后可查）推荐默认，大多数对话场景
lazy<1ms读时一致（查询触发 flush）高吞吐低延迟场景

在 290 天的生产实践中，eventual 模式覆盖了 95% 的场景。只有在用户紧接着追问刚刚写入的复杂关联信息时，strong 模式才有必要。

六、从写入到巩固：NREM/REM 模式

双系统写入解决的是实时问题。但 Agent 还需要一个更长期的巩固过程——类似于人类睡眠期间的记忆巩固。

def consolidate(self, mode="NREM"):
    """
    记忆巩固：在 Agent 空闲时执行深度整合。
    
    NREM（非快速眼动睡眠）：
        - 去重压缩、冗余删除、索引重建
        - 相当于"整理房间"
    
    REM（快速眼动睡眠）：
        - 跨域关联发现、抽象模式提取
        - 相当于"发现新洞察"
    """
    if mode == "NREM":
        merged = self._merge_similar_nodes()
        cleaned = self._gc_superseded()
        self._rebuild_indices()
        return {"mode": "NREM", "merged": merged, "cleaned": cleaned}
    elif mode == "REM":
        new_links = self._discover_cross_domain_links()
        new_skills = self._extract_skills_from_patterns()
        return {"mode": "REM", "new_links": new_links, 
                "new_skills": new_skills}

这个设计的灵感来自脑科学的一个发现：人类在 NREM 睡眠中做"减法"（修剪冗余突触），在 REM 睡眠中做"加法"（建立新的远距离关联）。Agent 的巩固过程也可以分为这两个阶段，在每天凌晨或空闲时段执行。

七、数字与反思

在 290+ 天的连续开发中，这套双系统写入模型处理了超过 8000 条测试用例覆盖的场景。几个值得分享的数据点：

  • System-1 缓冲区的命中率：在对话场景中，用户在 30 秒内追问刚写入信息的概率约 23%。System-1 缓冲区在这 23% 的查询中避免了"信息真空"。
  • System-2 的去重率：约 31% 的缓冲区事件在 flush 时被识别为重复并合并。这意味着如果不用双系统，三分之一的图节点会是冗余的。
  • 巩固阶段（NREM）的空间回收：每次 NREM 巩固平均回收 8-12% 的图节点空间，主要来自被 supersede 的旧版本。

回过头来看，双系统模型的核心洞察不是"快慢两条管道"，而是承认写入是一个有层次的复杂过程，不应该被简化为一次 API 调用。

业界很多人在争论"Agent 记忆应该用向量数据库还是知识图谱"。但真正的问题不在存储后端，而在写入管道的架构。一个用文件系统但写入管道设计良好的系统，会比一个用 Neo4j 但只有单系统写入的系统表现好得多。

Kahneman 教会我们的是：快速直觉和深度思考不是替代关系，而是协作关系。Agent 记忆系统也应该如此——System-1 保证新鲜信息的即时可用性，System-2 保证长期知识的结构一致性，巩固阶段保证知识的持续进化。
