Graph RAG 的成本悬崖与决策树：2026 年你该选什么

2026-08-09 · Graph RAG Knowledge Graph Agent Memory 检索增强

2024 年初，用 Graph RAG 索引一个 5GB 的法律数据集需要 $33,000 的 LLM 调用费用。18 个月后，LazyGraphRAG 把同样的成本压到了 $33——下降了 1000 倍。这不是渐进优化，这是成本悬崖：一条让之前所有架构决策都需要重新审视的断裂线。

本文不做文献综述。我要给出一个明确的观点：Microsoft GraphRAG 的原始架构在 2026 年已经被证明是过度设计，而真正活下来的不是某个产品，而是几个清晰的范式。我会用一个决策树告诉你该选什么，以及为什么 Mem0 从图退回向量是一个你必须知道的信号。

一、成本悬崖：1000 倍的断裂

先看数据。以下成本均基于真实论文和公开 benchmark：

系统索引成本查询成本发表时间
Microsoft GraphRAG$33,000 / 5GB$0.02-0.10/query2024.04
LazyGraphRAG$33 / 5GB (0.1%)可控预算2024.12
HippoRAG23.2M tokens (极低)低ICML 2025
PathRAG中等低2025.02
DCI (Contextual AI)零（无索引）Agent 自主控制2026

成本崩溃的原因不是 LLM 变便宜了（虽然确实变便宜了），而是架构范式的转变：把 LLM 推理从索引阶段推迟到查询阶段。GraphRAG 在索引时就做完实体抽取 + 关系抽取 + Leiden 社区检测 + 社区摘要——全用 LLM。LazyGraphRAG 只在索引时做轻量级 NLP 抽取（NER + embedding），把昂贵的 LLM 推理延迟到你真正发起查询的时候。

这意味着：如果你索引了 100 万文档但只查询 1000 次，GraphRAG 的成本是 LazyGraphRAG 的 ~1000 倍。因为 GraphRAG 为那些永远不会被查询的文档付了 LLM 推理费。

二、Agentic Search 的存在性挑战

在讨论 Graph RAG 的技术细节之前，必须先面对一个 existential question。Boris Cherny（Claude Code 团队）在 2026 年初公开表示：

早期 Claude Code 用 vector RAG，但发现 agentic search（grep + glob + 多轮搜索）效果更好。

这不是孤例。Contextual AI 推出了 DCI（Direct Corpus Interaction）范式：不构建任何静态索引，Agent 直接通过终端工具（rg, find, sed）与原始语料交互，根据推理状态动态调整搜索策略。在 BRIGHT benchmark 上，DCI 比 ColBERT-v2 和 BGE-M3 高出 12%——且零索引成本。

这对 Graph RAG 构成了真正的挑战：如果 Agent 自己能搜索、能迭代、能判断搜索结果质量，还需要预建图吗？

我的观点是：取决于查询类型，而不是技术热度。 Agentic search 和 Graph RAG 不是替代关系，而是分工关系。下面会详细展开。

三、赢家和输家已经清晰

经过两年多的实践，格局已经分化：

赢家

  • LazyGraphRAG — 索引成本降到向量 RAG 水平，延迟 LLM 推理到查询时。批量分析/研究的最佳选择。
  • Graphiti/Zep — 双时序知识图谱。Agent 记忆场景的杀手锏：94.7% LoCoMo 准确率、155ms 检索延迟，不需要 LLM-in-the-loop reranking。
  • HippoRAG2 — ICML 2025 论文，模仿海马体记忆机制。比迭代检索便宜 10-30x、快 6-13x。多跳 QA 的性价比之王。
  • PathRAG — 用流式路径剪枝解决图噪声问题。在 6 个数据集上全面超越 GraphRAG 和 LightRAG。
  • Agentic Search — 简单粗暴但有效。代码搜索的事实标准。

输家

  • Microsoft GraphRAG 原版架构 — $33K 索引成本的场景。索引阶段 LLM 噪声传播是致命问题。
  • LangChain + Neo4j 教程式 Graph RAG 管线 — 2025 年的标准建议，2026 年被推翻。
  • 纯向量 RAG — 在多跳推理任务上系统性落后。

四、Mem0 的退图信号：图不是万能药

这是我认为最值得关注的一个信号。Mem0 在 v3 中移除了图存储层，改用 spaCy 做实体链接 + 向量检索。原因是他们自己的论文数据：

变体LoCoMo 准确率搜索延迟Token 消耗
Mem0 纯向量66.881x1x
Mem0g (图变体)68.44 (+1.5)3x2x

图的收益只有 1.5 分，但代价是 3 倍延迟和 2 倍 token 消耗。ROI 为负。

更极端的例子：Letta 的"文件系统即记忆"实验用裸文件达到了 74.0%，超过了所有专用记忆系统（包括 Mem0 和 GraphRAG）。

这说明：图的收益取决于场景，不是普适的。 如果你做的是单点事实查询，向量 + BM25 混合搜索就够了，加图反而拖后腿。但如果你做的是 Agent 长期记忆——需要时序推理、事实失效、多跳关联——那图（特别是双时序图）就是必需品。

五、2026 年的正确决策树

这是我综合所有研究后给出的决策树。按查询类型选架构，而不是按技术热度选。

你的主要查询类型是什么？
│
├─ 单点事实查询（"X 的值是多少？"）
│   → 向量 RAG + BM25 混合搜索
│   → 成本最低，效果足够
│
├─ 多跳推理（"A 依赖 B，B 依赖 C，C 的状态变了，A 需要更新吗？"）
│   → HippoRAG2 或 PathRAG
│   → 图的价值真实存在，性价比高
│
├─ 全局摘要 / 主题分析（"这 10 万篇文档的核心主题是什么？"）
│   → LazyGraphRAG
│   → 索引成本可控，查询时才付 LLM 推理费
│
├─ Agent 长期记忆（"用户上周说过什么？哪些事实已经过时？"）
│   → Graphiti/Zep（双时序知识图谱）
│   → 时序维度是关键差异
│
├─ 代码搜索
│   → Agentic Search（grep + glob + 多轮）
│   → 不需要图，Agent 自己搜索更灵活
│
└─ <100K tokens 的小语料
    → 跳过 RAG，直接全塞上下文窗口
    → 2026 年的长上下文模型已经能处理好这个量级

六、代码示例：双时序查询的实际威力

为了说明为什么 Agent 记忆需要双时序图（而不是向量数据库），看一个真实场景。

假设你的 Agent 在管理项目知识。用户周一说"我们的定价是 $9.99"，周三说"定价改为 $14.99"。现在用户问"周一的时候定价是多少？"

向量数据库会返回语义最接近的结果——但它不知道"周一"这个时间约束意味着什么。它可能返回 $14.99（最新的，语义最匹配），这是错的。

双时序知识图谱给每条边两个时间维度：valid_from/valid_to（事实何时为真）和 recorded_at/invalid_at（系统何时知道/废弃这个事实）。查询"周一的定价"变成一个时间窗口过滤：

# 双时序查询：事实在 2026-08-03（周一）是有效的
result = graph.query_as_of(
    entity="pricing",
    timestamp="2026-08-03T00:00:00",
    relation_type="HAS_VALUE"
)
# → 返回 $9.99，因为 valid_from <= 2026-08-03 < valid_to

# 当前查询：现在的事实是什么
current = graph.query(
    entity="pricing",
    relation_type="HAS_VALUE"
)
# → 返回 $14.99，旧事实已被 invalided（不是删除）

# 审计查询：我们什么时候知道定价变了？
audit = graph.query_timeline(
    entity="pricing",
    relation_type="HAS_VALUE"
)
# → [
#   {value: "$9.99",  valid_from: "2026-08-03", recorded_at: "2026-08-03", status: "superseded"},
#   {value: "$14.99", valid_from: "2026-08-05", recorded_at: "2026-08-05", status: "active"}
# ]

关键区别：事实失效不等于事实删除。 旧事实被标记为 superseded 而不是被删除，这保留了完整的审计链。你可以回滚到任何时间点的知识状态。

Graphiti 的实践证明，这种模式在 94.7% 的情况下能正确回答时序问题——不需要 LLM-in-the-loop reranking。这意味着推理成本趋近于零。

七、记忆冲突：下一个战场

2026 年 6 月的 FactConsolidation benchmark 揭示了一个扎心的现实：即使最强的 RAG 系统，在多跳事实合并（FC-MH）任务上的准确率几乎是 0。

系统单跳事实合并多跳事实合并
HippoRAG254%0-7%
GraphRAG—7-28%
Graphiti—7-28%

架构复杂度并不能解决事实冲突，反而引入了更多 LLM 判断节点和噪声传播路径。这是下一个真正值得投入的研究方向：不是建更大的图，而是让图能正确处理矛盾信息。

Graphiti 提出了一个初步框架：区分 supersession（世界变了，新事实 valid_from 更晚）和 correction（之前就错了，新事实 valid_from 相同）。这是对的方向，但远不够。真正的冲突解决需要证据权重推理——哪个信息源更可信？多条证据是否互相印证？

八、行动建议

  1. 如果你在用 GraphRAG 原版——立即评估迁移到 LazyGraphRAG。索引成本会降 3 个数量级，查询效果不减。
  2. 如果你在评估 Agent 记忆方案——优先看 Graphiti/Zep。时序维度不是 nice-to-have，是核心需求。你的 Agent 需要知道"什么时候知道什么"。
  3. 如果你在做多跳 QA——看 HippoRAG2。Personalized PageRank + 海马体模型，性价比远超迭代检索。
  4. 如果你在纠结"要不要上图"——先问自己：你的查询需要时间推理吗？需要多跳关联吗？如果都不需要，向量 + BM25 就够了。Mem0 的退图信号要认真对待。
  5. 如果你的语料 <100K tokens——别折腾 RAG 了，直接塞进上下文窗口。2026 年的长上下文模型已经能处理好这个量级。

结论

Graph RAG 在 2024 年被过度炒作，在 2025 年经历清醒，在 2026 年走向分化。这不是技术失败的标志——恰恰相反，分化意味着不同场景找到了不同的最优解。

真正的教训是：没有银弹。 Graph RAG 原版的失败不在于图本身，而在于"在索引阶段用 LLM 做所有事"这个架构决策。LazyGraphRAG 证明了延迟推理的正确性。Graphiti 证明了时序维度的必要性。HippoRAG2 证明了生物启发的检索策略的可行性。Mem0 的退图证明了图不是万能药。

选架构的时候，看你的查询类型。别看 GitHub stars。
