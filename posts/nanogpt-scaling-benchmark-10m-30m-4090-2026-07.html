核心反直觉

参数量只涨了 2.8 倍，但生成质量是质变而非「量变」。原因不在模型大，而在数据集变了 2000 倍 + tokenizer 换了 773 倍词表。

关键洞察

换 BPE 后，模型主体没变（6 层 × 6 头 × 384 维还是 ~10M 参数），但 token embedding 从 25K 参数暴涨到 19.3M，主导了参数增长。这意味着模型「实际能用的容量」并没翻 3 倍。BPE embedding 那 19.3M 参数基本是字典查询表，不是「思考能力」。真正的 transformer 思考容量两次完全一样。

三Loss 不能直接比（重要）

10M 模型 val 1.48，30M 模型 val 1.42——看起来差不多，但这是两个不同尺度的 loss。

10M30M
Loss 单位每字符 nats每子词 nats
每 token 对应字符数1~4（BPE 平均压缩比）
换算到 bits/char1.48 / ln(2) / 1 = 2.141.42 / ln(2) / 4 = 0.51
困惑度（perplexity）e^1.48 = 4.4 字符e^1.42 = 4.1 子词 ≈ ~14 字符
结论

30M 模型在「每字符压缩效率」上是 10M 的 4.2 倍。这个差距远大于 val loss 数字本身的差距。

为什么 100M 值得跑

30M 模型在小逻辑（"兔子教狮子说话"反了）上天花板明显——长程依赖能力不够。100M 是「能保持角色设定 / 故事一致性」的最小尺度。5 小时在 4090 单卡可承受。

六关键工程洞察

1. Tokenizer 选择对参数量的影响巨大

换 BPE 后 vocab 从 65 → 50257，仅 token embedding 就占 19.3M 参数（占模型总参数 65%）。但这个 embedding 是「字典」，不是「思考力」——衡量模型「真实容量」应该看 transformer 主体参数，不是总参数。

2. 数据扩大 100 倍的收益是非线性的

数据扩大val loss 改善生成质量改善
22MB → 2.1GB（100×）1.94 → 1.42（-27%）质变（无意义 → 可读故事）

Loss 是对数指标，每降低 0.1 在生成质量上的视觉冲击远超数字本身。所以「loss 只降了 0.5」可能意味着「模型从废品变可用」。

3. Train/Val 同源 vs 异源是真实泛化能力的分水岭

设置Dry-run（22MB）正式训练（2GB）
Train 来源valid.txt 前 90%train.txt（独立文件）
Val 来源valid.txt 后 10%valid.txt（独立文件）
同源偏差val loss 偏乐观val loss 反映真泛化

结论：永远不要用「同源 train/val 切分」做严肃实验。这是 nanoGPT 教学代码省略的关键工程严谨度。

4. 4090 单卡 48GB 的实际能力边界

模型规模单卡可行性备注
10M-30M✅ 秒级训练浪费
100M✅ 小时级推荐实战尺度
350M✅ 几小时接近显存上限
1B⚠️ 需 FSDP 切多卡单卡勉强装下但训练慢
7B+❌ 必须 LoRA 或 FSDP全参数训练不可行

5. 多卡在 10M-30M 尺度是浪费

4090 没有 NVLink，PCIe 通信开销大。DDP 在小模型上加速比 2-2.5×（不是理想的 4×）。真正划算的多卡用法是并行实验：4 张卡同时跑 4 组超参，达到真 4× 吞吐。

八本基准的局限

  1. 只测了 2 个尺度（10M + 30M）。100M 是外推，没实测。建议有卡的人补测。
  2. nanoGPT 是教学代码，工程优化不极致。生产级框架（Megatron / DeepSpeed / Torchtitan）的 MFU 可能更高。
  3. TinyStories 是合成数据，词汇简单。换自然语言数据（FineWeb-Edu / OpenWebText）的 loss 不可比。
  4. 未测多卡场景。DDP / FSDP 的实际加速比待补。
  5. 未测采样效率。生产部署还需要 vLLM / llama.cpp 测推理速度。
