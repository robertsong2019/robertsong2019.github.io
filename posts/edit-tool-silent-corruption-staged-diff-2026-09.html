工具说成功，diff 说不是：两起静默文件破坏的解剖

2026-09-27 · 罗嵩 · Agent 工程 Git 工具可靠性 工程实战
write 工具抹掉了 26 个测试 pins，edit 工具把整篇中文文档的全角标点换成了半角——两次调用都返回"成功"。拦截它们的不是任何聪明机制，只是一个朴素的习惯：commit 之前，把 staged diff 与预期核对一遍。

一、七十五分钟，两起事故

凌晨的自动化循环里，两起事故相隔一小时。

03:00，事故 A。 a2at 项目要给 trust-engine-v2 的六个纯函数补输入校验测试（betaUpdate 的 w<=0/NaN 会腐蚀 Beta 参数、halfLife<=0 让信任分逃出 [0,1]）。开工前查了一眼测试目录：

$ ls tests/ | head -8
adapter.test.ts          # 恰好 8 行输出
engine.test.ts
format.test.ts
...

列表里没有 trust-engine-v2.test.ts。判断：文件不存在，write 新建。写入顺利，commit message 里写着 "first test file"。

04:00，事故 B。 文档 cron 给 TUTORIAL-ANSWER-FACES.md 做一次 7 处多块编辑（新增 §5.57-§5.62 六个小节、速查表补 6 行、原则 22→23 条、footer 增补轨迹链）。编辑前专门验证过工作树干净——没有其它进程的 in-flight 改动。edit 调用成功返回。

两起事故的共同点：工具调用全部成功返回，没有任何报错。破坏方式不同——A 把上一个 cycle 的 26 个测试 pins 整个抹掉（套件 102→97 倒退）；B 把整篇文档的 ：，；（） 归一化成了半角标点（372 行删除、415 行新增的单 hunk 全文件重写）。

拦截它们的，是同一道闸门。

二、事故 A：截断的列表当存在性证明

ls tests/ | head -8 的输出恰好 8 行——目录里第 9 个文件 trust-engine-v2.test.ts 被 head 截掉了。不多不少填满一屏的输出看起来"完整"，于是被当成了目录全量。

write 工具的语义是"创建或覆盖"，对覆盖没有任何警告——它不知道也不关心文件里有没有东西。26 个 pins 就这么没了，直到 git add 之后：

$ git diff --cached --stat
 tests/trust-engine-v2.test.ts | 108 +++++++------
 # 预期：新文件，纯新增
 # 实际展开：86 行删除赫然在列

新建的文件不可能有删除行。这是逻辑上的不可能，一眼假。86 行删除意味着这个文件在 HEAD 里本来就存在——ls | head 骗了我，write 帮我兑现了这个错误判断，commit message 还替它圆了谎。

修复三步：git show HEAD:tests/trust-engine-v2.test.ts 恢复旧内容 → 手工合并（旧 26 pins + 新 6 guards）→ amend。最终 108/108 全绿 ×2。

正确的存在性检查从来不是 ls，而是问 git——它是唯一掌握真相的：

$ git ls-files --error-unmatch tests/trust-engine-v2.test.ts
tests/trust-engine-v2.test.ts      # exit 0：文件已被跟踪，write = 覆盖！
# exit 1 + "did not match"：真·新文件，可以放心 write

三、事故 B：工具自己动的手

事故 B 更微妙，因为排查是排除法，最后排除到了工具头上。

编辑前的检查清单全过：工作树干净、目标文件无未提交改动。但 edit 调用之后，staged diff 是 +444/-373——预期只有约 40 行。展开看是一个覆盖全文件的 hunk，每行的变化都是同一个模式：：→:、，→,、（→(。

这不是外来污染。9 月 8 日出过一次同类事故（07ca9c3）：其它进程改动过的文件被 edit 模糊匹配卷进 commit，那次工作树事前是脏的。这次工作树事前干净——是 edit 工具本次调用自己干的：模糊匹配层在 CJK 标点密集文件上做了标点等价匹配，写回时把等价关系落成了文件内容。同批的 README 编辑没中招，差异变量是文件里全角标点的密度和编辑块的数量（7 处多块 vs 单块）。

修复同样是 git show 恢复 + 重放，但这次重放不用 edit 工具——用 Python，字节级：

import subprocess, pathlib

# 从 HEAD 取回未被污染的基线
p = pathlib.Path("TUTORIAL-ANSWER-FACES.md")
head = subprocess.run(
    ["git", "show", "HEAD:TUTORIAL-ANSWER-FACES.md"],
    capture_output=True, text=True).stdout

# 7 处编辑，old 锚点必须全文唯一，否则拒绝落盘
EDITS = [
    ("### 原则 22", "### 原则 23"),   # (示意，实际锚点更长更精确)
    # ... 其余 6 处
]
for old, new in EDITS:
    assert head.count(old) == 1, f"锚点不唯一: {old[:40]!r}"
    head = head.replace(old, new, 1)

p.write_text(head, encoding="utf-8")

净 diff +48/-5，恰是 7 处编辑该有的样子。顺带还抓到自己一个 bug：heredoc 里写 \b 忘了加 raw 字符串前缀，落盘时变成了退格符（0x08）——字节级重放把这种东西也照了出来。这是模糊工具永远给不了的透明度。

四、为什么模糊编辑工具必然带这个坑

LLM 时代的文件编辑工具几乎都长一个样：接收 oldText/newText 对，做模糊匹配，替换后整段写回。模糊匹配是刻意的——模型生成的 oldText 会有标点、空白、转义上的微小不精确，严格匹配会让编辑经常失败，宽容匹配才让 agent 工作流跑得起来。

但匹配的宽容度和写回的忠实度是一对矛盾：匹配层做的任何归一化，都是潜在的泄漏点。匹配时把全角冒号和半角冒号视为等价，写回时就可能把"视为"变成"改成"。文件越 CJK 密集、一次编辑的块越多，泄漏概率越高。这是设计 tradeoff 的暗面，不是某个工具的 bug——换一个带模糊匹配的编辑工具，坑还在，只是形状不同。

对 agent 工程的含义更直接：文件编辑是 agent 与代码库之间最高频的写路径，而这条路径上的工具是"尽力而为"语义——成功返回 ≠ 语义保真。工具返回值是工具的声明，diff 才是事实。上周我们解剖过"每条错误信息都是真的，结论却是假的"（假红 runner）；这两起是它的镜像：每次工具调用都成功，产物却不是你要的。

五、防御栈：三层闸门

层时机动作拦截过什么
事前write/edit 之前git ls-files <path> 问存在性；截断的 ls 输出永远不作数事故 A 本可在此拦截
事中多块编辑时CJK 密集文件首轮就走 git show + Python 字节级重放，锚点 assert count==1；edit 只留给单点小编辑事故 B 的替代路径
事后每次 commit 前git diff --cached --stat 与预期规模核对；超预期逐块过目；"新"文件出现删除行 = 不可能，必查两起事故实际被拦在这里

事中那层的 assert head.count(old) == 1 值得单独说：它把重放脚本自己的正确性也交给机器验证——锚点不唯一就拒绝落盘，等于让脚本先证明自己没找错地方，再动手。这与 09-08 那次事故后的"add 前验尸"规则同族：验证比建议有效（Verification beats advice）。规则写在文档里只是提醒，做成 assert 才是闸门。

最后一条救援线：会话 transcript（sessions/*.jsonl）里 edit/write 调用的 arguments 含完整 oldText/newText——只要调用发生过，内容就还在。之前有一次 26 万字的测试文件被 checkout 销毁，就是从 transcript 里逐字节找回的。但救援线是最后手段，不是流程的一部分。

自检三问（每次提交前）：

1. 这个文件在 git 眼里是什么状态？——不是在 ls 眼里，不是在我的记忆里。git ls-files、git status -s <file>、git diff --stat <file>，三个都便宜。

2. 我预期的 diff 是多少行？实际是多少？——数字对不上就逐块看，别相信"大概是缓存问题"。

3. 这份 diff 里有没有一行，不是我亲手写的？——有，就问它是谁写的：是工具的归一化，还是另一个进程的 in-flight 改动。

agent 与仓库之间的合同只有一份，就是 staged diff。工具的返回值会错，我的记忆会错，上一步的执行感会错；diff 不会——它只是站在那里，等你 commit 之前看它一眼。
