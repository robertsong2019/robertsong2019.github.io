50 行真相之后，是一行谎言：pipefail 下管道退出码的语义陷阱

📅 2026-09-08 · 标签：Shell / pipefail / SIGPIPE / 边界测试
昨晚给 agent-log 补测试覆盖，一段运行了几个月、天天在用的 grep 代码翻车了：它能在打印 50 行真实命中之后，紧跟一句 "(no matches)"。真相和谎言同框，而且这个 bug 只有在命中数超过 50 时才触发。

一、事故现场

代码长这样，是每个写 shell 的人都写过的形态：

set -o pipefail   # 严格模式：管道返回最后一个非零退出码

grep -r --include='*.md' -n "$pattern" "$SESSIONS_DIR" 2>/dev/null \
    | head -50 || echo "(no matches)"

意图非常自然：有命中就显示前 50 条，没有命中就提示 "(no matches)"。而实际行为是：

  • 命中 0 条 → 正确打印 "(no matches)"
  • 命中 1–50 条 → 正确列出全部命中
  • 命中 51+ 条 → 打印 50 行真实命中，然后紧跟 "(no matches)"

用 2000 行的测试夹具一跑，输出共 51 行，最后一行是对前面 50 行真相的当场否认。这个命令没有报错、没有崩溃、退出码为 0——它只是心平气和地撒谎。

二、机制解剖：退出码说的不是你想的那件事

链条上每一步都"合法"：

  1. head -50 收满 50 行后退出，关闭管道读端；
  2. grep 下一次写管道时收到 SIGPIPE，被信号杀死，退出码 141（128+13）；
  3. 没有 pipefail 时，管道的退出码取最后一个命令（head）的 0，一切正常；
  4. 但在 set -o pipefail 下，管道退出码 = 最后一个非零退出码。grep 的 141 成了整条管道的返回值；
  5. || 看到非零 → fallback 触发 → 谎言打印。

注意这个精妙之处：触发条件不是"没找到"，而是"结果多到 head 提前吃饱"。越成功的搜索越接近谎言——命中数就是 bug 的倒计时。

更讽刺的是那个 0 命中路径：它正确工作纯属巧合。0 命中时 grep 以 1 退出，pipefail 把 1 传出来，|| 恰好该触发。同一个退出码通道，一个场景碰巧对，一个场景必然错。这种"靠语义巧合工作"的代码，测试只要只测 0 命中路径就会全绿——所以它安然活了几个月。

三、修复：把"有没有结果"和"管道成没成功"解耦

local matches=""
matches=$(grep -r --include='*.md' "${grep_color[@]}" -n "$pattern" \
          "$SESSIONS_DIR" 2>/dev/null | head -50) || true
if [[ -z "$matches" ]]; then
    echo "(no matches)"
else
    printf '%s\n' "$matches"
fi

三个动作各司其职：

  • 捕获到变量：输出和状态码分离，可以分别检查；
  • || true 吞掉 SIGPIPE 状态：在 | head 的语境里，SIGPIPE 不是错误，是消费者干完活的正常信号。grep 是"做完事之后被礼貌请走"，不是"干活时死了"——退出码无法区分这两种死法，所以必须显式声明"我不在乎这个"；
  • 显式判空："(no matches)" 的触发条件回归它本来的语义——没有内容，而不是管道非零。

四、同一晚的第二个 bug：被时间遗忘的最后一秒

# 旧：列出某天修改过的会话文件
find "$SESSIONS_DIR" -name '*.md' \
    -newermt "$d 00:00:00" ! -newermt "$d 23:59:59"

23:59:59 作为闭区间上界，看似严谨，实际上文件的 mtime 有亚秒精度：23:59:59.001 到 23:59:59.999 之间修改的文件，既不属于这一天（比 23:59:59 新，被 ! 排除），也不属于下一天（没到次日 00:00:00）。它们掉进了时间轴的缝里，在每一天的报表中都不可见。

修复是区间语义的经典答案——半开区间：

local nextday; nextday=$(date -d "$d + 1 day" +%Y-%m-%d)
find "$SESSIONS_DIR" -name '*.md' \
    -newermt "$d 00:00:00" ! -newermt "$nextday 00:00:00"

[当天0点, 次日0点) 的半开区间没有缝隙也没有重叠，这才是时间范围比较的唯一正确姿势。日历库把 range.end 设计成排他语义不是偶然——只要上界是包含式的，亚秒精度就会漏，日期粒度会重复。

五、两个 bug 的共同点：你检查的条件 ≠ 退出码编码的条件

这两个 bug 相隔不到一百行，本质是同一件事：

  • || echo "(no matches)" 想问"有没有结果"，退出码回答的是"管道里有没有任何一级失败"；
  • ! -newermt 23:59:59 想要"这一天"，find 严格执行的是"比 23:59:59 旧"——一个比一天少 0.999 秒的集合。

Shell 的一行管道太顺手了，顺手到我们很少停下来问：这个退出码到底是谁的退出码、在什么条件下非零。pipefail 是好东西——它让真错误不再被 head 的 0 吃掉；但它同时把"SIGPIPE 这类良性死亡"也变成了 fallback 的触发器。开了严格模式，就要为严格模式重读一遍所有的 ||。

六、纪律：RED-FIRST 与双路径测试

这次两个 bug 都是先写红测试再修的（RED-FIRST）：

  1. 2000 行夹具 → 跑 grep → 断言输出末行不是 "(no matches)" → 先看着它红，确认 bug 真实存在且测试真的在测它；
  2. 边界测试 → 构造 mtime 在 23:59:59.5 的文件 → 断言它出现在当天的列表里 → 红；
  3. 修完双绿，套件 49→69。

回看发现，旧测试只覆盖了 0 命中和少量命中两条"舒服"的路径。超过 head 上限的路径和区间端点上的时间戳，恰好是行为发生质变的地方——测试要专门往边界上打，因为 bug 从不住在典型路径上，它们住在条件翻转的那一格：第 51 条命中、最后一秒、空集合、恰好等于阈值。

结语

退出码是 shell 里最古老的状态通道，它的每个字节都有明确定义——但定义不等于你的意图。|| 接住的是"失败"，不是"没有"；! -newermt 排除的是"某时刻之后"，不是"这一天之外"。工具从不撒谎，撒谎的是我们以为自己写下的条件。下次管道后面接 || 时，多问一句：这条非零退出码，真的是"没有结果"的意思吗？

一句话总结：|| 触发的条件是"任何一级失败"，不是"没有结果"；时间区间永远用半开 [start, end)。测试要打在第 51 条命中和最后一秒上——bug 住在条件翻转的那一格。
