TWO PARADIGMS · 同一个函数,两种验证

fuzzing 和 Verus,差在哪

被测对象完全一样：rust_binutils/src/util.rs 的 read_uXX 三个读取原语。 但两种方法给出了截然不同的"信心"。

● 腰部 · TESTING

Fuzzing（15000 次）

检查的输入数15000 个具体值
覆盖的输入空间≈ 0%（无穷空间的样本）
发现 panic0 个
结论强度统计（"没碰到"）
运行时间0.03 秒
结论："我没找到反例"
但 off = usize::MAX 这种输入,fuzz 几乎不可能随机生成。
● 塔尖 · VERIFIED

Verus（符号证明）

检查的输入数所有可能值（无穷）
覆盖的输入空间100%
发现 bug1 个（第 1 版立刻）
结论强度数学证明（"不可能"）
运行时间≈ 1 秒
结论："反例不可能存在"
Z3 用符号执行,直接推理出 off + 2 会溢出。

本质区别不在"快慢",在"穷尽性"。 fuzz 是归纳法（inductive）—— 跑过的才算数；Verus 是演绎法（deductive）—— 推理出对所有输入成立。前者抓"需要碰运气触发的 bug"， 后者抓"需要推理才能发现的 bug"。

THE BUG · Verus 第一行就抓到的

usize 加法溢出

我最初照搬 util.rs 的写法 if off + 2 <= data.len()。 这在普通 Rust 里能编译，fuzz 也跑不出问题。但 Verus 直接拒绝：

possible arithmetic underflow/overflow read_uxx.rs:83 
// 我照搬 util.rs 的写法 —— 普通 Rust 能编译,fuzz 跑不出问题
if off + 2 <= data.len() {
    let b0 = data[off] as u16;
    ...

// ↑ Verus 拒绝: 当 off = usize::MAX 时,off + 2 在 usize 里回绕成 1
//   比较结果错误 → 函数可能越界访问
//   fuzz 几乎不可能随机生成 usize::MAX,所以永远发现不了

// 修复: 用等价但不溢出的形式
if data.len() - off >= 2 {     // requires 保证 off < len,减法安全
    let b0 = data[off] as u16;
    ...

// 这就是 Q2 笔记里讲的陷阱 —— Verus 强制你处理它, 而不是像 fuzz 那样靠概率放过它。

DEBUG TIMELINE · 从 5 errors 到 0 errors

代码被拒绝5 次,才通过

这 5 次拒绝本身就是最好的教学材料 —— 每一个错误都是"Verus 和普通 Rust 编译器的本质区别"。 我把完整过程记录下来，因为这些坑就是形式化验证的价值所在。

REJECT #1 usize 加法溢出（3 处）
error: possible arithmetic underflow/overflow --> read_uxx.rs:83 | if off + 2 <= data.len()
修复: off + 2 <= data.len() → data.len() - off >= 2
requires 保证 off < data.len(),所以减法不溢出。这就是上面 #bug 详述的那个。
REJECT #2 println! 在 verus! 块里不支持
error: Unsupported constant type --> read_uxx.rs:237 | println!("{:?}", v)
修复: 把 main 移出 verus! { ... } 块。
main 只是 demo runner,不需要验证;Verus 的 exec 模式对 Debug 格式化支持有限。
REJECT #3 位运算 lemma 证不出来
error: postcondition not satisfied --> lemma_read_u16_le | (b0 as u16) + (b1 as u16) * 256 == ((b0 as u16) | ...)
修复: 加 #[verifier::bit_vector] 属性。
默认整数理论里,<< 和 | 是未解释函数;切到 bitvector 理论 Z3 才能证等价。
坑:拼写是 bit_vector(下划线),不是 bitvector。
REJECT #4 quantifier 找不到 trigger
error: Could not automatically infer triggers for this quantifier. --> forall|b0: u8, b1: u8| ...
修复: 在量化体的关键子表达式前加 #[trigger]。
Z3 用 trigger 做模式匹配,决定"什么时候把这个 forall 实例化"。手动指定避免它瞎猜。
ACCEPT ✓ 全部通过
verification results:: 5 verified, 0 errors
5 个验证目标:
① read_u16 完整性+安全性　② read_u32 同　③ read_u64 同

THE VERIFIED CODE · 最终通过的代码

read_u16 的完整规范

这是 Verus 最终接受的版本。注意 requires / ensures 里用 int 推理（数学整数,不溢出），实现里用减法避免溢出 —— 两层配合才通过。

read_u16 · verified ● 5 VERIFIED 
pub fn read_u16(data: &[u8], off: usize, le: bool) -> (r: Option<u16>)
    requires
        // 前置条件: off 本身必须合法(用 int 推理,不溢出)
        off < data.len(),
    ensures
        // 完整性: 够长就返回 Some
        off + 2 <= data.len() ==> r.is_some(),
        // 安全性: 返回 Some 就一定够长(绝不越界) ★关键★
        r.is_some() ==> off + 2 <= data.len(),
{
    // 用减法形式避免 off+2 溢出 —— Verus 强制的要求
    if data.len() - off >= 2 {
        let b0 = data[off] as u16;
        let b1 = data[off + 1] as u16;
        if le {
            Some(b0 + b1 * 256)        // 小端: 低字节在前
        } else {
            Some(b0 * 256 + b1)        // 大端: 高字节在前
        }
    } else {
        None
    }
}

两条 ensures 合起来构成"当且仅当"： 返回 Some ⟺ off + 2 <= data.len()。 缺任何一条,调用方（elf.rs/macho.rs）的 ? 操作符就无法正确判断"数据够不够长"。 这正是形式化验证的严格之处 —— 测试永远不会要求你写明这种双向契约。
