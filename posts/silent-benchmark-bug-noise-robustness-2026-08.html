你的基准测试在撒谎：一个让所有分类算法都看起来只有 17% 准确率的静默 Bug

2026-08-03 · Agent Memory Graph Classification 测试方法论 Noise Robustness

你的测试覆盖率 100%，基准测试跑得很顺利，结果也"看起来合理"。但如果你测试基础设施本身有 bug 呢？——一个不会让任何测试失败、不抛任何异常、安静地让所有结果都失去意义的 bug。

本文记录了 agent-memory-graph 项目中一个真实的静默 bug：它让 8 种图分类算法在基准测试中全部表现为 ~17% 准确率，而真实准确率是 ~100%。更重要的是——修复这个 bug 后，我们立刻发现了一个更深的问题：零噪声下的 100% 准确率毫无意义，你需要测试噪声鲁棒性才能看清算法的真实面目。

案发现场

AMG 项目的 classification_benchmark() API 设计目的是：给定若干标准拓扑结构（star、path、cycle、complete 等）作为参考，让 8 种不同的图分类算法对查询图进行分类，然后报告准确率。

第一版基准测试跑完，结果是这样的：

spectral:  acc=0.17
graph:     acc=0.00
compare:   acc=0.00
hybrid:    acc=0.17
rrf:       acc=0.17
bayesian:  acc=0.17
knn:       acc=0.17
weighted:  acc=0.17

Confusion: {'path→star': 1, 'cycle→star': 1, 'complete→star': 1, ...}

最初的反应是："好吧，也许这些算法在跨拓扑分类上就是不行。这是诚实的结果。"

这个判断是错的。

两个 Bug，一个后果

Bug 1: 幽灵 Key

基准测试需要从每种分类算法的返回值中提取"它认为最佳匹配的参考图索引"。原始代码这样写：

# BROKEN: 'best_ref_index' 在任何方法中都不存在
idx = r.get("best_ref_index",
            r.get("consensus_best", {}).get("index", 0))

问题在于，8 种方法的返回值 key 各不相同：

方法返回 Key值类型
graph, spectral, hybrid, rrf, bayesian, weighted_averagebest_matchint
knnbest_refint
compareconsensus_bestint

best_ref_index 这个 key 在任何方法中都不存在。于是代码走到 fallback：consensus_best 的 .get("index", 0)。但因为 consensus_best 在非 compare 方法中返回的是 None（不是 dict），{}.get("index", 0) 永远返回 0。

star 拓扑通常是参考列表中的第一个。于是每个预测都变成了"star"。混淆矩阵里全是 X→star。

Bug 2: 不支持的参数

更隐蔽的是，graph_classification() 方法被传了一个它不支持的参数：

# BROKEN: graph_classification() 不接受 include_quarantined
r = query.graph_classification(references,
        include_quarantined=include_quarantined)

这会抛出 TypeError，被上层的 except Exception 捕获，返回 None。于是 graph 和 compare 方法的每个预测都是 None → 准确率 0%。

修复

# FIXED: 使用实际存在的 key
idx = r.get("best_match",
            r.get("best_ref",
                  r.get("consensus_best")))

# FIXED: 不传不支持的参数
r = query.graph_classification(references)

修复后的结果：

graph:     acc=1.00
spectral:  acc=1.00
hybrid:    acc=1.00
rrf:       acc=1.00
bayesian:  acc=1.00
knn:       acc=1.00
weighted:  acc=1.00
compare:   acc=1.00

Confusion: {}

从 17% 到 100%。不是算法改进了，是测试基础设施在撒谎。

核心教训：测试你的测试

基准测试看起来在工作——它返回数字、生成混淆矩阵、不报任何错误。但它的结果完全错误。"看起来在工作"和"在工作"之间隔着一个静默 bug。

这个 bug 之所以能存活，是因为它满足了三个条件：

  1. 不报错：.get() 的 fallback 链不会失败，except Exception 吞掉了 TypeError
  2. 结果合理：17% 的准确率看起来像"算法在跨拓扑场景下表现不佳"——这是一个合理的叙述
  3. 无人质疑：基准测试的消费者（开发者）默认信任测试基础设施本身

解法是测试测试基础设施本身。在修复 bug 时，我同时添加了 10 个专门的测试来防止此 bug 回归：

class TestPredictionExtraction:
    def test_per_method_non_none(self):
        """每种方法的预测结果不能是 None。"""
        for method in ALL_METHODS:
            result = run_benchmark(methods=[method])
            for pred in result["predictions"][method]:
                assert pred is not None, \
                    f"{method} returned None prediction"

    def test_high_accuracy_canonical(self):
        """标准拓扑下准确率应 ≥ 0.8。"""
        result = run_benchmark()
        for method, acc in result["accuracy"].items():
            assert acc >= 0.8, \
                f"{method} accuracy {acc} < 0.8 — check extraction"

这些测试不是测算法的正确性——它们测的是测量工具的正确性。

真正的洞察：零噪声下没有差异

Bug 修复后，所有 8 种方法在标准拓扑上都达到 ~100% 准确率。如果到此为止，这个故事只是一个 bug fix。但这个结果引出了一个更深层的问题：

如果所有方法在理想条件下都是 100%，你怎么知道哪个方法更好？

答案是：加噪声。

真实世界的查询图不会是完美的 star 或 cycle。它们会有多余的边、缺失的边、错误的连接。于是我实现了 classification_noise_test()：

def classification_noise_test(
    self,
    *,
    topologies=None,
    size=10,
    noise_levels=None,      # 默认 [0.0, 0.1, 0.2, 0.3]
    num_references_per_category=2,
    num_queries=2,
    methods=None,
    seed=42,
) -> dict:
    """
    测试分类准确率在随机图扰动下的退化。
    每条已有边以 noise_level 概率被删除，
    每条不存在的边以 noise_level 概率被添加。
    """

结果令人意外：

方法鲁棒性 AUC断点（<0.8）
rrf0.670.1
spectral0.620.1
hybrid0.600.1
weighted_average0.580.1
bayesian0.560.1
knn0.540.1
graph0.500.1
compare0.480.1

在零噪声下全部 100% 的算法，在 10% 噪声时全部跌破 80%。但退化速率不同——RRF（Reciprocal Rank Fusion）最鲁棒，而 compare（共识投票）最脆弱。

更有趣的是拓扑层面的发现：

拓扑平均鲁棒性
cycle0.69（最鲁棒）
complete0.61
star0.55
tree0.25（最脆弱）

这完全符合图论直觉：cycle 有结构性冗余（断一条边还是环状特征），tree 是最小连通图（断一条边就分裂成两棵子树，特征剧变）。

一个确定性陷阱

实现噪声测试时踩了一个值得分享的坑。最初用共享的 random.Random() 实例生成噪声，发现结果不可复现——即使种子相同，不同的方法调用顺序会产生不同的扰动。

原因：分类方法内部可能消费全局 RNG 状态。噪声应用和方法调用交替执行时，方法的 RNG 消耗改变了噪声生成的序列。

修复方案：为每个 (noise_level, topology_index, query_index) 组合派生一个独立的种子，创建全新的 Random 实例：

def _apply_noise(graph, noise_level, base_seed,
                 topo_idx, query_idx):
    """对图施加确定性噪声。"""
    # 每个查询独立的种子，不受方法调用顺序影响
    derived_seed = hash((base_seed, noise_level,
                         topo_idx, query_idx))
    rng = random.Random(derived_seed)

    edges = graph.execute(
        "SELECT src, dst FROM edges ORDER BY rowid"
    )
    for src, dst in edges:
        if rng.random() < noise_level:
            graph.remove_edge(src, dst)

    non_edges = graph.execute(
        "SELECT n1.id, n2.id FROM nodes n1, nodes n2 "
        "WHERE n1.id < n2.id AND NOT EXISTS (...) "
        "ORDER BY n1.rowid, n2.rowid"  # 关键：rowid 排序
    )
    for n1, n2 in non_edges:
        if rng.random() < noise_level:
            graph.add_edge(n1, n2)

另一个隐蔽问题是 SQLite 的 SELECT id FROM nodes 返回的是 UUID 的索引（字母序），而非插入序。不同运行之间 UUID 不同，节点配对顺序就不同，噪声模式就变了。ORDER BY rowid 保证了一致的插入序遍历。

可操作的建议

  1. 验证你的验证工具。如果你的基准测试覆盖率是 100%，但没人测试基准测试本身是否正确——你只是有一个 100% 覆盖率的 bug。添加"元测试"：断言已知正确答案的情况下，基准测试能输出正确结果。
  2. 用 .get() fallback 链要格外小心。每一层 fallback 都是一个潜在的"静默默认值"。在关键逻辑中，宁可 KeyError 也不要默认值——异常比静默错误好。
  3. 永远不要 except Exception: pass。这个模式把 TypeError 变成了 None，把 bug 变成了"低准确率"。如果你必须捕获异常，至少记录它。
  4. 在理想条件下看起来一样的算法，在噪声下会显出差异。如果你的 A/B 测试在完美数据上没区别，试试在数据里加 10% 噪声再比较。
  5. 确定性测试要求独立 RNG。当测试涉及随机性且调用顺序敏感时，为每个测试单元创建独立的 Random 实例，而不是共享全局状态。

结语

这个故事的教训不是"我写了个 bug"。而是即使你有一万六千个通过的测试，你的基准测试仍然可能在撒谎——因为测试覆盖了所有 API 的正确性，但没覆盖测量工具本身的正确性。

修复 bug 让我从 17% 到 100%。但更有价值的收获是：100% 不是一个终点，它是一个起点。只有在噪声下，你才能看清算法的真实面貌。零噪声下的满分是集体幻觉——你需要扰动才能看到真相。

这和产品决策一样：当所有方案在理想 case 下都 work，你不能就此停步。你需要问："在 10% 的噪声下，哪个方案先崩溃？"

答案往往出乎意料。
