你的偏好没有关键词：Agent 记忆检索的语义旁路

Agent Memory 嵌入检索 RAG Benchmark 2026-08-22 · 基于 Research #083（86 题真实会话基准 + 可运行原型）· MiniLM / model2vec / LongMemEval 协议

问你的 agent："我之前说过更喜欢 Fender 还是 Gibson？" 它翻遍记忆库，返回三段上周的闲聊——唯独没有那段你在琴行门口聊"Fender 音色亮、Gibson 更厚"的对话。检索引擎没坏：那次对话和你的提问之间，没有任何一个词是重合的。你问的是乐器，证据聊的是逛店见闻——词形上隔着一整条类别鸿沟。这是 agent 长期记忆里一类真实存在的结构性缺口。本文讲我们怎么用一个 23MB 的嵌入模型把它填上（hit@5 从 60% 到 87%），路上撞见的两个反直觉发现——混合检索居然有害，快 69 倍的"查表模型"只差 4 题——以及一场几乎骗过所有人的基准事故。

一、缺口长什么样：不是检索差，是桥断了

把 agent 的长期记忆想成一座图书馆，检索是管理员。你提问，他拿着问题里的词去卡片目录里查。BM25、TF-IDF、token overlap——这套词法机制对"上次说的项目代号是什么"类问题非常好用，因为问题的词和证据的词高度重合。

但偏好类问题天然不适配。在这次实验的 86 道基准题（来自 LongMemEval 协议的真实合成会话，22002 个文本块、3983 段会话）里，preference 类 30 题，词法检索的 hit@1 只有 3/30，hit@5 也只有 18/30。这不是参数没调好——先前的取证已经证明，这 30 题里词法能做到"唯一最优命中"的只有 4 题。从问题到证据之间根本没有词形可走的路。

典型样本：问题是 "music store tips"（我在琴行聊过什么），标准答案会话的内容是 "Fender Stratocaster vs Gibson Les Paul"。类别词与实体词之间隔着一道语义鸿沟——每个 token 都对不上，但任何懂英语的人一眼就知道它们说的是同一件事。缺的不是记忆，是一座材质不同的桥：词法桥铺不过去的地方，语义桥可以。

二、换桥：384 维的语义旁路

方案朴素得出奇：用 all-MiniLM-L6-v2（23MB 的 int8 ONNX 模型，零 torch 依赖）把会话和问题各自编码成 384 维向量，算余弦相似度。工程上唯一值得注意的是chunk-max：长会话切成 150 词的块分别编码，会话得分取所有块的最大余弦——避免长文本把关键段落"平均稀释"。

语义真实性抽查也过了：把命中样本逐条人工看一遍，"music store tips" 命中 "Fender vs Gibson" 靠的是真实的类别-实体语义邻近，不是表面词巧合。这不是魔法——嵌入模型存在的前提就是学会"逛琴行"和"Fender"出现在相似的语境里。

三、反直觉发现一：混合检索不是默认答案

行业叙事里，hybrid retrieval（词法+dense 双路、RRF 融合）几乎是检索工程的"最佳实践"。但看上表第三行：RRF 融合的 hit@1 只有 10/30，比纯嵌入的 15/30 净损 5 题。

为什么？RRF 的机制是两路排名倒数融合——它隐含一个前提：两路信号都得有区分度。而 preference 类的词法臂 hit@1 只有 3/30，近乎随机。这时候融合就像让两位评委打分取平均：一位懂行，一位在掷骰子——骰子不会带来信息，只会稀释懂行者的意见。

于是集成策略不是"全局 hybrid"，而是 form-gated switch（按问题类型分流）：preference 类走纯嵌入旁路；ssa 类词法已 49/56、嵌入只负责补齐 @1。这个思路可以推广：要不要融合，应该由每一类问题各自的单臂基线决定，而不是由行业最佳实践决定。词法强的地方嵌入做增量，词法弱的地方嵌入做主干——配置面是分类器，不是融合参数。

四、反直觉发现二：快 69 倍的"查表字典"只差 4 题

第二个反直觉数字来自静态嵌入（static embeddings）：model2vec 家族的 potion-retrieval-32M。它的原理粗暴得可爱——把神经网络对每个 token 的理解预先算好，印成一本字典；句子向量 = 查表 + 取平均，没有任何神经前向计算。就像把一部电梯拆掉换成一截楼梯：没了电机，但大多数时候你只是上一层楼。

实测：2463 chunks/s，比 MiniLM 的 36 chunks/s 快 69 倍（22002 块从 611 秒降到 8.9 秒）；质量上 preference hit@1 是 11/30 vs 15/30——只差 4 题，仍是词法臂（3/30）的 3.7 倍。依赖面更是悬殊：numpy + safetensors + tokenizers 共约 30MB，不需要任何神经运行时。

这对部署小机器的 agent 是实打实的选择空间。工程上的落地形态是"双档可选依赖"：[sidechannel]（神经档，质量上限）与 [sidechannel-fast]（静态档，近实时），运行时探测装了哪个用哪个。"可选加速器"可以同时是"默认可用"——速度-质量谱系的两端都不是玩具。

五、一场几乎骗过所有人的基准事故

这篇实验的第一跑出了一个漂亮的数字：嵌入臂 hit@1 = 12/30，全组欢呼。一周后复核发现它是伪影。

事故链：一个数据处理 bug 把会话的 turn 字典展开成了 key 垃圾文本（"role content role content…"）→ 所有块的嵌入完全相同 → 余弦分数全部打平 → 排序退化到第二排序键 sid（会话 id）的字典序 → 而基准题目答案会话的 id 前缀 answer_* 恰好排在语料 id（ultrachat_* / sharegpt_*）前面 → 字母序凭空造出了 40% 的假命中率。

教训浓缩成三条，适用于所有做评测和排序系统的人：

  1. 好得可疑的数字，先查 tie-break。分数全同时，sorted 的第二键就是排序本身——一个没人审视过的 sid 在悄悄决定谁上榜。
  2. 基准 id 命名是隐藏变量。如果答案侧 id 与语料侧 id 在字母序上天然可分，tie-break 就有系统性偏置——务必随机化第二键，或确保分数连续。
  3. 每臂独立的 sanity 数字是伪影检测器。救了这次结论的是一个反常读数：词法臂在同一批坏数据上得了 0/86。一个"诚实到尴尬"的异常数字，价值高于一个漂亮的正常数字。

六、落地形态：写时嵌入，查询零成本

查询时现算嵌入在慢机器上要 7.5 秒/题，不可接受。但检索是读多写少的操作——把嵌入成本挪到写入时：会话落库的 ingest 钩子里顺手算好向量存起来，查询时只剩一次问题编码加一次矩阵乘，毫秒级。22k 块全量嵌入的内存峰值不到 400MB，1GB 的小盒也安全。旁路就此闭环：主干保持零 LLM、零神经运行时；需要语义桥的那几类问题，走一条 23MB 的小模型铺的路。

今天就能做的五件事

  1. 给你的检索问题分类，再谈架构。按问题类型（偏好/事实/时序/聚合）分别测词法单臂基线——某类 hit@1 掉到 1/3 以下，就是嵌入旁路的候选人。不要直接上全局 hybrid。
  2. 从 23MB 的 MiniLM 起步。fastembed + ONNX int8，无 torch 依赖，一台最破的 CPU 盒就能跑。速度不够再换静态嵌入（model2vec），先质量后速度的顺序通常不会错。
  3. 检查你所有打分器的第二排序键。搜代码里的 sorted(，看 tie 时排什么——如果是 id、时间戳或任何有命名规律的键，做一次"全同分"测试，看它是否在悄悄决定结果。
  4. 把嵌入挪到写入时。任何读多写少的检索系统都适用：ingest 时算向量存下来，查询路径只剩点积。
  5. 外部 benchmark 数字要在自有数据上复现一次。论文说嵌入有用，不等于在你的 form 分布上有用；复现一次，杠杆就从"引用"变成"证据"。

偏好没有关键词，但偏好有语义。当你的 agent 记不住你喜欢哪把吉他时，问题往往不在记忆力，在于桥的材质——而换一座桥，可能只需要 23MB。
