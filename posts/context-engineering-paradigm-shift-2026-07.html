上下文工程：Prompt Engineering 之后的下一个范式

2026-07-23 · 罗嵩 · Context Engineering AI Agent LLM 前沿研究
你精心打磨了 system prompt，调了 47 版 few-shot examples，温度设到 0.3——然后你的 Agent 还是在第 12 步搞砸了。不是因为它不够聪明，而是因为它的上下文窗口里塞满了垃圾。2026 年，研究者们终于说出了那个显而易见的结论：Agent 不是死于能力不足，而是死于上下文组装失败。

一、一个价值百万美元的问题

假设你在构建一个自主编程 Agent。它的任务是：在一个有 300 个文件的项目里修复一个 bug。

每次 LLM 调用时，你需要把以下信息塞进上下文窗口：

  • 系统指令（"你是一个专业程序员……"）——约 500 token
  • 工具描述（文件读取、搜索、终端……）——约 2000 token
  • 历史交互（前 11 步的所有操作和结果）——约 15,000 token
  • 当前文件内容——约 3000 token
  • 搜索结果——约 2000 token

看起来还行？但问题在第 12 步爆发了。Agent 突然开始"忘记"它之前看到的关键线索，重复执行已经做过的搜索，甚至回到之前已经放弃的错误路径。

这不是幻觉，这是上下文退化。信息并没有从窗口中消失，但被堆积的历史噪声"淹没"了。就像一个桌子上堆了太多文件——你要找的那份合同还在，但你就是找不到。

2026 年 7 月，一篇论文直接把这个问题摆在了台面上："AI Agents Do Not Fail Alone: The Context Fails First"。作者的核心论点很直接：

大多数 Agent 错误不是模型能力问题，而是上下文组装问题。错误的上下文产生错误的推理，错误的推理导致错误的行动。在 Agent 链路中，上下文是第一个失败的组件。

这不是一个孤立的观点。整个 2026 年上半年，arXiv 上以 "Context Engineering" 为关键词的论文出现了井喷——从上下文压缩到前瞻调度，从自主遗忘到权限分离，一个全新的研究方向正在成型。

二、从 Prompt Engineering 到 Context Engineering

为了理解这个转变，我们先做一个类比。

Prompt Engineering 就像写菜谱——你需要精确描述每一步操作："把鸡蛋打散，加盐 2 克，油温 7 成热，倒入蛋液翻炒 30 秒。"你关心的是：措辞、结构、示例的选择。核心假设是：只要指令足够清晰，模型就能做好。

Context Engineering 就像管理整个厨房——不仅是菜谱（指令），还有食材（数据）、厨具（工具）、厨师之前的尝试（历史）、冰箱里的存货（记忆）、以及隔壁桌客人刚点了什么（环境状态）。你关心的是：在厨师转身就能看到的地方，应该摆什么？

关键区别在于动态性。Prompt 是静态的——写好一次，反复使用。Context 是动态的——每次推理调用时都要重新组装。一个 Agent 在 50 步任务中的第 1 步和第 40 步，需要的上下文完全不同。

维度Prompt EngineeringContext Engineering
关注点怎么跟模型说话模型在每次推理时应该看到什么
时间性静态（一次写好）动态（每次调用重新组装）
核心技能语言艺术系统设计
类比写菜谱管理厨房
衡量标准单次回答质量多步任务成功率
失败模式回答不好上下文退化 → Agent 失控

这个转变不是语义游戏。2026 年 6 月的论文 "From Prompts to Contracts" 指出，企业级 Agent 应用正在经历一次形式化迁移：从"靠 prompt 携带行为逻辑"到"用合约定义上下文边界"。这意味着上下文开始有 schema、有审计、有测试——它正在从一个"调参技巧"变成一门工程学科。

三、上下文窗口是资源分配问题

明确了概念之后，下一个问题是：怎么管理上下文？

答案是把它当成一个资源分配问题，就像 CPU 调度或内存管理。一个 128K token 的上下文窗口，需要在以下维度分配预算：

┌──────────────────────────────────────────────────┐ │ 上下文窗口 Token 预算分配 │ ├──────────┬──────────┬───────────┬──────────────────┤ │ 任务指令 │ Few-shot │ 历史交互 │ 工具描述 │ │ ~500 │ ~1000 │ ~10000 │ ~2000 │ ├──────────┼──────────┼───────────┼──────────────────┤ │ 检索结果 │ 工作记忆 │ 环境状态 │ 安全约束 │ │ ~3000 │ ~2000 │ ~1000 │ ~500 │ └──────────┴──────────┴───────────┴──────────────────┘ ↕ 剩余空间用于推理过程（CoT 等）↕

问题在于：这个分配不是固定的。任务刚开始时，历史交互很少，空间充裕；到了第 30 步，历史交互可能占了 80% 的窗口，关键信息被挤出。这就像一个磁盘越来越满——不是没空间了，而是有用的数据被埋在了垃圾下面。

"Context by Distinct Information"（Pal & Rojkova, 2026.07）提出了一个更激进的观点：用 token 做内存单位本身就是错误的。100 个 token 的重复信息应该被压缩为 1 个"信息单元"。他们用 Dirichlet 过程实现了基于信息独特性的工作记忆——不是按 token 数量管理上下文，而是按信息价值管理。

这个思路跟操作系统从"按块管理内存"演进到"虚拟内存 + 按需换页"的历史如出一辙。

四、Agent 应该自己管理上下文

早期的上下文管理方案是被动的——当上下文窗口快满时，外部系统触发 summarization，把旧历史压缩成摘要。这就像妈妈每天帮你收拾书桌：你不需要操心，但你也不知道她扔了什么。

2026 年 1 月的 Focus agent 翻转了这个思路。它受到黏菌（Physarum polycephalum）的启发——这种生物会在食物丰富的地方扩展菌丝，在贫瘠的地方收缩。Focus agent 给 LLM 一个 "Knowledge block" 工具，让它自主决定：

  • 什么时候把当前交互的关键学习固化到 Knowledge block
  • 什么时候主动 withdraw（剪枝）原始交互历史
  • 保留什么、遗忘什么

实验结果令人振奋：在 SWE-bench Lite 上，Focus 实现了 22.7% 的 token 减排（从 14.9M 降到 11.5M），而准确率完全不变（3/5 = 60%）。平均每个任务执行 6.0 次自主压缩，个别实例节省高达 57% 的 token。

核心洞察：有能力自主管理上下文的模型，不需要外部 summarization 的"家长式管理"。给它工具，让它自己来——效果更好，成本更低。就像人会自然地遗忘不重要的细节、记住关键的教训——你不需要别人帮你清理大脑。

这个思路在 2026 年 7 月被多个系统进一步验证：

Twin Agent：权限分离的上下文压缩

Hu 等人提出的 Twin Agent 使用"双胞胎"架构——低权限 agent 做上下文压缩和过滤，高权限 agent 只看到精炼后的上下文。这是一种安全设计：即使压缩 agent 被注入攻击，也无法影响执行 agent 的核心决策。就像你有一个秘书帮你筛选邮件，但你的秘书看不到你的私人密码。

SWE-Pruner Pro：模型已经知道该剪什么

Wang 等人发现代码 LLM 其实"已经知道该 prune 什么"——不需要外部的 pruning 策略，模型内部就能识别哪些上下文是冗余的。论文标题一语双关："The Coder LLM Already Knows What to Prune." 这意味着上下文压缩不需要额外的模型或复杂的 pipeline，只需要给现有模型一个"修剪"工具。

CatalogAgent：从 Supervisor 学习注入上下文

CatalogAgent 通过 Supervisor agent 持续监控 Worker agent 的执行模式，把识别到的模式聚合为 "learnings"，然后把这些 learnings 注入到 Worker 的上下文中。这是一种上下文工程驱动的自我改进——不修改模型权重，通过动态注入"经验"让 agent 变强。

五、前瞻调度：上下文的"指令预取"

CPU 有一个经典的优化技术叫指令预取（Instruction Prefetch）——在执行当前指令时，提前把接下来几条指令加载到缓存。

SmoothAgent（Pan et al., 2026.06）把这个思路搬到了 Agent 场景。它提出了 "Lookahead Context Engineering"：

  1. 预测未来几步可能需要什么信息
  2. 提前加载这些信息到上下文
  3. 如果预测正确，Agent 在后续步骤直接命中"缓存"
  4. 如果预测错误，回退到按需加载

对于 50+ 步的长程任务，这可以显著减少端到端延迟。就像一个有经验的厨师，在炒菜的同时已经把下一步要用的调料拿出来了——而不是等上一步做完了才去翻冰箱。

更有趣的是，这种前瞻调度和世界模型（World Models）天然互补——世界模型负责"想象下一步会发生什么"，前瞻调度负责"根据想象提前准备上下文"。两者的结合可能是 2026 下半年的重要方向。

六、教 Agent "什么时候不做"

上下文工程不只是"放什么进来"，还包括"什么时候该停下来"。

"Agentic Abstention"（Luo et al., 2026.06）研究了一个被忽视的问题：Agent 知道什么时候该停止行动吗？

在 WebShop 实验中，研究者发现一个反直觉现象：更大的模型有时在"及时停止"这件事上表现更差。能力强的模型倾向于"多做一点"，结果在已经完成任务的情况下继续操作，反而搞砸了。这就像一个过于勤快的新员工——领导说"做完了"，他非要再"优化一下"，结果把好好的东西改坏了。

论文提出的 CONVOLVE 方法是一种上下文工程方案：从历史交互轨迹中提取可复用的停止规则，注入到当前上下文中。比如："如果搜索结果已经包含目标商品且价格匹配，停止搜索。" 这些规则不是硬编码的 if-else，而是从经验中自然蒸馏出来的。

这揭示了一个更深的道理：能力越强的 Agent，越需要上下文工程来约束自己。不是限制能力，而是给能力一个边界。

七、多 Agent 共享上下文：进程间通信问题

当我们从单 Agent 走向多 Agent 系统时，上下文工程面临一个新的维度：Agent 之间应该共享什么上下文？

"Shared Selective Persistent Memory"（Pedada et al., 2026.07）打破了一个隐含假设——每个 agent 有自己的独立上下文。实际上，在多 Agent 协作中，上下文应该是选择性共享的：

  • 广播级：任务目标、全局约束（所有 agent 都需要）
  • 团队级：子任务状态、共享工具结果（同组 agent 需要）
  • 个人级：具体操作历史、私有推理（单个 agent 独占）

这跟操作系统的进程间通信（IPC）极其相似。我们需要为 Agent 设计"上下文通信协议"——谁能看到什么、什么时候能看到、以什么格式看到。

实践原则：把 Agent 上下文当作进程地址空间来管理——有共享内存（shared context）、有私有内存（private context）、有消息传递（inter-agent messages）、有信号量（coordination signals）。这不是比喻，这是架构蓝图。

八、上下文健康度：Agent 的"体检指标"

如果上下文是 Agent 失败的首要原因，那我们应该监控上下文的健康度——就像运维团队监控 CPU 利用率和内存使用率一样。

综合现有研究的发现，我提出以下上下文健康指标：

指标定义告警阈值
信噪比有效信息 token / 总 token< 40%
冗余度重复信息占比> 20%
时效性最新信息 token / 历史信息 token< 15%
关键信息覆盖任务关键信息在窗口中的比例< 90%
上下文压力已用 token / 总窗口大小> 85%

当任何指标越过告警阈值时，系统应该触发上下文压缩、剪枝或扩窗。这比等 Agent 犯错后再调试要高效得多——就像在服务器 CPU 飙到 95% 时告警，而不是等它 OOM 崩溃。

九、上下文工程的实践建议

说了这么多研究，如果你现在就要改进自己的 Agent 系统，可以做什么？

1. 给 Agent 一个 "Knowledge Block" 工具

让 Agent 自己决定何时压缩历史。实现方式：提供一个 consolidate(learnings: str) 工具，Agent 调用后把当前关键发现写入持久化存储，同时清除对应的原始交互历史。Focus agent 已经证明这可以节省 20-50% 的 token。

2. 为上下文引入 Schema 标注

不要把所有信息都堆成无差别的文本。给每条上下文信息加元数据：[source=tool_result] [timestamp=step_12] [confidence=high]。这让未来的 pruning 和 compression 决策有据可依。

3. 实现"上下文体检"

在每次 LLM 调用前，快速检查上下文健康度。如果信噪比低于 40%，先做一轮压缩再发请求。这比盲目发送 100K token 然后得到低质量回答要划算得多。

4. 从历史轨迹提取"停止规则"

CONVOLVE 的思路可以直接落地：分析 Agent 的成功轨迹，提取"什么时候任务其实已经完成了"的信号，注入到未来的上下文中。防止 Agent 过度操作。

5. 低权限 Agent 做上下文过滤

参考 Twin Agent 的架构，用一个轻量级 LLM（如 Haiku 级别）做上下文压缩和过滤，核心 Agent 只消费精炼后的上下文。既省钱又安全。

结语：上下文是 Agent 的免疫系统

回顾整个研究脉络，一个清晰的图景浮现出来：

模型是大脑，上下文是血液。大脑再聪明，如果血液里充满了毒素（噪声信息）或者缺少氧气（关键信息），也一样会做出糟糕的决策。

2026 年的 Context Engineering 研究告诉我们：

  1. 上下文失败先于 Agent 失败——监控上下文健康度可以在问题发生前预警
  2. Agent 应该自主管理上下文——被动 summarization 已经过时，主动压缩才是未来
  3. 上下文工程正在形式化——从 prompt 调参走向有 schema、有合约、有审计的工程实践
  4. 前瞻调度是下一个突破——预测未来需要什么，比事后补救更高效
  5. 多 Agent 需要上下文通信协议——借鉴操作系统 IPC 设计，实现选择性共享

如果你正在构建 Agent 系统，现在最值得投入的一件事不是换个更强的模型，而是把你的上下文工程做好。一个用 70B 模型但上下文管理优秀的系统，大概率比用 frontier 模型但上下文混乱的系统表现更好。

这不是直觉，这是 2026 年多项研究的共同结论。
