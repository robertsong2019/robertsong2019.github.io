当代码图谱遇见 Agent 记忆：两个孤立世界的合并将开启下一个万亿 token 市场

2026-08-04 · Agent Memory Code Knowledge Graph Code-Aware Memory Procedural Memory TypeScript

2026 年 7 月，Claude Code v2.1.88 的源码泄露（512K 行 TypeScript），揭开了这个最强大的编码 Agent 的记忆架构。结果让所有人意外：它的记忆系统不过是 Markdown 文件 + 关键词搜索。与此同时，代码知识图谱（Code KG）社区和 Agent 记忆图谱社区各自繁荣，却几乎不相交。本文论证：这两个世界的合并不是"锦上添花"——而是 Token 经济学强制下的必然收敛。 包含完整的 TypeScript 实现方案和商业化分析。

一、一个让人尴尬的发现

Claude Code v2.1.88 的泄露源码揭示了一个四层记忆架构：

CLAUDE.md (手动规则文件)
    ↓
Auto Memory (4 类别，200 行索引上限)
    ↓
Auto Dream (后台整理，>24h + >5 sessions 触发)
    ↓
KAIROS (未发布的常驻守护进程，150+ 源码引用)

没有语义搜索。没有 embedding。没有向量数据库。没有知识图谱。

它的记忆系统就是：读 Markdown 文件 → 关键词匹配 → 注入 prompt。200 行的硬性上限逼迫它不断压缩。Auto Dream 本质上是一个后台 LLM 调用，把 "昨天说的那个 bug" 解析为 "2026-07-30 修复的 authentication token expiry bug"，然后更新 Markdown。

这不是讽刺——这是刻意的设计权衡。人类可读、可 git 提交、可预测。对于 200 行以内的记忆，关键词搜索的 ROI 确实高于语义搜索。

但问题来了：当 Agent 的经验超过 200 行时怎么办？

答案是：它不会超过。因为 Claude Code 的记忆架构设计就没打算处理大规模经验。这就像一个人的工作记忆只能容纳今天的事情——超过的部分被永久遗忘。

二、两个孤岛

在 Claude Code 的记忆架构被揭露的同时，两个研究社区各自繁荣着：

孤岛 A：代码知识图谱（Code KG）

代表项目： CodeGraph、Codebase-Memory、RepoGraph、Prometheus

核心问题： "代码长什么样？"

技术栈： tree-sitter、LSP、AST 解析、静态分析

成果：

  • CodeGraph：工具调用减少 89%，成本降低 60%，token 消耗减少 69%
  • Codebase-Memory：372 个问题上平均 token 减少 121 倍
  • Prometheus：工作记忆层跨推理步骤保留已探索的上下文

三、为什么它们必须合并

3.1 Token 经济学

大模型的 context window 在增长（GPT-5: 2M tokens，Claude 4.5: 1M tokens），但 token 成本也在增长。一个中型代码库（100K 行）的完整 context 约 3M tokens——即使放进 context window，每次交互也要花费 $15-50。

CodeGraph 的数据证明了这一点：使用代码知识图谱可以将 token 消耗降低 69%。Codebase-Memory 更夸张——121 倍的 token 减少。

但 Code KG 只解决了 "代码长什么样" 的 token 问题。它不解决 "Agent 上次怎么改这段代码的" 或 "为什么这个函数被废弃了" 的问题。

              Token 消耗对比（每次交互）

完整 context 注入     ████████████████████  ~3M tokens ($15-50)

Code KG 辅助          ██████               ~930K tokens ($5-15)
                      (-69%)

Code KG + Agent Mem   ██                   ~97% 减少
                         (预测值)

当两个 69%+ 的优化叠加时，Token 成本从 "不可持续" 变为 "可忽略"。 这是经济学上的强制收敛。

3.2 推理质量

纯 Code KG 的 Agent 知道 function A calls function B，但不知道：

  • 上次修改 A 时引入了什么 bug？
  • 为什么团队决定用这种设计模式而不是另一种？
  • 哪些代码路径已经被探索过且确认不需要改？

纯 Agent Memory 的 Agent 记得上次做了什么，但不知道：

  • 这次改动会影响哪些下游函数？
  • 这个文件的整体结构是什么？
  • 有没有未执行的测试路径？

合并后的 Agent 可以回答： "我 3 小时前探索了 auth/token.ts，发现了 token expiry 的 bug，修复了 validateToken() 函数。这个函数被 middleware/auth.ts 和 api/user.ts 调用。两处调用都依赖 Token.expiry > Date.now() 的判断。上次测试通过了，但如果 expiry 精度从毫秒改到秒，api/user.ts 的边界条件可能出问题——因为 3 天前我修过那个边界。"

这种推理需要代码结构（Code KG）和 Agent 经验（Agent Memory）同时在场。

四、统一架构：Code-Aware Agent Memory Graph

4.1 图的扩展

一个统一记忆图不需要新发明什么——只需要扩展现有图的节点和边类型：

// 节点类型扩展
type NodeType =
  // 原有时序记忆节点
  | { kind: 'episode'; content: string; timestamp: number }
  | { kind: 'fact'; content: string; confidence: number }
  | { kind: 'preference'; content: string }
  // 新增代码节点
  | { kind: 'code_function'; name: string; file: string; hash: string }
  | { kind: 'code_module'; name: string; path: string }
  | { kind: 'code_class'; name: string; file: string }

// 边类型扩展
type EdgeType =
  // 原有记忆边
  | { kind: 'derived_from'; from: string; to: string }
  | { kind: 'relates_to'; from: string; to: string }
  // 新增代码结构边
  | { kind: 'calls'; from: string; to: string }        // A calls B
  | { kind: 'imports'; from: string; to: string }       // A imports B
  | { kind: 'defined_in'; from: string; to: string }    // A defined in file B
  // 新增 bridging 边（关键！）
  | { kind: 'decided_by'; from: string; to: string }    // code A ← decision B
  | { kind: 'explored'; from: string; to: string }      // code A ← explored by episode B
  | { kind: 'fixed_by'; from: string; to: string }      // bug A ← fixed by episode B

decided_by 边是桥梁。 它连接代码世界（"这个函数为什么这样写"）和经验世界（"因为 Agent 在某次 session 中做出了这个决策"）。这种边在两个孤立系统中都不存在。

4.2 三个 API，一个新市场

基于上述扩展，只需要三个 API 就能打开 "Code-Aware Agent Memory" 这个新品类：

API 1: explainCode(nodeId) — 代码溯源

/**
 * 解释一段代码的来龙去脉：
 * - 谁在什么时候创建/修改了它？
 * - 关联的决策是什么？
 * - 有哪些 bug 修复记录？
 * - 下游影响范围？
 */
function explainCode(nodeId: string): CodeExplanation {
  const node = graph.get(nodeId);
  
  // 向上追溯：哪些 episode/decision 影响了这段代码
  const decisions = graph.traverse(nodeId, {
    direction: 'incoming',
    edgeTypes: ['decided_by', 'fixed_by', 'explored'],
    maxDepth: 2
  });
  
  // 向下分析：这段代码影响什么
  const impact = graph.traverse(nodeId, {
    direction: 'outgoing',
    edgeTypes: ['calls', 'imports', 'defined_in'],
    maxDepth: 3
  });
  
  // 利用已有的 provenance 工具
  const lineage = derivationLineageReport(nodeId);
  
  return {
    code: node,
    why: decisions.filter(d => d.kind === 'episode'),
    bugs: decisions.filter(d => d.edgeType === 'fixed_by'),
    impactScope: impact,
    lineage: lineage.summary,
    bottleneckScore: lineage.bottleneckScore
  };
}

实现量：~30 行，包装已有的 trace_derivation + 图遍历。

API 2: impactAnalysis(nodeId) — 变更影响分析

/**
 * 如果修改了 nodeId，什么会受影响？
 * 基于 calls/imports/depends_on 边做 BFS 级联分析。
 */
function impactAnalysis(nodeId: string): ImpactReport {
  const cascade = graph.bfs(nodeId, {
    direction: 'outgoing',
    edgeTypes: ['calls', 'imports', 'depends_on'],
    maxDepth: 5
  });
  
  // 按距离分层报告
  const layers: Record<number, GraphNode[]> = {};
  for (const { node, depth } of cascade) {
    (layers[depth] ??= []).push(node);
  }
  
  // 标记高风险节点（被多处依赖）
  const fanOut = graph.outDegree(nodeId);
  const isBottleneck = fanOut / Math.max(graph.inDegree(nodeId), 1) > 1;
  
  return {
    directDependencies: layers[1] ?? [],
    transitiveImpacts: layers,
    totalAffected: cascade.length,
    bottleneckWarning: isBottleneck
      ? `⚠️ 修改 ${nodeId} 可能影响 ${cascade.length} 个下游节点`
      : null,
    structuralImportance: entropyContribution(nodeId)
  };
}

实现量：~25 行，包装已有的 BFS 遍历 + entropy_contribution。

API 3: recordCodeDecision(codeIds, content, confidence) — 决策记录

/**
 * 当 Agent 做了一个涉及代码的决策时，
 * 创建经验节点并连接到相关代码节点。
 */
async function recordCodeDecision(
  codeIds: string[],
  content: string,
  confidence: number = 0.8
): Promise<string> {
  // 创建经验节点
  const episodeId = await memory.add({
    kind: 'episode',
    content,
    confidence,
    timestamp: Date.now(),
    metadata: { type: 'code_decision' }
  });
  
  // 创建 bridging 边
  for (const codeId of codeIds) {
    await memory.link(episodeId, codeId, {
      kind: 'decided_by',
      validAt: Date.now()
    });
  }
  
  return episodeId;
}

实现量：~20 行，调用已有的 add + link。

三个 API 总计 ~75 行新代码。 零新依赖。零算法变更。所有已有的 entropy/provenance/classification 工具自动适用于代码节点。

五、最有商业价值的缺口：程序性记忆

比 "代码 + 记忆" 更进一步的，是从 Agent 经验中提取可复用的程序性记忆（Procedural Memory）。

Mem0 的 2026 年报告明确指出：编码 Agent 的程序性记忆仍处于 "早期阶段"。当前没有任何系统做到：

观察团队的工作模式 → 提取为可复用的技能 → 在类似场景中自动应用。

比如：

  • 团队总是在 commit 前运行 npm test
  • PR 遵循 conventional commits 格式
  • 测试放在 __tests__/ 目录下
  • 新 API 需要写 JSDoc 注释

这些模式目前需要人类口口相传，或者写在 CONTRIBUTING.md 里被忽略。一个有 Code-Aware Memory 的 Agent 可以从观察中学习这些模式，因为代码领域的反馈信号是二值的（测试通过/失败、构建成功/失败）——这是模式提取的理想环境。

// 程序性记忆提取（概念实现）
async function extractCodePattern(
  episodes: Episode[]
): Promise<ProceduralPattern | null> {
  // 1. 从历史 episodes 中提取重复模式
  const patterns = await llm.extract(`
    Given these ${episodes.length} coding sessions,
    identify recurring workflow patterns:
    ${episodes.map(e => e.content).join('\n---\n')}
    
    Focus on: commit conventions, test patterns, 
    file organization, code review habits.
  `);
  
  // 2. 验证：这些模式是否在代码库中得到印证？
  const verified = patterns.filter(p => 
    verifyPatternInCodebase(p)
  );
  
  // 3. 如果验证通过，提升为程序性记忆节点
  if (verified.length > 0) {
    return await memory.add({
      kind: 'procedural_pattern',
      content: verified[0].description,
      confidence: verified[0].confidence,
      source: 'observed_pattern',
      evidence: verified[0].proof
    });
  }
  
  return null;
}

AEL 论文的研究表明，技能提取在噪声大的领域会退化 15%。但代码是低噪声领域——测试通过或不通过，构建成功或失败。这使得代码成为程序性记忆提取的最高 ROI 应用场景。

六、为什么这还没有发生

如果合并这么明显，为什么没人做？

三个结构性壁垒：

  1. 社区隔离。 Code KG 研究者发 SOSPE/ESEC/FSE，Agent Memory 研究者发 NeurIPS/ACL。两个群体的线下会议不重叠，引用网络不交叉。
  2. 技术栈不兼容。 Code KG 用 tree-sitter/LSP/编译器前端；Agent Memory 用 embedding/向量数据库/图谱数据库。让一个团队同时精通两者很难。
  3. 产品定位模糊。 Code KG 面向 IDE 插件和代码搜索；Agent Memory 面向 chatbot 和 Agent 框架。谁需要 "Code-Aware Agent Memory"？答案是：自主编码 Agent（Autonomous Coding Agents）——一个 2026 年才大规模出现的产品形态。

Claude Code、Cursor Agent、Devin、OpenHands——这些产品同时需要理解代码结构和记住 Agent 经验。它们的记忆系统目前要么是 Claude Code 式的 Markdown 文件，要么是 Mem0 式的纯语义记忆。没有人做到两者的深度融合。

七、总结：75 行代码，一个新品类

回到 Claude Code 的 200 行 Markdown 记忆。它的工作范围是：今天的对话 + 一些手动规则。超过这个范围的，遗忘。

三个 API，~75 行代码，零新依赖。 这不是技术挑战——这是想象力挑战。两个社区各自建造了半座桥，但没人走完中间的 75 步。

当有人走完这 75 步时，一个新的市场品类就诞生了：Code-Aware Agent Memory。它的第一批客户是每一个构建自主编码 Agent 的团队——在 2026 年，这个数字正在指数增长。
