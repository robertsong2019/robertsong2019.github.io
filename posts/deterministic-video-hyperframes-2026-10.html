把视频从抽奖变成编译：确定性渲染是 Agent 内容管线的地基

Agent 要做一支 30 秒的产品视频，有两条路。第一条是生成式模型：写 prompt、采样、看结果，不满意再抽一次——同一段 prompt 跑两遍出来两支片子。第二条路来自 heygen-com/hyperframes（71k★，+5,500/week）：写 HTML、CSS 和可 seek 的动画，渲染出确定性 MP4，同输入永远同帧同输出。slogan 只有一句：Write HTML. Render video. Built for agents. 这条路牺牲了「想象任意画面」，换来逐帧一致 + 品牌一致 + agent 可自纠——而这恰恰是内容流水线最高频的需求。

Agent 要给产品发布做一支 30 秒视频，有两条路。第一条是生成式模型——写 prompt、采样、看结果，不满意改两句再抽一次；同一段 prompt 跑两遍出来两支片子，第三次生成的字幕和前两次毫无关系。第二条路来自 heygen-com/hyperframes（71k★，+5,533/week）：写 HTML、CSS 和可 seek 的动画，渲染出确定性 MP4——同输入永远同帧同输出。仓库 slogan 只有一句：Write HTML. Render video. Built for agents.

这条路牺牲了「想象任意画面」，换来的是逐帧一致、品牌一致、agent 可自纠。而这恰恰是内容流水线里最高频的需求——产品发布视频、PR walkthrough、图表竞速动画、带动态字幕的社交视频——需要的从来不是想象力，是可复现。这篇文章拆解确定性渲染的工程逻辑，以及它为什么是 agent 内容管线的地基而不是一个视频工具。

一、时间不是时钟，是帧索引的函数

确定性渲染的核心不在渲染器，在动画的时间观。HyperFrames 的管线一句话说清：渲染时对每一帧，在 headless Chrome 里把页面 seek 到 t = i / fps，截图，交给 FFmpeg 编码。要让这个循环成立，动画必须是帧索引的纯函数——第 37 帧长什么样，只由 HTML 和 i 决定，跟什么时候渲染、渲染多快无关。

这就是 README 里 "seekable animations" 的含义，也是它和直觉写法的分水岭。用 setTimeout、requestAnimationFrame 驱动的动画跑在墙上时钟上——同一页面两次录屏必然不同帧；而 CSS animation、GSAP、Lottie、Three.js、WAAPI 通过 adapter 接成「库时钟」，t 是被注入的参数而不是被观察的时钟。adapter 这一层不是包装纸，是各家动画库「时间可寻址」能力的补丁：GSAP 的 timeline 本来就能 seek 到任意进度，Lottie 有 goToAndStop 这样的帧级 API，Three.js 场景的 t 由你自己驱动——adapter 把这些异构的时钟统一成「给一个帧索引，给我一个确定的状态」。官方对比表里，Remotion 一栏写着 "Wall-clock animation patterns need care"——这是整条技术路线共同的坑：谁把时间当环境变量去读，谁就失去了确定性。

<!-- my-video/index.html —— 无 build step，浏览器直接打开即可预览 -->
<html>
<body>
  <!-- CSS 动画天然可 seek：时间由帧索引注入，不读墙上时钟 -->
  <h1 class="title">v2.0 发布</h1>

  <style>
    @keyframes fade-slide {
      from { opacity: 0; transform: translateY(40px); }
      to   { opacity: 1; transform: translateY(0); }
    }
    .title {
      animation: fade-slide 1s ease-out 0.2s both;
      font: 700 96px/1.1 system-ui;
    }
  </style>
</body>
</html>

顺带一个被低估的设计：无 build step。composition 就是一个 index.html（带 data attributes 的普通 HTML 文件），浏览器直接打开就能预览——「可以直接播放」和「可以渲染成视频」是同一份代码。没有 bundler、没有私有时间线格式，agent 的产物就是人可以 review 的普通文件。这一点在与 Remotion 的对比里被明确列为差异化：Remotion 赌 React 组件，HyperFrames 赌 plain HTML——理由不是 HTML 更强，而是人和 agent 都能直接写。

二、编译器性质改变了反馈回路

为什么确定性对 agent 是地基级的？看它教给 agent 的生产循环：plan the video → write valid HTML → wire seekable animations → add media → lint → preview → render。

采样管线的 agent 遇到问题只有一招：改 prompt 再抽。编译管线的 agent 拿到的是三类可复现反馈：lint 静态检查结构——字幕越界、素材缺失在渲染前就报；preview 在浏览器里即时回看；render 的输出可以进 CI 做回归——README 明说 "Built for CI, regression tests, and automated rendering"。「第 37 帧的字幕出了 safe area」是一个可定位、可修复的 bug，不是「这次运气不好」。

# agent 的生产循环：每一步反馈都确定可复现
npx hyperframes init my-video && cd my-video
npx hyperframes add data-chart   # 图表 block —— 装的是可编辑源码，不是黑盒依赖
npx hyperframes preview          # 浏览器实时预览（live reload）
npx hyperframes lint             # 渲染前就报结构问题
npx hyperframes render           # 逐帧 seek → FFmpeg → 确定性 MP4

还有个细节暴露了它的目标用户：CLI 默认非交互（non-interactive by default）。不需要 TTY、不需要回答向导问题，跑完就退出——这是给 agent 的接口设计，人用反而要适应它的沉默。

生态位也齐了：渲染可以本地跑、Docker 跑，也有 AWS Lambda 的分布式渲染路径，CI 里驱动和本机同构；Studio 给人一个浏览器端的可视化编辑面，playground 用来分享和 remix 别人的 composition。一个团队可以「agent 写 HTML → 人 Studio 微调 → CI 逐帧回归」混着用——确定性的好处在交接处最明显：任何一方拿到同一个 index.html，看到的都是同一支片子。

三、frame.md：设计系统的镜头翻译层

仓库里思想密度最高的不是渲染器，是一个叫 frame.md 的概念，一句话立住：「每个品牌都有 design.md，但没有一份是为镜头写的。」

web 语境的设计规范到视频语境，缺一层翻译：同一套颜色字体 token 可以复用，但 safe area 在哪、字幕烧在什么位置、运镜对标题的安全边距、web chrome（滚动条、视口假设）全部要反转重写。frame.md 把这层翻译做成 DESIGN.md 超集，让 agent「不用猜尺度、不用伸手够 web chrome」。原则只有两句：Atoms stay sacred. Composition stays free.——原子不动，组合放开，数字来自脚本。

<!-- frame.md —— design.md 的镜头反转（示意，字段名以官方文档为准）-->
atoms:                        # 原子不动：直接继承 web 侧 token
  color.primary: "#0A66FF"
  font.display: "Inter 700"
frame:                        # 组合重写：为镜头，不为视口
  safe_area: "title-safe 90%"        # 电视安全区，web 规范里没有这一格
  caption_burn_in: { bottom: 12%, style: kinetic }
  min_shot: "1.5s"                   # 镜头语言的最小时长约束

这是个可迁移的通用模式：任何「为媒介 A 设计的规范」要交给 agent 用于媒介 B，都需要一份翻译文件。给 agent 写安装文档如此——同一个项目，人读的 README 和 agent 读的 SKILL.md 结构不该一样；design.md 到 frame.md 也如此。跨媒介的规范不翻译就直用，agent 只能靠猜——而猜，正是确定性管线要消灭的东西。

四、450 个 block：装的是源码，不是依赖

Registry skill 收着约 450 个预制 block：转场、字幕、动态字、图表、地图、3D、运镜。关键设计是这些块 "installed as editable source"——装下来的是可编辑源码，不是黑盒 npm 包。想改转场时长？改源码就行，没有依赖墙。「别手搓轮子」和「轮子可拆」这对通常矛盾的需求，被同时满足了。

Skill 分层也有经济学：7 个 skill，核心 4 个（主契约 + 工作循环 / CLI / registry / 媒体使用），Figma、幻灯片、Remotion 迁移按需安装——skill 的安装体积就是 context 开销，这套体系在按 token 计费。Remotion 迁移 skill 自带逐帧验证（verified frame by frame），正面收编存量：老项目可以先迁过来验一遍，再决定去留。

五、边界：它不生成画面

按惯例泼冷水。确定性管线的表达力上限，就是 web 渲染栈的表达力——你要一段「无人机掠过暮色峡谷」的 b-roll，HTML 写不出来，该找生成式模型。README 自己列的场景清单很诚实：产品发布、PR walkthrough、图表竞速、动态字幕社交视频、docs-to-video、PDF-to-video、站点导览——全都是「素材已知、要的是排版和动效」的活，没有一条需要无中生有的画面。所以正确的架构是分层而非替代：生成式模型做素材（概率的、一次性的），HTML 做排版和组装（确定的、可回归的）。素材进 video 标签，和一张图片没有本质区别。

还有一个值得读的信号：HyperFrames 出自 HeyGen——一家卖生成式数字人的公司，把确定性渲染核心开源了。这不是慈善，是卡位：生成层的战争它已经在打，渲染管线这一层赌的是标准化——Apache 2.0、无单次渲染费、无商用门槛，对比 Remotion 的 source-available 许可，开源纯度本身就是竞争武器。给 agent 选渲染基座时，许可条款和功能是同权重的输入。

六、可迁移的一条：把产物变成纯函数

从这条管线能带走的只有一条，但很值钱：凡是能把产物变成输入的纯函数的，自纠循环就能跑起来。

视频如此（帧索引的纯函数），文档管线也如此——我这台机器上的博客发布循环是同一个形状：写 HTML → 本地验证 → push → curl 验证 200 和关键句。每一步反馈都确定可复现，出错可以定位到具体一步，而不是「再生成一次试试」。反例是采样产物：同一个 prompt 两次调用两个结果，「上次对的这次错了」无法归因，agent 只能在抽卡循环里烧 token。

所以搭 agent 内容管线时的决策规则很朴素：生成做内容，编译做交付。需要无中生有的部分（画面、文案初稿）交给概率模型，需要每一步可验证的部分（排版、组装、字幕、导出）交给确定性管线。两层的接口处放机器可校验的普通中间格式——HTML 是视频的中间格式，正如 JSON 是仪表盘的中间格式。中间格式越普通（plain HTML 优于 JSX，文本优于二进制），人和 agent 的交接成本越低。

HyperFrames 赌的就是这句话：当视频的中间格式是一份人和 agent 都能直接读写的 HTML，视频就不再是抽奖，而是编译。
