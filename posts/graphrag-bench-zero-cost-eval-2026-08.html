零成本评测 GraphRAG：逐行读完官方评测器源码，我挖出五个坑

GraphRAG Benchmarks LLM-as-Judge 工程实践 2026-08-15 · 基于 GraphRAG-Bench（ICLR 2026）官方评测器源码逐行解析 + 真实数据冒烟验证

假设你自研了一套 GraphRAG 系统，想在 GraphRAG-Bench 上验一验成色。先算一笔账：20 部小说、82 万词的语料要用 LLM 抽取实体和关系，2010 道题每道还要请 judge 模型判两三次分——管线还没跑起来，API 账单已经先到了。但如果我告诉你，这条路可以一分钱 API 都不花，而且不是 hack，是官方原生支持的呢？前提只有一个：把评测器的源码读穿。

一、评测器到底在评什么：三次电话，一张考卷

GraphRAG-Bench 的检索评测（retrieval_eval）只有两个指标，但背后是每个样本三次独立的 LLM judge 调用：

指标机制judge 调用数
Context Relevancyjudge 对（问题, 上下文）打 0/1/2 分，两次独立评分取平均，除以 2 归一到 0-12 次
Evidence Recalljudge 逐条判定标准答案里的 evidence 能否从上下文推出，recall = 可推出条数 / 总条数1 次

打个比方：这像请了两位阅卷老师分别给卷面独立打分再取平均，外加一位核查员逐条检查你的答案有没有出处。两个指标都会把上下文截断到 2 万字符，都要求 judge 输出严格 JSON，解析失败还有两次自愈重试。

关键的一点：被评对象是预测文件里的 context 字段——也就是你的系统检索回来的东西。评测器不关心你怎么检索、用什么数据库，它只看"你交上来的上下文"。这意味着评测结果的可信度，取决于你有没有读懂它的评分规则。

二、"零成本"不是口号，是源码事实

把管线拆成三段，逐段检查成本：

  • 索引段：规则模式抽取实体关系，纯代码，零 LLM 调用。实测 3 部小说 12 万词 → 2946 节点 / 153 边，2.2 秒；外推 20 部全量约 15 秒；
  • 检索段：图查询 + 打分，每题约 0.06 秒，100 题不到 5 秒；
  • 评测段：官方评测器原生支持 --mode ollama——本地模型当 judge，不是绕过官方，走的就是官方通道。

这里有个读源码才能发现的细节：评测器的命令行参数里 embedding_model 看起来是必填项，但在 retrieval 这两个指标的代码路径里，embeddings 对象传进去之后从未被调用——一个彻底的死参数。就像装修时预留的灯位：开关装了，灯泡从来没拧上去。judge 判分只靠语言理解，根本不需要向量。

所以整条管线的成本清单是：磁盘上躺一个本地 judge 模型的权重，外加电费。对，就这么多。

三、五个坑：每个都写在源码里

坑一：子串归零的防作弊条款

源码里有一行冷酷的判断：if context_str.strip() in question: return 0.0——如果你的检索上下文恰好是问题的子串，直接零分。这是防作弊设计（防止把问题原样塞回上下文骗 judge），但也提醒你：检索结果里任何"复读问题"的成分都是毒药。

坑二：num_samples 不是你以为的抽样

评测器的 --num_samples 语义是先按题型分组、每组取前 N，不是全局取 N。数据集 2010 题分四种题型，你以为评了 100 题，实际是 4×N。正确姿势是在自己管线侧先做确定性抽样（固定 seed，按 id 排序后抽），产出固定题目集，评测时不传 num_samples——这样报告天然按题型分组，且完全可复现。

坑三：双采样方差与 NaN 隐身

Relevancy 的两次独立评分取平均，本身是为了压方差，但本地小模型当 judge 时两次评分容易打架，抖动反而被放大。更隐蔽的是：两次都解析失败会得到 NaN，聚合时用 np.nanmean 跳过——报告照常输出，不报错、不告警，有效样本数悄悄缩水。像一套只统计到场者的考勤系统：缺席的人根本不出现在点名名单上，出勤率看起来永远是满分。不开 --detailed_output 你永远发现不了。

坑四：judge 模型决定分数的"汇率"

官方榜单大概率用 GPT-4o-mini 判分。你用本地 7B 模型跑出的绝对分数会系统性偏低——小模型 JSON 输出不稳、打分保守。但这不意味着本地评测没意义：固定同一个 judge，版本间对比完全可靠，因为你比的是相对变化，不是绝对汇率。正式对外提交前，切一次 API 模式复测（约三百次调用，成本不到一美元），把本地分数换算成官方口径即可。省钱靠本地，对账靠远程。

坑五：格式错位——最深的坑

很多 GraphRAG 系统的检索输出是"实体卡"：格式化的实体清单，如 ## Relevant Entities / - 哈利 (人物)。而评测集里的 evidence 是完整句子。judge 被问的是"上下文能否推出这句 evidence"，实体卡天然吃亏——就像被问"这本书里有没有这句话"，而你递过去的是一张人物关系表。信息是对的，形态是错的，分数是低的。

修法很直接：在 context 里附上边的三元组原文（主语 → 关系 → 宾语），把"卡片"还原成"句子形态的证据链"。如果你的系统记了 provenance（每条边来自哪个原句），十几行代码就能加上。

四、瓶颈会转移到你没想过的地方

整条管线实测下来：20 部小说索引约 15 秒，100 题检索不到 5 秒，而 100 题 × 3 次 judge 调用在本地 7B 模型上要 10-20 分钟。结论有点反直觉：瓶颈不在检索管线，在 judge 基建。高速公路全线通车了，最后一个收费站还在用人工窗口。

更妙的是，首跑前的准备清单只剩一条命令：装 ollama，pull 一个 7B 模型。索引、检索、schema 对齐这些"看起来最重"的活，全部在秒级完成。评测系统的工程重心，早就从"跑得动"转移到了"判得准、对得上账"。

# 首跑收尾：唯一缺的一步
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5:7b   # 内存 8G 够用；想对齐榜首配方可上 14B

# 零 API 评测
python -m Evaluation.retrieval_eval \
  --mode ollama --model qwen2.5:7b \
  --base_url http://localhost:11434 \
  --embedding_model bge-m3 \
  --data_file results/amg.json \
  --output_file results/retrieval_eval.json \
  --detailed_output

五、今天就能做的三件事

  1. 20 分钟冒烟：从官方仓库直接拉 3 部小说、10 道题（GitHub raw 直连，不需要装 HF 工具链），验证你的管线能产出评测器要求的字段格式——id、question、question_type、context、evidence，一个都不能少；
  2. 装一个本地 judge：ollama + 一个 7B 模型，把评测闭环先转起来。第一份分数不用好看，用来当版本迭代的对照组；
  3. 盯住 Evidence Recall：如果它明显低于 Context Relevancy，先别怀疑检索质量——按坑五的思路检查 context 的形态，把三元组原文加进去再跑一次。多数"检索不行"的结论，其实是"格式不对"的误诊。

最后回到开头那笔账。评测的壁垒从来不在 API 预算，而在于你有没有把评测器的源码读穿——读穿之后会发现，真正贵的是判断力，不是账单。
