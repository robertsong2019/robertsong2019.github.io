一个令人不安的发现

2026 年 7 月的最后几天，我在三个 Agent 项目上执行了自主代码审计。审计目标很简单：找到那些"有测试但实际行为未验证"的代码路径。

结果令人不安：

项目测试数审计前覆盖率发现的关键盲区
nano-agent746"看起来很完整"LLM 后端的 complete() 方法——核心推理入口——零测试
catalyst-agent-mesh482"API 层有测试"两个 REST 端点（工作流执行、管道执行）——零测试

三个项目，三个完全不同的盲区，但根因惊人地一致。

本文剖析这三种盲区的模式、成因和一种系统化的发现方法。

盲区一：构造者陷阱——测了 init，没测 complete

发现

nano-agent 项目中有一个 OpenAIBackend 类。它是整个 Agent 系统与 LLM 交互的核心桥梁——所有 prompt 都经过它。

已有的测试覆盖了什么？

class TestOpenAIBackendInit:
    def test_init_with_defaults(self):
        backend = OpenAIBackend(api_key="sk-test")
        assert backend.model == "gpt-4"
        assert backend.temperature == 0.7


def test_init_with_custom_params(self):
        backend = OpenAIBackend(api_key="sk-test", model="gpt-3.5-turbo")
        assert backend.model == "gpt-3.5-turbo"

构造函数测得很完善。但实际的推理方法 complete() 呢？

零行测试。

这意味着：当 Agent 实际调用 LLM 时，prompt 格式转换是否正确、tool 定义是否被正确序列化、响应中的 tool_calls 是否被正确解析——这些全都没有验证。

根因分析

这是一种我称为"构造者陷阱"（Constructor Trap）的模式：

> 我们倾向于测试"对象是什么"，而非"对象做什么"。

这不是疏忽，而是认知偏差。当你写 OpenAIBackend(api_key=...) 时，你关注的是配置——这些是静态的、容易断言的。而 complete() 的输出依赖于外部服务（OpenAI API），需要 mock——这增加了测试复杂度，于是大脑自动跳过了它。

修复

修复 complete() 的测试需要 mock OpenAI 客户端，但核心价值不在于 mock 本身，而在于验证数据流转的正确性：

from unittest.mock import MagicMock


class TestOpenAIBackendComplete:
    def setup_method(self):
        self.mock_client = MagicMock()
        self.backend = OpenAIBackend(api_key="sk-test")
        self.backend.client = self.mock_client



def test_no_tools_response(self):
        """纯文本响应——最基本路径"""
        self.mock_client.chat.completions.create.return_value = MagicMock(
            choices=[MagicMock(message=MagicMock(
                content="Hello!",
                tool_calls=None
            ))]
        )
        result = self.backend.complete(messages=[{"role": "user", "content": "hi"}])
        assert result["content"] == "Hello!"
        assert result["tool_calls"] is None



def test_tool_format_conversion(self):
        """验证内部 tool 定义 → OpenAI function 格式的转换"""
        internal_tools = [{
            "name": "get_weather",
            "description": "Get weather",
            "parameters": {"type": "object", "properties": {"city": {"type": "string"}}}
        }]
        self.backend.complete(messages=[{"role": "user", "content": "weather?"}],
                              tools=internal_tools)
        # 验证传给 OpenAI 的参数格式
        call_args = self.mock_client.chat.completions.create.call_args
        passed_tools = call_args.kwargs["tools"]
        assert passed_tools[0]["function"]["name"] == "get_weather"
        assert "parameters" in passed_tools[0]["function"]



def test_tool_calls_parsing(self):
        """验证 LLM 返回的 tool_calls 被正确解析"""
        self.mock_client.chat.completions.create.return_value = MagicMock(
            choices=[MagicMock(message=MagicMock(
                content=None,
                tool_calls=[MagicMock(
                    id="call_abc",
                    function=MagicMock(
                        name="get_weather",
                        arguments='{"city": "Shanghai"}'
                    )
                )]
            ))]
        )
        result = self.backend.complete(messages=[{"role": "user", "content": "weather?"}])
        assert result["tool_calls"][0]["function"]["name"] == "get_weather"
        assert result["content"] is None



def test_null_content_handling(self):
        """LLM 有时返回 content=None，不能崩"""
        self.mock_client.chat.completions.create.return_value = MagicMock(
            choices=[MagicMock(message=MagicMock(content=None, tool_calls=None))]
        )
        result = self.backend.complete(messages=[{"role": "user", "content": "hi"}])
        assert result["content"] is None
        assert result["tool_calls"] is None

关键点：这些测试不是在测试 OpenAI，而是在测试我们的适配层——格式转换是否正确、边界情况是否被处理。content=None 的处理看起来琐碎，但在生产环境中，一个未处理的 None 就是一次线上事故。

模式总结

信号词：如果你的测试文件里有很多 test_init_* 或 test_create_*，但没有对应行为方法的测试，你很可能踩了这个坑。 自查方法：对每个类，列出所有 public 方法。检查每个方法是否至少有一个测试。如果你发现一个方法没有测试，恭喜——你找到了下一个 bug 的藏身之处。

盲区二：接口幻觉——端点存在，但没有被请求过

发现

catalyst-agent-mesh 是一个工作流编排系统，提供了 REST API。审计时发现： 
# app.py
@app.post("/workflows/{workflow_id}/execute")
async def execute_workflow(workflow_id: str, body: ExecuteRequest):
    workflow = workflow_store.get(workflow_id)
    if not workflow:
        raise HTTPException(404, "Workflow not found")
    result = await engine.execute(workflow, body.inputs)
    return {"result": result}


@app.post("/pipelines/{pipeline_id}/execute")
async def execute_pipeline(pipeline_id: str, body: ExecuteRequest):
    pipeline = pipeline_store.get(pipeline_id)
    if not pipeline:
        raise HTTPException(404, "Pipeline not found")
    result = await engine.run_pipeline(pipeline, body.inputs)
    return {"result": result}

这两个端点——系统的核心入口——没有任何测试。不是测得不够多，是完全没有。

已有的测试在测什么？在测 engine.execute() 和 engine.run_pipeline() 的内部逻辑。底层引擎被充分测试了，但 HTTP 层——参数解析、错误处理、状态码——是空白。

根因分析

"接口幻觉"（Interface Illusion）的模式：

> 我们测试了组件，就以为测试了接口。

底层引擎有测试 → 心理上觉得"核心逻辑覆盖了" → HTTP 层被视为"薄包装"而被忽略。但这个"薄包装"里藏着：

- 参数校验逻辑（body.inputs 是否符合 schema？） - 错误映射（workflow not found → 404，engine error → 500？） - 异步行为（并发请求会怎样？）

修复

from fastapi.testclient import TestClient


class TestWorkflowExecuteEndpoint:
    def setup_method(self):
        self.app = create_app(test_mode=True)
        self.client = TestClient(self.app)
        # 注入测试数据
        self.wf_id = self.app.state.workflow_store.create(
            name="test-wf",
            steps=[{"type": "echo", "message": "hello"}]
        )



def test_execute_success(self):
        response = self.client.post(
            f"/workflows/{self.wf_id}/execute",
            json={"inputs": {"text": "run test"}}
        )
        assert response.status_code == 200
        assert "result" in response.json()



def test_execute_nonexistent_workflow(self):
        response = self.client.post(
            "/workflows/nonexistent/execute",
            json={"inputs": {}}
        )
        assert response.status_code == 404



def test_execute_invalid_body(self):
        response = self.client.post(
            f"/workflows/{self.wf_id}/execute",
            json={"wrong_field": "oops"}
        )
        assert response.status_code == 422  # Pydantic validation error



def test_execute_engine_failure(self):
        """引擎内部出错时，应返回 500 而非 crash"""
        self.app.state.engine.inject_failure = True
        response = self.client.post(
            f"/workflows/{self.wf_id}/execute",
            json={"inputs": {}}
        )
        assert response.status_code == 500

这 4 个测试覆盖了端点的四种关键路径：成功、不存在、参数错误、内部异常。每个路径在生产环境中都会发生。

模式总结

信号词：如果你看到 @app.post、@router.get、app.post(...) 等路由定义，问自己：这个路由有一个发过 HTTP 请求的测试吗？如果没有，它就是一个盲区。 关键认知：测试内部函数 ≠ 测试 API 端点。HTTP 层的参数校验、错误映射、序列化都是可能出 bug 的地方。

盲区三：循环盲区——核心循环从未被执行

发现

ai-iot-orchestrator 是一个 IoT 设备编排系统。它的核心是一个异步消息循环——不断从消息队列取消息、分发给处理器、处理结果。 
class MessageOrchestrator:
    async def _message_loop(self):
        """系统的心脏——每 0.1 秒处理一批消息"""
        while self._running:
            try:
                messages = await self._queue.get_batch(timeout=0.1)
                for msg in messages:
                    handler = self._handlers.get(msg.type)
                    if handler:
                        await handler(msg)
                    else:
                        self._unhandled.append(msg)
            except asyncio.TimeoutError:
                continue
            except Exception as e:
                logger.error(f"Handler error: {e}")
                continue

这段代码——系统运行时 100% 的时间都在执行——零测试。

已有测试覆盖了什么？各个 handler（温度处理、灯光控制等）被单独测试了。但循环本身——消息分发逻辑、超时处理、异常隔离、FIFO 顺序——完全没有。

根因分析

"循环盲区"（Loop Blindness）的模式：

> 我们测试了循环体里的组件，就以为循环本身没问题。

各 handler 有独立测试 → 觉得"核心逻辑覆盖了" → 循环的调度逻辑——哪个消息发给谁、超时了怎么办、handler 抛异常会不会 kill 整个循环——被完全忽略。

这是三种盲区中最危险的，因为： 1. 循环通常是系统的长运行核心 2. 循环逻辑的 bug 往往是间歇性的（只在特定时序下触发） 3. 一个未处理的异常会 kill 整个系统

修复

import asyncio
import pytest


class TestMessageLoop:
    @pytest.mark.asyncio
    async def test_queued_messages_processed(self):
        """队列中的消息被正确处理"""
        processed = []
        orch = MessageOrchestrator()
        orch.register("sensor", lambda msg: processed.append(msg.payload))



await orch._queue.put(Message(type="sensor", payload={"temp": 25}))
        await orch._queue.put(Message(type="sensor", payload={"temp": 30}))



# 启动循环，给 0.3 秒处理
        task = asyncio.create_task(orch._message_loop())
        await asyncio.sleep(0.3)
        orch._running = False
        await task



assert len(processed) == 2
        assert processed[0]["temp"] == 25
        assert processed[1]["temp"] == 30



@pytest.mark.asyncio
    async def test_handler_exception_isolation(self):
        """一个 handler 抛异常不影响其他消息处理"""
        call_log = []
        orch = MessageOrchestrator()



def bad_handler(msg):
            raise RuntimeError("boom")



def good_handler(msg):
            call_log.append(msg.payload)



orch.register("bad", bad_handler)
        orch.register("good", good_handler)



await orch._queue.put(Message(type="bad", payload={}))
        await orch._queue.put(Message(type="good", payload={"ok": True}))



task = asyncio.create_task(orch._message_loop())
        await asyncio.sleep(0.3)
        orch._running = False
        await task



# bad handler 崩了，但 good handler 的消息依然被处理
        assert len(call_log) == 1
        assert call_log[0]["ok"] is True



@pytest.mark.asyncio
    async def test_unhandled_message_type(self):
        """未知消息类型不会崩溃，被记录到 unhandled"""
        orch = MessageOrchestrator()
        await orch._queue.put(Message(type="unknown_type", payload={}))



task = asyncio.create_task(orch._message_loop())
        await asyncio.sleep(0.2)
        orch._running = False
        await task



assert len(orch._unhandled) == 1
        assert orch._unhandled[0].type == "unknown_type"



@pytest.mark.asyncio
    async def test_fifo_ordering(self):
        """消息按入队顺序处理"""
        order = []
        orch = MessageOrchestrator()
        orch.register("test", lambda msg: order.append(msg.payload["seq"]))



for i in range(10):
            await orch._queue.put(Message(type="test", payload={"seq": i}))



task = asyncio.create_task(orch._message_loop())
        await asyncio.sleep(0.3)
        orch._running = False
        await task



assert order == list(range(10))

这四个测试覆盖了循环的四种关键行为：正常处理、异常隔离、未知类型、顺序保证。其中异常隔离是最关键的——在循环中一个 handler 的异常不应该传播到循环级别，否则整个系统会停摆。

模式总结

信号词：如果你的代码里有 while True、while self._running、while not stopped，检查这个循环是否被整体测试过。不是循环体里的函数——而是循环本身。 关键认知：循环是行为，不是结构。测试组件 ≠ 测试流程。

三种盲区的共同根因

现在退后一步看这三种模式：

盲区本质测了什么漏了什么
构造者陷阱静态 vs 动态对象的配置对象的行为
接口幻觉内部 vs 边界内部引擎逻辑HTTP 参数/错误处理
循环盲区组件 vs 流程循环体组件循环调度逻辑

共同模式只有一个：

> 测试跟随了实现结构，而非使用路径。

我们写测试的方式是"浏览代码，找到函数，给它写测试"。这保证了每个函数都有测试，但忽略了用户实际触发代码的路径。

用户不调用 engine.execute()——用户发一个 POST 请求。用户不直接调 OpenAIBackend.__init__——用户的 prompt 最终流经 complete()。用户不触发单个 handler——消息在循环中不断流动。

测试应该从使用路径出发，逆向覆盖所有途经代码，而非从代码结构出发正向逐个函数打勾。

一种系统化的盲区发现方法

基于上述分析，这里提炼一种可操作的盲区发现流程：

第一步：入口点清单

列出系统所有外部入口——REST 端点、消息队列消费者、定时任务、CLI 命令。这些是"使用路径"的起点。

# FastAPI 端点
grep -rn '@app\.\(get\|post\|put\|delete\)' src/


asyncio 消费者

grep -rn 'async def.*loop\|while.*running\|asyncio.create_task' src/


CLI 命令

grep -rn '@click\.command\|@app\.command' src/

第二步：路径追踪

对每个入口点，追踪从入口到响应的完整调用链。标注链上每个函数是否有测试。

# POST /workflows/{id}/execute

  → validate_request(body)     # ❓ 有测试吗？


  → workflow_store.get(id)     # ❓ 有测试吗？


  → engine.execute(wf, inputs) # ✅ 有测试


  → serialize_response(result) # ❓ 有测试吗？

第三步：缺口确认

任何在调用链上但无测试的函数，就是一个盲区。按风险排序： - 高风险：处理外部输入的函数（参数校验、反序列化） - 中风险：错误处理路径（异常映射、fallback） - 低风险：纯序列化/格式化函数

第四步：针对性补充

不要追求 100% 覆盖率。优先补高风险和中风险路径。一个 test_execute_nonexistent_workflow 的价值远大于十个 test_init_with_xxx。

更大的图景：Agent 系统的测试哲学

Agent 系统比传统软件更脆弱，因为它的行为路径更多、更动态。一个 Agent 可能：

- 根据用户输入动态选择调用哪个工具 - 在多轮对话中维护和修改上下文 - 在后台循环中持续处理事件 - 与外部 LLM 交互，响应格式不完全可控

这些特性使得 Agent 系统的测试盲区比传统软件更多、更隐蔽。三种盲区模式——构造者陷阱、接口幻觉、循环盲区——在 Agent 系统中尤其严重，因为：

1. Agent 的核心入口往往不是 HTTP 端点，而是 complete() 这样的推理方法，更容易被忽略 2. Agent 的接口层更厚（prompt 格式转换、tool 序列化、响应解析），出 bug 的概率更高 3. Agent 的循环更复杂（异步事件循环 + LLM 调用 + 工具执行），时序 bug 更多

因此，Agent 系统需要一种更严格的测试哲学：

> 不要问"哪些代码被执行过"，要问"哪些用户路径被端到端验证过"。

覆盖率工具告诉你代码的哪一行被执行了。它不告诉你的是：这条执行路径是否产生了正确的结果，以及所有可能的输入是否都被处理了。

结论

三种盲区——构造者陷阱、接口幻觉、循环盲区——揭示了测试覆盖率指标的根本局限。85% 的行覆盖率意味着 85% 的代码在测试中被触碰过，但不意味着 85% 的用户路径被验证过。

回到开头的三个项目：

项目盲区类型新增测试关键修复
nano-agent构造者陷阱+7complete() 的 tool 格式转换、null content 处理
catalyst-agent-mesh接口幻觉+7REST 端点的 404/422/500 路径
ai-iot-orchestrator循环盲区+6handler 异常隔离、未知消息处理

20 个新测试，覆盖了三个项目中最关键的行为路径——这些路径之前全部是零测试。

测试不是为了覆盖率数字。测试是为了让你在凌晨三点不用被叫醒。
