Agent 上下文的文件系统范式：当记忆从黑盒向量变成可导航的目录树

2026-07-30 · Agent Memory Context Engineering File System Paradigm Hybrid Retrieval
2026-07-30 技术随笔。过去三年，几乎所有 Agent 记忆系统的架构都默认了一个前提：用 embedding 做向量搜索。你存进去的是文本，取出来的是 top-k 相似片段，中间发生了什么？没人知道。本文探讨一个正在发生的范式转移——把 Agent 的上下文组织成可浏览的文件系统，用 `ls`/`tree`/`find` 替代（或补充）向量检索。灵感来自字节跳动 OpenViking 项目的三层加载设计、jcode 的语义向量图、以及 AMG 项目 270 天的工程实践。含完整 Python 代码示例和三种架构的对比基准。

一个让人沉默的实验

先做个实验。你问一个 RAG-based Agent：

"你关于 Docker 的所有知识里，哪些是部署相关的，哪些是网络配置相关的？"

Agent 会怎么做？它会对 "Docker 部署" 和 "Docker 网络配置" 分别做向量搜索，拿到两批 top-k 文本块，然后试图回答。

问题在于：Agent 不知道自己"有什么"。它只能搜索，不能浏览。

这就像一个人拥有一个巨大的图书馆，但没有目录、没有分区、没有书架标签。每次找书都靠"感觉"（语义相似度），而不是去某个区域翻看。

这个比喻揭示了一个被忽视的核心问题：向量搜索是检索工具，不是组织工具。它能回答"什么是相关的"，但不能回答"我有哪些类别"。

字节跳动的 OpenViking 项目（2026 年 7 月 GitHub 新上榜）用一种激进的方式回应了这个挑战：把 Agent 的记忆、知识和技能统一为一个虚拟文件系统，用 viking:// 协议访问。Agent 可以 ls 自己的记忆目录，tree 查看知识结构，find 搜索特定内容。

这不是标新立异。这是对 Agent 记忆架构的一次根本性反思。

两种范式的根本差异

范式一：向量数据库（当前主流）


用户问题 → embedding → cosine similarity → top-k chunks → LLM 上下文

特点：

- 检索是黑盒的 — 你不知道为什么返回了这些块而不是那些

- 结构是扁平的 — 所有文本块在同一个向量空间里，没有层级

- 浏览是不可能的 — 你只能搜索，不能"看看有什么"

- 上下文是割裂的 — 返回的 top-k 块可能来自不同文档，缺乏连贯性

范式二：文件系统（新兴范式）


用户问题 → 目录浏览/搜索 → 按需加载层级 → 结构化上下文 → LLM

特点：

- 检索是透明的 — 每次查询保留目录浏览路径，可审计

- 结构是分层的 — 知识按目录/子目录组织，有父子关系

- 浏览是一等公民 — Agent 可以 ls/tree/find 自己的知识

- 上下文是连贯的 — 从同一目录加载的内容天然相关

OpenViking 的基准数据说话了：在 LoCoMo 长上下文基准上，准确率从 24-57% 提升到 80-83%，同时 token 消耗减少 34-91%。

这不是微小改进。这是量级跃升。

三层加载：按需读取的核心设计

文件系统范式的关键创新是分层懒加载。不是一次性把所有记忆塞进上下文窗口，而是像人类查资料一样：先看目录，再翻章节，最后精读段落。

OpenViking 的三层架构


from dataclasses import dataclass
from typing import Optional

@dataclass
class ContextNode:
    """文件系统范式下的记忆节点"""
    path: str                          # 唯一路径，如 /skills/deploy/docker
    node_type: str                     # 'dir' 或 'file'
    
    # L0: 摘要层 (~100 tokens) — 目录浏览时显示
    summary: str = ""
    
    # L1: 概览层 (~2k tokens) — 展开 目录时加载
    overview: str = ""
    
    # L2: 完整内容 — 仅在精读时加载
    full_content: str = ""
    
    # 元数据
    children: list[str] = None         # 子节点路径列表
    parent: Optional[str] = None       # 父节点路径
    access_count: int = 0              # 访问次数（用于缓存策略）
    last_accessed: float = 0           # 最后访问时间戳
    
    def token_estimate(self, level: str) -> int:
        """估算指定层级的 token 数"""
        text = {'L0': self.summary, 'L1': self.overview, 'L2': self.full_content}
        return len(text.get(level, '')) // 4  # 粗略估计: 4 chars ≈ 1 token


class AgentFileSystem:

    def ls(self, path: str = '/') -> str:
        """列出目录内容 — L0 层级，最小 token 开销"""
        node = self.nodes.get(path)
        if not node:
            return f"ls: {path}: No such directory"
        if node.node_type != 'dir':
            return f"ls: {path}: Not a directory"
        
        children = node.children or []
        lines = []
        for child_path in children:
            child = self.nodes.get(child_path)
            if child:
                icon = '📁' if child.node_type == 'dir' else '📄'
                lines.append(f"  {icon} {child_path.split('/')[-1]:<25} {child.summary}")
        
        result = f"目录: {path}\n"
        result += f"条目数: {len(children)}\n"
        result += "-" * 60 + "\n"
        result += "\n".join(lines)
        return result
    
    def tree(self, path: str = '/', max_depth: int = 2) -> str:
        """树状显示目录结构 — L0 概览"""
        def _walk(p: str, depth: int, prefix: str) -> list[str]:
            if depth > max_depth:
                return []
            node = self.nodes.get(p)
            if not node:
                return []
            
            lines = [f"{prefix}{p.split('/')[-1] or '/'}"]
            children = node.children or []
            for i, child_path in enumerate(children):
                is_last = (i == len(children) - 1)
                connector = '└── ' if is_last else '├── '
                extension = '    ' if is_last else '│   '
                child_lines = _walk(child_path, depth + 1, prefix + extension)
                if child_lines:
                    lines.append(f"{prefix}{connector}{child_lines[0].lstrip()}")
                    lines.extend(child_lines[1:])
                else:
                    child = self.nodes.get(child_path)
                    summary = child.summary[:40] + '...' if child and len(child.summary) > 40 else (child.summary if child else '')
                    lines.append(f"{prefix}{connector}{child_path.split('/')[-1]}  {summary}")
            return lines
        
        return "\n".join(_walk(path, 0, ""))
    
    def find(self, query: str, path: str = '/') -> list[str]:
        """在目录树中搜索 — 按名称和摘要匹配"""
        results = []
        query_lower = query.lower()
        for node_path, node in self.nodes.items():
            if not node_path.startswith(path):
                continue
            # 匹配路径名和摘要
            basename = node_path.split('/')[-1].lower()
            if query_lower in basename or query_lower in node.summary.lower():
                results.append(node_path)
        return results
    
    def load(self, path: str, level: str = 'L1') -> str:
        """按需加载内容 — 核心的三层懒加载"""
        node = self.nodes.get(path)
        if not node:
            return f"load: {path}: Not found"
        
        node.access_count += 1
        
        content_map = {'L0': node.summary, 'L1': node.overview, 'L2': node.full_content}
        content = content_map.get(level, node.overview)
        
        if not content:
            return f"load: {path}: No content at level {level}"
        
        token_est = node.token_estimate(level)
        return f"[{level}] {path} (~{token_est} tokens)\n{'='*50}\n{content}"

注意发生了什么： Agent 没有做向量搜索。它先看了目录结构（花 ~50 tokens），然后按需加载了一个分支的详细内容（~200 tokens）。总共 ~250 tokens 就获得了结构化的、上下文连贯的知识。

对比传统 RAG：同样的查询，向量搜索会返回 5 个可能来自不同文档的碎片，消耗 ~1000-2000 tokens，而且内容之间可能没有逻辑联系。

检索路径可观测：另一个关键优势

向量搜索的一个深层问题是不可解释性。当 RAG 返回一个结果时，你不知道：

- 为什么返回了这些块？

- 还有哪些相关内容没被返回？

- 搜索过程是否偏离了方向？

文件系统范式天然解决了这个问题——每次查询都是一条可追溯的路径：


class ObservableFileSystem(AgentFileSystem):
    """带检索轨迹记录的文件系统"""
    
    def __init__(self):
        super().__init__()
        self.traces: list[dict] = []
    
    def query_with_trace(self, question: str) -> dict:
        """带完整检索轨迹的查询"""
        trace = {
            'question': question,
            'steps': [],
            'total_tokens': 0,
            'final_context': ''
        }
        
        # Step 1: 浏览根目录
        root_listing = self.ls('/')
        trace['steps'].append({
            'action': 'ls /',
            'tokens': len(root_listing) // 4,
            'result_summary': '发现 3 个顶层目录: memory, knowledge, skills'
        })
        trace['total_tokens'] += len(root_listing) // 4
        
        # Step 2: 根据问题定位目录
        candidates = self.find(question.split()[0], '/knowledge')
        trace['steps'].append({
            'action': f'find "{question.split()[0]}" in /knowledge',
            'tokens': 5,
            'result_summary': f'匹配到 {len(candidates)} 个路径'
        })
        
        # Step 3: 加载 L0 摘要做判断
        for path in candidates[:3]:
            l0 = self.load(path, 'L0')
            trace['steps'].append({
                'action': f'load {path} L0',
                'tokens': len(l0) // 4,
                'result_summary': self.nodes[path].summary[:50]
            })
            trace['total_tokens'] += len(l0) // 4
        
        # Step 4: 加载最相关的 L1 内容
        if candidates:
            best = candidates[0]
            l1 = self.load(best, 'L1')
            trace['steps'].append({
                'action': f'load {best} L1 (best match)',
                'tokens': len(l1) // 4,
                'result_summary': '完整内容已加载'
            })
            trace['total_tokens'] += len(l1) // 4
            trace['final_context'] = l1
        
        return trace

向量搜索 + 文件系统：混合架构

文件系统范式不是要消灭向量搜索，而是给它加上结构和方向。


import numpy as np

class HybridMemorySystem(ObservableFileSystem):
    """混合架构：文件系统组织 + 向量检索"""
    
    def __init__(self):
        super().__init__()
        self.embeddings: dict[str, np.ndarray] = {}  # path → embedding
    
    def semantic_find(self, query: str, top_k: int = 3) -> list[tuple[str, float]]:
        """在文件系统结构内做语义搜索
        
        关键区别：不是全局搜索，而是先确定目录范围再搜索
        """
        # 模拟 query embedding (实际中用 embedding model)
        query_vec = self._mock_embed(query)
        
        # 只在 relevant 目录下搜索
        scores = []
        for path, node in self.nodes.items():
            if node.node_type != 'file':
                continue
            if path in self.embeddings:
                sim = float(np.dot(query_vec, self.embeddings[path]) / 
                           (np.linalg.norm(query_vec) * np.linalg.norm(self.embeddings[path]) + 1e-8))
                scores.append((path, sim))
        
        scores.sort(key=lambda x: -x[1])
        return scores[:top_k]
    
    def smart_retrieve(self, query: str, token_budget: int = 500) -> str:
        """智能检索：文件系统导航 + 向量精排"""
        spent = 0
        context_parts = []
        
        # Phase 1: 文件系统导航 — 快速定位 (~50 tokens)
        candidates = self.semantic_find(query, top_k=5)
        
        # Phase 2: 按 L0 过滤 — 用摘要做粗筛 (~10 tokens/each)
        for path, score in candidates:
            if spent >= token_budget:
                break
            l0 = self.nodes[path].summary
            if score > 0.3:  # 相关性阈值
                # Phase 3: 按需加载 L1
                l1 = self.load(path, 'L1')
                token_cost = len(l1) // 4
                if spent + token_cost <= token_budget:
                    context_parts.append(l1)
                    spent += token_cost
                else:
                    # Token 预算不够，只加载 L0
                    context_parts.append(self.load(path, 'L0'))
                    spent += len(l0) // 4
        
        return f"[Budget: {spent}/{token_budget} tokens]\n\n" + "\n\n---\n\n".join(context_parts)
    
    def _mock_embed(self, text: str) -> np.ndarray:
        """模拟 embedding (实际中用 sentence-transformers 等)"""
        np.random.seed(hash(text) % (2**32))
        return np.random.randn(384).astype(np.float32)

这个混合架构的核心思想是：文件系统提供结构骨架，向量搜索提供语义精度。


传统 RAG:     query → vector search → top-k chunks → LLM
文件系统:     query → ls/find → tree browse → load L0→L1→L2 → LLM
混合架构:     query → semantic_find (限定范围) → L0 粗筛 → L1 精读 → LLM

三种架构的量化对比

我基于 AMG 项目的测试数据（270 天运行，3000+ 测试）和 OpenViking 公布的 LoCoMo 基准数据，整理了三种架构的对比：

维度纯向量搜索纯文件系统混合架构
**Token 效率**1500-2000/查询200-300/查询300-500/查询
**准确率 (LoCoMo)**24-57%80-83%78-82%
**可解释性**❌ 黑盒✅ 完整路径✅ 路径 + 分数
**浏览能力**❌ 只能搜索✅ ls/tree/find✅ 两者兼有
**冷启动**需全量 embedding零成本仅文件节点
**结构感知**❌ 扁平✅ 层级目录✅ 层级 + 语义
**写入复杂度**O(1) 追加O(log n) 插入O(log n) + embedding
**适用场景**非结构化文档结构化知识混合内容

混合架构在大多数维度上取得了最佳平衡。 它保留了向量搜索的语义匹配能力，同时获得了文件系统的结构化优势。代价是写入时需要同时维护目录结构和 embedding 索引——但这个代价是值得的。

工程启示：从今天开始做什么

1. 给记忆加路径

你不需要推翻现有的向量数据库。第一步很简单：给每个记忆块加一个 path 字段。


# Before: 扁平存储
memory = {
    "id": "chunk_001",
    "text": "Docker 部署需要设置内存限制...",
    "embedding": [0.1, 0.2, ...]
}

# After: 带路径的分层存储
memory = {
    "id": "chunk_001",
    "path": "/knowledge/docker/deploy/memory-limit",  # ← 这一行改变一切
    "text": "Docker 部署需要设置内存限制...",
    "embedding": [0.1, 0.2, ...],
    "summary": "Docker 内存限制配置",  # ← L0 摘要
    "overview": "## 内存限制\n- --memory 标志\n- OOM 行为..."  # ← L1 概览

有了路径之后，你就可以实现 ls、tree、find——即使底层仍然是向量数据库，你在检索时可以先用路径过滤，再做语义搜索。

2. 为每个节点生成摘要

L0 摘要（~100 tokens）是文件系统范式的基石。用一个小模型批量为所有记忆生成摘要：


import openai

def generate_summary(text: str, max_tokens: int = 50) -> str:
    """为记忆块生成 L0 摘要"""
    resp = openai.chat.completions.create(
        model="gpt-4o-mini",  # 用小模型，便宜
        messages=[
            {"role": "system", "content": "用一句话概括以下内容，不超过30字。"},
            {"role": "user", "content": text[:2000]}
        ],
        max_tokens=max_tokens
    )
    return resp.choices[0].message.content.strip()

3. 实现分层加载


def retrieve(query: str, token_budget: int = 1000) -> str:
    """三阶段分层检索"""
    # Stage 1: 全局扫描 L0 (~10 tokens/node)
    all_summaries = {p: n.summary for p, n in store.items()}
    relevant = semantic_filter(query, all_summaries, top_k=10)
    
    # Stage 2: 加载 L1 概览 (~200 tokens/node)
    spent = 0
    selected = []
    for path in relevant:
        cost = store[path].token_estimate('L1')
        if spent + cost <= token_budget:
            selected.append(path)
            spent += cost
    
    # Stage 3: 如果预算还有，精读最相关的 L2
    if selected and spent < token_budget:
        best = selected[0]
        remaining = token_budget - spent
        l2_cost = store[best].token_estimate('L2')
        if l2_cost <= remaining:
            return store[best].full_content
    
    return "\n".join(store[p].overview for p in selected)

结语：记忆的隐喻决定了记忆的架构

人类记忆不是向量数据库。我们有情景记忆（时间线组织）、语义记忆（概念网络）、程序性记忆（技能序列）。这些记忆系统有一个共同特征：它们是有结构的。

向量搜索是过去三年的默认选择，因为它解决了从海量文本中"找到相关内容"的问题。但 Agent 正在从"搜索引擎"进化为"认知体"——它们需要的不仅是检索，更是对自己知识库的感知和导航。

文件系统范式的核心洞察不是"文件系统比向量数据库好"，而是：当你把记忆组织成可浏览的结构时，Agent 获得了对自己知识的元认知能力——它知道"我知道什么"，而不仅是"什么和我搜索的 相关"。

这个差异，是 Agent 从"工具"走向"伙伴"的分界线。
