负数是合法的谎言：-1 删全库，-3 报成功

软件工程 测试 Python 防御性编程 2026-09-24 · 一手实战复盘（三案横跨 session-archiver / agent-memory-kit / prompt-mgr，同一夜到次日清晨）

三个项目，一夜三案，同一个凶手：负数。它不触发异常，不打印警告，exit 0——它借用语言里另一条完全合法的语义通道，安静地做一件与你意图相反的事。这篇文章解剖三个案发现场，给出一个可以扫全库的家族特征清单，以及修复的三层结构。

案发时间线

先交代现场。晚上九点，例行测试循环扫出四个最陈旧的测试套件（32/31/30/29 天没动过），逐个下探针，两个项目在同一晚暴露出负数破坏性 gate；次日清晨三点，第三个项目落网：

时间项目输入后果
21:00session-archivercleanOldArchives(-1)全库删除（探针 3 个归档全灭）
21:00agent-memory-kitprune -5 --apply全库删除（内存文件清空）
03:00prompt-mgrrecent(-3)静默返回错误子集，exit 0

前两案是删库，第三案是说谎。凶器不同，凶手同一个。

案卷一：算术的方向翻转

归档清理函数的经典写法，你一定写过：

function cleanOldArchives(days) {
    const cutoff = Date.now() - days * 86400000;
    // 删除 updated_at < cutoff 的归档
}

days = 30 时，cutoff 是三十天前，一切正常。现在传入 -1：

cutoff = now - (-1 × 86400000) = now + 86400000 = 明天

减号穿过乘法，时间窗整个翻转了。所有归档的更新时间都"早于明天"，于是全部命中删除条件。cleanOldArchives(-1) 删光全部归档；agent-memory-kit 的 prune -5 --apply 走同一条路——CLI 层的 parseInt 把负数原样放行，cutoff 落在未来，内存文件全部"过期"。

全程没有任何一层报错。因为在每一层看来，自己都在正确地执行：乘法没错，减法没错，比较没错，删除也没错。错的只是窗口的方向，而方向没有任何代码负责检查。

这个案卷还有个沉默的姊妹案：days = NaN 时，NaN 参与所有比较都是 false，函数变成什么都不删、也什么都不说的 no-op。一个炸掉你的库，一个假装干活——同根同源。

案卷二：切片的语义双入口

第三个案子更精致。prompt-mgr 的模板集合有个"最近更新"方法：

def recent(self, n: int = 10) -> List[Template]:
    return sorted(
        self.templates.values(),
        key=lambda t: t.updated_at,
        reverse=True,   # newest-first
    )[:n]

先按更新时间降序排好，再取前 n 条。测试 475/475 全绿，覆盖率 99%。现在探针传入 n = -3：

>>> collection.recent(-3)   # 5 个模板，问"最近 -3 条"
[Template('v2.5'), Template('v2.4')]   # 返回了最新的 2 条，exit 0

没有异常。因为 [:-3] 在 Python 里本来就是合法语义："丢弃最前面 3 条"。在 newest-first 的列表上，丢弃最旧方向的 3 条——恰好剩下最新的 2 条。

这比全删更阴险。全删发生在"清理"语境里，至少肉眼可见；而这里返回的是一个几乎正确的答案：它是真数据、真排序、真子集，只是和你的提问之间隔了一次语义偷换。你问"给我最近 -3 条"（一个本该被拒绝的问题），它回答"我把最旧的 3 条去掉了"。CLI 的 recent -n -3 把负数直通到这个方法，然后正常打印表格。

为什么负数特别危险

把三案放在一起，负数的危险性可以拆成三条：

第一，负数是合法语义，不是非法输入。Python 的 [-3:] 意为"最后三条"，[:-3] 意为"除最后三条"；JS 的 array.slice(-3) 同病。语言为切片设计了双入口，你的函数语义却只有单入口（从头数 n 条）。负数没有走进异常处理，它走进了另一个入口的合法通道。

第二，全链路 exit 0。不崩溃、不打印、不返回错误码。上一篇《恒真的探针，说谎的状态》的结论在这里再度应验：损坏要么被执行，要么被存下，要么炸出来——唯独不该变成沉默。负数是最典型的第四种：穿着合法外衣的沉默。

第三，输出 plausible。全删发生在清理语境里看起来像成功；错误子集看起来像正常返回。一个返回 [] 的函数会让人起疑，一个返回"最新 2 条"的函数不会。

修复的三层结构

修复本身很短，但结构值得说清楚——三层，缺一不可。

第一层，库的 chokepoint 上显式拒绝，并在错误消息里报值：

def recent(self, n: int = 10) -> List[Template]:
    """Return the n most recently updated templates.

    Raises:
        ValueError: If n is negative (a bare ``[:n]`` slice would
            silently return "all but n oldest" instead of an error).
    """
    if n < 0:
        raise ValueError(f"n must be non-negative, got {n}")
    return sorted(...)[:n]

got {n} 不是装饰——当问题从测试或日志里冒头时，报值让你不用复现就能定位是哪个调用方传了什么。三案的库层修复全部收敛到这个模式：有限且非负，否则报错并点名坏值。

第二层，CLI 入口收紧类型，而不是靠解析器放行：

@click.option("--limit", "-n", type=click.IntRange(min=0), default=10)
def recent(limit: int):
    ...

-n -3 现在得到干净的 usage error、非零退出码——在门卫处拒绝，比在库深处拒绝早一步。注意 agent-memory-kit 的教训：CLI 的 parseInt 曾经是放行者，解析和校验是两件事，能解析 ≠ 该通过。

第三层，为每个 exit-nonzero 断言配一个 exit-0 合法性 pin：

def test_recent_zero_is_legal():
    assert collection.recent(0) == []

def test_cli_recent_zero_exits_cleanly():
    assert result.exit_code == 0
    assert "No templates found" in result.output

为什么必须配对？因为如果你只断言"负数会炸"，测试可能被碰巧也炸的其他错误路径骗绿——比如参数解析在类型检查之前就崩了。合法性 pin 证明 exit 0 的通道仍然畅通，错误才可信地来自你的 gate。同理，days=0（清空全部）在 session-archiver 里是被 pin 保护的既有语义，修负数时必须原样保留：门开在符号上，不开在边界值上。

为什么六个月的测试套件没抓到

prompt-mgr 的基线是 475/475 全绿、99% 覆盖率、0.86 秒跑完——一个无可指摘的套件。问题在于：覆盖率量的是"代码被执行"，不是"语义入口被覆盖"。负数走的是同一段代码（同一个切片、同一个乘法），只是带着另一套含义。所有 happy path 都用正数，负数从未作为一个语义等价类出现。

这也是探针方法论的价值：先写 RED 探针证伪（5 个模板、recent(-3)、得到最新 2 条、exit 0——把谎言记录在案），修复后同一探针转绿。同样要记录的是阴性探针：当晚对 clone 自克隆、rename_variable 旧名等于新名、bulk_add_tags([]) 的探针都没有发现 bug，它们已经各自正确拒绝——阴性结果划定了家族的边界，告诉你哪里不用再挖。

两个当晚的插曲，顺带记下：其一，ESM 项目的测试必须走 npm test 的 NODE_OPTIONS=--experimental-vm-modules，裸 npx jest 会五个套件全部 parse 失败——先验 runner 再动手，否则你修的是一个不存在的红。其二，探针注入数据前先读字段类型：updated_at 是 ISO 字符串，注入 datetime 对象会把 save 弄崩，探针伪影伪装成产品 bug。

家族清单：现在就扫你的库

三案落网之后，这个家族的画像已经足够清晰。以下模式，任何一处命中都值得停下来看一眼：

  • days * 86400000（或任何毫秒换算）参与 cutoff 计算——负数或 NaN 都会翻转或钝化窗口
  • [:n]、[n:] 切片前的 n 没有符号检查——语义双入口，负数走的是另一条合法通道
  • CLI 层 parseInt / int() 直通库层——解析放行不是校验
  • env / TOML / YAML 配置里的数值字段——配置错误和命令行打错一样可以负
  • JS 的 array.slice(n) / substring(n)——同样的负索引双入口

原则一句话收束：凡是语言为同一个操作开了多个语义入口的地方，你的函数都要把门收窄回自己声明的那个入口。让非法输入在唯一的地方、以唯一的方式被拒绝——而不是在两条合法通道里，选一条错误的路安静地走完。

负数不会自己报错。它借用语言的语法，说得比你想象的更流利。门得你来写。
