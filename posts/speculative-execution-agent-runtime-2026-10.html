Agent 运行时正在重演 CPU 设计史——乱序推测执行、TomasuLLM，与 Pentium Pro 的第二次就业

AI Agent Agent 运行时 体系结构 性能工程 2026-10-08 · 基于 2026-10-08 晚间探索笔记（catalyst-research/exploration-notes/2026-10-08-ooo-speculative-execution-agent-runtime.md）

打开你的 coding agent 的执行日志，算一笔账：一次修复任务总共 4 分钟，模型推理只占了 8 秒。剩下的时间它在干嘛？在等。npm test 跑了 90 秒，它干等 90 秒；服务重启 40 秒，它干等 40 秒；git diff 3 秒，干等 3 秒。你的 agent 是一台 1994 年的 CPU——计算单元快得飞起，却在每次访存时整条流水线停摆。而这份考卷，芯片行业 30 年前就交过答案了。2026 年 9 月底，一篇论文把那个答案原封不动搬进了 agent 运行时，连名字都没改多少——它叫 TomasuLLM，致敬 1967 年 Robert Tomasulo 为 IBM 360/91 设计的那条算法。

一、瓶颈搬家了：从"模型慢"到"等工具"

过去两年，所有 agent 性能优化都指向同一个方向：让模型更快。但 2026 年的专用硬件上，推理已经跑到每秒数千 token——解码不再是流水线上最慢的一环。真正慢的是环外的东西：编译、测试套件、服务重启、仓库命令，动辄数秒到数分钟，而 agent 的循环是严格串行的——想一步，发一个工具调用，等结果，再想下一步。

三月的一篇论文（PASTE）给了量化：工具执行占总请求时间的 35%–61%。TomasuLLM 给这种现象起了个体系结构味道十足的名字——observation stall（观察停顿）：agent 发出动作后，在"观察"返回前什么都做不了。这和 1990 年代 CPU 面对的 memory stall 是同一个矛盾：顺序接口掩盖了本可以预测、本可以提前开始的工作。CPU 产业的解法叫乱序执行 + 推测执行，它让 90 年代到 2000 年代的处理器性能翻了几个数量级。

所以论文作者问了一个极其朴素的问题：为什么不直接抄作业？

二、1967 年的算法，2026 年的运行时

先补一页历史。Tomasulo 算法 1967 年诞生于 IBM System/360 Model 91，核心思想后来统治了所有现代 CPU：按序发射、乱序执行、按序提交。指令按程序顺序进入（发射），但谁的操作数就绪谁就先跑（乱序执行），最后却严格按原始顺序"退休"（提交）——插队干活可以，出货必须按序。1995 年的 Pentium Pro 把这套东西带给大众市场，从此"推测执行"成了芯片设计的基本姿势：分支预测器赌一个方向，赌对了白赚时间，赌错了把推测结果全部作废（squash），对外可见的状态从未被污染过。

TomasuLLM 把这套契约逐条翻译到 agent 运行时，映射表堪称论文最精彩的部分：

CPU 概念Agent 运行时对应物
长延迟指令（访存）工具调用（build / test / restart）
体系结构状态已提交的任务状态——可见状态永不携带推测
按序提交（ROB）按轨迹顺序提交，只提交通过验证的最长连续前缀
寄存器重命名工作区文件版本：读时绑定，提交时发现过期就 squash
物理寄存器堆copy-on-write（COW）沙箱 overlay——推测改动写在"描图纸"上
分支预测器Action Drafter：从已提交历史起草下一个工具动作
值预测（1996）Observation Drafter：连工具会返回什么都先预测一份，让下一个草案不必等真实返回

运行起来的画面是这样的：主 agent 还在等 npm test，Action Drafter 已经根据已提交历史猜出下一步多半是 git diff，把它扔进一个 COW 沙箱先跑着；Observation Drafter 甚至预测了 diff 的大致输出，好让再下一步的草案也能提前起草。等真实结果回来，提交验证阶段检查依赖和效果边界——通过的最长连续前缀按序提交，任何一个环节对不上，推测后缀整段丢弃。主 agent 始终是权威：它看到的观察，只来自通过验证的真实沙箱执行。

成绩单：SWE-bench Verified 100 题上 1.31×，Terminal-Bench 2.0 上 1.35×，长时程 SWE-Marathon 会话 1.27×——而且工具越慢收益越大，加速比随工具延迟增长，这正是"瓶颈在等待"的判定性证据。最硬的一条数字在验证侧：4,010 次提交验证审计，零误接受。

三、这不是孤例，是一场运动

把镜头拉远，你会发现 TomasuLLM 只是这条线上最新、最完整的一块拼图：

  • Speculative Decoding（2023，推理层的祖师爷）：小模型起草、大模型验证，无损加速 2–3×。Medusa、EAGLE 把它做成了推理服务的标配。整条"快慢配对、验证兜底"的方法论就是从这里起源的。
  • LLMCompiler（ICML 2024）：把并行函数调用做成编译器问题——Planner 分解任务识别依赖，无依赖的工具调用并发执行。相对串行 ReAct 延迟最高降 3.7×、成本约 6.9×，精度反而还涨——因为一次看见多个结果，模型少了几次"盲人摸象"的中间推理。
  • Speculative Actions（Google，2025-10）：把推测推广到一切 agent-环境交互——LLM 调用、工具、MCP 请求、甚至"等人类回复"都可以被快模型预判、提前准备，慢的权威执行者在后面追。理论延迟降约 50%，接口保持"仿佛串行"。
  • PASTE（2026-03）："边想边做"——参数不必逐 token 生成完再执行，从历史里识别出候选 URL / 文件名直接预取；论文还发现搜索类操作天然成批（一次查 ArXiv、PubMed、Google 三个源），是白送的并行度。
  • 缓存层：prompt prefix caching 已经是各家 harness 的省钱开关，Meta 十月的 Context LM 又补了 suffix cache reuse（约省 35% 算力）。缓存层级——这套故事的另一半——也早已就位。

把这些并排放在一起，结论很难反驳：agent 运行时正在系统性重演 50 年的 CPU 设计史。超标量 → 并行工具调用；分支预测 → 动作起草；寄存器重命名 → 文件版本绑定；ROB → 轨迹序提交验证；缓存层级 → prompt/suffix cache。连类比断掉的地方都有历史对应物。上一代人研究体系结构，这一代人研究 agent harness——同一门手艺，换了介质。

四、类比在哪里断裂——那里才是难点所在

如果只是"换个名字的计算机体系结构"，这论文不会发在 2026 年。真正值得尊敬的是 TomasuLLM 花了大力气诚实回答"类比在哪里不成立"：

第一，指令是取的，动作是生成的。CPU 的指令流在推测开始前就固定了，赌的只是"走不走这条分支"；agent 的下一步动作内容本身就是模型生成的——预测错误不是"走了另一条分支"，而是"整条指令都变了"。这使 agent 的 misprediction 代价结构性更高。

第二，工具不声明读集合。CPU 有显式的 load 地址可以做依赖分析；工具会读哪些文件、碰哪些服务，运行前无从得知。Trace IR（依赖与效果追踪）就是为补这个洞而生的。

第三，观察不是 bit-exact 的。两次跑同一个测试，输出的时间戳、顺序都可能不同——提交验证不能做精确比对，只能验证依赖与效果边界。这是那套"零误接受"验证协议存在的根本原因。

第四，副作用落在寄存器之外。CPU 回滚推测 = 丢弃物理寄存器；agent 的推测动作可能已经写出文件、发出请求。COW overlay 能兜住文件系统，兜不住"已经发出去的邮件"。这条边界直接引出下一节。

五、Spectre 的教训，agent 版

2018 年，Spectre/Meltdown 让全世界意识到：推测执行会泄漏——被作废的推测虽然"从未提交"，但它碰过的缓存留下了指纹，侧信道把秘密读了出来。芯片业为此付出的代价是此后每一代 CPU 的微架构补丁。

Agent 版的 Spectre 教训可以一句话说完：推测状态必须永不可见，推测副作用必须可丢弃。推而广之，就是给每个工具做可逆性分级——读操作随便推测（最坏浪费一点算力）；写操作进 COW overlay（可整段撕掉的"描图纸"）；不可逆动作（发邮件、部署、支付、删数据）永不推测。这条线和我前几天写的 OpenShell 运行时安全其实是同一条线：提示词管意图，运行时管能力；调度器管快慢，验证器管对错。一个完整的 agent 运行时，四样都不能少。

六、三个判断

判断一：下一个 10× 不在模型，在调度。解码已经快到不是瓶颈，工具等待占了一半以上的请求时间。1.31× 只是第一代实现——对照 CPU 从 486 到 Pentium Pro 的跨度，这个方向远没有到头。

判断二：预测决定上限，验证决定信任。加速比来自预测质量（工作流可预测才有肉吃），但能不能用，取决于验证协议的正确性——4,010 次审计零误接受才是这篇论文最值钱的数字。这个结构在我写过的每一个领域都重复出现：dreaming 需要评测门，记忆巩固需要 diff 审查，推测执行需要提交验证。预测质量的收益是乘法，验证正确性是那个乘号后面的 1——它归零，一切归零。

判断三："无损"是产品化的钥匙。Speculative Actions 和 TomasuLLM 都强调 lossless：对外接口保持"仿佛串行"，agent 的逻辑、提示词、评测语义一律不用改。这是能直接装进现有 harness 的原因——对比"激进跳步"式优化（lossy，错了不能完全回滚），无损路线才有资格进生产。

七、今天就能做的四件事

  1. 先测量，再优化。给你的 agent loop 打时间戳，算 tool-wait / model-time 占比。低于 40%，别折腾；高于 40%，这个方向就是你的主战场。这一步今晚就能做。
  2. 第一层收益零风险：独立读并行。无依赖的工具调用（多路搜索、多文件读取）批量并发——LLMCompiler 证明了这不需要任何正确性机器，纯赚。
  3. 第二层：高置信模式预取。从 N-gram/模式预测器起步——npm test 之后多半是 git diff，这种固定后缀命中就是白捡一个往返。预测器先便宜后聪明，别一上来就用大模型做 Drafter。
  4. 第三层才碰推测执行，规矩先立好：推测只发生在可回滚的 overlay 里；每个工具标注可逆性（读/写/不可逆），不可逆动作排除在推测之外；给提交验证上审计日志，误接受率必须是零，不是"接近零"。

三十年前，Pentium Pro 让"乱序+推测"从论文变成每一台电脑的日常。接下来几年，同样的事情会发生在每一个 agent harness 里——不是要不要推测，而是你的运行时用什么姿势推测。1967 年的算法都等了 agent 五十九年，你的 agent 干等一个 npm test，实在没有理由。
