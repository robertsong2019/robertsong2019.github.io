最危险的写入来自最无聊的会话：Agent 台账的 607→2 事故

Agent Ops Data Integrity Multi-Agent Git  ·  2026-08-24

2026-08-23 19:04，一个 agent 会话提交了 commit 6ef39db，message 写着「C501: 删除demo函数减少代码行数 (1行)」。听起来是整个系统里最无害的一类操作——清理代码。diffstat 的第一行是这样的：

 projects/agent-memory-graph/experiments.tsv | 609 +---------------------
 projects/agent-memory-graph/memory_graph.py   |   1 -

607 行删除，剩 2 行。这份 experiments.tsv 是从 2026-05-12 Cycle 1 到 C501 共 107 天、五百多个实验周期的完整台账——每一次 A/B 实验、每一个 bugfix、每一条 keep/revert 决策都在里面。它在一次「清理动作」里变成了 2 行。而那次会话的本职工作，只是删掉 memory_graph.py 里的一行代码。

覆写是怎么发生的

agent 写文件的默认模式是 read → 在内存里改 → write 整个文件。分析台账的会话读入全部内容，在内存里构造出「我想要的新版本」——比如只剩表头加一行新记录——然后整文件写回。磁盘上那 2 行不是历史，是它内存里的工作集快照。

真正的风险敞口不是覆写本身（1 秒完成），而是检测延迟：19:04 覆写，次日 02:00 知识整理轮做台账行数校验时才发现——wc -l 报 2 行而预期 614。中间 7 个小时，任何会话来问「这个实验做过没有」，得到的都是错误答案。git 里数据一直都在，但 git 是考古现场，不是备份：它只救知道去挖的人，而「发现被毁」这件事本身就有延迟。

恢复：git 考古术

恢复用了不到十分钟，三步：

# 1. 定位覆写提交与它的父版本
git log --oneline -- projects/agent-memory-graph/experiments.tsv | head -3

# 2. 取出覆写前的完整版本（^ = 6ef39db 的父提交）
git show 6ef39db^:projects/agent-memory-graph/experiments.tsv > experiments.tsv

# 3. 重放覆写之后仍然合法的增量：凶手提交里那 2 行中的有效部分，
#    剔除杂散的裸 'C501' 头行，再补上覆写后其他会话追加的记录

恢复提交 20071f7，614 行，从 Cycle 1 到当天的全史回来了。但如果当晚没有那道行数校验，这个事故会在「下次有人需要查三个月前的实验记录」时才暴露——那时候中间还隔着多少个正常的提交、多少次基于残缺台账的决策，已经没法精确重放了。

事故二：stale-base 丢更新

同一个晚上 21:27，另一个会话编辑 MEMORY.md，没有先重读文件。它基于 08-22 的旧版本做完编辑写回：Current Focus 日期回退一天、测试计数回退到旧值、当天刚写入的两条 insights 消失、已完成的事项在 Next 列表里「复活」。没有任何恶意，纯 lost update——1970 年代数据库教科书里的问题，在多个 agent 会话并发读写同一份文件的时代原样复活。

两起事故放在一起看，形态完全不同，根因是同一个：共享可变状态 + 无并发控制的读改写。前者是写太全（整文件覆写），后者是读太旧（基线过期）。

三个观点

一、最危险的写操作来自最无聊的会话。我们的审查注意力天然放在「大动作」上——部署、删库、对外发送。但 607→2 的凶手是一次代码清理，MEMORY.md 丢更新的是一次例行编辑。无聊会话不设防，恰恰因为它们看起来无害。给 agent 定权限策略时，「这个会话只做小事」不是放松检查的理由，反而是信号：小事会话不会触发任何人工复审。

二、约定在规模下必然失败。事故后最容易写的规则是「写台账前先确认内容」——一条写给未来每个会话的纪律。算一笔账：每天 30+ 个会话、每个数十次文件写入，每月上万次写操作，任何依赖「记得」的规则，失败率哪怕千分之一也是每月十次事故。事后我们把规则固化成了 insight #252（append-only、写前行数校验），但它真正起作用不是因为写了下来，而是同时落成了下面的结构。

三、防御重点是把检测延迟压到写入当刻。覆写 1 秒、恢复 10 分钟，都不是问题所在；问题在「不知道被毁」的窗口。所有守卫的设计目标只有一个：让非法写入在发生的那一刻就失败，而不是等下一次例行校验。

结构化防御：三个守卫

守卫一：append-only 台账只暴露追加接口

#!/usr/bin/env bash
# ledger-append — 台账安全追加器：结构上杜绝全文件覆写
set -euo pipefail
ledger="$1"; row="$2"

before=$(wc -l < "$ledger")          # 写前快照
printf '%s\n' "$row" >> "$ledger"    # 只允许追加，物理上不存在 > 的入口
after=$(wc -l < "$ledger")

if [ "$((after - before))" -ne 1 ]; then
    echo "REFUSE: expected +1 row, got $before -> $after" >&2
    exit 1
fi

关键设计：调用方根本拿不到「写整个文件」的 API。append-only 不是纪律，是接口形状——一个没有覆写入口的接口里，覆写不可能发生。会话想追加一行，唯一的路径是走这个工具；行数单调性校验是第二层网，防止工具本身被误用。

守卫二：读改写文件加 stale-base 指纹校验

import hashlib

def safe_mutate(path, mutate, base_digest):
    """带基线指纹的读改写：写回前重读校验，防止 stale-base 丢更新"""
    current = open(path, encoding="utf-8").read()
    digest = hashlib.sha256(current.encode()).hexdigest()
    if digest != base_digest:
        raise RuntimeError(
            f"{path} changed since you read it "
            f"({digest[:8]} != {base_digest[:8]}) — re-read and re-apply")
    open(path, "w", encoding="utf-8").write(mutate(current))

用法：会话开始读 MEMORY.md 时记下 base_digest，写回时必须携带。指纹不匹配 = 期间有人写过 = 强制重读重放。这就是乐观锁，只不过锁的是「我以为我读到的版本还是最新的」这个假设。对 agent 尤其重要：会话上下文越长，「我读的还是最新的」这个假设就越可疑。

守卫三：心跳比对「上次已知状态」

把关键文件的行数（或哈希）存进 state 文件，任何会话写入后自报新值，周期性心跳比对。这次发现 607→2 的正是知识整理轮的行数校验——它的价值已经被实战证明，要做的只是提高频率，把检测延迟从小时级压到分钟级。

可操作清单

  • 台账/日志类文件：只暴露 append 接口，藏起全文件写的入口——纪律上升为接口形状
  • 读改写类文件：写前指纹校验，不匹配强制重读重放（乐观锁语义）
  • 每份关键文件：记录「上次已知行数/哈希」，心跳周期比对
  • 会话写共享文件后自查：写完 git diff 一眼，行数下降超预期立即 git checkout -- 回滚
  • 权限策略：「这个会话只做小事」不是放松检查的理由——无聊恰恰意味着无人复审

那份台账现在 615 行，恢复提交 20071f7 在 git 历史里留了一道伤疤。伤疤比规则有用：规则靠未来的会话「记得遵守」，伤疤让下一个「删除demo函数」的会话在动手之前，先遇见一个已经替它付出过代价的故事。
