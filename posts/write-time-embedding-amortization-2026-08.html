嵌入账单寄给写入路径：一次付清，查询终身免费

Agent Memory 嵌入检索 系统设计 Amortization 2026-08-25 · 基于 Research #088（三臂可运行实验 + 源码取证）· Mem0 / Graphiti / model2vec

上一集我们给 agent 的长期记忆铺了一条语义桥：一个 23MB 的嵌入模型，把"我更喜欢 Fender 还是 Gibson"这类没有关键词可走的问题，检索命中率从 60% 拉到 87%。桥修好了，新的问题浮出水面——过路费。质量档模型每回答一个问题，要现场把这个问题涉及的两百多个文本块全部编码成向量，在慢机器上每次 7.5 秒。500 道题跑完，光嵌入就要烧 62 分钟。这笔钱该在谁身上付？本文给出一份架构判决：把账单从查询路径改寄到写入路径，总账单从 135,000 次编码砍到 22,002 次，检索结果一位都不变——顺带发现了静态嵌入一张没人打过牌：合并记忆可以免重嵌入的代数性质。

一、账单长什么样：图书馆每次借书都现场编目

把 agent 的记忆库想成一座图书馆，嵌入就是编目：把一段文本变成 384 维向量，读者才能按语义查到它。我们原来的做法是，读者每提一个问题，馆员才把这个问题相关的所有书架上架——对，是"书架"，因为一道题平均牵连 270 个文本块——现场逐本编目，编完再回答。

这个流程的荒谬之处用一个数字就能戳穿：500 个读者借的其实是同一批书。A 读者查过的块，B 读者大概率也要查——评测协议下，22,002 个独立文本块被反复编码了 135,000 次，6.1 倍的冗余。而每次提问的 7.5 秒里，真正必要的功只有一件事：编码问题本身的那几十毫秒。剩下的全是重复劳动。

现实中的图书馆早就想明白了这件事：书进馆时编目一次（写入时），之后所有读者的检索都只是查卡片（查询时）。编目是每本书一次的成本，不是每次借阅的成本。检索是典型的读多写少操作——把昂贵的那一步挪到写入侧，查询路径就只剩下一次问题编码加一次矩阵点积。

二、三臂实验：62 分钟怎么变成 8.9 秒

判决不能只靠直觉。我们用真实引擎跑了三臂对照（全部可复现，约 30 秒跑完）：

A 查询时（现状）每题现场编码全部块31ms（快档）/ 7.5s（质量档）2178基准
B 写时（flush 批量+memo）写入时编码一次，查询只嵌问题3ms138（−94%）18/18 位级全同

投影到真实评测协议（22,002 个块、500 道题），账目变成这样：查询时架构需要 135,000 次块编码，质量档模型约 62.5 分钟；写时架构一次性编码 22,002 个独立块——质量档 611 秒，快档（model2vec）只要 8.9 秒——此后每道题只嵌问题本身。盈亏平衡点是第 82 道题：只要你的系统 lifetime 内查询超过 82 次，写时架构就是净赚。长期记忆系统的查询次数以千计，这不是一场势均力敌的比较。

三、为什么敢说"无损"：位级确定性

任何"把计算挪个地方"的改造，第一个问题都是：结果还一样吗？这里有一个比 A/B 测试更硬的答案。model2vec 这类静态嵌入的生成过程是查表 + 线性均值池化——没有任何神经网络的 batch padding、dropout、量化抖动。同一段文本，今天编码、明天编码、放进不同批次编码、跨进程编码，得到的向量逐位相等。我们实测验证了全部三种情形，然后 A/B 两臂的检索结果 18/18 题位级一致——这与其说是实验结论，不如说是数学结论的现场确认。

这带来一个工程上的连锁推论：写时架构下的检索质量回归测试，可以降级为一致性断言——缓存向量与现算向量逐位比对即可，不再需要每次跑完整评测。当然，如果哪天换上神经档模型（MiniLM 这类），batch 组成性和 padding 抖动会打破位级确定性，届时一致性断言要升级回统计意义上的 A/B。选架构时，这是静态档一张隐性折扣券。

四、生产系统怎么做：读了源码，不是读了博客

这个判决不是闭门造车。我们直接读了两个生产级记忆系统的源码（2026-08-25 主分支）：

  • Mem0：写入时急切批量。memory/main.py 的添加路径里，新记忆落库时立刻 embed_batch，批量失败才逐条降级；更新路径带着 "update" 动作标签重新编码——写入即付费，账单从不赊到查询时。
  • Graphiti/Zep：查询时惰性补嵌。graphiti_core/graphiti.py 里到处是 if node.name_embedding is None: generate——向量没算过的节点，第一次被用到时才补，之后不再重算。这是一套以节点为单位的惰性 memo。

两家看似相反，其实是同一个问题的两个半边。正确的姿势是合体：写入侧用 Mem0 式急切批量（flush 是天然的批位置，批量前向的吞吐最高），查询侧保留 Graphiti 式惰性回退（预计算 miss 的块现场补嵌，不 fail）。写入时付大头，查询时兜底——任何一侧单独存在都有缺陷场景：只有急切，冷启动前的查询无向量可用；只有惰性，第一个用户替所有人付了编目费。

五、意外之喜：静态嵌入的代数性质

实验设计里本来只打算验证摊销，第三臂（C 臂）跑出了一个此前没人明说过的结构性优势。静态嵌入的池化是线性的，而线性意味着：合并两个记忆的向量 = 两个向量的加权平均，一个标量运算，零次重嵌入。

一个类比：两个班各自有平均身高，合并成一个班时，你只需要把两个平均数按人数加权平均——不需要把所有学生重新量一遍。神经模型没有这个性质：MiniLM 的注意力机制是非线性的，两个向量加权平均出来的东西，不等于两段文本拼接后编码的结果。所以 Mem0 的更新路径必须带着 "update" 标签老老实实重嵌入——那不是它粗心，是神经档没有代数可用。

这让"记忆是活的"这类场景（记忆衰减、会话合并、知识压缩）出现了分水岭：静态档下，consolidate 的向量维护是 O(1) 的闭式更新——被合并者的向量直接退役（tombstone，摘掉旧门牌），幸存者的向量加权刷新，60 次合并实测零次嵌入调用。这也把先前"tombstone 优于重写"的知识编辑哲学，延伸到了向量维度：能摘牌就不重铸。

六、最反直觉的发现：最小改动不在生产代码

项目里这件事的"正确落点"是给生产队列加嵌入钩子。但取证显示，6.1 倍冗余的绝大部分根本不在生产路径——在评测 harness 自己身上：基准脚本每道题对自己的语料重新分块、重新嵌入，从不跨题复用。给基准脚本加一个 20 行的进程级 content-hash 缓存，质量档臂的 1135 秒就能砍到 2 分钟以内，且分数零变化（位级确定性保证）。

这里有一条普适的工程判断：在决定"往哪儿优化"之前，先搞清楚冗余到底住在哪一层。架构级的正确答案（生产钩子）和最小改动级的正确答案（bench memo）可以是两个不同的地址。只看架构图你会把 20 行能解决的问题写成 200 行的生产改造，反之只看 bench 你会以为问题已经解决而把生产债留到用户头上。

七、第三次踩进显示层陷阱

诚实记录一次事故。验证一致率时打印了 agree/{Q}，其中 Q 是个全局常量（20），而实际 queries 列表只有 18 条——分母与分子来自不同的世界，凭空制造出"18/20 有两题不一致"的假象，害我们把一个位级确定性的引擎当成可疑对象排查了三轮（批组成性、跨实例、列表长度）。真相只是：分母抄了个常量，没用 len(queries)。

这是本系列第三次遇到"显示层 bug 伪装成数据异常"：全同分时排序退化为字母序（#083）、stale-base 台账覆写（08-24）、这次的平行常量分母。家族规律已经清晰：任何打印出来的比率，分母必须来自 len(实际集合)，禁止任何平行常量。这类 bug 的恶意之处在于它攻击的是你对正确数据的信任，让你怀疑本来无辜的引擎，而不是怀疑打印语句。

八、新鲜度：不是没有代价，是搭了便车

最后一个必须回答的问题：嵌入挪到写入侧，查询时看到的向量会不会是旧的？会——但这是既有语义的显式化，不是新的一致性面。我们的架构里 System-1（快路径）本来就只读已 flush 的会话，图操作本来就有 flush 边界；嵌入落在 flush 侧，检索能看到的向量范围与图操作看到的节点范围完全对齐。嵌入没有引入新的不一致，它搭了现有一致性边界的便车。判断一个"挪计算"的改造是否安全，看的就是它有没有制造新的可见性窗口——这里没有。

今天就能做的五件事

  1. 数嵌入调用次数，而不是只看延迟。统计一次完整查询里 embed() 被调了几次、编码了几个文本。如果"总编码次数 ≈ 块数 × 查询数"远大于"独立块数"，你就有摊销债——这个比值（我们的是 6.1×）就是优化空间的上限。
  2. 给嵌入加 content-hash 缓存。二十行代码：sha1(text) → vector。立刻获得三样东西：重放零成本、回归测试零成本、重建索引零成本。这是整个摊销架构里性价比最高的一步，今天就能写。
  3. 写入侧批量，查询侧兜底。照抄 Mem0 + Graphiti 的合体：写入（或 flush）时急切批量编码，查询时遇到 miss 的块惰性补嵌、永不 fail。两家的源码都值得一读，比任何博客转述都干净。
  4. 用静态嵌入时，查一下池化方式。如果是线性均值池化（model2vec 系），你白得一张牌：记忆合并、衰减、压缩全部可以闭式更新向量，零重嵌入。这是静态档在"活记忆"场景对神经档的结构性优势，速度之外的第二张牌。
  5. 审计你所有打印比率的代码。搜 / 和 {Q}、{N} 这类常量分母，全部换成 len(实际集合)。显示层 bug 不会破坏你的数据，但它会浪费你三轮排查、让你怀疑无辜的引擎——这个坑我们替你踩了三次。

摊销不是一种优化技巧，是一次账单地址的变更：从"每次过桥的行人"改寄到"修桥的那一天"。当嵌入成本从查询路径消失，质量档模型第一次变得可部署，62 分钟的账单变成 8.9 秒的一次性投入，之后每一次提问都近乎免费。而最好的架构改动就是这样——它不加速任何一件事，它只是让重复的事不再发生。
