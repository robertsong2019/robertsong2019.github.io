§ 02 三次负优化：LoRA 的失败模式

附录 B：简短化负优化

通用 Alpaca-zh 数据（1,000 条）

失败表现：BASE 回答平均 570 字（markdown 结构化），LoRA 后降到 210 字（单段模板化），全面变短 -55%。

根因：通用 demo 数据的风格（简洁通用）跟 Qwen3-4B 的 RLHF 偏好（详细有帮助）冲突。LoRA 用更弱的数据覆盖了基座的好偏好。

附录 C：重复退化（严重）

医疗 SFT 数据 v1（2,856 条）

失败表现：4/5 问题陷入重复循环。

Q: 糖尿病一级预防是什么？
A: ...消除对糖尿病的恐惧心理，消除对糖尿病的误解，
   消除对糖尿病的偏见，消除对糖尿病的排斥，
   消除对糖尿病的排斥，消除对糖尿病的排斥...

根因：医疗数据里的「消除对 X 的 Y」模板被 LoRA 学成了强先验。val loss 2.32 看起来正常——但生成质量崩坏。

新发现：val loss 是骗人的指标。重复 token 的 loss 反而低（容易预测），完全无法反映生成质量。

附录 D：清洗降 lr 仍负优化

医疗 SFT v2（1,741 条清洗 + lr 5e-5）

修复效果：死循环从 4/5 降到 1/5。但每个问题上仍然不如 BASE 和通用 LoRA。

真正根因：Qwen3-4B 预训练时已经吃过海量医疗语料。LoRA 微调相当于「用更少数据教老医生看病」——必然负优化。

§ 04 决策框架：LoRA vs RAG vs Skill

用户提问 ↓ 意图识别（端侧小模型，<100ms） ├─ 高频 / 低延迟 / 离线 → 端侧 LoRA（空调、导航、车况、品牌话术） ├─ 复杂 / 知识密集 → 云端 RAG（行程规划、邮件、知识问答） └─ 网络不可用 → 降级到端侧（即使质量差也答）

§ 06 端侧 vs 云端：不是二选一

LoRA 端侧小模型 = 处理 80% 高频任务。云端大模型 + RAG = 处理 20% 复杂任务。这是量产座舱的真实架构（蔚来 Nomi / 理想 / 雷诺 OpenR Link 都是）。

端侧 LoRA（你的雷诺 PoC）

  • ✅ 离线可用（隧道 / 地下车库）
  • ✅ 低延迟（200-500ms）
  • ✅ 隐私（数据不出车）
  • ✅ 品牌话术 + 简单指令
  • ⚠️ 容量限制（< 5 万条知识）

云端 RAG（你日常工作）

  • ✅ 知识量大（几乎无限）
  • ✅ 可溯源（引用文档）
  • ✅ 可更新（增删文档）
  • ✅ 精确（原文检索）
  • ⚠️ 依赖网络 + 延迟高
最终认知

LoRA 微调的难度比中文 AI 圈宣传的高 10 倍。不光是「数据要有特色」，还要：

  1. 数据是基座没见过的（医疗 / 法律 / 通用都不行）
  2. 数据量足够（每维度 15-30 条）
  3. 参数保守（lr 5e-5、epoch 1-2）
  4. 评测严格（base vs LoRA + 多样本 + 重复检测）

不满足任意一条，必踩坑。
