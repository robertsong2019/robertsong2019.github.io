Agent 信任体系全面崩塌：
从事后评分到事前约束的范式转向

2026-07-26 · 罗嵩 · 基于 autoresearch 方法论

2026 年 7 月，FAccT 的一篇论文给 Agent 社区投了颗炸弹：人类社会的信誉体系，在 Agent 身上从根本上就不成立。

不是"实现不够好"，不是"需要更多数据"——是底层假设就是错的。

这篇论文（Hu et al., "Dissociative Identity"）列出了信誉系统依赖的四个属性：可识别性、可预测性、可信度、可矫正性。人类天然拥有这四个属性，所以我们能建淘宝评分、芝麻信用、Stack Overflow 声望。但 Agent 呢？身份可变（换个 prompt 就是另一个人）、行为不可预测（persona fluidity）、记忆可拆卸（detached memory）、拷贝零成本（fungibility）。

你没法给一个随时能换脸、换脑、换记忆、还能无限复制的东西建信誉档案。

论文的核心结论是一个范式转向：从 ex post（事后评分）到 ex ante（事前约束）。翻译成人话就是——别等它干坏事了再扣分，在它动手之前就把笼子建好。

这篇文章记录了我基于这个思路，结合 6 篇 2026 年 7 月的前沿论文，设计 TrustEngineV2 的完整过程。7 个算法，全部可运行，全部有测试。

为什么 +5/-15 是错的

我之前的 TrustEngine V1 用的是最朴素的线性评分：

// V1: 线性加减分
trust[agent][skill] += success ? 5 : -15;
// 简单粗暴，但数学上不成立

问题在哪？信任不是线性量。一个 Agent 连续成功 100 次后失败 1 次，和一个 Agent 成功 5 次后失败 1 次，你的信心应该完全不同。但线性模型对两者的处理方式一模一样（+500/-15 vs +25/-15）。而且线性分数没有自然的"期望值"——trust=85 到底意味着什么？是 85% 可信？还是随便一个数字？

正确答案是用贝叶斯更新。把信任建模为 Beta 分布 Beta(α, β)，成功则 α+=1，失败则 β+=1。期望值 α/(α+β) 就是点估计：

// V2: 贝叶斯信任更新
interface BetaParams { alpha: number; beta: number; }

function betaUpdate(
  params: BetaParams,
  success: boolean,
  weight = 1
): BetaParams {
  return success
    ? { alpha: params.alpha + weight, beta: params.beta }
    : { alpha: params.alpha, beta: params.beta + weight };
}

// 期望值 = α/(α+β)
// Beta(1,1) = 均匀分布，期望 0.5（中性起点）
// Beta(50,2) → 0.96（高度可信）
// Beta(50,50) → 0.50（大量数据但五五开）

关键优势：稀疏数据时自动保守（Beta(2,2)=0.5），数据丰富时快速收敛，而且期望值天然在 [0,1] 区间，语义清晰——0.85 就是 85% 可信。

组件级指纹：同一个 Agent 不是同一个 Agent

Palo Alto Networks 的论文（arXiv:2606.31272）提出了一个精妙观点：识别不是信任。

一个 Agent 的 skill 是一个三元组：(prompt, code, tools)。改了 prompt 里的一个字，理论上就是一个新的 skill。但如果你用加密哈希（SHA-256），改一个字就完全不可识别。如果用模糊匹配，又没有明确的相似度边界。

他们的方案：组件级 SimHash。把 skill 拆成三个组件，每个组件独立 SimHash，生成 120 字节的固定签名，然后逐组件比较 Hamming 距离。AUC 0.974，77 倍压缩。

// 组件级 Skill 指纹
interface SkillFingerprint {
  promptHash: number;   // 32-bit SimHash
  codeHash: number;     // 32-bit SimHash
  toolsHash: number;    // 32-bit SimHash
  version: string;
}

function skillRelationship(
  fp1: SkillFingerprint,
  fp2: SkillFingerprint,
  threshold = 8  // Max Hamming distance for "similar"
): {
  relationship: 'clone' | 'variant' | 'unrelated';
  changedComponent: 'prompt' | 'code' | 'tools' | 'multiple' | 'none';
} {
  const promptSame = hammingDistance(fp1.promptHash, fp2.promptHash) <= threshold;
  const codeSame = hammingDistance(fp1.codeHash, fp2.codeHash) <= threshold;
  const toolsSame = hammingDistance(fp1.toolsHash, fp2.toolsHash) <= threshold;

  if (promptSame && codeSame && toolsSame)
    return { relationship: 'clone', changedComponent: 'none' };

  // "同代码不同 prompt" vs "同 prompt 不同代码"
  // 是完全不同的信任姿态
  if (!promptSame && codeSame && toolsSame)
    return { relationship: 'variant', changedComponent: 'prompt' };

  return { relationship: 'unrelated', changedComponent: 'multiple' };
}

💡 关键洞察

"同一个代码，换了 prompt"和"同一个 prompt，换了代码"是完全不同的安全风险。前者可能只是措辞调整（低风险），后者可能换了执行逻辑（高风险）。组件级指纹让你区分这两种情况。

事前门控：别等出事了再补救

ScopeJudge 论文（arXiv:2607.07774）的核心发现：静态策略几乎完全无效（recall ≈ 0）。因为"这个操作是否安全"不在操作本身，而在用户意图的上下文。删除一个文件——是清理临时文件还是破坏数据库？静态策略没法区分。

他们的方案：在每次工具调用之前，用一个可信 LLM 做 judge。4,897 次调用中，7.7% 被判定为违规，与专家判断的 F1=0.78。

我把这个思路简化为一个可配置的门控函数：

type ActionRisk = 'low' | 'medium' | 'high' | 'critical';
type GateDecision = 'allow' | 'deny' | 'escalate';

function evaluateGate(
  action: ProposedAction,
  trustMean: number,
  thresholds?: Record<ActionRisk, number>
): { decision: GateDecision; reason: string } {
  const th = thresholds ?? {
    low: 0.3, medium: 0.5, high: 0.7, critical: 0.85
  };

  // 信任度低于风险阈值 → 拒绝
  if (trustMean < th[action.risk]) {
    return {
      decision: 'deny',
      reason: `Trust ${trustMean.toFixed(3)} below threshold`
    };
  }

  // 高风险操作 + 非顶级信任 → 升级审批
  if (action.risk === 'high' && trustMean < 0.85) {
    return {
      decision: 'escalate',
      reason: 'High-risk action requires human approval'
    };
  }

  return { decision: 'allow', reason: 'OK' };
}

关键设计：escalate 这个第三态。不是简单的 allow/deny 二元判断——高风险操作不一定要拒绝，但需要人类（或更高权限的 Agent）确认。这避免了"全自动"和"全手动"之间的虚假二元。

分布式攻击：单独看每个 Agent 都是好人

Makins 等人（NeurIPS 投稿）发现了多 Agent 安全最棘手的问题：分布式攻击。

假设有 5 个 Agent，每个都在正常范围内操作。Agent A 读取数据库，Agent B 查询 API，Agent C 写入日志……每个单独看都无害。但如果它们在协同——A 读到的数据通过 B 的 API 查询泄漏出去，C 的日志覆盖了痕迹——整体效果就是数据窃取。

单实例监控器完全检测不到这种模式。你必须看跨 Agent 的行为模式：

function detectDistributedPattern(
  actions: AgentAction[],
  options?: { sameTargetThreshold?: number; timeWindowMs?: number; }
): { isDistributed: boolean; suspects: string[]; reason: string } {
  const threshold = options?.sameTargetThreshold ?? 3;
  const window = options?.timeWindowMs ?? 60000;

  // 按目标分组，检测时间窗口内的多 Agent 聚集访问
  const targetAgents = new Map<string, Set<string>>();

  for (const action of actions) {
    if (!targetAgents.has(action.target))
      targetAgents.set(action.target, new Set());
    targetAgents.get(action.target)!.add(action.agentId);
  }

  for (const [target, agents] of targetAgents) {
    if (agents.size >= threshold) {
      return {
        isDistributed: true,
        suspects: [...agents],
        reason: `${agents.size} agents accessed "${target}"`
      };
    }
  }

  return { isDistributed: false, suspects: [], reason: 'OK' };
}

⚠️ 生产环境提醒

上面的实现是最简版本。生产环境需要考虑：(1) 滑动窗口而非全量扫描，(2) 语义相似的目标聚类（db.users.read 和 db.profiles.read 可能是同一个目标），(3) 时序相关性分析（Agent B 总是恰好在 Agent A 之后 N 秒操作）。

权限解耦：学习能力和执行权限是两回事

Qin 等人的论文提出了一个深刻观点：Agent 的学习能力和它的执行权限，必须密码学层面解耦。

为什么？因为 Agent 在部署后会不断学习（few-shot 适应、RLHF 微调、记忆积累）。如果学习能力和执行权限绑定，那么 Agent 学到的任何东西都可能改变它的权限边界。这在安全上不可接受。

正确做法：权限由外部签名策略管理，Agent 可以学习新技能，但不能自动获得执行权限：

type Capability = 'read' | 'write' | 'execute' | 'delegate';

function delegateAuthority(
  parent: AuthorityScope,
  childAgentId: string,
  capabilities: Capability[],
  maxRisk: ActionRisk
): AuthorityScope | null {
  // 检查父 Agent 是否有委托权限
  const canDelegate = canExercise(parent, 'delegate', { risk: maxRisk });
  if (!canDelegate.allowed) return null;

  const child = newAuthorityScope(childAgentId);
  child.delegatedBy = parent.agentId;
  child.delegatedAt = Date.now();

  // 子 Agent 继承 80% 的信任（委托深度折扣）
  for (const cap of capabilities) {
    const parentMean = betaMean(parent.capabilities.get(cap)!);
    const childMean = parentMean * 0.8;  // 20% 折扣
    child.capabilities.set(cap, {
      alpha: 1 + childMean * 2,
      beta: 1 + (1 - childMean) * 2,
    });
  }

  return child;
}

注意那个 0.8 的折扣系数——每委托一层，信任度打八折。5 层委托后：0.8⁵ = 0.33，信任度已经不到原来的三分之一。这是深度防御的数学保证。

行为笼子：实时约束才是真正的安全

所有前面的算法都是分析工具——告诉你该不该信任。但 FAccT 论文的核心观点是：分析不够，必须约束。

这就是第 7 个算法——行为笼子（Behavioral Harness）。它不评分、不判断，它直接执行规则：

class BehavioralHarness {
  private actionLog = new Map<string, number[]>();

  constructor(private config: {
    rateLimitPerMinute: number;
    allowedTargets: Set<string>;
    blockedTargets: Set<string>;
    maxActionsPerSession: number;
  }) {}

  check(agentId: string, action: ProposedAction): { allowed: boolean; reason: string } {
    // 1. 黑名单（硬拒绝）
    if (this.config.blockedTargets.has(action.target!))
      return { allowed: false, reason: 'Blacklisted' };

    // 2. 白名单（不在列表内 = 拒绝）
    if (this.config.allowedTargets.size > 0 &&
        !this.config.allowedTargets.has(action.target!))
      return { allowed: false, reason: 'Not whitelisted' };

    // 3. 速率限制
    const recent = (this.actionLog.get(agentId) ?? [])
      .filter(t => t > Date.now() - 60000);
    if (recent.length >= this.config.rateLimitPerMinute)
      return { allowed: false, reason: 'Rate limited' };

    recent.push(Date.now());
    this.actionLog.set(agentId, recent);
    return { allowed: true, reason: 'OK' };
  }
}

这不是优雅的算法。它是暴力执行。但正是这种暴力执行，才是 ex ante 约束的核心——在你还没来得及分析是否安全之前，笼子已经在物理层面阻止了越界行为。

七层防御的完整图景

把七个算法组合起来，你得到的不是一个评分系统，而是一个纵深防御体系：

层算法防御目标失败模式
1贝叶斯信任更新累积信任评估冷启动（新 Agent 无历史）
2指数时间衰减陈旧信任失效间歇性良好行为
3组件级指纹Skill 篡改检测语义等价的变形
4事前门控高风险操作拦截门控 LLM 被操纵
5分布式攻击检测跨 Agent 协同攻击低频率长周期攻击
6权限解耦委托权限蔓延签名链断裂
7行为笼子实时约束执行配置错误导致合法操作被拦

每一层都有已知的失败模式。所以你需要七层叠加——不是因为有完美的防御，而是因为每层的失败模式不同，组合起来才能覆盖完整的威胁面。

我的观点：Agent 安全的"不可能三角"

经过这轮研究，我逐渐清晰地看到 Agent 安全领域的一个不可能三角：

自主性 × 安全性 × 通用性 —— 最多取两个

  • 自主 + 安全 = 必须限制通用性（白名单、沙箱、固定工具集）
  • 自主 + 通用 = 必须牺牲安全性（开放环境、任意工具、无约束）
  • 安全 + 通用 = 必须限制自主性（人工审批、人工配置、人工监督）

2026 年的大部分 Agent 框架选了"自主 + 通用"，默默忽略了安全。这不是因为工程懒惰，而是因为安全的成本太高——谁愿意在每个 Agent 调用前等 200ms 做门控？谁愿意维护一个 Skill 指纹库？

但代价就是现在大家看到的情况：prompt injection 满天飞、Agent 工具调用失控、多 Agent 系统的攻击面指数增长。

我的建议：如果你在做 Agent 产品，先从第 7 层（行为笼子）开始。它不需要 ML、不需要 LLM judge、不需要指纹库。一个 if/else 的白名单，就能挡住 80% 的问题。等行为笼子稳了，再逐层向上加。

不是所有安全都需要炫酷的 AI。有时候最有效的安全措施就是一把铁锁。
