重放，而不是重排版——一个纯 C 推理引擎把确定性做成了稀缺品

推理引擎 确定性 KV 缓存 AI Agent 2026-10-06 · 基于 antirez/ds4 (DwarfStar) README 与实现的调研

antirez（Redis 作者）今年的开源新作 ds4 是一个纯 C 本地推理引擎。第一眼看，卖点好像是"不依赖 Python 栈、Mac 上能跑"；读完实现你会发现，它真正稀缺的品质是确定性——几乎每个关键机制都在回答同一个问题："同样的输入，能不能得到字节级相同的处理路径？"在 agent 时代，这件事从美德变成了刚需：多轮对话、工具调用、断点续跑、评测回归，每一步都在考验系统对"同一个"的判定能力。

零、先认识一下这个项目

DwarfStar（ds4）主要面向 DeepSeek V4 Flash，兼容 GLM，支持 Metal / CUDA / ROCm 三条后端。它刻意做窄——不是通用 GGUF runner：模型加载、prompt 渲染、工具调用、KV 状态、HTTP server、coding agent，在同一个 C 代码库里一起构建、一起测试。核心引擎不链接 GGML，但作者明确致谢 llama.cpp 打开的道路。

这种"窄"换来的是一种罕见的品质：整个系统每一步都可以问为什么。ds4 给我上了四课，每一课都关于确定性。

一、缓存身份：键是字节，不是 token

KV 缓存是长上下文本地推理的生命线：已见过的 prompt 前缀不必重算，直接复用注意力状态。问题在"命中"怎么判定。

直觉方案是拿 token 序列（或其哈希）当键。但 BPE 分词不是拼接安全的：合并可能跨越切分边界，"分块编码再拼接"未必等于"整体编码一次"——同一段文本，在不同 chunk 边界切开分别编码，边界处的字节可能被并进不同的 token。也就是说，token 流不仅取决于内容，还取决于切分历史。拿它做身份键，就会出现内容没变却被判为"新会话"的假阴性（白算一遍 KV），以及更危险的假阳性。

ds4 的选择：用字节前缀做身份——对 prompt 的原始字节算 SHA1，字节相同才算同一个前缀；冷保存时宁可裁掉尾部若干 token、对齐 chunk 边界留出 BPE 合并余量，也不让分词错位污染身份。

import hashlib

# 反例：token 序列做缓存键 —— 随切分历史漂移
joined_a = encode("".join(chunks))                 # 整体编码一次
joined_b = encode(chunks[0]) + encode(chunks[1])   # 分块编码再拼接
assert joined_a != joined_b  # BPE 边界合并 → token 流不稳定

# ds4 的做法：字节前缀哈希做身份，与切分历史无关
def prefix_id(prefix_bytes: bytes) -> str:
    return hashlib.sha1(prefix_bytes).hexdigest()[:16]

def try_restore(new_prompt: bytes):
    pid = prefix_id(new_prompt)
    if pid in cache_index:          # 字节相同 ⇒ 同一个前缀
        restore(cache_index[pid])   # KV 不必重算

配套设计也值得抄一笔：/strip 命令保留会话文本、删掉大块 KV 载荷——身份与载荷分离，文本可以廉价长期保存，重的注意力状态按需重建（恢复时 prefill）。这与数据库圈"逻辑日志与物化状态分离"是同一条老定律。

通用法则：缓存键要对你控制不了的东西不变（重新分词、切分历史），对你关心的东西敏感（内容本身）。选错键的缓存系统，会在最难调试的时刻给你假命中。

二、工具调用：重放字节，不重排版

Agent 多轮工具调用有一个隐蔽的漂移源。模型采样出工具调用时，产出的是一段具体的字节块（ds4 的 DSML 格式）。客户端执行完工具、把结果发回来时，引擎要把历史重新渲染进 prompt。此时最容易犯的错：引擎"顺手"用自己的格式化器把工具调用重新排版一遍——格式对得上，字节对不上。

后果是双重的：前缀字节变了 → token 流变了 → KV 缓存整体 miss；更糟的是，重新排版后的文本不再是模型实际采样过的分布——模型在"读一段它没说过的话"。

ds4 的第一道防线是精确重放：每个工具调用拿一个不可猜测的 tool ID，server 在一张有界的、radix tree 支撑的内存映射里记住 tool id → 模型采样时的精确 DSML 字节块。客户端带着 tool ID 回来时，渲染器用当年采样的字节，不用新格式化的近似品。这张映射还会存进 KV 快照文件，跨 server 重启存活——渲染请求前先扫缓存文件，把历史中出现的 tool ID 对应的映射加载回来，精确重放甚至不依赖"命中的就是同一份 KV 快照"。

class ExactReplay:
    """tool_id -> 采样时的精确字节块；重放优先，重排版兜底"""
    def remember(self, tool_id, sampled_bytes):
        self.radix.set(tool_id, sampled_bytes)   # 有界内存，radix 压缩

    def render_tool_call(self, tool_id, reformatter):
        hit = self.radix.get(tool_id)
        if hit is not None:
            return hit                 # 第一层：精确重放采样字节
        try:
            return canonical(reformatter())     # 第二层：确定性规范化
        except NotCanonicalizable:
            return enforce_dsml(reformatter())  # 第三层：语法强制兜底

三层兜底承认一个现实：精确重放覆盖不了所有情况（映射有界、客户端可能不带合法 ID），但每一层的输出都比下一层更接近"模型采样过的事实"。

通用法则：模型采样过的东西是不可变数据，不是可以重算的函数。任何"系统对同一信息的两次表达"（重新格式化、重新序列化、重新分词）都是潜在的分布漂移源。

三、故障分类学：两种失败，两种药

分布式推理（多副本）下，ds4 把失败语义二分：传输失败（消息没送到，但状态可复现 → 换路由重发）和 hash 失配（对端没有你以为的那个状态 → 必须重放前缀，而不是重发）。

def on_error(err):
    if isinstance(err, TransportError):
        return reroute(next_replica)     # 状态可复现 → 换路由重发
    if isinstance(err, HashMismatch):
        return rebuild_prefix(err.ctx)   # 对端缺状态 → 重放

把两种失败折叠成同一种"重试"，是分布式系统里最贵的偷懒：对 hash 失配做重发，永远命中同一个失配，重试风暴就是这么来的。这和 shutil.which() 把 missing / broken / timeout 三种失败看成一种，是同一条定律在单机与分布式两端的投影：可靠性工程的第一步是失败分类学——不同的病，不同的处方。

四、评测指纹：把"期望输出"钉到 token 级

ds4-eval 跑 92 题嵌入式能力回归，期望的 token 数被钉死在用例里；--regrade-trace 能对一份已有 trace 重新打分而不重新生成；README 诚实注明"这是 DwarfStar 的集成检查，不是官方排行榜分数"。

为什么钉 token 数这么较真？因为它把"能力回归"和"管线漂移"区分开了：输出 token 数变了，先怀疑的不是模型变笨，而是分词、渲染、采样路径上有东西悄悄变了。这和我自己在评测管线里维护的指纹纪律完全同构——官方 run 前钉死 PYTHONHASHSEED，跑完核对三个指纹数字，偏离即说明数据或管线错了，好得可疑先查伪影。确定性引擎给用户的核心资产不是"更快"，是归因能力：坏数字出现时，你能问出正确的问题——模型变了？数据变了？还是管线变了？——并且系统答得上来。

尾声：确定性是人机协作的土壤

ds4 的 README 有一节 "AI full disclosure"：这个项目在 AI coding agents 的强辅助下开发，人类主导想法、测试与调试。很多人把这读成一句坦诚的声明，但它其实是一个循环论证：这种协作方式在这个代码库上成立，恰恰因为代码库每一层都为可复现而设计——缓存身份是字节级的、工具调用可精确重放、失败有分类学、评测有指纹。AI 写代码的速度越快，"每次运行是否还是同一个系统"就越值钱。

antirez 在 Redis 上证明了"简单数据结构 + 极端克制"能撑起全球基础设施；ds4 在推理引擎上证明的是同一件事的新版本：在生成式时代，手写的、窄的、每一步都能问为什么的系统，反而是最能承载 AI 协作开发的系统。速度是参数，确定性是接口。选引擎的时候，多看一眼后者。
