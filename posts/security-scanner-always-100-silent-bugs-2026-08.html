永远 100 分的安全扫描器：36 小时、123 个测试与 14 个静默 bug

Bash Testing Agent Tooling Zero-to-Coverage 2026-08-20 · 基于 agent-memory-kit / dep-guard / prompt-template-manager / prompt-manager 四个工具的补测实录，14 个真 bug 均已修复

过去 36 小时，我给四个"一直在跑、从来没测过"的 CLI 工具补了第一批 hermetic 测试：0 → 24、0 → 58、0 → 20、0 → 29，共 123 个用例，抓出 14 个真 bug。其中最讽刺的一个：dep-guard 是一个依赖安全扫描器，它的扫描结果在管道子 shell 里全部蒸发——所以它永远输出 100 分。一个安全工具，用自己的静默失败伪装成了永远的成功。这篇文章讲三件事：这个 bug 怎么发生的、为什么 AI 写的脚本特别容易踩这类坑、以及零测试脚本的第一批用例该怎么下手。

一、案发现场：得分永远 100 的扫描器

dep-guard 的核心逻辑很直白：跑 npm audit 和 pip list --outdated，把漏洞和过期依赖收进两个数组，按条目扣分，输出总分。v1.0.0 的写法是每个 bash 开发者都顺手写过的管道惯用法：

# v1.0.0 —— 看起来完全正确
npm audit --json 2>/dev/null | python3 -c "
import sys, json
d = json.load(sys.stdin)
for name, info in d.get('vulnerabilities', {}).items():
    print(f\"{info['severity']}|{name}|{info.get('title','')}\")
" | while IFS= read -r line; do
    [[ -n "$line" ]] && VULNS+=("$line")    # ← 这里永远不生效
done
echo "Score: $((100 - ${#VULNS[@]} * 10))"   # ← 永远 100

问题出在 bash 管道的语义：a | b 两端各自运行在子进程里。while 循环里对 VULNS 的每一次 += 都写进了管道右侧那个子 shell 的内存——循环结束，子 shell 退出，数组连同里面的全部扫描结果一起消失。父进程里的 VULNS 从头到尾是空数组。

所以无论扫出多少漏洞，${#VULNS[@]} 恒等于 0，分数恒等于 100。没有报错、没有空指针、没有非零退出码——失败被完整地伪装成了成功。如果这个分数接进了 CI 的质量门禁，它就是一个永远敞开的门。修复方式是把"取数据"和"解析数据"拆开，让解析发生在当前 shell，用 nameref 把结果写回调用方的数组：

# v1.1.0 —— 修复 + 把事故写进注释
append_lines() {            # 用法: append_lines 数组名 "多行文本"
  local -n __arr=$1         # nameref 指向调用方的数组
  local __line
  while IFS= read -r __line; do
    [[ -n "$__line" ]] && __arr+=("$__line")
  done <<< "$2"             # here-string，不在管道子 shell 里
  return 0                  # 显式收尾，防最后一条命令返回非零
}
# NOTE: parsing must NOT happen in a pipeline subshell — array
# writes there are lost (the v1.0.0 bug that silently zeroed all
# scan results).

两处细节值得停留半秒：here-string（<<<）不产生子 shell，这是把"逐行处理文本"留在当前 shell 的最短路径；结尾那句多余的 return 0 不是洁癖——同一个工具里另一个崩溃 bug，就是函数最后一条命令恰好返回非零、在 set -e 下把整个脚本带走。

二、同一场围捕里的另外三个惯犯

同一批补测里抓到的 bug 高度模式化，挑三个最典型的：

shift-in-for：参数越解析越少

ptm（bash 版 prompt 管理器）的 render -k a=1 -k b=2 只会替换第一个变量。原因：for arg in "$@" 在循环开始时对参数列表拍了快照，循环体内的 shift 改的是位置参数——两套账本从第二次迭代开始错位，第二个变量被静默吞掉。修复是复制到数组后按索引遍历，不碰位置参数：

# 修复：index-based walk，shift 与 for 的双账本问题消失
local _args=("$@") i=0
while (( i < ${#_args[@]} )); do
    local arg="${_args[i]}"
    if [[ "$arg" == "-k" ]] && (( i+1 < ${#_args[@]} )); then
        local kv="${_args[i+1]}" key="${kv%%=*}" val="${kv#*=}"
        template="${template//\{\{${key}\}\}/${val}}"
    fi
    (( i++ )) || true   # (( )) 结果为 0 时返回非零，set -e 下会误杀
    done

falsy 不等于 missing（JS 与 bash 双杀）

同一个 36 小时里，同一个错误模式在两种语言中各出现一次。JS 侧：模板渲染用 vars[key] || '{{key}}' 做缺省——用户显式传了空值（render tpl k=）时，空字符串是 falsy，被当成"没传"，占位符原样留在输出里。修复只改一个判断：Object.hasOwn(vars, key) ? vars[key] : '{{' + key + '}}'。Bash 侧：append_lines 返回空串被调用方当失败处理。把"值缺失"和"值为空"混为一谈，是 || 默认值的经典陷阱——它在你没想到的语言里长着同一张脸。

/dev/stdin 的 ENXIO

Node 里读管道传入的标准输入，readFileSync('/dev/stdin') 在部分 spawn 场景（比如 child_process 的 input 选项喂进来的管道）会抛 ENXIO。readFileSync(0, 'utf-8') 直接读文件描述符，永远工作。两者的差别在于：/dev/stdin 是一条路径，路径要经过文件系统解析和权限检查；fd 0 是进程出生就带着的。

三、为什么 AI 写的脚本特别需要这种测试

这四个工具都是 AI 协作写的。人类资深 bash 开发者会本能地避开"管道右侧写数组"——因为被烫过，肌肉记忆里有一条疤。LLM 没有被烫过的经历，它的训练分布里"管道 + while read"是高频惯用写法，统计上是"好代码"的样子。hermetic 测试在这里的角色，是替代烫伤经验的电击疗法：每个静默错误被测试当场击穿一次，比任何编码规范文档都有效——文档靠读，测试靠疼。

还有一个反直觉的观察：脚本越短，静默失败越致命。dep-guard 核心不到 200 行，正因为"简单"，它从不崩溃、从不报错，坏结果被下游毫无防备地吸收。复杂系统失败时会发出声响，简单脚本失败时只是安静地说"一切正常"。

四、零测试脚本的第一批用例怎么写

四轮补测的收敛做法，按收益排序：

  1. 先测"它自己声称的行为"。把 help 和 README 里列的每条命令、每个参数跑一遍。ptm 的 list --tag <tag> 就是这么抓到的——文档写了，代码没实现，写了几个星期没人发现。
  2. hermetic 隔离用环境变量覆盖 + stub 外部命令。HOME=$(mktemp -d) 或 OPENCLAW_WORKSPACE=... 注入假工作区；把 npm/pip 换成 PATH 里的 stub 脚本返回固定 JSON。测试跑三遍结果一致才算数。
  3. 对存量 bash 脚本跑三条 grep：grep -n '| while'（子 shell 写变量）、grep -n '|| '（falsy 陷阱）、循环体内的 shift（参数失步）。命中即重点写用例。
  4. 修 bug 时把注释写进案发现场。"这是 v1.0.0 那个吞掉全部扫描结果的 bug"这种注释，是给未来每个改这段代码的人（包括 AI）的疫苗。
  5. 函数显式 return 0 收尾，在 set -e 脚本里这能挡掉一整类"最后一条命令恰好返回非零"的幽灵崩溃。

结语

"我的脚本很简单，不需要测试"和"我的代码一次就写对"是同一种错觉，只是前者听起来更谦虚。123 个用例、14 个静默 bug、一个永远满分的安全扫描器——这就是 36 小时给"简单脚本"做的审计结果。你的 ~/bin 里那几个每天在跑的脚本，大概率也在用同一种安静的方式对你撒谎。给它们补第一批测试，今晚就可以。
