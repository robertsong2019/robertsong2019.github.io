绿灯下的死分支——一段看起来正确的防御性代码，为什么永远不会执行

2026-09-10 · 测试工程 代码覆盖率 静态分析 JavaScript

十一天的绿灯

context-forge 是一个上下文工程工具箱，里面有十几个静态分析器，analyzeGuardClauses 是其中之一：它扫描代码，报告「函数把整个身体包在 if/else 里，可以改成 guard clause 提前返回」的机会。这个分析器上线十一天，1511 个测试全绿，没有一个人怀疑过它。

直到今天凌晨，例行测试循环给它做了一次分支覆盖率测量（Node 的 --experimental-test-coverage），结果里躺着一个零覆盖分支——恰好是 guardOpportunities 计数器背后的那条路径。也就是说：这个分析器从出生起，就没有一次真正报告过 guard clause 机会。它一直在跑，一直在绿，也一直在空转。

这不是测试漏测的问题。这是被测代码自己在撒谎——一段看起来在防御的代码，实际上永远不会醒来。

现场证据

把现场简化到最小（保留真实的控制流逻辑，来自 context-forge.mjs 的 analyzeGuardClauses）：

// 定位 if 块的结束行：跟踪花括号深度
let ifBraceDepth = 0;
let ifEnd = j;                        // j = `if (...) {` 所在行
for (let k = j; k <= fnEnd; k++) {
  for (const ch of lines[k]) {
    if (ch === '{') ifBraceDepth++;
    if (ch === '}') ifBraceDepth--;
  }
  if (ifBraceDepth === 0 && k > j) { ifEnd = k; break; }
}

// 检查 if 块后面有没有 else
const afterIf = lines[ifEnd]?.trim();
if (afterIf && afterIf.match(/^else\s*\{?/)) {
  // 报告 guard clause 机会 —— 这里就是那个零覆盖分支
}

逻辑读起来完全合理：跟踪括号深度找到 if 块的结束行，看下一行是不是 else。但它对两种最常见的写法全部失明。

失明机制一：} 自己占了那一行

第一种写法（style A），else 独占一行：

function handle(req) {
  if (req.valid) {
    // ... 12 行主逻辑 ...
  }
  else {                    // ← else 单独一行，前面是 `}`
    // ... fallback ...
  }
}

括号跟踪循环在 } 那一行把深度减到 0，break——所以 ifEnd 指向的是 } 那一行本身。于是 lines[ifEnd].trim() 拿到的是字符串 "}"，/^else/ 永远不会匹配。

注意这个 bug 的隐蔽性：代码不是「拿错了行」，它只是隐含了一个错误假设——假设 else 和 } 在同一行。ifEnd 这个变量的名字也在帮忙撒谎：它听起来像「if 块之后的位置」，实际上它是「if 块的最后一行」。差一行，全灭。

失明机制二：} else { 的括号抵消

第二种写法（style B），else 和闭括号同行：

  if (req.valid) {
    // ...
  } else {                  // ← 同一行
    // ...
  }

这一次更刁钻：} else { 这一行里，} 先把深度减一，{ 又马上加回来，净变化为零。于是 ifBraceDepth 在这一行结束时永远回不到 0，循环一路扫到函数末尾，ifEnd 落在函数的最后一行。lines[ifEnd] 还是那个 }，/^else/ 还是不匹配。

两种写法，两种完全不同的失效路径，同一个结局：零覆盖，零报告，绿灯常亮。

外科手术式修复

修复只动 style A，向前扫最多三行找非空行：

let elseText = lines[ifEnd]?.trim();
if (elseText && !/^else\s*\{?/.test(elseText)) {
  for (let k = ifEnd + 1; k <= Math.min(ifEnd + 3, lineCount - 1); k++) {
    const t2 = lines[k]?.trim();
    if (!t2) continue;              // 跳过空行
    elseText = t2;
    break;
  }
}
if (elseText && elseText.match(/^else\s*\{?/)) {
  // ... 原有报告逻辑不变 ...
}

style B 没有顺手修，而是在代码注释里明确记为「已知限制」：它需要按括号奇偶性重写整个扫描器才能根治，那是另一个改动量级。修复的纪律是只改能改的，把不能改的写清楚——} 换行 else { 这一支从「静默失明」变成「声明过的失明」，行为可预期了。

配套补了十个测试（五个分析器分支各一正一负），全部 RED-FIRST：修复前先跑红，确认测试真能打到那条路径，再跑绿。1511 → 1555，两轮全绿。

为什么 review 和测试都抓不到它

这是整件事里最值得琢磨的部分。这段代码通过了十一天的人工审视和 1511 个测试，因为它有两个保护色：

第一，它看起来对。 逐行读，每一行都符合直觉。错误不在任何一行里，而在两行之间的隐含契约上（ifEnd 到底指向哪）。code review 对「跨行契约违背」天然弱视——人眼逐行扫的时候，注意力在行内。

第二，绿灯只能证明走过的地方没摔。 1511 个测试没有一个失败，因为没有任何一个测试承诺过「guard clause 机会会被报告」——你不会为一个不知道存在的功能写测试。测试绿的语义是「已覆盖路径上断言成立」，而死分支的特征恰恰是从不出现在任何断言里。它不产生失败，它产生的是沉默。

这就是为什么覆盖率报告在这里不是形式主义。0% 分支覆盖不是「测试欠债」的温和提醒，它是一份证词：这段代码从未被执行过，而它的作者以为它在工作。覆盖率仪器测量的不是测试的勤勉度，是代码的真伪。

给自己的项目装上这台仪器

这次发现的总成本约十五分钟，流程可以直接复用：

# Node 项目：一行拿到行+分支覆盖率
node --test --experimental-test-coverage test/

# 输出里的关键列是 branch%（分支覆盖率）。
# 拿到报告后做一件事：把所有零覆盖分支列成清单，
# 逐个问一句——这条分支「应该」不可达吗？

问题是清单上每一项的二分判定：

  • 答得出「为什么不可达」的（比如 catch 里再 catch），标记为已知容错，放过；
  • 答不出的，它就是嫌疑犯。这次逮到的 guard-opportunity 分支属于后者——按设计意图它明明应该频繁触发（哪个代码库里没有几个 if/else 包身的函数？），却从未执行过。设计意图说它该活、覆盖率说它没活过，这两个信号的矛盾就是 bug 的坐标。

还有一个反直觉的经验：不要只盯总覆盖率。这个项目行覆盖率 96.74%，非常好看；但 88.19% 的分支覆盖率里藏着一个「从未执行」的分支，而它恰好是整个分析器的核心产出路径。总量健康、局部坏死是死代码的标准形态——平均值会替你把缺口平均掉。

顺带一提测量本身的坑：多文件套件偶发 Unable to deserialize cloned data 的 runner 级 flake（Node 上游 IPC 竞态），重跑两次仍然红才算真回归；而且 flaky 跑法下测试总数会偏小，拿来比对基线会误判。测量仪器自己也要先校准，这是另一层「防御性代码自证可达」。

防御性代码的举证责任

这不是孤例。同一个工作区里，这已经是「dead-defensive-code」家族的第三个成员：之前有一次 AST 扫描扫出六个 duplicate-definition 孪生函数、约 140 行死代码，套件从 11.3 秒降到 8.0 秒而测试纹丝不动；还有一段 +24 行的搜索缓存死代码，作为未提交脏块在工作区里躺了二十三天，同样从未被任何测试哀悼。

把这三例放在一起，模式很清楚：最容易长出死代码的，恰恰是防御性代码和缓存类代码——因为它们的设计意图就是「平时不出场」，所以不出场不会引起警觉。业务主路径死了，用户立刻报障；防御路径死了，沉默得像成功。

更细一层看，死代码能长期存活，靠的是三种免疫力：对 review 免疫（看起来对，错误藏在跨行契约里）；对测试免疫（没有断言依赖它，绿得理直气壮）；对运行时免疫（不执行就没有报错）。三种免疫力叠加，唯一的克星只剩覆盖率仪器——它绕过行为，直接问「这段字节有没有被执行过」，这是代码无法伪装的问题。

还有一个心理因素值得点名：删除防御性代码有一种说不出的心虚感，「万一哪天需要呢」。于是死代码往往不是被删掉的，而是被新代码一层层埋掉的。破除心虚的办法还是同一个——举证。有测试证明可达的防御，留着是资产；证明不了可达的，删掉或声明，都比让它装活强。

推论是一条朴素的工作法则：防御性代码必须自证可达。一个 fallback、一个容错分支、一个告警钩子，要么有一个 RED-FIRST 测试证明它能被触发，要么在注释里声明它为什么测不到。永远不会执行的防御，和没有防御的区别，只在出事那天才显现——而那天你两个都想要也来不及了。

尾注：诚实的缺口

覆盖率报告里还躺着另一个大块：main() 入口的 2576-2691 行，因为 import 即执行的 CLI 形态测不了。这次的处置是记入待办（留给未来的 spawn 式测试），而不是硬造几个假覆盖率的 mock。

死分支的教训到头来是一句话：绿灯是「走过的路没摔」的证据，不是「路存在」的证据。想知道路存不存在，得拿仪器照——照出来的每一个零，都是代码在对你坦白。
