给 Agent 一台"电脑"：Agent 运行时环境的演进与设计

2026-08-12 · AI Agent Runtime Infrastructure Python
2026-08-12 技术随笔。过去三年，Agent 技术栈的焦点从"框架"（LangChain、AutoGen）转向了"记忆"（Mem0、Letta），现在正在进入第三个阶段——运行时。2026 年 8 月，Cloudflare 开源了 computer 项目，给 Agent 一台真正的"电脑"：持久文件系统、多后端执行环境、状态在重启间存活。这不是孤例——loopx、OpenClaw、TencentDB-Agent-Memory 都在从不同角度收敛到同一个抽象。本文梳理 Agent 运行时环境的设计空间，给出一个最小可用运行时的 Python 实现，并讨论这个新基础设施层的未来方向。

一、从 API 调用到"拥有电脑"

1.1 Agent 的 homelessness 问题

当前主流的 AI Agent 有一个未被言说的尴尬：它们无家可归。

一个典型的 Agent 交互是这样的：


用户 → [LLM API] → 推理 → [工具调用] → 结果 → [LLM API] → 回答

每次交互都是无状态的。Agent 没有"家"——没有持久的工作目录，没有跨会话的文件系统，没有可以在重启后恢复的进程状态。所谓的"记忆"不过是一个外挂的向量数据库，就像一个人每天早上醒来都失忆了，只能靠翻笔记本回忆昨天发生了什么。

这不是设计缺陷，而是历史遗留。Agent 技术栈从聊天机器人演化而来，而聊天机器人本来就不需要"家"——它们只需要回答问题。但当 Agent 开始执行多步骤任务——写代码、管理文件、运行测试、协调多个工具——"无家可归"就变成了真正的工程瓶颈。

考虑一个真实场景：你让 Agent 帮你重构一个 Python 项目。Agent 需要：

  1. 浏览项目文件结构
  2. 理解模块间的依赖关系
  3. 制定重构计划
  4. 逐文件修改
  5. 运行测试验证
  6. 如果失败，回退并重试

这个过程可能持续几个小时，中间需要多次暂停和恢复。在当前的架构下，每一次暂停都意味着丢失所有中间状态——文件浏览器中缓存的目录结构、已经制定的计划、已修改但未验证的文件列表。Agent 必须"重新发现"这一切。

这就是 Agent 的 homelessness 问题：不是没有能力，而是没有持久的工作环境来承载这些能力。

1.2 Cloudflare 的"电脑"

2026 年 8 月，Cloudflare 开源了 computer 项目，提出了一个简洁有力的概念：给 Agent 一台真正的电脑。

这不是比喻。computer 在 Cloudflare Durable Object 上构建了一个虚拟文件系统，以 SQLite 为权威状态，支持三种执行后端：


// 同一接口，三种执行环境
await workspace.runtime.exec(source, { backend: 'container' });  // 真实 Linux (FUSE 挂载)
await workspace.runtime.exec(source, { backend: 'isolate-shell' }); // Worker 内 bash
await workspace.runtime.exec(source, { backend: 'isolate-js' });    // Worker 内 ES module

关键设计决策：

  • 文件系统是权威状态：不是 LLM 的上下文窗口，不是内存中的临时变量，而是 SQLite 支持的持久文件系统。Agent 写入的文件在重启后仍然存在。
  • 执行后端可切换：同一个 API 可以在真实 Linux 容器、Worker Isolate 和纯 JS 环境之间无缝切换，按需选择安全性和能力的平衡点。
  • computerd 守护进程：通过 capnweb RPC 同步状态，FUSE 元数据操作的性能甚至超过真实磁盘。

这是一个重要的范式转变：Agent 的"运行时"不再只是 LLM 的推理过程，而是一个包含文件系统、进程管理、状态持久化的完整计算环境。

1.3 不只是 Cloudflare

Cloudflare 不是唯一走这条路的项目。2026 年中，多个独立项目从不同方向收敛到"Agent 运行时"这个概念：

项目方向核心抽象
Cloudflare/computer基础设施层虚拟文件系统 + 多后端执行
loopx控制层持久化控制状态（objective + gates + todos + scope）
OpenClaw操作层Workspace + Skills + Session + Heartbeat
TencentDB-Agent-Memory记忆层四类资产（Chat/Skill/Wiki/CodeGraph）的团队级共享
Uber/ADR安全层Agent 行为检测与响应（ADR Sensor）

这五个项目分别解决了 Agent 运行时的不同侧面，但它们有一个共同点：都在为 Agent 构建"持久化的工作环境"。 这不是巧合——当 Agent 从 demo 走向生产，从单次交互走向持续运行，运行时环境就成了绕不开的基础设施。

二、Agent 运行时的设计空间

2.1 从操作系统借用概念

传统操作系统解决了三个核心问题：

  1. 进程管理：谁在运行？谁拥有资源？
  2. 文件系统：数据如何组织？如何持久化？
  3. IPC（进程间通信）：多个执行单元如何协作？

Agent 运行时面临高度类似的问题，但有一个关键区别：Agent 的"进程"是由 LLM 推理驱动的，而非确定性的机器代码。这意味着传统 OS 的设计不能直接搬用——每个抽象都需要为"概率性执行"重新设计。

2.2 四层抽象

一个完整的 Agent 运行时需要四层抽象：

Layer 1: Workspace（工作空间）

类比操作系统的用户主目录。每个 Agent 实例（或每个用户-Agent 对）有自己的独立工作空间，包含文件、配置和状态。Workspace 是隔离的边界——一个 Agent 不能访问另一个 Agent 的文件（除非显式共享）。

关键设计：

  • Workspace 状态持久化在数据库（而非内存）中
  • 重启后可以恢复到精确的之前状态
  • 支持快照和回滚

Layer 2: Session（会话）

类比操作系统的进程。一个 Agent 可以同时运行多个会话——一个处理代码审查，一个处理日程安排，一个在后台监控邮件。每个会话有自己的上下文窗口、工具权限和执行状态。

关键设计：

  • 会话是并发的基本单位
  • 会话之间可以通过共享 Workspace 协作
  • 会话有生命周期：创建、暂停、恢复、终止

Layer 3: Skills（技能）

类比操作系统的应用程序。Skills 是 Agent 可以调用的结构化能力——读文件、搜索 Web、操作数据库、调用外部 API。每个 Skill 有自己的权限边界和执行环境。

关键设计：

  • Skills 是声明式的（描述"做什么"而非"怎么做"）
  • Skills 可以动态加载和卸载
  • Skills 的执行结果缓存在 Workspace 中

Layer 4: Memory（记忆）

类比操作系统的虚拟内存交换文件。Memory 是 Agent 跨会话的知识基础——过往交互的总结、用户偏好、学到的经验教训。

关键设计：

  • Memory 是分层级的（短期/长期/元认知）
  • Memory 的写入和检索是两个独立的操作
  • Memory 需要维护（整合、衰减、冲突解决）

2.3 为什么这四层缺一不可

去掉任何一层，你都会得到一个"残缺"的 Agent：

  • 没有 Workspace：Agent 无法持久化中间结果，每次重启从零开始
  • 没有 Session：Agent 无法并发处理多个任务，一次只能做一件事
  • 没有 Skills：Agent 只能"说"，不能"做"——无法与外部世界交互
  • 没有 Memory：Agent 不记得过去，无法从经验中学习

当前主流的 Agent 框架通常只实现了其中一到两层。LangChain 有 Skills（Tools）和 Session（Memory），但没有真正的 Workspace 和 Memory（它的"memory"本质上是会话历史）。Letta 有 Memory 和 Session，但 Workspace 概念薄弱。OpenClaw 是少数尝试实现全部四层的系统。

三、实现一个最小 Agent 运行时

让我们用 Python 实现一个最小可用的 Agent 运行时——大约 200 行代码，但包含全部四层抽象。这个实现不追求生产级，而是帮助你理解核心设计。

3.1 Workspace：基于 SQLite 的持久文件系统


import sqlite3
import json
import time
from pathlib import PurePosixPath
from contextlib import contextmanager

class Workspace:
    """Agent 的持久工作空间。基于 SQLite，支持文件系统语义。"""

    def __init__(self, db_path: str):
        self._conn = sqlite3.connect(db_path, check_same_thread=False)
        self._conn.execute("""
            CREATE TABLE IF NOT EXISTS filesystem (
                path TEXT PRIMARY KEY,
                content BLOB,
                metadata TEXT,  -- JSON: {created, modified, owner, tags}
                created_at REAL,
                modified_at REAL
            )
        """)
        self._conn.execute("""
            CREATE TABLE IF NOT EXISTS snapshots (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                timestamp REAL,
                state TEXT  -- 完整文件系统的 JSON 序列化
            )
        """)
        self._conn.commit()

    def write(self, path: str, content: bytes, metadata: dict | None = None):
        """写入文件，自动管理时间戳和元数据。"""
        now = time.time()
        meta = metadata or {}
        meta.setdefault("created", now)
        meta["modified"] = now

        self._conn.execute(
            "INSERT OR REPLACE INTO filesystem VALUES (?, ?, ?, ?, ?)",
            (path, content, json.dumps(meta), meta["created"], now)
        )
        self._conn.commit()

    def read(self, path: str) -> bytes | None:
        row = self._conn.execute(
            "SELECT content FROM filesystem WHERE path = ?", (path,)
        ).fetchone()
        return row[0] if row else None

    def list_dir(self, prefix: str = "/") -> list[str]:
        """列出某前缀下的直接子项（类似 ls）。"""
        rows = self._conn.execute(
            "SELECT path FROM filesystem WHERE path LIKE ? ORDER BY path",
            (f"{prefix}%",)
        ).fetchall()
        return [r[0] for r in rows]

    def snapshot(self) -> int:
        """创建当前状态的快照，用于回滚。"""
        now = time.time()
        all_files = self._conn.execute(
            "SELECT path, content, metadata FROM filesystem"
        ).fetchall()
        state = json.dumps({
            r[0]: {"content": r[1].hex(), "metadata": r[2]}
            for r in all_files
        })
        cur = self._conn.execute(
            "INSERT INTO snapshots (timestamp, state) VALUES (?, ?)",
            (now, state)
        )
        self._conn.commit()
        return cur.lastrowid

    def restore(self, snapshot_id: int):
        """恢复到指定快照。"""
        row = self._conn.execute(
            "SELECT state FROM snapshots WHERE id = ?", (snapshot_id,)
        ).fetchone()
        if not row:
            raise ValueError(f"Snapshot {snapshot_id} not found")

        state = json.loads(row[0])
        self._conn.execute("DELETE FROM filesystem")
        for path, data in state.items():
            self._conn.execute(
                "INSERT INTO filesystem VALUES (?, ?, ?, ?, ?)",
                (path, bytes.fromhex(data["content"]),
                 data["metadata"], time.time(), time.time())
            )
        self._conn.commit()

注意几个设计决策：

  1. SQLite 作为权威状态，而非内存。即使进程崩溃，文件系统状态也完好无损。
  2. 快照是一等公民。Agent 在执行有风险操作前可以先 snapshot，失败后 restore。这比 git 轻量得多，但解决了同样的"安全网"问题。
  3. 元数据是 JSON，而非固定 schema。不同类型的文件可以有不同的元数据（代码文件有 language tag，日志有 rotation policy）。

3.2 Session：会话生命周期管理


from dataclasses import dataclass, field
from enum import Enum
import uuid

class SessionStatus(Enum):
    ACTIVE = "active"
    PAUSED = "paused"
    TERMINATED = "terminated"

@dataclass
class Session:
    """Agent 会话：一个独立的执行上下文。"""
    id: str = field(default_factory=lambda: str(uuid.uuid4()))
    workspace: Workspace = None
    status: SessionStatus = SessionStatus.ACTIVE
    context: list[dict] = field(default_factory=list)  # 消息历史
    tool_permissions: set[str] = field(default_factory=set)
    metadata: dict = field(default_factory=dict)
    created_at: float = field(default_factory=time.time)
    last_active: float = field(default_factory=time.time)

    def add_message(self, role: str, content: str):
        """向会话上下文添加消息。"""
        self.context.append({
            "role": role,
            "content": content,
            "timestamp": time.time()
        })
        self.last_active = time.time()

    def get_context_window(self, max_tokens: int = 8000) -> list[dict]:
        """获取最近的消息，控制在 token 预算内。

        策略：从最新消息向前回溯，估算 token 数（~4 chars/token），
        直到达到预算。同时保留 system prompt（如果有）。
        """
        if not self.context:
            return []

        system_msgs = [m for m in self.context if m["role"] == "system"]
        non_system = [m for m in self.context if m["role"] != "system"]

        budget = max_tokens
        result = list(system_msgs)

        for msg in reversed(non_system):
            msg_tokens = len(msg["content"]) // 4
            if budget - msg_tokens < 0:
                break
            budget -= msg_tokens
            result.insert(len(system_msgs), msg)  # 插在 system 之后

        return result

    def pause(self):
        self.status = SessionStatus.PAUSED

    def resume(self):
        self.status = SessionStatus.ACTIVE
        self.last_active = time.time()

    def terminate(self):
        self.status = SessionStatus.TERMINATED

get_context_window 是一个值得注意的方法。它实现了一个简单但有效的上下文预算策略：system prompt 永远保留，其他消息从最新向前回溯，直到 token 预算耗尽。这是运行时"资源管理"的一个微型实例。

3.3 Skill：声明式工具系统


from typing import Callable, Any

@dataclass
class Skill:
    """Agent 技能：一个可声明、可发现、可审计的能力单元。"""
    name: str
    description: str
    handler: Callable[..., Any]
    required_permissions: set[str] = field(default_factory=set)
    cost_estimate: float = 0.0  # 预估成本（美元），用于预算控制
    cache_ttl: int = 0  # 结果缓存时间（秒），0 表示不缓存

class SkillRegistry:
    """技能注册表：管理 Agent 可用的所有技能。"""

    def __init__(self):
        self._skills: dict[str, Skill] = {}
        self._cache: dict[str, tuple[float, Any]] = {}  # key -> (expiry, result)

    def register(self, skill: Skill):
        self._skills[skill.name] = skill

    def list_skills(self, permissions: set[str] | None = None) -> list[Skill]:
        """列出当前可用的技能，可按权限过滤。"""
        if permissions is None:
            return list(self._skills.values())
        return [
            s for s in self._skills.values()
            if s.required_permissions.issubset(permissions)
        ]

    def execute(self, skill_name: str, session: Session, **kwargs) -> Any:
        """执行技能，自动处理缓存和权限检查。"""
        if skill_name not in self._skills:
            raise ValueError(f"Unknown skill: {skill_name}")

        skill = self._skills[skill_name]

        # 权限检查
        if not skill.required_permissions.issubset(session.tool_permissions):
            missing = skill.required_permissions - session.tool_permissions
            raise PermissionError(
                f"Session lacks permissions: {missing}"
            )

        # 缓存检查
        cache_key = f"{skill_name}:{hash(frozenset(kwargs.items()))}"
        if skill.cache_ttl > 0 and cache_key in self._cache:
            expiry, cached = self._cache[cache_key]
            if time.time() < expiry:
                return cached

        # 执行
        result = skill.handler(session=session, **kwargs)

        # 缓存写入
        if skill.cache_ttl > 0:
            self._cache[cache_key] = (time.time() + skill.cache_ttl, result)

        return result

这里有几个值得讨论的设计决策：

为什么 Skill 是 dataclass 而不是函数？ 因为 Skill 需要携带元数据（权限、成本、缓存策略），这些元数据需要在执行前被检查。一个裸函数无法表达"这个操作需要写权限"或"这个 API 调用大约花 $0.03"。

为什么有成本预估？ 在生产环境中，Agent 的每次工具调用都可能在花钱——API 调用、云服务费用、LLM token。一个成熟的运行时应该在执行前检查预算，而不是在月底收到账单时才后悔。

3.4 把它们组合起来


class AgentRuntime:
    """最小 Agent 运行时：组合四层抽象。"""

    def __init__(self, workspace_path: str):
        self.workspace = Workspace(workspace_path)
        self.skills = SkillRegistry()
        self.sessions: dict[str, Session] = {}
        self._heartbeat_handlers: list[Callable] = []

    def create_session(self, permissions: set[str] | None = None) -> Session:
        """创建新会话。"""
        session = Session(
            workspace=self.workspace,
            tool_permissions=permissions or set(),
        )
        self.sessions[session.id] = session
        return session

    def get_session(self, session_id: str) -> Session | None:
        return self.sessions.get(session_id)

    def cleanup_stale_sessions(self, max_idle_seconds: int = 3600):
        """清理长时间不活动的会话。"""
        now = time.time()
        stale = [
            sid for sid, s in self.sessions.items()
            if now - s.last_active > max_idle_seconds
            and s.status == SessionStatus.ACTIVE
        ]
        for sid in stale:
            self.sessions[sid].pause()

    def on_heartbeat(self, handler: Callable):
        """注册心跳处理器，用于定期检查和后台任务。"""
        self._heartbeat_handlers.append(handler)

    def heartbeat(self):
        """执行一次心跳：清理、检查、后台任务。"""
        self.cleanup_stale_sessions()
        for handler in self._heartbeat_handlers:
            handler(self)


# ---- 使用示例 ----

if __name__ == "__main__":
    runtime = AgentRuntime("/tmp/agent_workspace.db")

    # 注册技能
    def read_file_handler(session, path: str):
        return session.workspace.read(path)

    def write_file_handler(session, path: str, content: str):
        session.workspace.write(path, content.encode())
        return f"Written {len(content)} bytes to {path}"

    runtime.skills.register(Skill(
        name="read_file",
        description="Read a file from the workspace",
        handler=read_file_handler,
        required_permissions={"read"},
        cost_estimate=0.0,
    ))
    runtime.skills.register(Skill(
        name="write_file",
        description="Write a file to the workspace",
        handler=write_file_handler,
        required_permissions={"write"},
        cost_estimate=0.0,
    ))

    # 创建会话
    session = runtime.create_session(permissions={"read", "write"})
    session.add_message("system", "You are a helpful coding assistant.")
    session.add_message("user", "Create a file called hello.py with a print statement.")

    # 执行技能
    runtime.skills.execute("write_file", session, path="/hello.py", content="print('Hello, World!')")
    content = runtime.skills.execute("read_file", session, path="/hello.py")
    print(f"File content: {content.decode()}")

    # 快照与恢复
    snapshot_id = runtime.workspace.snapshot()
    runtime.skills.execute("write_file", session, path="/temp.py", content="# temporary")
    print(f"Files before restore: {runtime.workspace.list_dir('/')}")
    runtime.workspace.restore(snapshot_id)
    print(f"Files after restore: {runtime.workspace.list_dir('/')}")

    # 上下文窗口管理
    for i in range(100):
        session.add_message("user", f"Message number {i} " * 50)
    window = session.get_context_window(max_tokens=2000)
    print(f"Context window: {len(window)} messages (from {len(session.context)} total)")

四、Agent 运行时的未来：三个方向

4.1 安全边界：从 sandbox 到 capability

当前 Agent 运行时面临的最大挑战不是性能，而是安全。

Cloudflare/computer 用容器隔离来解决这个问题——Agent 在一个受限的 Linux 环境中运行，无法突破。但这是一种粗粒度的隔离。更精细的方案是 capability-based security：Agent 不拥有全局权限，而是每个操作都需要显式的 capability token。


# 概念示例：capability-based 权限
class Capability:
    """细粒度权限：不授予 'write' 全局权限，而是精确到路径。"""
    def __init__(self, action: str, resource: str, expires_at: float):
        self.action = action        # "write"
        self.resource = resource    # "/projects/blog/_drafts/*"
        self.expires_at = expires_at

    def is_valid(self) -> bool:
        return time.time() < self.expires_at

    def matches(self, action: str, resource: str) -> bool:
        import fnmatch
        return (self.action == action
                and fnmatch.fnmatch(resource, self.resource)
                and self.is_valid())

这种模型让 Agent 的权限遵循最小权限原则——只能写入草稿目录，不能碰生产代码。Uber 的 ADR 系统更进一步，通过运行时监控 Agent 的实际行为来检测异常，即使在权限范围内的操作也可能被标记为可疑。

4.2 多 Agent 协作：从单机到网络

当前我们讨论的 Agent 运行时都是单 Agent 的——一个 Workspace、一个 Session 集合、一个 Memory。但生产环境中的 Agent 系统越来越像微服务架构：

  • 一个"编排 Agent"负责任务分解和分配
  • 多个"专家 Agent"负责具体领域（代码、文档、测试）
  • 一个"审计 Agent"负责监控和验证

这意味着 Agent 运行时需要支持跨 Agent 通信。loopx 项目给出了一个有趣的思路：把 Agent 的控制状态（objective + gates + todos）作为共享的持久化数据结构，多个 Agent 可以读写同一个看板（Kanban），通过 claim/gate/monitor/writeback 操作器协作。这本质上是微服务架构中的共享数据库模式。

4.3 Agent 的"操作系统"标准

更远的问题：会不会出现一个 "Agent OS" 标准，就像 Linux 之于服务器、Android 之于手机？

2026 年的趋势正在指向这个方向。MCP（Model Context Protocol）正在成为 Agent 与工具之间的标准接口——相当于 USB 协议。Agent 运行时的概念正在从各个方向收敛——相当于 BIOS 和引导加载器。OpenClaw 的 Workspace + Skills + Session 抽象、Cloudflare 的虚拟文件系统、loopx 的控制状态模型，都是这个未来操作系统的不同侧面。

但 Agent OS 不会像传统 OS 那样统一——因为 Agent 的执行模型本质上不同于确定性代码。Agent OS 需要处理概率性执行、上下文窗口限制、LLM API 的延迟和不可用性。它更像是一个弹性运行时——假设每一步都可能失败，每一步都需要验证和回退机制。

五、结语：运行时不是终点，是起点

Agent 技术栈的成熟遵循一条清晰的路径：

  1. 框架时代（2023-2024）：解决"怎么调用 LLM"——LangChain、AutoGen
  2. 记忆时代（2025-2026 上半年）：解决"怎么让 Agent 记住"——Mem0、Letta、agent-memory-graph
  3. 运行时时代（2026 下半年-）：解决"Agent 在哪里运行"——Cloudflare/computer、OpenClaw、loopx

每个阶段都建立在前一个的基础之上。没有记忆，运行时只是空壳；没有运行时，记忆只是无组织的堆积。

如果你正在构建 Agent 系统，现在是一个好时机来思考这些问题：你的 Agent 有"家"吗？它的文件在重启后还在吗？它能在多个任务之间并发吗？它的权限是否受到约束？

这些问题看起来是工程细节，但它们决定了你的 Agent 是一个"玩具"还是一个"工具"。

Agent 不需要变得更聪明——它需要一个住的地方。
