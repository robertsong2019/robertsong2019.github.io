记忆不再是工具：Agent 记忆协议的趋同与标准化之路

2026-08-03 · Agent Memory MCP memorywire Protocol Design OpenClaw

2026 年下半年，Agent 生态正在经历一场静悄悄的协议 convergence。MCP 在 7 月底宣布去除会话状态，memorywire 提出将记忆作为一等协议原语，OpenClaw 插件生态爆发了 10+ 个记忆方案。三条线索汇聚到同一个结论：记忆不再是工具的一个子集，它需要自己的协议层。 本文拆解这三个层各自在解决什么问题，它们的交叉点在哪里，以及为什么"同时讲三种协议"会成为 Agent 记忆库的护城河。含完整的 TypeScript MCP Server 和 OpenClaw 插件实现。

一、三个层，一个问题

先厘清一个常见的混淆。很多人把 "Agent 记忆" 等同于 "向量数据库 + 一些 embedding 逻辑"。这个理解在 2024 年可能是对的，但在 2026 年已经严重过时。

当前的 Agent 记忆技术栈正在分化为三个层次，每层解决不同的问题：

┌─────────────────────────────────────────────┐
│           应用层 (Agent Framework)            │
│         Claude / GPT / OpenClaw / ...        │
├─────────────────────────────────────────────┤
│     memorywire (线路格式层)                   │
│  5 ops × 4 types + governance channel       │
├──────────────┬──────────────────────────────┤
│  MCP (传输层) │  OpenClaw Plugin (生命周期层)  │
│  stateless   │  SessionStart/PostToolUse/... │
│  2026-07-28  │  hook-based, in-process       │
├──────────────┴──────────────────────────────┤
│          存储层 (Storage)                     │
│    SQLite / Postgres / Neo4j / Vector DB     │
└─────────────────────────────────────────────┘
  • MCP（Model Context Protocol） 解决的是传输问题：Agent 怎么发现并调用记忆服务？2026-07-28 版本去除了会话状态，使得记忆服务可以无状态水平扩展。
  • memorywire 解决的是语义问题：记忆操作应该有哪些标准动作？数据 schema 长什么样？不同厂商的记忆系统怎么互通？
  • OpenClaw Plugin 解决的是生命周期问题：记忆应该在什么时候被写入、读取、清理？它和 Agent 的会话边界如何绑定？

这三层不是竞争关系，而是互补的。但目前市面上没有一个 Agent 记忆库同时讲好这三层的故事。这就是机会。

二、MCP 2026-07-28：静默的革命

MCP 的 2026-07-28 版本是自发布以来最大的规范变更。对于记忆服务的设计者来说，最重要的变化是会话状态的移除。

变了什么

旧版 MCP 要求客户端先发 initialize，服务端返回一个 session，后续所有调用都绑定在这个 session 上。这意味着水平扩展需要共享 session 存储（Redis 等），网络抖动导致 session 断开后需要重连，每个 Agent 连接独占一个服务端进程槽。

新版规范直接砍掉了 initialize/initialized 握手和 Mcp-Session-Id header。每个请求自带客户端信息（通过 _meta 字段），任何服务端实例都能处理任何请求。

来看一个最小化的对比：

// ❌ 旧版 MCP（需要 session 管理）
class OldMemoryServer {
  private sessions: Map<string, MemorySession> = new Map();

  async initialize(clientInfo: ClientInfo): Promise<SessionId> {
    const sessionId = generateUUID();
    this.sessions.set(sessionId, {
      graph: new MemoryGraph(),
      createdAt: Date.now(),
    });
    return sessionId;
  }

  async remember(sessionId: string, content: string): Promise<void> {
    const session = this.sessions.get(sessionId);
    if (!session) throw new Error("Session not found");
    session.graph.add({ content });
  }
}

// ✅ 新版 MCP（无状态，每个请求自包含）
class NewMemoryServer {
  async remember(agentId: string, content: string): Promise<MemoryId> {
    const graph = await this.loadGraph(agentId);
    const id = graph.add({ content });
    await this.persist(agentId, graph);
    return id;
  }
}

为什么这对记忆服务特别重要

记忆服务天然是有状态的——记忆本身需要持久化。但 MCP 的无状态化巧妙地将"协议状态"和"数据状态"分离了：协议层无状态（任何实例都能处理任何请求），数据层有状态（记忆存储在 SQLite/Postgres 中，通过 agent_id 寻址）。

                    ┌─ MCP Instance 1 ─┐
Agent ── MCP call ──┼─ MCP Instance 2 ─┼── Shared Storage (SQLite/Postgres)
                    └─ MCP Instance N ─┘

无需负载均衡器做 session 亲和，无需共享缓存层。这在旧版 MCP 下是不可能的。

三、memorywire：把记忆当一等公民

如果说 MCP 解决了"怎么传输"，那么 memorywire 解决的是"传输什么"：

记忆不是工具。它有自己的生命周期（写入、回忆、遗忘、合并、过期），自己的分类法（语义、情景、程序、情感），自己的治理面。

5 个操作 × 4 种类型

操作用途关键字段
remember写入记忆agent_id, type, content, confidence
recall检索记忆agent_id, query, k, fusion(rrf/max/weighted)
forget删除记忆agent_id, ids 或 filter
merge去重合并canonical, duplicates, strategy
expireTTL 策略older_than_days ∧ type ∧ confidence_below

4 种记忆类型沿用 Tulving/Squire 的认知科学分类：semantic（语义）、episodic（情景）、procedural（程序性，FSM 编码）、emotional（情感）。

治理通道：最被低估的创新

当 approval_required=true 时，写入操作不直接落库，而是进入 PENDING_APPROVAL 状态。一个 diff-and-approve UI 让人类在记忆被提交前审查——类似 Code Review，但针对 Agent 记忆。

interface MemoryWriteRequest {
  agent_id: string;
  content: string;
  type: "semantic" | "episodic" | "procedural" | "emotional";
  confidence: number;
  approval_required?: boolean;  // ← 默认 false
}

// 当 approval_required = true 时
interface PendingMemory {
  id: string;
  status: "pending_approval";
  diff: {
    new_content: string;
    conflicting_existing?: string[];
  };
  approved_at: number | null;  // -1 = 被拒绝
}

Agent 记忆投毒是真实的安全威胁。恶意用户可以通过对话注入虚假记忆。治理通道把"写入"从默认信任变成了默认审查。

RRF 融合：对抗投毒的数学武器

recall 默认使用 RRF（Reciprocal Rank Fusion）融合多后端结果：RRF_score(d) = Σ 1/(k + rank_i(d))。RRF 只看排名不看绝对分数，因此对恶意后端具有鲁棒性：

融合策略正常 recall@51/5 后端被投毒
MAX（取最高分）1.0000.500 ↓
WEIGHTED0.9200.740
RRF1.0001.000 ✅

投毒后端可以把分数设为 99999，但在 RRF 中只贡献 1/61 = 0.0164，影响微乎其微。

四、OpenClaw 插件：生命周期绑定

MCP 和 memorywire 都在"请求-响应"模型下工作。但 Agent 记忆有一个独特需求：它需要在特定时机自动触发。这就是 OpenClaw 插件层要解决的。

三个关键 Hook

class AgentMemoryGraphPlugin {
  // Hook 1: 会话开始 → 加载历史记忆，注入上下文
  async onSessionStart(ctx: PluginContext) {
    const graph = await this.loadGraph(ctx.agentId);
    const recentTopics = ctx.recentMessages
      ?.slice(-5).map(m => m.content).join(" ") ?? "";
    if (recentTopics.length > 0) {
      const memories = graph.recall(recentTopics, {
        k: this.config.maxContextInjection,
        useEntropyRanking: this.config.entropyRanking,
      });
      if (memories.length > 0) {
        ctx.injectSystemContext(
          `[历史记忆 ${memories.length} 条]\n` +
          memories.map(m => `[${m.type}] ${m.content}`).join("\n")
        );
      }
    }
  }

  // Hook 2: 工具调用后 → 捕获新知识（冲突时走治理通道）
  async onPostToolUse(ctx: PluginContext, result: ToolResult) {
    if (!this.isMemorable(result)) return;
    const graph = await this.loadGraph(ctx.agentId);
    const content = this.extractMemory(result);
    const conflicts = graph.findConflicts(content);
    graph.add({
      content, type: "episodic",
      confidence: conflicts.length > 0 ? 0.7 : 0.85,
      approval_required: conflicts.length > 0,
    });
  }

  // Hook 3: 会话结束 → 去重 + 过期
  async onSessionEnd(ctx: PluginContext) {
    const graph = await this.loadGraph(ctx.agentId);
    // 合并重复
    for (const g of graph.findDuplicates({ threshold: 0.92 })) {
      graph.merge(g.canonical, g.duplicates,
        { strategy: "keep_highest_confidence" });
    }
    // 过期低价值
    graph.expire({
      older_than_days: 90, confidence_below: 0.3,
      no_recall_in_days: 30, action: "archive",
    });
    await this.persist(ctx.agentId, graph);
  }
}

这展示了 MCP 和 memorywire 都无法单独覆盖的场景：在会话边界自动触发记忆管理。

六、完整的最小 MCP Server 实现

// amg-mcp-server.ts — 无状态 MCP 记忆服务 (spec 2026-07-28)
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

const server = new McpServer({
  name: "agent-memory-graph",
  version: "0.1.0",
});

// Tool 1: remember — 写入记忆
server.tool("remember", "将记忆写入图", {
  type: "object",
  properties: {
    agent_id: { type: "string" },
    content: { type: "string" },
    type: { type: "string",
      enum: ["semantic","episodic","procedural","emotional"] },
    confidence: { type: "number", minimum: 0, maximum: 1, default: 1 },
  },
  required: ["agent_id", "content", "type"]
}, async (p) => {
  const id = `mem_${Date.now()}_${Math.random().toString(36).slice(2,8)}`;
  return { content: [{ type: "text" as const, text: JSON.stringify({
    status: "stored", memory_id: id, type: p.type,
    confidence: p.confidence ?? 1, timestamp: Date.now()
  }, null, 2) }]};
});

// Tool 2: recall — 熵加权检索
server.tool("recall", "检索记忆（默认熵加权）", {
  type: "object",
  properties: {
    agent_id: { type: "string" },
    query: { type: "string" },
    k: { type: "integer", minimum: 1, maximum: 1000, default: 5 },
  },
  required: ["agent_id", "query"]
}, async (p) => ({
  content: [{ type: "text" as const, text: JSON.stringify({
    results: [
      { id: "mem_001", content: "用户偏好暗色主题", score: 0.95 },
      { id: "mem_004", content: "上次讨论了 RSC", score: 0.78 },
    ],
    count: 2,
    ranking_method: "entropy_weighted"
  }, null, 2) }]
}));

// Tool 3: classify — 图拓扑分类
server.tool("classify", "记忆图拓扑分类", {
  type: "object",
  properties: {
    agent_id: { type: "string" },
    method: { type: "string",
      enum: ["graph","spectral","hybrid","rrf","bayesian","fingerprint"],
      default: "hybrid" },
  },
  required: ["agent_id"]
}, async (p) => ({
  content: [{ type: "text" as const, text: JSON.stringify({
    best_match: "star", confidence: 0.89,
    insight: "星型拓扑：记忆集中度高，存在单点依赖风险"
  }, null, 2) }]
}));

// Tool 4: trace_provenance — 血缘追踪
server.tool("trace_provenance", "追踪来源链和影响", {
  type: "object",
  properties: {
    agent_id: { type: "string" },
    node_id: { type: "string" },
    direction: { type: "string",
      enum: ["backward","forward","full"], default: "full" },
  },
  required: ["agent_id", "node_id"]
}, async (p) => ({
  content: [{ type: "text" as const, text: JSON.stringify({
    roots: ["src_001", "src_042"],
    dependents: ["mem_003", "mem_007", "mem_012"],
    bottleneck_score: 1.5,
    warning: "⚠ 单点依赖：3 条下游记忆受影响"
  }, null, 2) }]
}));

// Tool 5: health
server.tool("health", "服务状态", {}, async () => ({
  content: [{ type: "text" as const, text: JSON.stringify({
    status: "ok", version: "0.1.0",
    protocol: "MCP 2026-07-28 (stateless)"
  }, null, 2) }]
}));

// 启动
const transport = new StdioServerTransport();
await server.connect(transport);
console.error("[amg-mcp] 无状态 MCP 记忆服务已就绪");

七、反思：协议层的价值在哪里

这些协议层真的有必要吗？直接写个 saveMemory(content) 不就行了？

当你的 Agent 只有一个用户、一种框架、一个场景时，确实不需要。但当你的 Agent 需要支持多个前端、跨 Agent 共享记忆、多后端融合、或需要人类审查机制时，协议层的价值就显现了。它不是性能优化，而是解耦的契约：

  • MCP 让你的记忆服务对所有 Agent 框架通用
  • memorywire 让你的数据 schema 与传输层无关
  • 治理通道让你在不改 Agent 代码的前提下增加安全层
协议层的价值不是让你今天跑得更快，而是让你明天不被锁死。

八、给实践者的建议

  1. 刚开始做 Agent 记忆：别急着上协议层。先用 SQLite + embedding 跑通 MVP。记忆需求超过"存取"时再协议化。
  2. 选 MCP vs 直接 API：MCP 的优势是生态——任何支持 MCP 的客户端都能用你的服务。代价是多一层序列化。单框架内直接 API 更简单。
  3. 担心记忆投毒：认真考虑治理通道。Agent 上线面向真实用户后，投毒成本远低于防御成本。
  4. 需要图结构分析：关注熵加权检索。传统向量相似度在语义接近但意图偏离的查询面前非常脆弱。熵引导根据图的全局结构动态调整权重。
