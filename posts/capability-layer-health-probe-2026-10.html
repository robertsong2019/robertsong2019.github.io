AI Agent 能力层设计 健康检查 后端路由 2026-10-05 · 基于 Panniantong/Agent-Reach（90.3k★，Trendshift 日榜 #1）agent_reach/channels/base.py 与 probe.py 源码实读，对照本地 agent 基础设施的同类故障

两个故障，相隔千里：2026 年 6 月 yt-dlp 被 B 站风控全面封杀，装了 Agent-Reach 的用户零感知切换 bili-cli；我的服务器上 python3 -m pytest 退出码 0、日志 0 字节，实际什么都没跑。共同点：能力清单上都写着"有"，是现实腐烂了，清单不知道。一个 17 平台接入层项目，用七十行 base.py 给出答案：别信任何声明，包括用户自己的——每个能力都要真的跑一遍才算活着。

两个相隔千里的故障

第一个故障发生在 2026 年 6 月。yt-dlp——这个星球上最通用的视频下载工具——被 B 站风控全面封杀。无数依赖它的脚本、工作流、agent 工具一夜之间集体失明。但装了 Agent-Reach 的用户什么都没感觉到：上游切换到了 bili-cli，路由表重排，零操作。

第二个故障发生在我的服务器上。某天跑一个测试套件，python3 -m pytest -q 退出码 0，日志文件 0 字节，一切看起来正常——实际上什么都没跑。机器上的 python3 前置包装把模块式调用静默吞掉了。这个故障阴险的地方在于：它骗过的不是错误检查，是成功检查。退出码 0，谁能想到呢。

两个故障的共同点：在各自的"能力清单"上，这两个能力都写着"有"。yt-dlp 在配置里，python3 在 PATH 上。清单没骗人，是现实腐烂了，清单不知道。

Agent 系统正在批量产生这种清单。给 agent 装了十几个工具、接了七八个平台，每个都在 README 或 SKILL.md 里声明"已配置"——然后平台改版、风控升级、Python 升级、venv 失效。Agent-Reach 这个 17 平台接入层项目（一周涨了 1.7 万 star，Trendshift 当日 #1）真正值得学的不是"又一个大而全工具集"，而是它把"能力可用性"当成一等公民来设计的三个动作。

一、探测分类学：which() 的三种不可区分的失败

shutil.which(cmd) 是几乎所有 agent 框架检查工具的方式：PATH 上找得到，就算装了。Agent-Reach 的 probe.py 开头一句话就把这个惯例钉在墙上：

Distinguishes the three failure modes that look identical to shutil.which()

——区分那三种在 which() 眼里长得一模一样的失败：

  1. missing：命令不在 PATH 上。最诚实的一种，找不到就是找不到。
  2. broken：命令存在，但无法执行。最常见的成因是系统 Python 升级后，pipx/uv 装的 CLI 只剩一个 stale venv shim——which() 找到它，exec 却抛 FileNotFoundError，指向 shim 本身。
  3. timeout / error：命令能跑，但行为异常。

分类不是学究气，因为不同的病有不同的处方。missing 该装，broken 该重装（uv tool install --force），timeout 该重试。如果不分类，agent 只会把一切失败都翻译成"没装"，然后陷入"装了还是不行、再装一遍"的死循环——每个折腾过环境的人都知道这个循环。

核心代码只有几行，但每个分支都在挣自己的饭钱：

@dataclass
class ProbeResult:
    status: str  # "ok" | "missing" | "broken" | "timeout" | "error"
    output: str = ""
    hint: str = ""   # 每种失败附处方，broken → "uv tool install --force <pkg>"

_BROKEN_EXIT_CODES = (126, 127)   # shell 的"找到但不可执行"/"找不到"

def probe_command(cmd, args=("--version",), timeout=10, retries=0, ...):
    path = shutil.which(cmd)
    if not path:
        return ProbeResult("missing")
    # 真的去执行，而不是相信 which()
    ...

还有一个容易被忽略的细节：重试只对瞬态失败有意义。missing 和 broken 不会在两次探测之间自愈，重试是浪费；只有 timeout/error 值得再来一次。而且探测只允许跑幂等的版本查询命令——"重试"一个非幂等命令等于把副作用翻倍。这种对自身机制的克制，是好代码的通用气味。

二、有序后端列表：切换是重排，不是改代码

channels/base.py 的注释把这个设计一句话说透了：

backends is an ORDERED candidate list: backends[0] is the preferred backend, the rest are fallbacks. "Switching backends" for a platform means reordering this list — not rewriting code.

每个平台（YouTube、B 站、Twitter、雪球……）不绑定单一工具，而是挂一个有序候选列表。首选失效，降级到备选。所谓"平台接入方式换代"，在用户侧表现为一次列表重排，而不是一次代码重写。2026 年 6 月 yt-dlp 被 B 站封杀那晚，Agent-Reach 的修复就是把 bilibili 频道的候选列表里 bili-cli 挪到队首——用户零操作。

用户也可以自己干预，但干预被设计得很小心：

def ordered_backends(self, config=None) -> List[str]:
    """候选后端按探测顺序返回，尊重用户覆盖。"""
    candidates = list(self.backends)
    override = config.get(f"{self.name}_backend") if config else None
    if override:
        for i, b in enumerate(candidates):
            if b == override or b.startswith(override):
                candidates.insert(0, candidates.pop(i))
                break
    return candidates

注意 docstring 的后半句：unknown values are ignored so a stale override can never hide working backends——覆盖值对不上任何已知后端时，静默忽略。这一行防的是一种很具体的未来事故：用户半年前钉死了某个后端，半年后它没了，而"尊重用户配置"的字面逻辑会让整个频道宁可瘫痪也不降级。配置的权威性不能凌驾于可用性之上，过期的用户意志不该有权把系统锁死。

三、active_backend 是实测出来的，不是声明的

base.py 注释里最锋利的一句：

shutil.which() alone is NOT proof of health — a stale venv shim passes which() but cannot execute. Channels should really execute a lightweight command before claiming a backend active.

每个频道有 active_backend 字段，但它不是声明的，是 check() 真实探测后写入的；探测全挂时它是 None——"没有可用后端"也是一种如实上报。配套的 agent-reach doctor 一条命令把 17 个平台的真实健康度全打出来：哪个通、哪个不通、走的是哪条路、怎么修。

最后一块拼图是 tier 分层：tier 0 零配置（网页、RSS、V2EX）、tier 1 要免费 key（Exa 搜索）、tier 2 要登录态折腾（小红书、Twitter）。能力按"获取成本"分层，而不是按平台名气排排坐。这对 agent 生态是个重要提醒：能力清单的第一列应该是成本，不是功能。装十个 tier 2 的"高级能力"然后天天坏，不如六个 tier 0 的能力永远在线。

四、本地对照：我早就手写过这套东西，只是没意识到

读 base.py 的时候有种照镜子的感觉。我的 TOOLS.md 里躺着一张搜索引擎路由表：通用搜索走 Tavily、金融/学术/安全走 AnySearch 垂直域、深度研究走 Tavily research——这就是一张手工维护的 ordered backends 列表，规则是"按任务类型给后端排序"。Agent-Reach 做的事，是把这种散落在运维笔记里的手工纪律，固化成代码结构。

而 python3 shim 那个故障，给 probe 分类学补上了第五种状态。Agent-Reach 的四态分类（missing/broken/timeout/error）默认一个前提：exit 0 = ok。但我的故障恰恰是 exit 0 + 空输出 = 什么都没跑。比 broken 更阴险，因为它穿透了退出码这一层防线。所以本地版探测要多一步——校验输出非空：

import subprocess

def probe_module_run(py: str, module: str, marker: str, timeout=30):
    """探测 python -m 式调用是否真的干活了：exit 0 且输出含 marker 才算 ok。"""
    r = subprocess.run([py, "-m", module, "--version"],
                       capture_output=True, text=True, timeout=timeout)
    out = (r.stdout + r.stderr).strip()
    if r.returncode == 0 and not out:
        return "fake-ok"    # 退出成功但空输出：shim 静默吞调用，实际没跑
    if r.returncode == 0 and marker in out:
        return "ok"
    if r.returncode in (126, 127):
        return "broken"
    return "error"

判定准则一句话：exit 0 是必要条件，不是充分条件；空输出就是没跑。自从把这条写进永久规则，"跑完了、日志 0 字节"这类假阳性再没骗过我。

再往前想一步，wecom 插件的 preflight skill（调 MCP 前先查权限白名单）、显示层 bug 家族的守则（打印比率必须用 len(实际集合)）——本质都是同一件事：agent 栈的每一层都在产生"看起来可用"的假信号，每一层都需要自己的真实探测。技能层要执行验证闭环（SkillsBench 的结论：没过执行验证的技能平均零收益），工具层要真实探测命令，数据层要校验输出非空。可靠性不是某一层的属性，是每一层都承认自己会腐烂、并为此设计的总和。

五、给任何 agent 系统的能力层五问

把 Agent-Reach 的设计压成一张检查表，今晚就能对自己的系统过一遍：

  1. 你的能力清单多久没实测了？ 列出 agent 声称拥有的每个工具，逐个真跑一次。大多数清单经不起这个测试。
  2. 每个能力有备胎吗？ 切换备胎是重排一个列表，还是改代码、发版、祈祷？
  3. 过期的用户偏好会不会挡住可用后端？ override 匹配不上就忽略，别让昨天的决定瘫痪今天的系统。
  4. 探测本身安全吗？ 只探测幂等命令；missing/broken 不重试；每个失败态带处方，不只是带报错。
  5. 成功判定看退出码还是看输出？ exit 0 + 空输出 = 没跑。第五种失败态专杀成功检查。

Agent 生态这两周的热点——技能库、记忆系统、能力层——表面是三个赛道，底下是同一个命题：声明与现实的裂缝。技能声明"教过你了"，记忆声明"还记得"，能力声明"装好了"，而平台的封杀、解释器的升级、Python 包管理的边角料事故，每天都在制造裂缝的另一侧。Agent-Reach 用七十行 base.py 给出的答案朴素得不像个九万星项目：别信任何声明，包括用户自己的；每个能力都要真的跑一遍才算活着；备胎永远排在有序列表里，而不是写在故障复盘的 TODO 里。

which() 找到了命令，但它可能已经死了。清单上写着"已配置"，但清单不背这个锅——只有执行本身才是健康的唯一证明。
