上下文折叠：让 Agent 学会"忘掉过程，记住结论"

2026-08-12 · LLM Agent Context Management Context Folding ICML 2026
2026 年 ICML 和 ICLR 上，一批论文不约而同地指向了同一个方向：让 Agent 主动管理自己的上下文——做完子任务后，把详细过程"折叠"成一句摘要。这不是简单的文本压缩，而是一种可学习的元认知能力。本文拆解 Context Folding 的核心机制，给出一个你今天就能用的 Python 实现，并解释为什么"上下文管理是比模型规模更重要的 scaling 维度"。

一、一个你可能正在经历的问题

你让一个 ReAct Agent 执行一个复杂任务："调研竞品定价，分析差异，写一份报告"。Agent 很努力地执行了 40 步——搜索、阅读网页、提取数据、对比、撰写。但在第 35 步，它开始"迷糊"：重复搜索已经搜过的内容，忘记第 5 步发现的关键数据，最终报告遗漏了一半分析。

这不是模型不够聪明。这是上下文饱和。

ReAct 范式将所有历史（observations + actions）线性追加到 context。40 步下来，context 膨胀到 60K+ tokens。虽然模型声称支持 128K context window，但研究表明：在 128K token 的上下文中，位于中间位置的关键信息被遗漏的概率高达 40%——这就是著名的 "lost in the middle" 问题。

更糟糕的是成本：KV cache 在 128K+ 时占 70-90% 的 GPU VRAM，每一步推理的延迟和费用都在线性增长。你花在"重新阅读自己 30 步前的搜索结果"上的 token 费用，可能比实际推理还多。

二、Context Folding 的核心思想

Context Folding 的灵感来源非常人类：

你做一道复杂的菜。你不会在脑子里回放每一步切菜、调火的细节——你只记得"我炒了一个青椒肉丝"。细节被自然地压缩了，但结论（味道不错、下次少放盐）被保留了下来。

形式化地说，Agent 的轨迹 τ = [s₀, a₁, s₁, a₂, ..., sₙ] 中，存在若干"分支点" b_k（开始子任务）和"返回点" r_k（结束子任务）。折叠操作将中间步骤替换为一个摘要：

F(τ) = τ \ ⋃ₖ {s_{b_k+1}, ..., s_{r_k-1}} ∪ {summary_k}

两个核心操作：

  • Branch（分支）：Agent 创建临时子轨迹处理子任务
  • Fold/Return（折叠/返回）：子任务完成后，中间步骤被折叠，只保留结构化摘要

三、为什么手动摘要不管用

"在每 N 步之后加一个 summary 步不就行了？" 这是绝大多数工程师的第一反应。不行。原因是：

  1. 不同任务需要不同的压缩策略。搜索任务需要保留 URL 和数据点；代码任务需要保留 API 签名和错误信息；推理任务需要保留逻辑链。固定摘要规则无法自适应。
  2. 什么值得保留取决于后续需求。第 3 步发现的 API 文档可能在第 30 步才需要。当你第 10 步做摘要时，你不知道什么是重要的。
  3. 摘要本身会丢失信息。一旦你把 "用户预算是 500 元，偏好 Python， deadline 是周五" 压缩成 "用户需求已记录"，后续推理就失去了这些具体约束。

这就是为什么 FoldGRPO（ByteDance/CMU, ICML 2026）和 AgentFold（阿里 Qwen, ICLR 2026）的核心贡献不是"做摘要"，而是用 RL 训练 Agent 学会何时折叠、折叠什么。这是一种元认知（meta-cognition）能力——思考自己正在思考什么。

四、今天就能用的实现：Function-Call Folding

你不需要等 RL 训练好的模型。基于现有的 LLM API，你可以实现一个简易但有效的 Context Folding——我称之为 Function-Call Folding。

核心思路：在 tool call 完成后，不保留原始返回结果，而是让模型自己生成一个结构化摘要替换它。

import json
from typing import Any, Callable

class ContextFolder:
    """
    Context Folding for ReAct-style agents.
    
    Replaces verbose tool outputs with structured summaries
    after each tool call completes, keeping active context compact.
    """
    
    def __init__(self, llm_summarize: Callable, max_raw_tokens: int = 2000):
        self.llm_summarize = llm_summarize
        self.max_raw_tokens = max_raw_tokens
        self.folded_summaries: list[dict] = []
    
    def fold_tool_result(
        self, 
        tool_name: str, 
        tool_args: dict, 
        raw_result: Any,
        current_task: str
    ) -> str:
        """
        Fold a tool execution into a compact summary.
        
        Instead of keeping the full tool output in context,
        extract only what matters for the current task.
        """
        raw_str = str(raw_result)
        
        # Short results: no folding needed
        if len(raw_str) < self.max_raw_tokens:
            return raw_str
        
        # Long results: ask the LLM to extract what matters
        summary_prompt = f"""You are a context manager for an AI agent.
The agent called {tool_name} with these args: {json.dumps(tool_args)}
Current task: {current_task}

Tool output (will be REMOVED from context after this step):
{raw_str[:8000]}

Extract ONLY what an agent needs to continue the current task:
1. Key findings / data points (with exact values)
2. Errors or blockers encountered
3. Next logical step suggested by this result

Be terse. No commentary. No restating the task."""

        summary = self.llm_summarize(summary_prompt)
        
        folded_entry = {
            "tool": tool_name,
            "args": tool_args,
            "summary": summary,
            "original_tokens": len(raw_str) // 4,  # rough estimate
            "folded_tokens": len(summary) // 4,
        }
        self.folded_summaries.append(folded_entry)
        
        return f"[FOLDED {tool_name}] {summary}"
    
    def context_report(self) -> dict:
        """Report how much context was saved."""
        total_original = sum(f["original_tokens"] for f in self.folded_summaries)
        total_folded = sum(f["folded_tokens"] for f in self.folded_summaries)
        return {
            "folds": len(self.folded_summaries),
            "original_tokens": total_original,
            "folded_tokens": total_folded,
            "saved_tokens": total_original - total_folded,
            "compression_ratio": (
                round(total_original / total_folded, 1) 
                if total_folded > 0 else float("inf")
            ),
        }

使用方法——在你的 ReAct 循环中插入折叠步骤：

# In your agent loop:
folder = ContextFolder(llm_summarize=client.complete)

for step in range(max_steps):
    # ... agent decides to call a tool ...
    result = execute_tool(tool_name, tool_args)
    
    # FOLD: replace verbose output with task-relevant summary
    folded = folder.fold_tool_result(
        tool_name=tool_name,
        tool_args=tool_args,
        raw_result=result,
        current_task=task_description
    )
    
    # Add folded result to context (not the raw result!)
    messages.append({"role": "tool", "content": folded})

# Check how much you saved
print(folder.context_report())
# {'folds': 12, 'original_tokens': 45000, 'folded_tokens': 3200, 
#  'saved_tokens': 41800, 'compression_ratio': 14.1}

这个简易实现能给你 10-15x 的上下文压缩比。在一个 40 步的调研任务中，原始 context 约 60K tokens，折叠后约 8K——完全在模型的"高效注意力区间"内。

六、我的观点：Folding 是 Agent 的"工作记忆"

当前的 Agent 记忆系统有一个分层缺失：

  • 长期记忆（Long-term Memory）：向量数据库、知识图谱。解决"记住什么"的问题。
  • 上下文窗口（Context Window）：LLM 的 attention 范围。解决"当前看到什么"的问题。
  • ??? 中间层：当前任务的工作记忆。

Context Folding 填补的正是这个中间层。它不是长期记忆的替代品，也不是上下文窗口的扩展。它是 Agent 的工作记忆——类似人脑的前额叶皮层，容量有限，但通过主动管理（chunking、 rehearsal、 selective attention）实现复杂推理。

这意味着 Agent 架构应该是三层联动：

┌─────────────────────────────────────────┐
│         Long-term Memory (Graph/Vector)   │  ← agent-memory-graph
│  支撑：知识图谱、时间衰减、激活扩散          │
├─────────────────────────────────────────┤
│      Working Memory (Context Folding)     │  ← ContextFolder
│  支撑：子任务摘要、过程压缩、分支管理        │
├─────────────────────────────────────────┤
│       Context Window (LLM Attention)      │  ← LLM
│  支撑：当前推理步骤的注意力                  │
└─────────────────────────────────────────┘

当 Agent 开始一个子任务时，从长期记忆中检索相关信息进入工作记忆；子任务完成后，工作记忆被折叠——结论写回长期记忆，过程被丢弃。

这个循环——检索 → 工作 → 折叠 → 巩固——就是 Agent 的认知循环。跳过折叠步骤，你得到的就是一个不断膨胀、最终饱和的 context buffer。

七、可操作的建议

立即可做（今天）

  1. 实现 Function-Call Folding：用上面的代码模板，在 tool call 返回后加一步 LLM 摘要。10 行代码，10x 压缩。
  2. 检测上下文饱和：统计你的 Agent 在长任务中的 token 使用量。如果 context 超过 32K 且仍在增长，说明你需要 folding。

短期（1-2 周）

  1. 引入子任务分支：让 Agent 显式声明 "我现在要开始一个子任务"，子任务完成后自动触发折叠。这比每 N 步定时摘要更精准。
  2. 评估折叠质量：对比全上下文 vs 折叠上下文的任务成功率。分析失败案例——是被折叠掉的关键信息导致了失败，还是折叠本身没问题？

中期（1-3 月）

  1. 预算感知折叠：根据剩余 token 预算动态选择策略——预算充足时保留更多细节，预算紧张时激进压缩。ContextBudget (2026) 的研究显示这能在峰值 token 减少 26-54%。
  2. 多尺度折叠：区分细粒度凝聚（只折叠最近一步）和深度合并（折叠整个子任务）。不同任务阶段需要不同粒度。

八、争议与未解问题

Context Folding 不是银弹。几个未解决的问题：

1. 训练稳定性。FoldAct 的研究指出 RL 训练折叠策略面临三大难题：gradient dilution（折叠决策的信号被 action token 稀释）、self-conditioning（折叠后状态依赖摘要，违反 PPO 平稳性假设）、computational cost（每次折叠产生唯一 context，无法复用 KV cache）。这些问题在 2026 年初才被初步解决。

2. 折叠不可逆。一旦信息被摘要丢弃，后续步骤无法恢复。ACON (Microsoft, ICML 2026) 通过对比成功/失败轨迹来优化压缩策略，减少关键信息丢失——但这是离线分析，不是实时折叠。

3. 评估困难。我们缺少好的指标来评估"折叠质量"。任务完成率是终极指标，但太粗糙。我们需要的是："这条信息在折叠后是否还可用？" 这需要新的 benchmark 设计。

总结

Context Folding 代表了 Agent 架构的一个重要转变：从"尽可能多地记住"到"聪明地选择遗忘"。这不是一个微优化——它是一个架构层的认知。

当你看到你的 Agent 在第 30 步开始重复搜索、遗忘早期发现时，不要急着换更大的模型。先问自己：你的 Agent 有工作记忆管理吗？还是它一直在用长期记忆（全量历史）做短期推理（当前步骤）？

忘掉过程，记住结论。 这是人类大脑几亿年演化的结果。现在，Agent 也需要学会这个能力。
