提示工程已死，上下文工程当立

2026-07-30 · 罗嵩 · Context Engineering LLM AI Agent 工程实践
2025 年 6 月，Shopify CEO Tobi Lütke 在内部备忘录中写下一句话：「Context engineering 描述了核心技能，比 prompt engineering 更好。」Andrej Karpathy 随即转发赞同。三个月后，Anthropic 发布了系统框架，Google DeepMind 工程师称之为「新技能」，LangChain 说它是「最重要的技能」。一个名字的变更，背后是整个 AI 工程范式的迁移——从"怎么写提示词"到"如何系统性地管理模型的全部输入"。

一、为什么"提示工程"不够用了？

想象你在管理一个新入职的工程师。你能做的最差的事情是什么？不是给他模糊的任务——至少他还会问。最差的是一次性倒给他 500 页文档，然后说"这里面有你需要的所有信息，自己找吧"。

这就是 2025 年 AI 工程的现状。模型的上下文窗口从 4K 涨到 128K，再到 1M、10M。很多人的第一反应是："太好了，什么都能塞进去了！"于是把整个代码库、所有工具定义、全部对话历史、所有可能相关的文档——一股脑塞进上下文窗口。

结果呢？模型表现更差了。

Chroma Research 对 18 个主流 LLM 做了系统测试，发现了一个他们称之为 "Context Rot"（上下文腐烂）的现象：随着输入 token 数量增加，模型的准确检索能力持续下降，即使在最简单的任务上也是如此。所有模型无一幸免。

关键发现：Gemini 2.5 的技术报告承认：当 agent 的上下文显著超过 100K token 后，它开始重复历史行为，而非生成新策略。上下文越长，模型越像一个"只会翻旧账"的实习生。

问题的根源不是模型不够聪明，而是 Transformer 架构的基本数学约束：注意力机制是 O(n²) 的——每个 token 都需要和所有其他 token 计算注意力权重。token 越多，注意力越"稀薄"。就像一个房间里 10 个人聊天你能跟上，1000 个人同时说话就是噪音。

这就引出了一个核心结论：上下文不是"能放就放"，而是"必须修剪"。每个 token 都有成本。而这个"修剪"的工程实践，就是 Context Engineering。

二、什么是 Context Engineering？

Philipp Schmid（Google DeepMind）给出了最清晰的定义：

Context Engineering 是设计和构建动态系统的学科——在正确的时刻，以正确的格式，提供正确的信息和工具，让 LLM 拥有完成任务所需的一切。

注意几个关键词：

  • 系统，不是字符串——上下文不是一个静态的 prompt 模板，而是一个在每次推理前动态组装的系统
  • 动态——不同请求需要不同的上下文。这次是日历数据，下次是邮件历史，再下次是代码库
  • 正确的格式——一份精炼的摘要胜过原始 JSON dump；一个清晰的工具 schema 胜过模糊的自然语言描述
  • 正确的时刻——不是预加载所有信息，而是按需加载

用 Schmid 自己的例子来说明。有人发邮件问："明天有空聊聊吗？"

糟糕的 Agent（没有上下文）回复：

感谢您的消息。明天可以，请问您希望几点？

优秀的 Agent（有完整上下文）回复：

Jim 你好！明天我全天满档，从早到晚都是会。周四上午有空，方便吗？已经发了邀请，确认一下。

第二个回复的"魔法"不在于用了更好的模型或者更精妙的 prompt——而在于在调用 LLM 之前，系统已经把日历、历史邮件、联系人关系都准备好了。Agent 的好坏，80% 取决于上下文工程，20% 才是模型和提示词。

三、上下文的四种死亡方式

Drew Breunig 在一篇广泛传播的文章中，系统性地分类了上下文失败的四种模式。每一个做过 Agent 开发的人都会会心苦笑——因为我们都踩过这些坑。

模式 1：Context Poisoning（上下文中毒）

症状：模型产生了幻觉（比如错误地认为某个函数存在），这个幻觉进入了对话历史，然后被反复引用和强化。最终，整个 agent 的行为都建立在一个虚假前提上。

类比：就像一个人的记忆被植入了虚假事件——他所有后续的决策都基于这个不存在的事实。电影《盗梦空间》里植入一个想法就能改变一个人的人生；上下文中毒就是 LLM 版的盗梦空间。

Gemini 2.5 在玩 Pokémon 时展示了这个问题的严重性：一旦"目标"部分被幻觉污染，agent 会执着地追求一个不可能完成的目标，反复尝试相同的行为。

模式 2：Context Distraction（上下文分心）

症状：上下文太长，模型开始过度依赖上下文中的历史行为，忽略了自己在训练中学到的知识。

类比：就像考试时带了一本太厚的参考书——学生在里面找到了一个"差不多"的答案就直接抄，而不是用自己脑中的知识去思考。

Databricks 的研究量化了这个问题：Llama 3.1 405b 在上下文超过 32K token 后开始出错，更小的模型更早。如果你的 agent 跑了很久，对话历史不断累积——恭喜，你正在经历 Context Distraction。

模式 3：Context Confusion（上下文混淆）

症状：上下文中有太多不相关的内容（尤其是过多的工具定义），模型被干扰，做出低质量的决策。

数据：Berkeley Function-Calling Leaderboard 表明——每多给一个工具，准确率就下降。更惊人的是：一个 8B 参数的 Llama 模型，给 46 个工具时失败，给 19 个工具时成功——问题不是模型不够大，而是工具太多。

类比：就像给一个新员工一本 500 页的操作手册，里面包含了所有可能用到的工具——从咖啡机到核反应堆。他找一个"打印"按钮都要翻半天，最后按错了。

模式 4：Context Clash（上下文冲突）

症状：上下文的不同部分互相矛盾。比如系统指令说"用中文回复"，但用户消息里有一段英文指令说"respond in English"。模型行为变得不可预测。

类比：就像两个领导给下属下达了矛盾的指令——一个说"赶紧做完"，另一个说"务必仔细检查"。下属不管怎么做都是错的。

实践建议：每次 agent 出错时，先别怪模型。按这四种模式做一次诊断——大概率是上下文的问题，不是模型的问题。

四、Just-In-Time：让 Agent 学会"按需加载"

Anthropic 在 Claude Code 中实践了一种叫做 "Just-In-Time Context"（即时上下文）的策略，这是目前最成熟的上下文管理方案。

核心思路可以用一个类比解释：

人类不记忆整个互联网。我们记住的是在哪里能找到信息——文件在哪个柜子、联系人在通讯录里哪个位置、网页收藏夹的目录结构。需要时，我们按需取出。

Agent 也应该这样工作。不要预加载整个知识库，而是：

  1. 维护轻量级引用——文件路径、URL、查询语句，而非完整数据
  2. 通过工具按需加载——agent 自己决定何时取出什么信息
  3. 利用元数据——文件名、目录结构、时间戳本身就携带语义。test_utils.py 在 tests/ 目录下和 src/core/ 下含义不同，agent 能理解这种差异
  4. 渐进式发现——每次交互获得的信息指导下一次决策。先看文件大小判断复杂度，再决定是否深入

Claude Code 就是这个策略的最佳实践者：CLAUDE.md 预加载核心指令（"我是谁、代码规范是什么"），其余通过 glob 和 grep 按需获取。这让它能在大型代码库中高效工作，而不会把上下文窗口塞满。

当然，纯即时检索也有代价：速度慢。每次工具调用都是一次 round trip。所以实践中，混合策略是最优解：

策略预加载即时检索适用场景
纯预加载（传统 RAG）全部相关数据无静态文档问答
纯即时检索最小核心指令全部动态数据探索性分析
混合策略（推荐）核心指令+关键配置具体数据+大文件大多数 Agent 场景

五、系统提示词的"正确高度"

Anthropic 提出了一个精妙的比喻——系统提示词应该找到"正确的高度"（The Right Altitude）。

想象你在飞一架飞机。飞太低（过于具体的指令），你能看清每棵树但很容易撞上——每次场景变化都需要修改 prompt，脆弱不堪。飞太高（过于模糊的指令），你什么都看不到——模型不理解你到底想要什么。

正确的高度在中间：

  • 太低（过于具体）："如果用户说X就做Y，如果用户说A就做B，如果条件C满足且D不为空则..."——这是一堆 if-else，不是 prompt。一旦场景超出你的枚举，立刻崩溃。
  • 太高（过于模糊）："你是一个有帮助的助手，请尽力帮助用户。"——说了等于没说。
  • 正确高度：提供清晰的行为准则和少量多样化示例（few-shot），让模型理解"怎么思考"而非"每一步做什么"。

Anthropic 的建议是：从最小化 prompt + 最好的模型开始，测试它在你的任务上表现如何。根据失败模式，逐步添加明确的指令和示例。不要一开始就写一个 500 行的 prompt——那是在掩耳盗铃，掩盖了模型本身的能力不足。

核心原则：Few-shot 示例是"值千言的图片"。与其写一千字的规则描述，不如给三个多样化的、能体现期望行为的示例。模型从示例中泛化的能力，远超从规则中推断。

六、工具设计的隐藏成本

如果你在做 Agent 开发，你可能犯过这个错误：给 agent 一堆工具，希望它"什么都能做"。搜索、邮件、日历、代码执行、数据库查询...二十个工具一股脑塞进去。

Berkeley 的研究告诉我们：这是一个灾难。

工具定义本身就是上下文的一部分。每个工具的名称、描述、参数 schema 都在消耗 token 预算。更重要的是，工具越多，模型的选择空间越大，决策质量越低。这和人类面对过多选择时的"决策瘫痪"是一样的。

好的工具设计遵循三条原则：

  1. 最小集合——如果人类工程师无法在 3 秒内说出"这个任务该用哪个工具"，模型也不行
  2. 无重叠——两个工具不应该能完成同一件事。如果可以，合并它们
  3. 自描述——工具名和参数名应该让人一看就懂。不要叫 process_data，要叫 search_customer_by_email

七、你能立刻做的 6 件事

理论说得够多了。以下是你可以今天就开始的上下文工程实践：

1. 审计你的上下文

把你的 agent 每次调用 LLM 时的完整输入记录下来（包括系统指令、历史、工具定义、检索结果）。打印出来，用红笔标出：哪些信息是这次调用真正需要的？哪些是在"以防万一"？你会发现 30-50% 的 token 可能是浪费的。

2. 设定上下文预算

为每个组件分配 token 预算。比如：系统指令 10%、工具定义 15%、对话历史 30%、检索结果 35%、用户输入 10%。超出预算就触发压缩或截断。没有预算的上下文就像没有预算的项目——注定失控。

3. 从"预加载"切换到"按需加载"

找出你的 agent 上下文中最大的数据块（通常是 RAG 检索结果或对话历史）。问自己：这些信息是否每次都需要？如果不需要，把它替换成一个工具调用——让 agent 自己决定何时加载。

4. 修剪你的工具集

如果你的 agent 有超过 8 个工具，做一次审计。合并功能重叠的、移除使用率低于 5% 的。如果确实需要很多工具，考虑分层加载——先给核心工具，agent 判断需要时再"解锁"高级工具。

5. 实现对话压缩

当对话超过 N 轮（比如 10 轮），自动把前面的历史摘要为一到两段话。保留最近 5 轮的原始记录，更早的只保留摘要。这能减少 60-80% 的历史 token，同时保持关键信息。

6. 建立可观测性

用 LangSmith、OpenTelemetry 或自建工具，追踪每次 LLM 调用的完整上下文和输出。当 agent 出错时，你能快速定位：是上下文太多（Distraction）？太矛盾（Clash）？还是缺失关键信息？没有可观测性的 agent 工程，就像没有日志的生产系统——出了问题只能猜。

结语：从"写好一句话"到"管好一个系统"

2020 年，GPT-3 发布时，我们面临的问题是"怎么写好一个 prompt"。答案是一堆技巧和模板——zero-shot、few-shot、chain-of-thought。

2026 年，我们面临的问题变成了"怎么管好一个动态系统"——上下文窗口是有限的注意力资源，模型在每个 token 上都有递减的边际收益，agent 在多步推理中不断产生新信息。

Context Engineering 不是又一个 buzzword。它是一个认知框架的迁移：从把 LLM 当作"接受指令的机器"，到把它当作"在有限注意力下工作的协作者"。

当你开始用"注意力预算"的视角看你的 agent，而不是"提示词优化"的视角——你就已经从一个 prompt engineer 变成了一个 context engineer。

这条路没有终点。但好消息是：每一步修剪、每一次按需加载、每一个被移除的冗余工具，都会立刻反映在你的 agent 表现上。

记住 Karpathy 的话：Context engineering 是"在上下文窗口中放入恰好的信息，供下一步推理"的艺术与科学。不是太少，不是错的格式——而是刚刚好。
