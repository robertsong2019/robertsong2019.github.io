给声音去掉 token：语音合成连续路线的量产答卷

语音合成 TTS 扩散模型 开源模型 2026-10-24 · 基于 VoxCPM 官方 README / 技术报告核实（arXiv 2606.06928、2509.24650 ICLR 2026）与 10-23 晚 Trending 分析

过去五年，语音合成走的是一条「先交税再干活」的路：把连续的声音量化成一串离散码本编号，再让语言模型学这些编号。VoxCPM2 用 2B 参数、200 万小时、30 语种给出了连续表示路线的量产答卷——税不用交了，而且复用文本 LLM 全部 serving 基建。 这篇文章拆解它怎么做到的，以及哪些地方依然在补课。

一、七个月，从论文噱头到四万星

先把时间线摆出来，因为斜率本身就是故事：

  • 2025 年 9 月：VoxCPM-0.5B 发布，双语（中英），16kHz 输出，技术报告挂 arXiv（2509.24650），HuggingFace Trending 第一
  • 2025 年 12 月：VoxCPM1.5，0.8B，44.1kHz，补上 SFT/LoRA 微调，GitHub Trending 第一
  • 2026 年 4 月：VoxCPM2——2B 参数、200 万小时训练数据、30 语种、48kHz 录音棚音质、Voice Design、可控克隆，Apache-2.0 权重代码全开，技术报告 2606.06928
  • 现在：40k 星，老项目靠模型级更新重回日榜

七个月三代，0.5B 双语到 2B 三十语种。这个斜率说明的不是一个产品的迭代节奏，而是一条技术路线从「论文里能用」到「产能量产」的速度。

二、token 税：离散化在最前面收的税

要理解 tokenizer-free 在赌什么，得先说清楚它赌掉了什么。

VALL-E 一脉的主流做法：神经编解码器（EnCodec / SoundStream 家族）把音频压成离散 token——每秒 50~100 帧乘以多层残差码本，一秒钟语音变成几百上千个码本编号，语言模型逐个预测这些编号，最后声码器还原成波形。这套架构的诱惑很明显：离散 token 就是语言模型的母语，采样、温度、KV cache、temperature scheduling，文本 LLM 的全套工具箱直接搬过来用。

但代价在最前面就收走了。量化的本质是有损压缩——把无限连续的声学空间映射到有限个码字，每一帧的量化误差都发生在管线第一步，后面任何模块都无法挽回。而恰恰是最有信息量的东西藏在连续细节里：气声、沙哑、颤音、句尾那一丝迟疑、情绪的渐变。这些被码本压扁之后，模型学到的已经是「打了马赛克的声音」。

# 离散路线的税，三行伪代码说清楚
z = encoder(audio)              # 连续潜表示，韵律细节都在
tokens = quantize(z, codebook)  # ← 税在这里收：找最近的码字，误差永久丢失
audio_hat = decoder(tokens)     # 后面再努力，也只能还原"最像的码字"

这就是「token 税」：用信息损失，换基建兼容。 这笔税在图像生成领域早就被算过一遍——VQ-VAE 路线最终输给了 DiT 直接在连续潜空间做扩散。语音晚了几年，因为语音有个图像没有的硬约束：它必须流式、必须低延迟、必须逐段自回归。

三、连续路线的三件套

VoxCPM2 的解法是在 AudioVAE V2 的连续潜空间里跑一个「扩散自回归」架构，四段管线 LocEnc → TSLM → RALM → LocDiT。名字很唬人，但核心工程洞察可以压缩成三句话：

第一，潜速率降到 6.25Hz。 一秒钟语音只对应 6.25 个连续潜帧——对比离散路线每秒 50~100 token，序列长度直接砍到 1/16 以下。这就是为什么 2B 的 AR 骨干（MiniCPM-4）扛得住一分钟语音：375 个潜帧而已。粗粒度交给 AR，细粒度交给别的模块，这个分层是整个架构成立的前提。

第二，AR 骨干 + 扩散头分工。 语言模型天生只会吐离散分布，怎么让它吐连续向量？VoxCPM 的答案是：AR 骨干负责预测「下一帧潜变量的条件分布」，一个轻量扩散 transformer（LocDiT）负责从这个分布里采样出真正的连续变量。语言结构、韵律节奏这些「宏观」决策走 AR；音色质感、微表情这些「微观」细节走扩散——而且扩散只要 10 步（inference_timesteps=10），流水线延迟没有爆炸。

第三，非对称编解码。 AudioVAE V2 的编码器接受 16kHz 参考音频，解码器直接输出 48kHz——编解码器不必镜像。参考音频可以是手机录音的烂音质，输出依然是录音棚级，因为解码器做的是「生成」而非「重建」，内置超分，它被允许比输入更好。这个设计顺手干掉了外部 upsampler 依赖。

三件套合起来，换到的是：AR 部分仍然像一个低速率 token LM 一样运转（对调度器完全友好，后面细说），而离散化税一分钱不用交。

四、上手：自然语言成了音色的接口

基础用法十行以内：

from voxcpm import VoxCPM
import soundfile as sf

model = VoxCPM.from_pretrained("openbmb/VoxCPM2", load_denoiser=False)

# Voice Design：括号里用自然语言描述音色，凭空造一个声音，零参考音频
wav = model.generate(
    text="(一位年轻女性，声音温柔甜美，语速平缓)欢迎收听本期节目。",
    cfg_value=2.0,           # classifier-free guidance，2.0 是默认甜点
    inference_timesteps=10,  # 扩散步数，10 步够用
    seed=42,
)
sf.write("demo.wav", wav, model.tts_model.sample_rate)  # 48000

注意 text 的格式：括号前缀是音色描述，正文才是要合成的内容。这个接口设计值得单独说——音色的控制面从「上传参考音频 + 调 speaker embedding」坍缩成了一段自然语言，和图像生成里「prompt 即接口」是同一个范式迁移。克隆场景同理：给 reference_wav_path 保音色，再叠括号指令调情绪语速（「稍快一点，欢快的语气」）；追求逐字还原就用终极克隆，参考音频加转写文本做音频续写。

流式输出是一等公民：

import numpy as np

chunks = []
for chunk in model.generate_streaming(text="长文本段落，边生成边播……"):
    chunks.append(chunk)
wav = np.concatenate(chunks)

五、部署账本：为什么 serving 决定路线生死

基准分数决定一篇论文，部署成本决定一个范式。这里是连续路线最惊喜的部分：

RTF（实时率）0.3 起步，Nano-vLLM 加速到 0.13（RTX 4090，即合成 1 秒语音只要 0.13 秒），显存约 8GB。更关键的是官方 serving 栈的完整度——vLLM-Omni 是 vLLM 官方的全模态扩展，原生支持 VoxCPM2：

vllm serve openbmb/VoxCPM2 --omni --port 8000

# 任何 OpenAI 兼容客户端直接调
curl http://localhost:8000/v1/audio/speech \
  -H "Content-Type: application/json" \
  -d '{"model":"openbmb/VoxCPM2","input":"Hello from VoxCPM2!","voice":"default"}' \
  --output out.wav

PagedAttention、continuous batching、多 GPU、流式分块——文本 LLM 这五年攒下的 serving 武器库原样复用。为什么能复用？回想第三节：AR 部分跑在 6.25Hz 的低速率潜序列上，在调度器眼里它和一个慢速 token LM 没有区别。这就是「分层」设计的第二重红利：省掉的税和拿到的基建，居然是同一枚硬币的两面。

端侧也有路：llama.cpp-omni 提供 GGUF 支持（BaseLM Q8_0 + Acoustic F16 两件套），CPU/Metal/CUDA/Vulkan 全覆盖，Apple M4 Pro 上 RTF 约 1.76——略慢于实时但已可跑。从云端到手机，推理生态全部就位，这在开源 TTS 里是第一份。

六、冷静读分：它不是全 SOTA，信号在别处

按惯例泼冷水。Seed-TTS-eval 上 VoxCPM2（EN WER 1.84 / SIM 75.3，ZH 0.97 / 79.5）中英成绩均衡漂亮，但不是每格都第一：Qwen3-TTS EN WER 更低（1.23），FishAudio S2（4B）EN 0.99 / ZH 0.54 全面领先，LongCat-Audio-DiT 的相似度更高。多语种短板更明显——Minimax-MLS 测试里阿拉伯语 WER 13.0、捷克语 24.1、粤语 38.6，这些格子离「30 语种」的宣传语有肉眼可见的距离。

所以正确的读法不是「VoxCPM2 天下第一」，而是：tokenizer-free 在 2B 规模上，于它的主场（中英、相似度、自然度）追平甚至超过了交着 token 税的离散路线——而且带着 Apache-2.0 商用许可、九种中文方言（川话、粤语、吴语、东北话……开源里成体系的独一份）、Voice Design 和可控克隆这些离散路线做起来别扭的能力。路线验证完成，格局竞争才刚开始。

顺带一个工程视角的隐忧：VoxCPM2 的 RTF 0.3 比 1.5 代的 0.15 慢了一倍——模型大了，单位成本涨了。连续潜变量每帧是整个向量而不是一个码字，KV cache 的宽度天然更高，8GB 显存门槛也把低端卡挡在了外面。连续路线省了税，但「带宽费」涨了，这笔账最终要靠推理栈优化（Nano-vLLM 已经做到 0.13）和量化（GGUF）往下压。

七、token 税之辩，不止于语音

把镜头拉远。离散化 vs 连续表示是所有模态进 LLM 范式时都要过的一道门：视频生成里 token 化路线正在被连续扩散挤压；字节级语言模型（不依赖 BPE）在长上下文上重新抬头；语音是这场辩论里第一个从论文走到 2M 小时量产的战场。VoxCPM2 的意义是为连续阵营补上了最缺的一块证据：规模。0.5B 时你可以说「小打小闹」，2B / 30 语种 / 48kHz / vLLM 官方 serving 之后，这句话说不出口了。

它给出的可迁移经验就一条，但很值钱：不要在「离散」和「连续」里二选一，在粒度上分层——宏观决策交给低速率 AR（顺便白拿整套文本 LLM 基建），微观细节交给小而快的扩散头（顺便保住连续表示的信息量）。任何模态的生成管线都可以问一遍这个问题：我的 6.25Hz 在哪？

落地建议：要做本地化中文语音能力（agent 语音输出、方言内容、有声书），VoxCPM2 当前是开源第一候选——Apache-2.0 商用免费、vLLM-Omni 生产级 serving、GGUF 端侧兜底；评估时直接看它 README 的三张基准表，别看宣传语，阿拉伯语和捷克语的格子替你踩过坑了。至于离散路线的存量模型，不必急着换——如果你的场景是纯中英、对延迟极敏感、基建已经成熟，token 税暂时还交得起。路线之争的终局从来不是一夜切换，而是新项目不再默认从老路线开始。
