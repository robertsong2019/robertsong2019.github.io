Engineering Manifesto · 2026.08

信息外置,
纪律蒸发

Agent 编程的脚手架正在经历一场淘汰:模型每半年内化一批旧技巧, 你精心搭建的工作流反而和它自己的判断打架。 但不是所有东西都在蒸发——信息不会内化,只有纪律会。 这份宣言划出那条线,并给出测试在 Agent 时代的完整角色。

Core Thesis
信息 vs 纪律
保留项
测试 + 设计文档
蒸发项
工作流脚手架
Review Cadence
每半年重置
"产品质量不是由测试保障的——是由 spec 的质量 × 验证回路的质量 保障的。 测试恰好是这两者的交点:它是人表达『什么算对』的唯一可执行形式。"
§ 01 / 切分维度

这条东西是给模型
信息,还是教它纪律?

不要按功能切(保留测试、删掉编排),按性质切:信息保留,纪律蒸发。判断方法也简单——换新模型时裸跑一次,看默认行为是否已覆盖你的规则。

↓ 正在蒸发 · 教模型怎么思考

Prompt 技巧
"你是资深架构师,先一步步分析再动手"——模型已内化。早期还得教"先读文件再改",现在谁还写这条?
强制瀑布工作流
先规划→再分工→再执行→再测试。模型看到一个 typo,工作流却逼它走全流程——这就是你感受到的"前后矛盾"。
角色分工式 SubAgent 编排
每个 subagent 重新探索,context 传递损耗经常大于并行收益。作为"分工机制"在消失。

↑ 正在升值 · 给模型可验证信号

测试 / 类型 / CI
角色变了:从"教纪律"变成"给 oracle"。强模型写代码已经不是瓶颈,证明写对了才是。
设计文档 / 决策记录
解决的不是模型能力,是状态外置:模型再强也没有跨会话记忆,"为什么选 X 不选 Y"只能活在文件里。
SubAgent 作为上下文隔离工具
作为"独立评审者"在升值——以前请第二个人盲评很贵,现在开一个无污染会话,边际成本为零。
模型能力 →
认知脚手架的需求↓ 下降

模型越强,越不需要"指导它怎么想"。半年重置一次技能库:换新模型裸测,被默认行为覆盖的规则直接删。

模型能力 →
验证信号的价值↑ 上升

模型越强,越需要"告诉它做得对不对"。它能一次改 20 个文件,人 review 跟不上,只能靠机械验证兜底。

§ 02 / 同源偏差

测试的关键不是有没有,
是断言的值从哪来

同一个模型写实现又写测试,它的测试往往在"验证自己的实现"而非"验证规范"。这就是 TDD 在 Agent 时代复活的原因——不是纪律,是 oracle 的来源问题。

✗ 同源污染

断言来自实现快照

// 跑一遍实现,把输出抄下来当期望值 assert_eq!(parse("2026-08-15"), result_刚才跑出来的那个值); // 只能抓"以后改坏了" // 抓不住"现在就错了"

快照镜像了实现的行为,而不是规范的行为。实现本身就错时,测试忠实地保护着错误。

✓ 独立来源

断言来自 Spec

// 期望值从 spec / issue / 类型签名推导 assert_eq!(parse("2026-08-15"), Date{y:2026,m:8,d:15}); // 实现错了 → 测试红 → 拉回正确方向

测试编码的是人的意图,不是机器的输出。这才是可执行的 spec,也是 agent 迭代的客观奖励信号。

一句 prompt 就能杀掉大半偏差——"断言的期望值必须来自 spec/issue/类型签名,禁止从当前实现的输出快照取值。写完告诉我哪些行为你找不到外部依据、只能从实现推断——那部分就是 spec 的缺口。"最后一句是关键:它把模型不确定的地方暴露给你,那正是需要人补信息的地方。

§ 03 / 盲评

切断上下文,
制造独立性

让学生批改自己的卷子,能找出粗心错,找不出理解错——写测试的偏差和 review 测试的偏差是相关的,因为上下文是同一个。解法:开一个全新的会话,只给 spec 和测试,不给它看实现。

§ 04 / 责任分层

哪些交给 Agent,
哪些必须留给人

写测试便宜了,判断测试是不是好测试没变便宜。人的时间只该花在一处:review 断言的来源。其他一切(数量、覆盖率、跑 CI)都可以完全交给 agent。

层Agent 全权负责人必须给的
类型 / 编译器—已有,免费的 oracle
单元测试写、跑、修review 断言来源(唯一值得花人时的环节)
回归测试postmortem → 测试,全自动bug 的正确行为定义
属性 / 模糊测试全权——写 property 比写 example 更适合 agent指出哪些模块值得
E2E / 集成全权(以前太脆没人写,agent 不怕维护成本)哪条用户路径最重要
形式化验证写 proof harness选安全关键的不变量——全量形式化的成本模型没变
§ 05 / Rust 工具箱

替代"提两嘴"
的具体清单

与其说"加下 fuzz、搞下形式化验证",不如给对指令:让 agent 找出模块的不变量,用对工具验证。按成本排序——便宜的默认全开,贵的只给安全关键路径。

cargo miri
未定义行为检测
几乎零成本,agent 自己会跑。解释执行器级别抓 UB:越界、别名违规、数据竞争。
成本 ≈ 0 · 默认开
loom
并发正确性模型检查
碰 Arc / Mutex / channel 的模块就该上。穷举交织,抓最阴的竞态。
成本低 · 并发模块必开
proptest / cargo-fuzz
属性测试 / 模糊测试
指令给法:"找出这个模块的不变量,然后用 proptest 验证"。写"排序后长度不变且有序"这类 property 是 agent 的甜点,且最难被同源偏差污染。
成本中 · 按模块开
kani
形式化验证(有界模型检查)
只值得给安全关键的不变量:解析外部输入、权限检查、加密协议。agent 只是把"写 proof harness"的边际成本降了,不是让全量验证变便宜。
成本高 · 仅安全关键
§ 06 / 单调改进

测试保障的不是没有 Bug,
是每个 Bug 只发生一次

测试能抓的都是已知模式:写过的回归、定义过的不变量、spec 描述过的边界。真正的线上事故一定是新模式。质量的真实机制是这条曲线的斜率,不是覆盖率的数字。

产品质量 = spec 的质量 × 验证回路的质量
测试对 agent 是生产资料而非防御设施:在有客观信号的代码库上迭代会收敛到正确,
在没有信号的代码库上会"自信地错"。评估一个团队的 agent 就绪度,先看测试回路,再看用什么模型。
§ 07 / 落地

已经写进
全局配置的四条规则

你希望固定发生的行为,口头说是不可靠的——模型的行为偏好会漂,换会话、换模型,口头约定就没了。和测试断言外置到 spec 是同一个道理:规则也要外置到配置。

断言来源

测试断言的期望值必须来自 spec / issue / 类型签名 / 用户陈述的需求,禁止从当前实现的输出快照取值。快照只能用于回归测试并明确标注。

Spec 缺口申报

写完测试后主动报告哪些行为找不到外部依据、只能从实现推断——那部分是 spec 的缺口,交给用户补。

关键模块盲评

触及安全、并发、解析外部输入的模块时,用独立 subagent 做断言盲评:只给 spec + 测试,不给实现,逐条推导期望值,标出推不出来的。

Bug 只发生一次

每个修复的 bug 必须配套回归测试,且该测试要能证明修复前会失败。
