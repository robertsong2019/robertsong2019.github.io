Agent Skill 的回归税：当技能让你的 AI 变得更蠢

📅 2026-07-28 · 标签：Agent Skills, LLM, Regression Tax, Skill Osmosis

我们给 AI Agent 加技能时，默认假设是：技能越多，能力越强。但 2026 年 7 月的两篇论文告诉我们一个不舒服的真相——每个新技能都在暗中交税，而税有时候比收益还高。

这篇随笔拆解"回归税"的机制，给出具体的检测代码和应对策略。不是综述，是实战指南。

核心发现：59% 的增益被回归吃掉了

Tank 和 Nama 在 The Regression Tax（arXiv:2607.22520）中对 5832 次 Agent 运行做了逐任务分解。他们发现：

  • 553 次任务因为技能获得了改善（gross gain）
  • 324 次任务因为技能而退化（regression）
  • 净改善只有 229 次——回归吞掉了 59% 的总增益

更反直觉的是：表现最好的技能库不是增益最大的，而是回归最少的。这就像投资——控制回撤比追求收益更重要。

关键结论： 平均成功率提升是最危险的指标。它把"帮了 10 个任务"和"毁了 6 个任务"净额显示为正数，让你觉得一切正常。你需要的不是平均值，而是 gain/regression 的分解。

三种回归机制：技能是怎么搞砸的

论文识别了三种回归模式。我把它们翻译成日常开发的场景：

1. 技能描述渗透（Skill Description Osmosis）

这是最隐蔽的一种。技能描述仅仅通过存在于系统提示中，就改变了 Agent 的行为——即使技能从未被触发。

机制很简单：LLM 的注意力机制会在整个上下文窗口中分散。系统提示里有一段"当用户提到 SQL 时，使用 TransactionGuard 技能确保事务安全"——这段话里的"SQL"、"事务"等词汇会在模型处理无关任务时产生微妙的锚定效应。比如用户问"怎么写一个 SQLite 查询"，Agent 可能会过度谨慎地加上不必要的事务包装。

类比： 这和心理学中的锚定效应（Anchoring Bias）高度类似。人类在看到无关的数字后，后续的数值估计会被那个数字拉偏。LLM 表现出同构的认知偏差——这不是拟人化，是注意力机制的数学后果。

2. 方法覆盖（Method Override）

新技能定义的执行流程与已有技能冲突。Agent 在两个 SOP 之间犹豫，执行质量下降。这类似于代码库里的多重分派歧义——当两个方法都能匹配参数类型时，编译器需要 disambiguation，而 LLM 没有 compile-time check。

3. 上下文挤压（Context Squeeze）

每个技能占用系统提示的 token 预算。技能越多，留给任务上下文的窗口越小。当技能描述占到系统提示的 40% 时，Agent 对用户实际输入的理解能力下降——因为注意力被稀释了。

实战：检测技能描述渗透

这是最值得投入的检测手段。核心思路：A/B 测试——在系统提示中包含技能描述但不允许触发，测量对无关任务的影响。

# skill_osmosis_detector.py
"""
检测技能描述对无关任务的渗透效应。
方法：在系统提示中添加/移除技能描述，对比同一组无关任务的通过率。
"""
import json
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class OsmosisTest:
    """单个渗透测试用例"""
    skill_description: str          # 被测试的技能描述
    unrelated_tasks: list[str]      # 不应触发该技能的任务
    llm_call: Callable              # 你的 LLM 调用函数
    
    def run(self) -> dict:
        results = {}
        
        # Baseline: 系统提示不含技能描述
        baseline_sys = "你是一个有用的助手。请直接回答用户问题。"
        for task in self.unrelated_tasks:
            key = f"baseline::{task[:30]}"
            results[key] = self._score(baseline_sys, task)
        
        # Treatment: 系统提示包含技能描述（但不允许触发）
        treatment_sys = (
            f"你是一个有用的助手。请直接回答用户问题。\n\n"
            f"可用技能：\n{self.skill_description}\n"
            f"（注意：以下任务与上述技能无关）"
        )
        for task in self.unrelated_tasks:
            key = f"treatment::{task[:30]}"
            results[key] = self._score(treatment_sys, task)
        
        return self._analyze(results)
    
    def _score(self, sys_prompt: str, task: str) -> float:
        """调用 LLM 并对输出打分（0-1），1 = 完美回答"""
        response = self.llm_call(sys_prompt, task)
        # 这里用你自己的评分逻辑：可以是 LLM-as-judge、
        # 关键词检查、或人工标注
        return self._judge(response, task)
    
    def _judge(self, response: str, task: str) -> float:
        """简单的关键词/长度启发式评分。生产环境用 LLM-as-judge。"""
        # 检测是否被技能描述污染
        skill_words = set(self.skill_description.lower().split())
        resp_words = set(response.lower().split())
        overlap = len(skill_words & resp_words) / max(len(resp_words), 1)
        
        # 技能词溢出越多，得分越低
        base_score = 1.0 if len(response) > 20 else 0.3
        return max(0, base_score - overlap * 2)
    
    def _analyze(self, results: dict) -> dict:
        baseline_scores = [v for k, v in results.items() if k.startswith("baseline")]
        treatment_scores = [v for k, v in results.items() if k.startswith("treatment")]
        
        b_avg = sum(baseline_scores) / len(baseline_scores)
        t_avg = sum(treatment_scores) / len(treatment_scores)
        
        return {
            "skill_description": self.skill_description[:80] + "...",
            "baseline_avg": round(b_avg, 3),
            "treatment_avg": round(t_avg, 3),
            "osmosis_effect": round(b_avg - t_avg, 3),  # 正值 = 存在渗透
            "verdict": "⚠️ 渗透显著" if (b_avg - t_avg) > 0.1 else "✅ 渗透可控",
            "n_tasks": len(self.unrelated_tasks),
        }


# 使用示例
if __name__ == "__main__":
    # 模拟 LLM 调用（实际使用时替换为你的 LLM API）
    def mock_llm(sys_prompt: str, user_input: str) -> str:
        # 在真实场景中，如果 sys_prompt 包含 SQL 技能描述，
        # LLM 的回答会被"潜移默化"地影响
        if "SQL" in sys_prompt and "数据库" not in user_input:
            return "这个问题可以从多个角度理解..."  # 被污染的回答
        return f"关于 {user_input} 的直接回答..."
    
    test = OsmosisTest(
        skill_description=(
            "SQL安全技能：当用户提到数据库操作时，"
            "使用事务包装所有写操作，检查SQL注入风险，"
            "验证表结构匹配，并在执行前输出预览。"
        ),
        unrelated_tasks=[
            "解释快速排序算法",
            "写一个 Python 函数计算斐波那契数",
            "推荐一本关于系统设计的书",
        ],
        llm_call=mock_llm,
    )
    
    report = test.run()
    print(json.dumps(report, indent=2, ensure_ascii=False))

运行这段代码，你会得到类似这样的输出：

{
  "skill_description": "SQL安全技能：当用户提到数据库操作时，使用事务包装所有写操作，检查SQL注入风险...",
  "baseline_avg": 1.0,
  "treatment_avg": 0.333,
  "osmosis_effect": 0.667,
  "verdict": "⚠️ 渗透显著",
  "n_tasks": 3
}

0.667 的渗透效应意味着：仅仅在系统提示中存在 SQL 安全技能的描述，就让无关任务的回答质量下降了 66.7%。这就是"技能描述渗透"的威力。

三阶段模型：你在投资错误的阶段

论文提出了 Agent 任务的三阶段模型，并指出当前技能生态的系统性偏差：

阶段 类比 当前技能覆盖率 失败占比
Grounding（接地） 正确理解输入 🔴 ~10% 🔴 高
Method（方法） 执行过程 🟢 ~80% 🟢 低
Verification（验证） 检查输出 🔴 ~10% 🔴 高

大量技能教 Agent 怎么做（Method），但极少有技能帮 Agent 看清楚输入（Grounding）或检查输出（Verification）。然而数据显示，Grounding 和 Verification 才是失败的主要来源。

这像极了软件工程中的经典反模式：开发者热衷写业务逻辑（happy path），却忽视输入验证和输出测试。Agent 技能生态在重蹈覆辙。

回归预算：像管技术债一样管技能

GRASP 框架（Moll et al., 2026）提出了"回归预算"机制——每个新技能在准入时设置回归上限，超过就拒绝或需要人工审核。我把这个思路实现成一个轻量级守卫：

# regression_budget.py
"""
回归预算守卫：新技能准入前必须通过回归测试。
思路：在包含新技能和不包含新技能两种配置下运行同一组回归任务，
如果退化超过阈值，拒绝准入。
"""
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class RegressionBudget:
    """
    threshold: 允许的最大回归幅度（0.05 = 5% 的任务允许退化）
    min_tasks: 回归测试集最小任务数
    """
    threshold: float = 0.05
    min_tasks: int = 50
    regression_suite: list[dict] = field(default_factory=list)
    # 每个 task: {"input": str, "expected": str, "check": Callable}
    
    def add_task(self, input_text: str, expected: str, 
                 check: Callable[[str, str], bool]):
        """添加回归测试任务"""
        self.regression_suite.append({
            "input": input_text,
            "expected": expected,
            "check": check,
        })
    
    def evaluate_skill(self, skill_desc: str, 
                       llm_with_skill: Callable,
                       llm_without_skill: Callable) -> dict:
        """
        评估新技能的 gain/regression 分解。
        返回决策：admit / reject / manual_review
        """
        if len(self.regression_suite) < self.min_tasks:
            return {"decision": "manual_review", 
                    "reason": f"回归测试集不足 ({len(self.regression_suite)}/{self.min_tasks})"}
        
        gains = 0
        regressions = 0
        neutrals = 0
        
        for task in self.regression_suite:
            # 不含技能的回答
            baseline_resp = llm_without_skill(task["input"])
            baseline_pass = task["check"](baseline_resp, task["expected"])
            
            # 含技能的回答
            skilled_resp = llm_with_skill(task["input"])
            skilled_pass = task["check"](skilled_resp, task["expected"])
            
            if not baseline_pass and skilled_pass:
                gains += 1      # 技能救了这个任务
            elif baseline_pass and not skilled_pass:
                regressions += 1  # 技能搞砸了这个任务
            else:
                neutrals += 1   # 无变化
        
        total = len(self.regression_suite)
        regression_rate = regressions / total
        gain_rate = gains / total
        net = gain_rate - regression_rate
        
        decision = "admit"
        if regression_rate > self.threshold:
            if net > 0:
                decision = "manual_review"  # 有净收益但回归超标
            else:
                decision = "reject"          # 净负且回归超标
        
        return {
            "decision": decision,
            "gains": gains,
            "regressions": regressions,
            "neutrals": neutrals,
            "total": total,
            "gain_rate": round(gain_rate, 3),
            "regression_rate": round(regression_rate, 3),
            "net_benefit": round(net, 3),
            "threshold": self.threshold,
            "skill": skill_desc[:60],
        }


# 使用示例
if __name__ == "__main__":
    budget = RegressionBudget(threshold=0.05, min_tasks=3)
    
    # 添加回归测试（实际应覆盖各种任务类型）
    budget.add_task(
        "写一个 Python hello world",
        "print('Hello, World!')",
        lambda resp, exp: "hello" in resp.lower() and "world" in resp.lower()
    )
    budget.add_task(
        "解释什么是递归",
        "函数调用自身",
        lambda resp, exp: "调用自身" in resp or "calls itself" in resp.lower()
    )
    budget.add_task(
        "1+1等于几",
        "2",
        lambda resp, exp: resp.strip().endswith("2")
    )
    
    # 模拟：有技能的版本在简单数学题上"想多了"
    def llm_without(input_text):
        return f"直接回答：{input_text} → 简洁回答"
    
    def llm_with(input_text):
        if "1+1" in input_text:
            return "让我们分析这个问题的多个维度..."  # 被技能污染
        return f"直接回答：{input_text} → 简洁回答"
    
    report = budget.evaluate_skill(
        skill_desc="深度分析技能：对每个问题提供多角度分析...",
        llm_with_skill=llm_with,
        llm_without_skill=llm_without,
    )
    
    import json
    print(json.dumps(report, indent=2, ensure_ascii=False))
    # 输出：
    # "regression_rate": 0.333 > threshold 0.05
    # "decision": "reject"

独到观点：技能是一种技术债

我想提出一个不太有人在论文里说的视角：Agent 技能和软件工程中的技术债是完全同构的。

每个技能就像一个 abstraction layer——它降低了某些任务的认知负担，但增加了系统整体的复杂性。当你有 5 个技能时，每个都是净正收益。当你有 50 个技能时，描述之间的交互效应、上下文挤压、注意力分散开始产生负回报。这和 Joel Spolsky 的"抽象泄漏定律"（Law of Leaky Abstractions）一脉相承。

更具体地说：

  • 技能 = 抽象层：降低特定任务的成本，但增加系统理解成本
  • 技能描述 = 公共接口：即使不被调用，也占用"认知预算"（context window）
  • 技能交互 = 抽象泄漏：两个技能对同一输入的解读冲突，导致不可预测的行为
  • 技能审计 = 代码审查：定期评估每个技能的 gain/regression 比率，移除负收益技能

如果你用这个框架思考，很多决策变得清晰：技能不在多，在精。每加一个技能之前，问自己——"这个抽象层的收益，能不能抵消它对所有现有任务的渗透成本？"

行动清单：今天就做的事

  1. 盘点技能库：列出你 Agent 系统提示中所有技能描述。统计它们占用了多少 token（你的上下文预算的 X%）
  2. 跑一次渗透检测：用上面的 OsmosisTest 代码，对每个技能做 A/B 测试。找出渗透效应最大的 3 个技能
  3. 建回归测试集：收集 30-50 个"必须正确回答"的基准任务。每次加新技能前跑一遍 RegressionBudget
  4. 补 Grounding 和 Verification 技能：别再写"怎么做"的 SOP 了。写"怎么确认你读对了输入"和"怎么验证你的输出"的技能。这是投入回报最高的地方
  5. 设置技能上限：根据你的上下文窗口大小，设置技能描述的 token 上限（建议不超过系统提示的 25%）。超过就启动淘汰机制

未来方向：自进化技能库

Qwen 团队的 Skill-SP（arXiv:2607.22529）指向了一个有意思的方向：让 Agent 自己进化技能库。三方博弈结构——proposer 生成任务，solver 解决任务，skill controller 更新技能——和 GAN 的 generator/discriminator 有结构相似性，但引入了"技能库"作为第三个实体。

但在此之前，更重要的问题是：我们的评估基础设施够好吗？ Regression Tax 论文发现 226 个任务的原评分有误——grader 自己就判错了。如果我们连正确评估 Agent 输出都做不到，讨论技能改进就是空中楼阁。

验证基础设施是技能系统的真正瓶颈。不是模型不够强，不是技能不够多——是我们衡量"好不好"的能力跟不上。

一句话总结： 下次想给 Agent 加技能时，先问三个问题——(1) 它的 gain/regression 分解是什么？(2) 它的描述会渗透到无关任务吗？(3) 它补的是 Grounding/Verification 还是又一个 Method？三个答案决定它值不值得进你的技能库。
